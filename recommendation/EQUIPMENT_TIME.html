Equipment as a Time line built 2026-10-12

Source: Google Doc "W1 Equipment" ("Do not code. Analyze and improve pattern. Make ./recommendation/EQUIPMENT_TIME.html"). I read the task-line, plan, person, role, budget-item and project-settings code and checked every statement below against it. (When this page was written nothing in the app had been changed; see the status below.)

Status: built. D1-D7 and the answers Q1-Q8 were accepted (Q1 = Person or Equipment; Q2 = hide the tabs that are not needed; Q3 = the labels Time input needed · Material input needed · Expense input needed, and so on; Q4-Q8 as recommended). Where it lives:
  • Switches: kit8/pm/model/taskInputScope.ts + PMProjectTaskEditScreenTab.tsx (the renamed PMProjectFinanceTab); keys projectTimeCostsNeeded, projectTimeOfPersonNeeded, projectTimeOfEquipmentNeeded, projectMaterialCostsNeeded, projectExpenseCostsNeeded. The master keeps its label "Expense budget needed".
  • Hiding tabs (Q2 / D5 phase 2): master on + an EMPTY tab whose input is off = hidden; a tab that has lines is never hidden; master off = as before.
  • Equipment catalog: kit8/catalog/equipment (README there) + route /catalog/equipment/dashboard; SQL = PART 17 of start_sql_structure.sql (also in start_sql_code.sql / start_sql_data.sql), PART 6 of delete_sql_structure.sql; tested on Postgres 15 with kit8/docker/test_sql.sh.
  • Time line: taskResourceKind, the menu Resource, taskLineResource.ts (P1), generalized taskLinePersonMatch.ts (P3), the role type resourceKind (D4), the Plan view fix; P2 = product/crud/descriptorSides.ts; P4 = catalogEntityNameOf in ReusableTable.
  • Not built (on purpose): a lessor contract / hours per day on the equipment (D3 phase 2), the second budget item "Equipment time" (Q8, later), double-booking of a machine, translations of the new texts (pmT shows the English text until the dictionaries have them, as for the other Finances texts).
The text below is the recommendation as it was written, before the work.

What the document asks for (my reading)

  1. Project settings. When projectExpenseBudgetNeeded is on, show more switches: timeCostsNeeded (with timeOfPersonNeeded and timeOfEquipmentNeeded inside it), materialCostsNeeded, expensesCostsNeeded.
  2. Equipment is a Time line. It is entered in task_line_table on the Time tab, not on a new tab.
  3. equipmentTable works as an analog of the person: it has Properties, it has Variants, and it can be selected on a Time line.
  4. The extra menu. If timeOfEquipmentNeeded = true, the Time line first asks Person or Equipment ("Person on Equipment" in the doc - I read "on" as "or"), and only then lets the user pick the resource.

What is already true in the code (the facts the recommendation stands on)

The flags are dead today.
projectRevenueBudgetNeeded / projectExpenseBudgetNeeded are saved by PMProjectFinanceTab and copied by import/template code, and read by nothing else (grep over kit8/). Adding five more flags without a consumer would make seven dead flags.
The resource kind is decided by the genus.
TaskLineGenusDef.resource is 'person' for Time and 'product' for the rest. Eight places branch on it (list in section 6). A Time line that may be a person or a machine breaks that assumption.
The person pattern is already generic underneath.
personAsProductData() shows persons to the descriptor rules as products; taskLinePersonMatch.ts looks variants up by owner GUID, so it would work for an equipment GUID unchanged. Reuse is cheap - if the seams are made explicit.
Existing Time lines must not change.
Every saved Time line has taskResourceItem = a person and no kind field. The design must treat "no kind" as person so there is no data migration.

Where: PMProjectFinanceTab.tsx (section "Budgets"), stored in project_table.rowJSON.

The five switches appear only while "Expense budget needed" is on, indented under it; Person / Equipment appear only while "Time costs needed" is on.

Rules (pure function, unit-tested)
  • Hidden is not deleted. Turning a parent off hides its children and keeps their values (the same rule the person form uses for employeeData).
  • Time needs a kind. If "Time costs needed" is on, at least one of Person / Equipment is on. Turning off the last one switches "Time costs needed" off; switching "Time costs needed" on with none chosen sets Person on.
  • Defaults for a missing key: Time = on, Person = on, Equipment = off, Material = on, Expense = on. That is exactly today's behaviour, so old projects need no migration.
A trap in the existing helper. financeValuesOf() turns a missing flag into false (!!j?.projectExpenseBudgetNeeded). Copying that line for the new keys would make every old project look like "everything off". The new keys need ?? default, not !!.

Give the flags a consumer: financeScopeOf()

One pure function next to financeValuesOf turns project JSON into what the Finances screen may offer:

  material: boolean, expense: boolean, revenue: boolean
}

Rule that protects data: a tab or kind that already has lines is never hidden by a switch. It stays visible with a one-line banner ("Equipment is switched off in the project settings; the existing lines are kept"). The user can still read and edit them. Hiding is for empty tabs only. This is why Phase 1 can ship without a migration.

Naming (D7) and one wording problem

  • The master flag is called "Expense budget needed" but it covers Time + Material + Expense lines. Under it sits "Expenses costs needed" - the same word at two levels. The catalogs already say Costs for the folder (costsGenus, costsBudgetFolder).   • Singular like the genus: projectExpenseCostsNeeded (genus is expenseGenus), not expensesCostsNeeded.
  • Cost: each new label is a pmT key; keys.ts + 14 language files + build.py, and pmT.test.ts fails when one language is missing. About 6 texts × 14 languages.

Three ways to model equipment - and why only one

recommended
A. Own tables + adapter
equipmentTable, equipmentTypeTable. Descriptor tables are shared (the owner is already polymorphic: product / role / person). A machine has no first name, e-mail, IBAN, personal code, so none of the GDPR-restricted person data is touched. Cost: a fourth "side" on the shared descriptor tables (P2 makes that one line instead of three edits).
reject
B. Equipment = a person type
Cheapest on paper (zero new tables), but a machine becomes a row of personTable with personFirstName required (validatePerson), a contract parent 'person', and it appears in every person picker, the Persons list, PersonEdit and the person SQL seeds' 50/50 split. It also puts equipment under the "authenticated only for GDPR" rationale for no reason.
reject
C. Equipment = a product
Products already have properties, variants, prices. But a product is something you buy (Material / Expense lines have a supplier and a contract template). Machine time is booked as hours of a role on a Time line. The doc itself says "analog of person".

What is an "equipment type"?

For persons the type is the legal relation (Employee / Contractor) and it decides the contract and the descriptor set. For equipment the descriptors depend on the kind of machine (a crane has Lifting capacity, a laptop has RAM), so I recommend equipmentType = kind of machine (Heavy machinery, Vehicle, Tool, Workstation) and keeping ownership as a plain field on the equipment: equipmentOwnership = 'own' | 'rented' | 'leased'. Ownership is what later (Phase 2) decides whether the cost comes from a lessor contract, the way Employee/Contractor decides it for persons. Q4 asks you to confirm.

Proposed row shape

equipmentTable   rowGUID · rowOwnerGUID 'equipmentCatalog' · rowParentGUID 'empty' · orderInList · rowJSON:
  equipmentTitle           "Excavator CAT 320"   (the only required field; auto-filled from code + model if blank, like personTitle)
  equipmentCode            inventory number, unique when set
  equipmentType            equipmentTypeTable.rowGUID  (decides the descriptor sets)
  equipmentOwnership       'own' | 'rented' | 'leased'
  equipmentManufacturer · equipmentModel · equipmentSerialNumber       (free text, optional)
  equipmentPartner         partnerTable.rowGUID of the lessor (Phase 2, optional)
  isActive                 false = not offered on new lines, old lines keep it   (same rule as person)
equipmentTypeTable   same shape as personTypeTable: title, description, propertySet, variantSet, variantMode, isActive

Deletion protection copies the person rule: equipment used on a task line cannot be hard-deleted; the UI asks to set isActive = false.

3 - The Time line changed

3.1 The data: taskResourceKind (D1)

Today taskResourceItem is already polymorphic (person for Time, product for the rest) and the genus tells which. After the change the genus no longer tells for Time, so the line says it itself:

task_line_table.rowJSON.taskResourceKind   'person' | 'equipment' | null      null = person (all existing Time lines)
task_line_table.rowJSON.taskResourceItem   personTable.rowGUID | equipmentTable.rowGUID | productTable.rowGUID
taskResourceAttributesKey                  descriptorKey of a variant of THAT person / equipment
taskResourceContract                       person's contract only (equipment: null in Phase 1)
  • No SQL column change - it is rowJSON. The existing index on taskResourceItem keeps working. A CHECK keeps the value honest (section 5).
  • The name follows the existing family taskResource*. The TypeScript type TaskLineResourceKind = 'person' | 'product' in taskLineModel.ts already uses that word for the genus level; rename it (TaskLineResourceFamily) so the two ideas do not collide.
  • Why not a second field (taskEquipmentItem): two nullable GUID fields that must never both be set, every reader (columns, plan view, reports, SQL) must read both, and a future third kind (subcontractor team? vehicle fleet?) adds a third field. One kind + one GUID scales.

3.2 The menu and the columns (D6)

The rule from the doc - "before the Time resource is selected" - becomes a column placed before the resource. Today's Time order is Budget item · # · Role · Role attributes · Person · Person variant · Contract · Qty ….

Project allowsTime table columns
Person only = todayBudget item · # · Role · Role attributes · Person · Person variant · Contract · Qty · Unit · Price · …
Equipment onlyBudget item · # · Role · Role attributes · Equipment · Equipment variant · Qty · Unit · Price · … (no Contract column in Phase 1)
BothBudget item · # · Resource (Person | Equipment - the new menu) · Role · Role attributes · Person / Equipment (one column, catalog by kind) · Variant · Contract (enabled for Person only) · Qty · …
1. Resource: Equipment→ 2. Role: only roles whose role type has resourceKind = equipment→ 3. Equipment: active equipment (optionally of the role's type)→ 4. Variant: the equipment's own variants (automatic = first that covers the role)→ 5. Price: role rate × unit hour

3.3 What happens when the kind changes

In computeTaskLineRowJSON (rule 2 of its header comment) add: if taskResourceKind changed, clear taskResourceItem, taskResourceAttributesKey, taskResourceContract, and clear the role when its role type's kind no longer matches. The price then follows the role by the existing priceAutoTaskLine mechanism (a price the user typed stays). This is the same idea as "changing the partner clears the partner contract". It is silent by design - the table already behaves this way for the other dependent cells.

3.4 Problems shown as ⚠ (data is never refused)

  • "The role is not an equipment role" / "The role is not a person role" (extends lineProblems, next to "The role is not a Time role").
  • "The equipment does not exist any more" / "is not active".
  • Equipment variant does not cover the role; equipment property below the role's requirement ("Lifting capacity: needs at least 20 t, has 12") - the same messages the person match produces, from the generalized module (P3).
  • Equipment line with a person contract (only possible after a kind change by a script) - cleared by compute, listed here for completeness.

3.5 Plan view and Post

  • Post / calculateTaskLinePlan: no change. It spreads totals over days and does not care who the resource is. create_task_line_plan copies budgetItemTaskLine and the genus into the plan rows; I recommend also copying taskResourceKind into the plan row's rowJSON, so a future report "person-hours vs machine-hours" is one SQL query without a join to the lines.
  • Plan view needs a fix: planColumns.tsx:27-29 resolves the resource as "person, else product". An equipment GUID would be looked up in products and show an empty title. It must resolve by kind (otherwise the Plan view shows blank resources for equipment).
  • Budget item: equipment time is budgeted as timeBudgetItem by default, because the item picker filters only by genus. Optional Phase 2: a second level-2 item "Equipment time" (genus timeGenus) and a default chosen by kind in defaultBudgetItemOfGenus, so budget reports can separate machine hours from work hours. Not required for the doc.

3.6 Cost - and an assumption to avoid

Phase 1 uses the role rate: add a role type "Equipment Resources" (genus timeGenus, resourceKind = equipment), roles such as "Excavator 20 t", and hourly rates in rolePriceTable - the machinery already built for roles. suggestForLine needs only one change: skip the contract branch when the kind is equipment.

Do not reuse contractPeriodHours for machines. It converts a contract's sum to an hourly price with 8 h/day, 21 days/month. A rented machine that runs 10 or 24 hours a day, or is rented per day but billed per hour of use, would get a wrong hourly price silently. If Phase 2 adds rental contracts, the working hours per period belong on the equipment (equipmentHoursPerDay), not in a constant.

4 - Improving the pattern the "analyze and improve" part

Four seams that are implicit today. Making them explicit is what turns "add equipment" from a copy-paste of person into a small change - and makes a third resource kind cheap later.

P1 - Replace genus.resource branching by a per-line resolved kind

TaskLineGenusDef gets resources: TaskLineResourceKind[] (Time: ['person','equipment']; Material / Expense / Revenue: ['product']). One pure helper, in a new taskLineResource.ts, answers every question the eight call sites ask today:

lineResourceKind(genus, json, scope) -> 'person' | 'equipment' | 'product'
   Time:  json.taskResourceKind ?? (scope allows person ? 'person' : 'equipment')
   other: 'product'
resourceRowsOf(data, kind) -> data.person | data.equipment | data.product
resourceTitle(data, kind, guid)  -> "First Last" | equipmentTitle | product title

Every existing genus.resource === 'person' becomes kind === 'person' (a mechanical edit) and equipment falls out of the same code paths. This also removes the risk of forgetting a place: a test can enumerate the kinds.

P2 - Descriptor "sides" as a list, not as hand-written argument lists

Properties/variants of products, roles and persons live in the same five tables; each dashboard hides the other sides' rows. The hiding is hand-wired in three places that each name the other two sides: usePersonCatalogData.ts:64, useProductCatalogData.ts:70, useResourceRoleCatalogData.ts:73 (e.g. sideOf(all, [...roleTypes, ...personTypes], [...roles, ...persons])). A fourth side means editing all three, and forgetting one shows equipment descriptors inside the Products dashboard - an error that no test would catch today.

Recommendation: a registry DESCRIPTOR_SIDES = [product, role, person, equipment] (each with its type entity and item entity) and sideOf(all, thisSide) that hides every side except thisSide. The three call sites shrink to one line, and a unit test asserts "every side hides the other three". Do this before adding equipment so the person/product/role behaviour can be proven unchanged by the existing tests.

P3 - Generalize taskLinePersonMatch.ts instead of copying it

The file (169 lines) works on GUIDs: personVariants filters variant.rowOwnerGUID === personGUID; the requirement check reads the person's type to find the property set. Only two lines are person-specific: d.person.find(...).rowJSON.personType and the guard genus.resource !== 'person'. Replace them with a small ResourceSide = { rows, typeOf(row) } argument (person: personType, equipment: equipmentType) and rename the functions to resourceVariants, unmetRequirements …, keeping the person* names as re-exports so the existing taskLinePersonMatch.test.ts stays green untouched. The ⚠ texts say "The person has no variant…" - they get the resource word as a parameter.

P4 - A row-aware catalog column in ReusableTable

SelectColumn.options may already be a function of the row; CatalogColumn.catalogEntityName is a fixed string. That is the only reason the doc's menu would otherwise need four columns. Add an optional catalogEntityNameOf?: (row) => string (plus catalogEntityNames?: string[] for the title/search lookup), default unchanged. Three places read the name:

  • ReusableTable.tsx:208 - subscribes to the catalog rows per column for search/filter/sort titles (must subscribe to every entity the column can show).
  • ReusableTableCell.tsx:59 - renders SelectElementFromCatalog (use the row's entity).
  • ReusableTableFillColumnModal.tsx:47 - "Fill all lines" would write one GUID into rows of both kinds. Restrict it to rows whose kind equals the kind picked in the modal, or disable Fill for this column.

Two small gaps found while checking: editable on a column is a plain boolean, so the "Contract" cell cannot be disabled for equipment rows (use the existing validate to refuse, or let editable accept (row) => boolean), and the same applies to hiding the cell. If you prefer not to touch ReusableTable in this step, the fallback is the four-column layout - it works with zero table changes and can be replaced later without changing stored data.

P5 - Contract catalog: leave it alone in Phase 1

contractTable has a CHECK rowParentGUID IN ('person','partner') (start_sql_structure.sql:469) and a contractPartyType that must equal it. A machine is not a contracting party: a rental contract is with the lessor (a partner). So Phase 2 should link equipment to a partner contract (equipmentPartner + taskResourceContract pointing to that partner's contract) and the CHECK stays as it is. Widening it to 'equipment' would be the wrong model.

5 - SQL kit8/sql/start only

All SQL goes into start_sql_structure.sql / delete_sql_structure.sql (project rule: nothing else in kit8/sql), and must be run on Docker postgres:15 with the existing kit8/docker stubs before it is handed over.

  1. New tables equipmentTable, equipmentTypeTable by kit8_setup_def_table() (same helper as personTypeTable), signed-in-user RLS, realtime publication, index on (rowJSON->>'equipmentType'). Idempotent (IF NOT EXISTS, DROP POLICY IF EXISTS).
  2. Task line CHECK (idempotent add): COALESCE("rowJSON"->>'taskResourceKind','person') IN ('person','equipment'), and equipment only on the Time genus: COALESCE("rowJSON"->>'taskResourceKind','person') = 'person' OR "rowParentGUID" = 'timeGenus'. Existing rows pass (no kind = person).
  3. Role type kind: no column - resourceKind is in resourceRoleTypeTable.rowJSON. The seed sets resourceKind='person' on "Human Resources" (and the app treats missing as person).
  4. Seed (upsert like the other seeds, so it is re-runnable): 2-3 equipment types with descriptor sets (Capacity, Power, Year, Certificate), ~6 pieces of equipment, role type "Equipment Resources" (genus timeGenus, kind equipment), 3-4 roles, hourly Bill/Cost rates, a few variants and property values.
  5. Plan table (optional): copy taskResourceKind into the plan row's rowJSON in create_task_line_plan.
  6. delete_sql_structure.sql: drop the two tables and the CHECK, in reverse order, following the file's existing pattern.
  7. Project flags: none - they are project_table.rowJSON.
Generating the seed through start_sql_data.sql versus the structure file is your existing convention (KNOW_HOW says DDL in start_sql_code.sql, seed in start_sql_data.sql; your SQL-workflow note says only the two structure files). I follow your note; tell me if the other layout is now the rule (Q7).
