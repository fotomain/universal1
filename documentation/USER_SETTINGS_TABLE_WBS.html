User settings table

One table, userSettingsTable, keeps how the interface looks for ONE user on ONE kind of device: the design system, the fonts of the inputs and of the dashboards, the colors of the cells. It is a redux entity of SystemMetaData that refreshes by itself on every login of the user. The app looks like the operating system before anybody signs in.

BUILT 2026-11-25 (SQL PART 59, redux entity, settings screen, fonts, Expo UI theme; section "What was built" says what is NOT done and NOT seen). The first plan came the same day; the owner answered Q1, Q4, Q9, Q10, Q11 and asked for more native Expo UI components and for the colors in the row. Source: the owner's Google Doc "RUN_NOW" (1qIC8GCT0XB77a7uAZBezwi_Zd2xVHYz07vVkGNYXcMU).

The request, in the owner's order

  1. Rule 1. The app just opened, signed in or not: the default look is as native as possible. Not Apple devices: react-native-paper (system style). Apple devices: the Expo UI theme, built on @expo/ui.
  2. userSettingsTable is a SystemMetaData entity with auto refresh for all logins of the user.
  3. It is COMMON for all userWorkPlaceGUID of the user and holds the settings of the input visualisation: the MOST NATIVE font for each OS, plus the choice System (native font of the device or browser) · Roboto · Inter · Selawik.
  4. Size small · medium · large, values from Google's recommendations for Angular (Angular Material 3 type scale); the settings the Google Material 3 typefaces need and allow; font files go to assets/fonts.
  5. Columns: rowOwnerGUID = user · rowParentGUID = device type (desktop, phone, tablet) · rowFolderGUID = OS (macOS, Windows, Android ...). Unique key = the three. A new device gets default settings.
  6. rowJSON: lastUsedAt (time stamp of the last upsert; older than 1 month = the row is deleted by the redux background saga deleteNotUsedUserSettings) and uxuiState with themeSettings (no themeStoreTable; the changeable font settings of the theme elements) and extendedSettings (fonts + cell background of the Estimation dashboard and of the Project dashboard; cell background transparent by default).
  7. The redux uxuiState holds the data of userSettingsTable.rowJSON.uxuiState.

Unique key: UNIQUE (rowOwnerGUID, rowParentGUID, rowFolderGUID) - one row per user, device type and OS. The save is an upsert on that triple (onConflict), like project_dashboard_user_settings_table.
Why not per userWorkPlaceGUID: the request says the settings are common for all work places. Two Chrome profiles on the same Mac are two work places and ONE row (desktop + macos): they look the same on purpose.
RLS: a user selects, inserts, updates and deletes only his own rows; no administrator exception (it is a personal look). The matrix of permissions (permission_matrix.py) needs the table: owner-only, CRUD for the user himself.
Realtime: in the publication; the entity listens with match = { rowOwnerGUID: user }.

  1. Not signed in. There is no row (no user to own it). The defaults above come from platformDefaults(deviceKey); the user may change them and the change stays in the local redux-persist copy only.
  2. Signed in, a row exists. It is read and applied; Realtime keeps it fresh.
  3. Signed in, no row for this triple (a new device). A row with the defaults of the platform is created at once (Q4: not copied from another device, because the fonts differ per OS). The local choices the user made before signing in are uploaded into it (U13).
  4. A design system the user already chose by hand stays. The default applies only when the state has no choice yet: a flag designSystemChosenByUser (or the absence of the persisted key) tells; otherwise every update of the app would throw users out of the look they picked (Q6).
  5. Sign out / another user signs in on the same device. The redux copy is replaced by the platform defaults at SIGNED_OUT, then by the row of the new user (Q8) - user A's look must not carry over to user B.

1b. Apple fonts: what is free (checked against the owner's question, 2026-11-25)

  • None of Apple's system fonts may be bundled or self-hosted: San Francisco (SF Pro, SF Compact, SF Mono) and New York are licensed by Apple for designing and developing apps FOR APPLE PLATFORMS. The license does not allow hosting the files on our own server, and it is not a general web-embedding license. So there will never be an SF_Pro.ttf in assets/fonts or public/fonts.
  • What is free: asking the device for it. In normal web text the value system costs no file and shows SF Pro on every Mac and iPhone by itself. In the native iOS app the system font is the platform's own - using it is exactly what the license is for.
  • Three roles, three keywords: sans = system-ui (older Safari / Chrome: -apple-system, BlinkMacSystemFont), serif = ui-serif (New York on Apple), mono = ui-monospace (SF Mono on Apple). Other platforms answer with their own font (Segoe UI, Roboto, Cascadia / Consolas ...). Only the sans role is a user choice in this round; the mono role is used for GUID / code cells and the serif role is kept in the registry for later.
  • If the SAME look is needed on every device, use an open lookalike we may self-host (SIL OFL): Inter is the closest match to SF Pro and the most popular choice - already in the list. Others are Public Sans (neutral, similar proportions), Geist and IBM Plex Sans (slightly different character); for SF Mono: JetBrains Mono, Fira Code. Not added now (Q12).
  • Inter plus the system stack as the fallback gives SF-like text everywhere with no license risk - this is the rule for every non-system choice below.

3. Google Material 3 typefaces: what is needed and possible

  • Material 3 uses two typeface slots: brand (display, headline, title) and plain (body, label). Both default to Roboto. The user setting is one name, applied to both slots; a later step may let the two differ (not planned now).
  • Weights M3 uses: 400 (body, display), 500 (title, label, buttons), 700 (strong). A name that lacks a weight (Selawik has no 500) maps to the nearest one (Semilight / Semibold) in the registry, so the interface never falls back to a fake bold.
  • Variable axes: Roboto Flex (wght, wdth, opsz, GRAD ...) and Inter (wght, opsz) allow fine settings. Possible but NOT offered in this round: one weight + size per element is enough; axes need variable font support in Skia and React Native that is uneven. Written down as a later option.
  • Letter spacing and line height come with the size table below (the M3 values), they are not separate user settings.
  • Paper reads the font from configureFonts of the MD3 theme: the registry builds that object from the chosen name and size. Expo UI (SwiftUI) takes the system font by default; a choice other than system is passed with the font modifier / fontFamily of the view when it supports it (the spike U11 finds out which components do).

Sizes: small, medium, large

The values are the Angular Material 3 type scale (the Google recommendation for Angular, the same as Material 3): body-small 12 / 16, body-medium 14 / 20, body-large 16 / 24, label and title in the same three steps. The three names pick one STEP of that scale for the three roles that matter in this app:

  • The numbers are px on web; on a phone they are the same dp / pt and scale with the system font size of the user (allowFontScaling stays on - accessibility first).
  • Row heights of the tables follow the line height of the size (a table with large data cells has taller rows); the Skia grids (estimate, Gantt tree) take both numbers from the same table, so the canvas and the React Native tables agree.
  • Not Google-recommended = not offered: no free pixel field. Three sizes keep the screens testable.

Redux: the entity, the two copies, the sync

The entity

userSetting in SystemMetaData through ...userSettingsSystemMetaData() (the pattern of routeVisitMetaData.ts): table name, defaultData = platformDefaults, create / read APIs, Realtime by the entity channel with match = { rowOwnerGUID: user }. "Auto refresh for all logins": a change saved on the phone arrives by Realtime on the Mac of the same user; the screen of the Mac repaints with no reload.

Two copies, one truth

The slice uxuiState stays persisted locally (it makes the first paint instant and works with no network and for a guest). When the user is signed in, the ROW is the truth: SIGNED_IN reads it and applies it to the slice with a new reducer applyUserSettings; a change of the slice is written back to the row after a short pause (debounced, one upsert for a burst).

No echo

The upsert of this device comes back through Realtime. The saga compares the incoming rowJSON.uxuiState with the slice and dispatches nothing when equal; an incoming row from ANOTHER device with the same key (another browser on the same Mac) is applied.

Read rule for components: they never read the row. They read uxuiState.themeSettings through selectors (selectFontOf('input'), selectDashboardFont('estimation', 'header')) that return a STORED reference (zustand / redux lesson of PART 53: a selector that builds a new object per call loops).

Clean-up: deleteNotUsedUserSettings

  1. A redux-saga background task, started with the other sagas of the store; it runs after sign in and then every 24 hours while the app is open.
  2. It reads the rows of the signed-in user (RLS shows only his), and deletes every row whose rowJSON.lastUsedAt is older than one month - EXCEPT the row of this very device (it was just touched).
  3. The time stamp must really mean "last used". The request says "last upsert". A device that is opened every day but changes no setting would never upsert, and after a month its row would be deleted although it is in use. So the touch rule (Q3): lastUsedAt is upserted when a setting changes AND once per start of the app (at most once per 24 hours). Cost: one small write a day per device.
  4. Time comes from the device clock; a skew of hours does not matter against a month. A row without lastUsedAt (hand-made) is treated as just used, never deleted.
  5. The deleted device just gets the platform defaults again at its next start (a new row).

Limits of this plan

  • Nothing here was run: no SQL, no Docker, no Jest, no device. The facts of the "Today" section come from reading the repository on 2026-11-25.
  • The @expo/ui part is the least known: the package is installed but unused by the app, so which of its components render on web and macOS is an open question until the spike (U11).
  • Font facts (which system font each OS uses) are general knowledge. The legal column of section 1d is a risk assessment, not legal advice; the Apple and Microsoft license texts were not read.
  • Not planned: user-chosen colors of the whole theme (the table is only the place for them; userTheme still keeps the palette), the two typeface slots of M3 chosen separately, variable-font axes, a copy of settings between devices.

Install

  1. Supabase SQL Editor: start1_sql_tables.sql, then start2_sql_code.sql (PART 59). It adds a column to many tables - run it when nobody edits. start3 is NOT needed (no pg_cron job); start4 only to refresh the permission seed (one new row for userSettingsTable).
  2. .env: nothing. Fonts are already in assets/fonts and public/fonts.
  3. Reload the app (web: npx expo start --web -c only if the fonts do not appear). A native build is NOT needed for the fonts (expo-font loads them at run time); the Expo UI components on a phone need a dev build that contains @expo/ui.
  4. Verify: open /settings, tab Fonts, pick Inter; sign in on a second browser of the same kind - the font follows; tab "This device" shows the row and "Copy from my other device" for the other kind.
