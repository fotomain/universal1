Passport / ID: 1st photo, 2nd scan

The user no longer types the document number and the two dates. The app asks what the document is (ID or passport), the user takes a photo of the machine readable zone, the phone recognises the text on the device, and the NFC scan that exists today opens the chip with those values.

BUILT 2026-11-19 (first version, not tried with a real document) plan + decisions below; code in kit8/ui/components/media/nfc/identification, README there
  • Why a photo: the chip gives its personal data only to a reader that knows the document number, the date of birth and the date of expiry (or the CAN). The card enforces it. The three values are PRINTED on the document - so reading them from a photo replaces typing and does not weaken the protection (whoever holds the document sees them anyway).
  • Client side: yes, on phones (Google ML Kit on Android, Apple Vision on iOS: on the device, no upload) and on the web (tesseract.js, WebAssembly in the browser). The photo never leaves the device and is deleted as soon as the text is read.
  • Bonus: the photo step already gives the data PRINTED in the zone (name, nationality, sex ...). The NFC step then gives the data signed in the chip. Comparing the two shows a forged page (optional, step 4 below).

One API for all platforms

kit8/ui/components/media/nfc/identification/ocrEngine.ts (+ .web.ts): recognizeText(imageUri): Promise<string[]> - the text lines top to bottom. Everything above it is pure TypeScript and tested without a camera.

From text to the three values (mrzFromText.ts, pure)

OCR reads the OCR-B font with typical mistakes: O/0, I/1, B/8, S/5, Z/2, G/6, a lost <. The MRZ has check digits, so mistakes can be found and repaired.

  1. Find the zone: normalise each line (upper case; keep A-Z 0-9 <; « ‹ K-runs at the end of a line count as <), take 2 or 3 lines of nearly equal length (44 / 36 / 30). The expected format from step 1 is tried first, the others after it. Existing: mrz.ts normalizeMrzLines.
  2. Pad / cut a line to the exact length (a lost trailing filler is the most common error).
  3. Repair by field class: a position that must be a digit (dates, check digits, the digit part of numbers) maps O→0 I→1 B→8 S→5 Z→2 G→6 Q→0 D→0; a position that must be a letter (names, state codes, document code) maps the other way. Which positions are which is fixed by the format (the table of parseMrz).
  4. Check digits decide: number, date of birth, date of expiry and the composite check digit (existing: checkDigit, parseMrz gives allValid). For the few ambiguous characters try the alternatives (at most 2^6 combinations) and keep the candidate whose digits all agree; if several agree take the one with the fewest changes.
  5. Result: { documentNumber, birthDate, expiryDate, mrz, confidence: 'checked' | 'partly' | 'unchecked', changes }. checked = every check digit agrees, partly = the three fields agree but the composite does not, unchecked = the user must look at it.
  6. Never goes on by itself: the NFC scan starts only after the user confirms the three values (some national cards count wrong passwords - see Risks).

Then accessFromMrz(parsed) (existing) gives the values the reader needs; IdCardReader takes them as initialForm.

Acceptance tests

  • The ICAO specimens (TD1 ID, TD3 passport) read back from text with 0 to 4 injected OCR mistakes (O/0, I/1, B/8, S/5, a lost filler, a missing line break) return the right three values with confidence = checked.
  • A zone with a wrong digit that cannot be repaired returns unchecked and the flow does NOT start the scan by itself.
  • Flow test (fake camera, fake OCR, software card of the existing tests): ID or passport → photo → values → scan → the chip data appears; the photo file is deleted; Clear wipes the values.
  • On the Samsung with the real Latvian ID card: the three values are recognised from a photo of the back, PACE-MRZ or BAC opens the card (the step list shows which).

Spike result (P1, 2026-11-19)

  • Chosen: expo-mlkit-ocr 0.2.7. Android: the bundled ML Kit model (com.google.mlkit:text-recognition:16.0.1, works offline from the first start); result = blocks → lines → elements with boxes. iOS: ML Kit pod (needs iOS 16; Apple Vision as the fallback on the simulator).
  • Compiles on this project (Expo SDK 57, React Native 0.86): ./gradlew :expo-mlkit-ocr:compileDebugKotlin = BUILD SUCCESSFUL; the Android JS bundle exports. iOS was not compiled (this Mac has command line tools only, no Xcode).
  • Not chosen: expo-text-extractor 2.0.0. Android uses the UNBUNDLED ML Kit model (downloaded through Google Play services on first use - not offline at once) and returns text blocks only; iOS leaves Vision's language correction ON (it "corrects" the <<< and the codes) and ignores the photo orientation.
  • Learned on the way: Expo SDK 57 refuses an iOS deployment target under 16.4 (the whole app config fails to load), so none is set: the default already satisfies ML Kit.
  • Still to test on the phone: how well ML Kit reads the zone of the real Latvian ID card. The confirm step has "Show recognised text" for that. If it reads badly: crop the lower band before the recognition, or write the own 150-line module (Q1 fallback).
  • Built from this plan: P2 mrzFromText, P3 ocrEngine (native; the web says "not yet"), P4-P7 the four steps and the flow, menu Scan → Identification. Not built: P8 (compare printed zone with the chip), the gallery picker (Q7), the web OCR (Q6), the crop of the band.

Google AI reads the photo (added 2026-11-19)

  • No strict rectangle any more: the whole document can be anywhere in the picture; Google AI (or the phone) finds the zone itself.
  • Opt-in: the switch "Read with Google AI" is OFF by default and remembered on the device. When ON the photo is sent to Google's Gemini API and deleted here at once. OFF = the photo never leaves the phone (ML Kit on the device).
  • Called from React Native: straight to generativelanguage.googleapis.com with the key of .env GOOGLE_AI_API_KEY (through app.config.js extra - the key is then inside the app: restrict it in Google AI Studio / Cloud). Alternative for production: the Edge Function identification-recognize (key stays on the server).
  • The prompt (fixed in supabase/functions/identification-recognize/handler.ts): copy what is printed, never guess, null when unreadable, the zone lines exactly with <, count the fillers, O/0 I/1 B/8 S/5, dates YYYY-MM-DD, the CAN only when labelled; the answer is JSON by schema (zone lines, number, dates, names, CAN, quality).
  • Not trusted blindly: the zone goes through the check digits. Measured live (2026-11-19, synthetic specimen): Google AI read number, dates and names exactly but miscounted the long runs of < (31 / 31 / 32 instead of 30 characters); the repair now adjusts the filler run and the zone passes its check digits (checked, 7-8 s). A zone that fails is shown as "printed fields, no check digits"; a failure or an empty answer falls back to the phone.
  • Model: default gemini-flash-lite-latest (about 2-3 s). Measured the same day: the gemini-flash-latest alias took minutes / answered 503 "high demand"; gemini-2.5-flash is no longer available to new users. Set GOOGLE_AI_MODEL in .env to try another.
  • Google's terms apply to the photo (whether the content may be used to improve Google products depends on the plan of the key: check before using real documents - not confirmed here).

Questions (with the recommended default)

Q1 Which OCR on the phone?
Default: expo-text-extractor if the spike (P1) works on SDK 57; otherwise the own 150-line module (ML Kit bundled model + Apple Vision).
Q2 Live scan (no photo button) instead of a photo?
Default: no - the flow asked for "make photo", and live recognition needs the frame processor stack that conflicts with the worklets of the app. Can be added later.
Q3 Must the user confirm the values before the NFC scan?
Default: yes, always (wrong passwords can use up retries on some cards).
Q4 Show the printed data (name, nationality ...) already after the photo?
Default: yes, in a small grey block "printed, not verified"; the chip result later is the green block.
Q5 Keep the photo?
Default: never: deleted right after the text is read; no upload; no media post.
Q6 Web: is a first download of the OCR model (a few MB) acceptable?
Default: yes, loaded only on this screen and cached; the web cannot do the NFC step anyway (the flow stops after step 3 on the web and says so).
Q7 Gallery picker in step 2?
Default: yes (a sharper photo from the system camera works too); needs a picker module - expo-image-picker is not installed today, expo-document-picker is.
Q8 Passports of countries whose zone is on the inside of a cover, or cards with a CAN only?
Default: the zone is always the same; for cards that offer a CAN the flow adds the optional CAN field in step 4.

Risks and limits

RiskWhat we do
Community OCR modules may not build on Expo SDK 57 / React Native 0.86Spike P1 first; fallback = own small module. The rest of the flow does not depend on the choice (API recognizeText).
OCR reads the OCR-B font badly (glare, a bent page, a laminated card)Guide frame + torch + crop of the lower band; repair with check digits; honest unchecked; the user can retake or type.
A wrong password attempt on a cardPACE / BAC with a wrong MRZ does not lock a normal passport; some national cards count failed attempts of their own passwords. The values are confirmed first and the reader tries at most the MRZ attempts it does today.
Privacy: a photo of an identity documentHeld in memory / cache only until the text is read, then deleted; never shown in a list, never saved as a media post, never sent; screen wiped on leaving.
The photo can give the printed data but not the chip's proofThat is why step 4 stays: the chip data is signed (hash check) and the printed one is not.
Not built hereLive scanning, reading the visual zone (the printed page outside the MRZ), the signature check of the chip against state certificates (separate item of the ID reader), languages other than the Latin MRZ alphabet.
