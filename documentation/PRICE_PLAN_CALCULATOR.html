Price plan calculator

The administrator wants to know what the application costs to own per month. He types how big his work is (projects, tasks, plan lines, users, changes, ROI, reports) and the screen ApplicationCostsPlanCalculator.tsx answers with the Supabase cloud bill: the total, the virtual machine that is needed, and the numbers behind them. Later the same calculator is the base of the sales pricing plans.

PLAN ONLY, 2026-11-12. No app code is written. Prices were read from the public Supabase pages today; sizes of rows were measured today on the local Docker database.

What it is

  • One screen for the organization administrator: parameters on the left, the bill on the right.
  • A pure model (no network): parameters + price list + coefficients → resources → dollars.
  • A price list that is fetched from the public Supabase data by an Edge Function, stored with its date, and never trusted blindly.

What it is not

  • Not the real invoice. It is an estimate: the load model has assumptions (marked A below).
  • Not a monitor of the live Supabase usage (the Supabase dashboard is that).
  • Not the sales price itself: it gives the COST; the margin and the plans come later (section Sales plans).

Three findings of the analysis

  • For most sizes the bill is plan fee + virtual machine. Disk, traffic, users and Realtime stay inside the included amounts for a long time.
  • The virtual machine is chosen by memory and by the biggest single project, less by the number of users.
  • The pg_cron log of the 2 second worker is never cleaned today: about 1.5 million rows a month. It is a hidden disk cost (section Model, finding F1).

4. The model: parameters → resources → dollars

One pure function, three steps. Every number it uses is a named coefficient in ONE table, with its source: M measured today, B from the benches of the project, A assumption to calibrate.

Step 1 - volumes

tasksAvg   = maximumTasksInOneProject     x fill          linesAvg = maximumPlanLinesInOneProject x fill
tasksTotal = numberOfProjects x tasksAvg                   linesTotal = numberOfProjects x linesAvg
peakClients = numberOfUsers x concurrentUsersPercent

Step 2 - resources

DISK     data = base
              + tasksTotal x (task row + links)
              + linesTotal x (line row + planRowsPerLine x plan row + report rows)
              + versions x (tasksTotal x task row + linesTotal x line row)
              + documentsPostedPerMonth x months kept x document
              + ROI rows (per task; + history per post and month kept)
              + pg_cron log (7 days of it, or all months when it is not cleaned)
         database = data x bloat            disk = (database + write ahead log and system) x free space

CPU      busy time of a month = date changes x (base + per task of the project)
              + line changes x line write
              + posts x (base + per plan row of the task + worker + ROI step)
              + documents x document post
              + report requests x (base + per line of the project) + open minutes x 20 checks
              + project opens x (base + per row read)
         needed vCPU = busy time / working seconds of a month x peak factor   (+ the pg_cron ticks, day and night)

MEMORY   needed GB = Postgres and Supabase services + database x share that is hot + peakClients x per client

REALTIME connections = peakClients x tabs per user
         messages = changed rows x clients that look at the same project

EGRESS   GB = project opens x (tasks + lines as JSON) + report requests x report rows as JSON
              + messages x message size + the 3 second checks

Step 3 - dollars

total = plan fee
      + price of the chosen machine - compute credits (not below 0)   [+ a Micro for the second environment]
      + max(0, disk GB - 8) x disk price
      + max(0, egress - 250 GB) x egress price
      + max(0, connections - 500) / 1000 x 10  +  max(0, messages - 5 million) / million x 2.50
      + max(0, users - 100 000) x user price
      + add-ons that are switched on

Finding F1 - the pg_cron log. pg_cron writes one row into cron.job_run_details for every run. The workers run every 2 s (monitor01_tick), every 10 s (cash_ledger_tick) and every minute (files_cleanup_tick): about 1.5 million rows a month, about 230 MB a month with the assumed row size. Nothing in start2 / start3 deletes them (searched today: no job_run_details in kit8/sql/start). After a year this alone is more than the 8 GB that are included. Recommended, as a separate small job: a daily pg_cron line that deletes rows older than 7 days (Supabase's own advice). The calculator has the switch so that both cases can be seen. Not checked on the owner's Supabase: the real size is select pg_size_pretty(pg_total_relation_size('cron.job_run_details')).
Finding F2 - the 2 second tick is a fixed cost, not a per-user cost. 43 200 runs a day happen with zero users. On a Micro machine it is small but never zero, and it keeps a Free project from pausing. A sales plan for very small customers may want a slower tick (5-10 s): the open report already has its own 3 second safety net.

5. How the virtual machine is chosen

The calculator walks the list of sizes from the smallest and takes the FIRST one that passes all five tests. The test that rejected the size before it is shown as the limiting factor - the administrator sees WHY he pays for this machine.

#TestRule
1Memorymemory of the size ≥ needed GB (services + hot share of the database + clients)
2CPUsteady vCPU of the size x target load (60 %) ≥ needed vCPU of the busy hour
3Database size"Database up to" of the size ≥ the database (Supabase's own recommendation)
4Biggest projectmore than 2 000 tasks in one project → at least Small; more than 10 000 → Medium; more than 50 000 → Large. Reason: one user action on such a project (open, repost all, leveling, fill from a template) must finish inside the 8 s statement limit of a signed-in user. A thresholds, from the benches (2 000 rows of a template: under 4 s on the test machine)
5Add-onpoint in time recovery → at least Small

Database connections are not a test: the app talks through the Supabase API (a small shared pool), not one connection per user. Realtime connections are billed, not limited by the machine.

6. The results

Total costs

  • Total per month (USD; optional second currency by the app's exchange rates) and per year.
  • The bill by lines: plan fee · machine (minus credits) · disk · egress · Realtime · users · add-ons · second environment. A line that is 0 says "inside the included amount".
  • Cost per user and cost per project - the two numbers the sales plans start from.

Virtual machine type

  • The size (Micro … 16XL), its CPU, memory, price per month and per hour.
  • The limiting factor (memory | CPU | database size | biggest project | add-on).
  • Headroom: how much of the machine the busy hour uses, and "the next size is needed at about …" (the number of projects / users at which the answer changes - found by running the model upward).

Important parameters

  • Database size and disk to pay for (GB), with the three biggest parts (plan rows, lines, pg_cron log …).
  • Total tasks, total lines, total plan rows.
  • Needed memory (GB) and busy-hour CPU (vCPU).
  • Realtime: peak connections and messages a month, each against its included amount (a bar).
  • Egress GB a month against 250 GB.
  • Growth: disk after 12 and 24 months with the same activity.
  • Date and source of the price list; a warning when it is older than 30 days or the built-in snapshot.

8. The price fetcher ("Uncle ATO")

The prices change (Supabase changed them several times). The calculator must not carry a price list that silently goes old, and must not break when the fetch fails.

Why a Supabase Edge Function

  • A browser cannot read supabase.com pages (no cross-origin permission); a server can.
  • One fetch serves every user and organization; the result is stored, the page of Supabase is asked at most once a day.
  • The parsing rules live in one place and are fixed without a new app build.
  • Cost: a few calls a day, nothing against the 2 million included.

Where the public data is

  • No official price API was found. The pricing page is a web page.
  • Source 1 (preferred): the data files the pricing page itself is built from, in the public repository supabase/supabase: packages/shared-data/plans.ts (plan fees as plain numbers) and pricing.ts (included amounts and overage as short texts like "then $0.125 per GB" - read with patterns). Checked today: both exist and hold the numbers of section 2.
  • Source 2: the compute table of docs/guides/platform/compute-and-disk (sizes, hourly and monthly price, CPU, memory, database size). It is NOT in pricing.ts; whether a data file of the repository holds it is the first thing of spike P0.
  • Source 3 (cross-check): supabase.com/pricing itself.

Rules of the function

  • Fetch → parse → validate → store. Validation: every key of the price list is present, every number is inside a sane range (a plan fee between 1 and 10 000, a size list of at least 8 rows with rising prices …) and no number moved more than x 3 against the last stored list without a flag.
  • A list that fails is NOT stored; the last good one stays, the answer carries state: stale and the reason.
  • The calculator shows "Prices of 2026-11-12 · supabase.com · Refresh" and, for the administrator, an editable copy: a price typed by hand wins over the fetched one (enterprise discounts, another region, another cloud).
  • Never fetched and no network → the built-in snapshot of section 2, with a visible warning.
  • The function reads public pages only; it sends nothing about the user or the organization.

10. Later: from cost to sales pricing plans

  • Who pays the Supabase bill decides everything. Today ONE Supabase project holds ALL organizations. Two ways to sell: (a) shared - customers share the machine, the cost of a customer is his SHARE (his rows, his changes) plus a part of the fixed fee; (b) dedicated - one Supabase project per customer, his cost is the whole bill of this calculator. The model is built so that both are one switch: "share of a machine" against "own machine". Phase 1 answers (b) and the owner's own bill.
  • Saved scenarios (phase 2): a parameter set with a name (Small / Medium / Large …) stored for the organization; a table that compares them side by side = the draft of the price list.
  • Price = cost x margin + what is not Supabase: e-mail sending, Google / Microsoft storage (the customer's own), app stores, support hours. Phase 2 adds free lines "other monthly cost".
  • Plan borders come from the model: "the next machine is needed at about N projects" is exactly where a plan should end.
  • The stored price history lets a plan be re-priced when Supabase changes its list.
