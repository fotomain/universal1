Reasons for Dates Changes – Work Breakdown Structure

Scope: the app registers why a user changed the dates of a task. Project setting taskDatesChangesReasonsFunctionalityEnabled (Project settings → Task). Planning document only – no code is written by this document. Status: plan, 2026-10-29

1. Goal

When a user moves a task (start, finish, duration, any other date of the task), the plan changes – and a month later nobody knows why. The app must ask for the reason, make the user choose it from a catalog (so the reasons can be counted and compared, not typed in free text), keep a history of every change (task, reason, user, old and new dates), and show the last reason in the task tree.

Hard constraint. With taskDatesChangesReasonsFunctionalityEnabled = false (the default) nothing changes: no dialog, no history row, no new column, no extra request. The same project behaves byte for byte as today.
  • Obligatory. With the switch on, a date change without a reason from the catalog is not saved. Cancel in the dialog = nothing changes.
  • Catalog, not text. The reasons live in the catalog project_reasons_for_changes_table, shared by all projects of the organization.
  • History. The SQL table project_reasons_for_changes_history is append-only: one row per task per change, with the reason and the user.
  • Works after manual changes (section 5.9): every way the user can change a date by hand goes through the same ask – the edit window, the tree cell, the Gantt bar drag, the bulk edits, the shift of a block of tasks.
  • Task tree shows the title of the last reason (task.rowJSON.reasonForDatesChanges.title).

4. Definitions

TermMeaning in this document
User actionOne gesture of a person that changes dates: one typed value, one bar drag, one bulk edit, one “shift selected tasks by N days”. One user action = one reason, even if it changes 30 tasks.
Direct changeA task whose date the user changed himself.
Cascade changeA task whose date moved because of a direct change (successors by links, the stage roll-up, auto-scheduling). Gets the same reason as the direct change, marked cascade.
BatchAll task changes of one user action: one batchGUID. The history rows of a batch share it.
ReasonAn item of the catalog project_reasons_for_changes_table (code, title, active flag). Free text is not a reason; an optional comment may accompany it (5.4).
Last reasonThe snapshot in task.rowJSON.reasonForDatesChanges: the reason of the most recent change of the task.
System writeA write that is not a user's decision about a date: the scheduler write-back without a cause, import, template copy, version restore. Never asks; is marked in the history (source).

5. Proposed design

5.1 The setting (R2)

  • Project settings → Task (new tab TabTask): a switch taskDatesChangesReasonsFunctionalityEnabled (project JSON, boolean, false by default). Under the switch, shown only while it is on:
    • the ask mode taskDatesChangesReasonsAskMode: everyChange (default) | onlyWhenEmpty (the literal reading of the request, Q1);
    • a link “Reasons catalog” (opens the catalog list, 5.3);
    • a short text with the plusses and minuses (like the leveling radio): + the plan can be explained, + counts per reason, − one more click per date change, − tasks moved by import or the scheduler are marked “system”, not explained.
  • The switch is saved with the other project settings (same Save / Cancel, same permission as the other project settings).
  • Switch on in a project that already has dated tasks: nothing is asked retroactively; reasonForDatesChanges stays empty until the next date change. The tree column shows an empty cell.
  • Switch off again: the history and the snapshots stay (nothing is deleted); the ask, the column and the writing stop.

5.2 What counts as a date change

A change of the value of one of these keys of a task (compared as the day, not as the timestamp text):

KeyMeaningCounts?
startAtplanned start (typed or computed)yes
rowDuration (column) / durationplanned finish (the exclusive end) – a change of the duration moves the finishyes
taskManualStartAt, manualStartAtA1 manual start; Start No Earlier Thanyes
taskConstraintDate, taskDeadlineA3 constraint date; A5 deadlineyes
actualStartAt, actualFinishAtC3 actual datesyes, option – they are facts, not plans. Proposal: they ask too, because “other dates” is in the request; the reason catalog has an item “Actual date correction”. Q3.
baselinesC1 snapshots of the planno – Set baseline is a deliberate freeze, not a change of the plan.
dependency lag / link typemoves dates indirectlyindirect – the tasks that move because of it are cascade changes with the reason of the dependency edit (5.9).
time of day (startHourStart, planMinute…)only when planHour / planMinute is onyes (the same date family)

The list lives in one constant (TASK_DATE_KEYS) used by the client guard and documented for the SQL trigger, so a new date key is added in one place.

5.3 The catalog project_reasons_for_changes_table (R4)

  • Def-table layout like the others. rowOwnerGUID = the organization (not the user, not the project) → every project of the organization sees the same items. RLS: select/insert/update for users of that organization (organization_of_current_user()); delete refused (an item used by the history is only deactivated).
  • rowJSON: { reasonCode, reasonTitle, reasonColor?, isActive, askComment }; code and title unique inside the organization (case-insensitive); title obligatory.
  • Default items seeded for every organization (by organization_ensure_user for new organizations and a one-time backfill for existing ones, start4_sql_insert_missing.sql): Customer request · Resource unavailable · Delay of a predecessor · Scope change · Estimate was wrong · Weather / force majeure · Supplier delay · Management decision · Error correction · Actual date correction. The owner of the organization edits the list afterwards.
  • UI: kit8/catalog/reasonsforchanges (model, list, edit, README) like kanbanstage; hamburger menu → Catalogs → Reasons for changes; route /pm/reasonsforchanges/list + /edit; registered in SystemMetaData.ts.
  • A reason can be added from the ask dialog (button “New reason”) for users who may edit the catalog – the user does not lose the work he started.

5.4 The ask dialog (R3)

PMDatesChangeReasonDialog – a modal, opened by the guard (5.5) before the save:

  • Title: “Why do you change the dates?”. Under it a compact list of what changes: for each task (max 5, then “+ N more”) the old → new dates; for a block “N tasks”.
  • A required selection list of the active catalog items (radio list or a searchable select; the last used reason first). No default is preselected – the OK button is disabled until the user picks one (this is the “obligatory” of the request).
  • An optional one-line comment (stored in the history, max 500 characters).
  • Buttons: OK (saves with the reason) and Cancel (nothing is saved; the screen goes back to the old value – the tree cell, the form field, the bar).
  • If the catalog has no active item: the dialog says so and offers “New reason” (permitted users) or tells the user to ask the organization owner. The save is still refused – the rule cannot be bypassed by an empty catalog.
  • Keyboard: Enter = OK when a reason is selected; Esc = Cancel. Works the same on web, iOS, Android.

5.5 When the dialog opens – the guard

  • Where: one wrapper useDatesChangeGuard(projectGUID) around the task mutations of taskQueries.ts: it looks at the patch, compares the date keys of the old and the new row (5.2). No date key changed → the save goes on untouched.
  • Switch off → the guard returns the original functions (no extra render, no extra request).
  • Ask mode everyChange (default): every user action that changes a date asks once. The action may already carry a reason (a bulk dialog that asked first, the Gantt “shift” that asked first) – then it does not ask again.
  • Ask mode onlyWhenEmpty (literal): asks only if task.rowJSON.reasonForDatesChanges of the changed task is empty; if it is already filled, the new change keeps that reason – which means the history row repeats the old reason. This is cheap for the user and poor for the quality of the data; therefore it is not the default (Q1).
  • One reason per action: a batch of 30 tasks asks once; all 30 history rows carry the same reason and batchGUID.
  • Optimistic UI: the screen shows the new value only after OK (the dialog comes first), so a Cancel never shows a flicker.

5.6 task.rowJSON.reasonForDatesChanges – the last reason

  • A snapshot, written together with the dates in the same update (one write, atomic): { reasonGUID, title, code, comment?, changedAt, changedByGUID, changedByName, batchGUID, cascade }.
  • title is copied (not looked up) so the tree needs no join and a later rename in the catalog does not rewrite history – the history keeps the title of the time. (Rename shows in new changes only; Q6.)
  • Empty = null / absent: no date change has been registered for this task since the function was switched on.
  • It is part of the task row, so copying a task copies the snapshot; template copy and version restore clear / restore it consistently (5.9).

5.7 The history table project_reasons_for_changes_history (R5)

  • Append-only. One row per task per change: historyGUID, projectGUID, taskGUID, batchGUID, reasonGUID, reasonTitle (copy), reasonComment, changedByGUID, changedByName (copy), changedAt, source (user | cascade | system), changes (JSONB: for each changed key {from, to}), organizationGUID (for the cross-project report).
  • Written by the database, not by the client: an AFTER UPDATE trigger on project_task_table. When a date key of rowJSON differs between OLD and NEW and the project switch is on, it inserts the row, taking the reason from NEW.rowJSON.reasonForDatesChanges. Reason: one place that cannot be forgotten by a new screen, it also covers writes of the offline queue and of other clients.
  • The server is soft, the UI is hard. If a date changed but the marker is not new (same batchGUID as before / absent), the trigger still writes the row with reasonGUID = null, source = 'system' – it never blocks a write, because a refusal would break the scheduler write-back, the import and the offline queue. Those rows are exactly what a report “changes without a reason” would list (Q2).
  • No UPDATE and no DELETE for users (RLS: select only, for the users of the organization who can see the project). Rows disappear only with the project (ON DELETE CASCADE) or by the delete script.
  • Index: (taskGUID, changedAt desc) for the task history window; (projectGUID, changedAt), (organizationGUID, reasonGUID) for the reports.
  • RPC task_dates_changes_history(p_task, p_limit) returns the rows for the task window (names resolved from userTable.rowJSON).
  • Creating a task is not a change (no history row); the first date change after creation is.

5.8 The task tree shows the last reason (R7)

  • New tree column “Reason for dates change” (id reasonForDatesChanges), read-only, text = task.rowJSON.reasonForDatesChanges.title; tooltip = who, when, comment. Shown only while the project switch is on; added to the column chooser and to the existing column filter / sort / fill-column infrastructure as a text column.
  • Click on the cell opens the history window of the task (section 7): the list of its changes, newest first.
  • An empty snapshot shows an empty cell (not “–”, so the filter “empty” works).

5.9 “It must work after the manual changes” – the entry-path matrix (R6)

“Manual changes” = every way a person changes a date by hand. Each is one user action; none may bypass the guard. “System” rows never ask but are marked.

5.10 Other behaviour

  • Permissions: the same users who may change the dates today may change them; the catalog is edited by the roles that may edit organization catalogs. The reason dialog adds no new right for dates.
  • Realtime: the snapshot arrives with the task row; the history window refreshes when open (realtime on the history table is optional – Q7).
  • Two users at the same time: the later save wins as today; both have their own history rows (the trigger sees every write).
  • Posted lines and payments that unpost on a date change (task_line_plan_unpost_on_dates) are not affected; the reason is only an extra key.
  • No change of dates → no ask: typing the same value, or a value that equals the old one after rounding to the day, is not a change.
  • Performance: the guard compares only the date keys of the patched tasks; no request is added before the dialog (the catalog is cached per organization with react-query / the redux entity).

11. Acceptance criteria

  1. Switch off: no dialog on any path of 5.9, no history rows, no column, no new request – verified by a test.
  2. Switch on: changing a start / finish / duration / constraint / deadline in the edit window, the tree and the Gantt opens the dialog; OK is disabled until an item is picked; nothing is preselected.
  3. Cancel leaves the task, the tree cell, the form field and the bar exactly as they were; nothing is written.
  4. OK writes the new dates, the snapshot reasonForDatesChanges and (by the trigger) one history row per changed task, with the user, the reason, from / to.
  5. A bulk edit of N tasks asks once and creates N rows with one batchGUID; successors that moved are rows with source='cascade' and the same reason.
  6. Scheduler write-back, import, template and restore create no dialog and (where dates change) source='system' rows; the tree keeps the last human reason.
  7. The catalog of one organization is invisible to another organization; all projects of the organization see the same items; an item used by history cannot be deleted, only deactivated.
  8. The history cannot be changed or deleted by a user (RLS); the trigger never blocks a write.
  9. The tree column shows the title of the last reason; click opens the task history.
  10. Ask mode onlyWhenEmpty asks only for tasks with an empty snapshot.
  11. Switch on in an existing project: no retroactive ask, empty cells, first change asks.
  12. All new texts exist in the 14 languages; tests and READMEs exist; SQL runs twice and from scratch on the test Postgres.

12. Questions and decisions (recommended defaults – proceed with them unless changed)

#QuestionRecommended default
Q1The request says: ask when reasonForDatesChanges is empty. Read literally the task is asked only once in its life, because after the first reason it is never empty. Is that wanted?Ask every date-changing action (everyChange), with the literal mode available as a project option onlyWhenEmpty. The field then means “the last reason”, which matches “the tree shows the last reason”.
Q2Should the server refuse a date change without a reason?No (soft server): the trigger records it as source='system' without reason. Refusal would break the scheduler write-back, import and the offline queue. The UI is the hard gate.
Q3Do actual dates (actualStartAt, actualFinishAt) ask too?Yes (“any date” in the request), with the catalog item “Actual date correction”.
Q4Is a free comment allowed next to the catalog item?Yes, optional, 500 characters, in the history only.
Q5Who may edit the catalog?The users who may edit organization catalogs today; everyone in the organization may use it.
Q6Rename of a reason?The history keeps the old title (copy); new changes use the new title; the snapshot of existing tasks is not rewritten.
Q7Realtime on the history table?No in the first version; the history window reloads when opened.
Q8Default reason titles in other languages?Seeded in English; the owner edits the titles (data, not UI text).
Q9Is the reason required when a task is first created with dates?No – creation is not a change.
Q10Does a change of a project date (project start / finish) ask?Not in this version (the request says task dates); the tasks that move because of it are system rows (S2).

13. Out of scope (this version)

  • Approval workflow for a date change (a manager approves the reason).
  • A report / dashboard “changes per reason” (the RPC reasons_for_changes_usage prepares it; the screen is later).
  • Reasons for changes of budgets, payments or resources (only dates of tasks).
  • Retroactive reasons for changes made before the switch was turned on.
  • Export of the history to MS Project / Excel.

14. Risks

RiskCounter-measure
A new screen writes dates and forgets the ask.The guard sits in the shared mutations; the trigger catches everything else and marks it system; a Jest test lists the entry paths (matrix) so a new one is noticed.
Users click through the dialog with the first item.No preselection; last used reason first is a convenience, not a default; the report of “most used reason” makes lazy choices visible later.
Dialog fatigue on drags.One ask per action, not per task; the ask mode onlyWhenEmpty exists for teams that want it quiet.
The history trigger slows large writes (import, scheduler of 5000 tasks).The trigger returns at once when the project switch is off or no date key differs; bulk inserts of tasks (import) are INSERTs, not UPDATEs; index set is small.
Snapshot and history disagree (offline replay, two clients).The history is written from the same row the snapshot is in (one write); a mismatch is impossible within one update.
Cancel leaves the UI in a state different from the data (a stale bar).The dialog comes before the optimistic update; Cancel simply does not call the mutation.
An organization without any active reason cannot change dates.Seeds for every organization; the dialog offers “New reason”; the project switch can be turned off by the project owner.
