Resource Optimization, phase 2 – the time-of-day model (hourByHourModel) – Work Breakdown Structure

Scope: the work package WP15 of RESOURCE_LEVELING_WBS.html (section 7.10, “phase 2”), made a document of its own as that package asks (item 15.1). It makes the choice Hour by hour in Project settings → Resources → Resource optimization selectable: a calendar with clock windows, a task with a start time and a duration, a scheduler, Post and a busy check, and leveling that all work to the minute (the model keeps its stored name hourByHourModel; “hour” is the name of the choice, the precision is the minute – section 4.0). Planning document – no code (2026-11-18). Everything below is checked against the code of that date; what is a proposal is marked proposal, what already exists exists, what the owner decided in the first document decided.

1. Why the choice is disabled today

The text under the radio button is “Phase 2: the time-of-day model is not available yet.” (PMResourceLevelingSettingsTab.tsx; the switch is the constant HOUR_BY_HOUR_MODEL_AVAILABLE = false in resourceLevelingSettings.ts, and resourceLevelingValuesOf forces dayByDayModel whatever is stored). It is off because the data the app keeps has no clock: a resource calendar says “8 hours on Monday”, not “from 09:00 to 17:00”; a task starts on a day and lasts whole working days; Post writes one row per line and day. With such data “hour” and “day” leveling find the same conflicts. The owner decided (answer 16 of the first document): yes, hour-by-hour needs a time-of-day model, as a separate phase chosen by the project setting resourceOptimizationMode. This document is that phase.

Hard constraint (same as phase 1): with resourceOptimizationMode = dayByDayModel (the default, and the value of every existing project) nothing changes: the scheduler, the Gantt chart, Post, the busy check, the reports and every screen work exactly as today. Every new column, field, button and table of this document is invisible and unused in that model. A golden test proves it (WP15.12).

4. Design

4.0 Minute precision – what it means everywhere (adapted: minutes did not exist)

  • Stored. Every time value of the model is an integer number of minutes: window ends ('HH:MM'), taskStartMinute (0..1439), taskDurationMinutes, taskLevelingDelayMinutes, hour-table minutes. Instants are timestamptz on a minute boundary (seconds = 0; a trigger refuses a start / window with seconds).
  • Working minutes. A duration or a delay counts working minutes of a calendar (4.3), as the day model counts working days. A day = the sum of its window minutes (an 8 h day = 480).
  • The smallest task is 1 minute (a milestone stays 0). A task shorter than the step (resourceSlotMinutes) is allowed when typed; leveling moves it by whole steps.
  • Typing. 90m, 1h30m, 1.5h, 2d (a day = the working minutes of that day) all give minutes; 45s is rounded up to 1 minute with a hint; a number without a unit uses the unit of the project (planMinute / planHour / planDay decide only the default unit of an untyped number in this model, not the arithmetic).
  • Display. “1h 30m”, “09:15”; the Gantt zoom steps reach the minute (4.7); money is not affected (the day rows keep the sums).
  • Not in this phase: seconds, and a step finer than 1 minute.

4.1 The calendar with windows (2a)

  • Storage. Day row of managementCalendarDaysTable: rowJSON.windows = [{ "from": "09:00", "to": "13:00" }, { "from": "14:00", "to": "18:00" }], sorted, no overlap, each inside one day, minutes only. Hours of the day = the sum of the windows; the trigger that keeps isActive and hours in step (PART 21) is extended: when windows exist, hours is computed from them and a typed hours that disagrees is refused.
  • A day without windows (every row that exists today) = one window that starts at the calendar’s workFrom (default '08:00') and lasts its hours; if that would pass midnight it ends at 24:00 and the rest is lost (a check at the calendar editor says so). So no existing calendar needs a data change, and the four seeded calendars (08:00–16:00, 08:00–12:00) already give their windows.
  • Fill (CalendarFillMenu): a week pattern gets a window pattern per weekday (weekWindows next to weekPattern); a manual day (vacation, sick leave) clears its windows, as it clears its hours today.
  • Lock (PART 23): a day with posted hours cannot change its hours; the rule extends to windows – a change that moves posted hour rows outside a window is refused with the same message (the new window may only keep or enlarge the posted slices).
  • RPC. organization_resource_capacity_windows(kind, guid, from, to) returns (day, from_minute, to_minute) per resource and day with the same priority as organization_resource_capacity_info (contract in force → resource calendar → Standard week); a day without a row is unknown (never guessed), as in phase 1.
  • UI. The calendar day editor (ManagementCalendarCRUD) gets a Windows editor under the hours: a list of from / to pairs, “Add break”, a total that must equal the hours. Shown only while the project (or, for a catalog calendar, any project of the organization) is in the hour model – hidden otherwise.

4.2 Task time keys (2a)

  • taskStartMinute (H2), taskDurationMinutes (H3), taskLevelingDelayMinutes (H5) – all whole minutes – in project_task_table.rowJSON; typed in PMTaskJSON (types.ts) and stripped by task_template_clean_task (like taskLevelingDelayDays); the trigger trg_project_task_leveling_chk is extended: whole minutes ≥ 0 (a duration ≥ 1), none on a stage, milestone or subproject origin task, taskStartMinute in 0..1439.
  • Written back with the dates. startAt keeps being the written timestamp, now with the time (UTC instant of the wall-clock start); the finish stays in rowDuration. durationDays is written as the number of calendar days the task touches, rounded up, so the day Gantt bar, Monitor01 and every reader that knows only days keep a valid value (they see the task as occupying those days).
  • Normalizers. A new rowJSON key must also be added where the task is rebuilt on save (the lesson of normalizeOrganization / normalizePerson), checked by a test that saves a task with each key (WP15.12).
  • Typing. In this model the duration cell of the tree and the task window read 2.5h, 90m, 1h30m, 1d (a day = the working minutes of that day’s windows) and write taskDurationMinutes (4.0); the project’s planHour / planMinute switches only choose the unit of an untyped number there (H7) and the settings tab says so.

4.3 The time axis (2a)

The hour model works on a working-minute axis: for a calendar, the sequence of its windows over the days, with every non-working stretch removed. Two pure functions, shared by the scheduler and the leveling engine, live in a new file kit8/pm/hourmodel/workMinutes.ts:

  • instantAtWorkMinute(calendar, fromInstant, n) – the instant that is n working minutes after fromInstant (n = 0 → the first working instant on or after it);
  • workMinutesBetween(calendar, a, b).

Windows come from a PMHourCalendar = the PMCalendar of today + windowsOf(day) (a map from the day’s UTC midnight to its windows in wall-clock minutes of projectTimeZone) + the zone. A day-light-saving jump changes the instants of a window, not its length in the wall-clock sense (a 09:00–17:00 window is 8 h on every day; the jump night has no window). The scan guard of the day model (MAX_SCAN_DAYS) applies.

4.4 The hour scheduler (2a)

  • A new function scheduleProjectHours(input) in kit8/pm/hourmodel/scheduleHours.ts, called by the dashboard only when resourceOptimizationMode = hourByHourModel; the day function scheduleProject is untouched, so the day model cannot regress.
  • Same graph, minute arithmetic. It reuses the leaf graph, the stage roll-up, the link types and the cycle report of the day scheduler (those parts are exported and shared, not copied); durations become working minutes, a lag becomes working minutes (a lag typed in days = days × the working minutes of the task calendar’s day), start and finish are instants. FS: the successor starts at the finish of the predecessor (plus lag), SS / FF / SF accordingly.
  • A pinned start. A task with taskStartMinute or a manual start (A1) starts not before that wall-clock instant; a constraint (A3) works on instants. The project start is a day; its time is the start of the first window.
  • Splits. A task paused by a break is a task with its bar in pieces (the pieces are derived, never stored); the A12 splits of the day model are not combined with hour windows in 2a (the function says splitUnsupportedInHourModel and ignores them, visible in the task window).
  • Output. The same PMScheduleResult shape plus per task startInstant / finishInstant / pieces[]; the write-back (pm_apply_schedule) takes the timestamps, the day keys as described in 4.2. Performance: a bench of 3 000 tasks must stay under 1.5 × the day scheduler (WP15.12).

4.6 Hour leveling (2c)

  • Detector (resourceLevelingDetect.ts twin): over-allocation per resource and minute interval (period: 'minute'; the load views aggregate it to the step), capacity from organization_resource_capacity_windows.
  • Engine (resourceLevelingEngine.ts twin …Hours.ts): the same orders, priorities, leveling / smoothing and reason codes; the delay is in working minutes of the task calendar (H5), always a whole multiple of the step resourceSlotMinutes (H12); scheduleProjectHours reads taskLevelingDelayMinutes as a lag. Deterministic and idempotent, tested with generated plans like phase 1.
  • Server side computation (section 20 of the first document) is not offered in the hour model in 2c: the radio shows “Client side” only, with a note (serverSideNeedsDayModel). It can follow when the hour twin is proven.
  • Posted tasks: the same question as phase 1 (Unpost and move / Move and post again / Keep); a moved start unposts the day and hour rows through the existing triggers (task_line_plan_unpost_on_dates also fires when only taskStartMinute or the delay changes: the trigger is extended).
  • Result in the history: project_resource_leveling_task (PART 42) gets nullable columns for the delay in minutes before / after and the instants; the run row says runGrain = 'minute' (the step is in the options snapshot).

4.8 Switching the model and old data

  • Day → hour: days are kept; taskStartMinute is absent (= start of the first window), a task’s taskDurationMinutes = its durationDays × the working minutes of its first day proposal (so the Gantt looks the same after the switch); no posted row is changed – the day rows stay, and the hour rows of the old lines are missing until the user presses Post again (the hour check treats a posted line with no hour rows as its day total spread over its day’s window, so it still counts).
  • Hour → day: the new keys are ignored, never deleted; the Gantt returns to whole days using durationDays as written back (4.2).
  • Templates, import / export, project copy: the project file (kit8.pm.project) gets the optional keys; the importer ignores them for a day project; task_template_clean_task strips them; projectCopy copies them (WP15.13).

13. Server side computations in the time-of-day model (O7)

  • Same switch, no new setting: Project settings → Resources → Resource optimization → Server side computations. The database proposes, the device checks and continues from the proposal with its own scheduler (seed), exactly as in the day model.
  • Problem v = 2 (hourServerProblem.ts): the calendar is already inside the virtual axis, so the database works on a plain axis: a “day” is a step of resourceSlotMinutes of working time, every day is worked, dates are 2000-01-01 + the number of the step. Durations, lags and delays are in steps; capacity and foreign load come with the problem as runs of steps (cap / for), lastSlot = the last step the capacity is known for, maxSearch = the longest search. The answer has the shape of the day answer (delays in steps, buckets as virtual dates).
  • What it does not take (the run is calculated on the device and says why): a start time or a Start No Earlier Than date, a manual task, a subproject, an inactive task, other distributions than uniform, a cycle, more than 30 000 steps or 400 000 resource-steps.
  • Exactness: durations are rounded UP to whole steps for the database; the device continues from the proposal on the exact minutes, so a proposal that is off by a fraction of a step costs time, never a wrong plan.
  • Tests: Docker 101_time_of_day.sql (section 5) and __tests__/pm/hourmodel/hourServer.test.ts.
