Project budget calculation plan - no code yet

Today a task has finance lines (task_line_table) with a total per line (sumForContract, sumForBudget, qtyTaskLine) and a chosen distribution (distributionForBudgetTaskLine), but the money has no dates and nothing is rolled up: a stage and the project have no budget (kit8/pm/view/task/finances/README.md, "Not in this version"). This plan adds:

  1. a budget item on every task line (what the money is budgeted as);
  2. a Post step: the line total is spread over the days of the task, on a calendar, by the line's distribution, and saved as period rows;
  3. role and resource detail rows for the budget by role / by person or product;
  4. calculateProjectBudget: the budget of every stage of the project tree and of the whole project, by period, from the posted rows.

Everything below follows what the code already does (def-table pattern rowGUID · rowOwnerGUID · rowParentGUID · orderInList · rowJSON, ReusableTable, the distribution catalog, FX snapshot per line, one .sql file per feature + run_fresh_data.sql).

Best practice taken from 1C and Dynamics 365

Budget lines are a ledger, not a calculation

D365 (Project management and accounting, Budgeting) and 1C (ERP / "Бюджетирование") keep the plan as stored period entries that reports add up. Reports never re-derive money from the planning screen. So: Post writes period rows; calculateProjectBudget only reads and sums them.

Posting is explicit and repeatable

Both systems separate "draft lines" from "posted / confirmed" ones. A change to a draft line does not move the budget until it is posted again. Here: taskIsPosted per line, and re-posting replaces the line's earlier period rows in one transaction (so a line is never half posted).

Budget item (article) + dimensions

1C "статья бюджета" and D365 budget/ledger accounts with dimensions: the amount is classified by an item and sliced by dimensions (stage, role, resource, period). That is budgetItemTable + the role / resource detail tables.

Working calendar drives period spreading

1C "производственный календарь / график работы" and D365 "calendars / working times": amounts are spread only over active days. Several calendars (project, role, person) are kept as folders; the project chooses which one plans tasks and which one plans the budget.

Rounding and currency

Amounts are rounded to the currency decimals per period and the rest goes to the last period so the periods add up exactly (this is what distributeAmount already does). The currency conversion is a snapshot per line (already in fxSnapshotTaskLine); periods are never converted again.

Roll-up follows the WBS

Stage budget = sum of its children, project budget = sum of the top stages (WBS roll-up in both systems). A stage has no lines of its own in this version, so a stage is always a pure sum.

This is a design summary, not a quote of the vendors' documentation; the mapping to the screens of 1C / D365 is a guide, not a requirement.

Why three detail tables and not one: the request asks for them, and they have different grains (a line without a role has no role row), but all three are written by the same posting function from the same split, so they always add up to the line. The RPC checks sum(details) = line total before it commits.

The money fields spread are sumForBudget (budget currency), sumForContract (line currency, optional) and qtyTaskLine. VAT is not spread: the budget is net of VAT (sumVATForBudget stays on the line for reports that want it).

Calendars

  • Where: kit8/catalog/management/calendar/ - managementCalendarModel.ts, managementCalendarMetaData.ts, useManagementCalendarData.ts, ManagementCalendarCRUD.tsx, calendarFill.ts (pure), calendarResolve.ts (pure), README, route + drawer entry. Built from the existing pieces: FolderTreeReusable (the three folders), ReusableTable (the days of the selected calendar), the same ProductTableDef pattern as genus / distribution.
  • Folders: Project, Resource role, Person (seeded like the genus folders). A calendar lives in one folder; this decides where it can be picked (project.calendar… picks from Project; the role / person screens pick from their folders - stored now, used by availability planning later).
  • Business level setup: there is no "business" entity in the code today. Until it exists, the owner is the constant managementCalendarCatalog (as managementGenusCatalog); when the business entity arrives only rowOwnerGUID changes. The setup screen is the calendar CRUD itself, with a header "Fill" menu.
  • Fill options (current year and previous year, chosen by the user): Working days (Mon-Fri, holidays off), 5-day week (Mon-Fri, holidays on), 6-day week (Mon-Sat), All days (7 days). Fill writes the day rows (reason: 'fill', 'weekend', 'holiday') with one upsert; days the user switched manually (reason:'manual') are kept unless "overwrite manual changes" is ticked.
  • Exclude a day: toggle isActive in the days table (a check box column; a range select later). Excluded days are never used for spreading.
  • Holidays: needs a source. Proposal: "Working days" uses a public-holiday list for the country of the project (fetched once by a small server function, like the ECB rates script) and writes the rows; until then the user switches holidays off by hand. Open point.
  • Project: project_table.rowJSON.calendarForTaskPlan and calendarForBudgetPlan (calendar GUIDs), picked in Project settings → Finances. Default for both: a calendar named "Working days", created and filled for the current year when a project is first posted if none is chosen (so Post never fails for lack of a calendar).
  • Resolving a day (calendarResolve.ts): an explicit day row wins; a day with no row (a year nobody filled) uses weekPattern of the calendar header and the UI warns "year not filled".
The two calendars have two jobs. calendarForTaskPlan: the days of the task between start and finish are cut by the excluded days into working segments; the task line rows (task_budget_line_details) exist only on these days. calendarForBudgetPlan: the same cut with the budget calendar; the role and resource detail rows exist only on its active days. If both are the default they are identical.

Post - the algorithm

A pure module kit8/pm/view/task/finances/budgetPosting.ts (tested like taskLineMoney.ts) builds the rows; an RPC writes them.

  1. Collect the lines of the task shown in the table (all genus tabs) that have a budgetItemTaskLine. Lines without one are skipped and reported ("3 lines have no budget item").
  2. Validate each line (messages go to the existing Errors column): a budget item exists and its genus equals the line's; distributionForBudgetTaskLine is set and is not manualDistribution (manual is not allowed by posting; an empty distribution on a line gets uniformDistribution as the default when the line is created, so this error only appears for old lines); the task has start and finish; sumForBudget exists when the project has a budget currency (strict, as the FX rule: no rate = no post).
  3. Days: take the task's start and finish (rowJSON.startAt inclusive, rowDuration exclusive) as calendar days. Active days of calendarForTaskPlan in that range = the periods of the task. No active day → error on the lines ("calendar has no active day in the task dates"). The active days are grouped into segments (a gap = an excluded day) - only for display; the split uses the days.
  4. Spread each of sumForBudget, sumForContract, qtyTaskLine with the existing distributeAmount(code, amount, periods, params, decimals): money to the decimals of its currency (currency.decimals), quantity to 4 decimals. The rest goes to the last period, so every column adds up to the line.
  5. Write rows: one task_budget_line_details row per line and day (rowPeriod = the day at 00:00:00). For lines with a role: one task_budget_role_line_details row per day of calendarForBudgetPlan (the amounts spread over that calendar's days). For lines with a resource: the same into task_budget_resource_line_details. A contract sum is written only when the line has one.
  6. One transaction: RPC pm_post_task_budget(p_task uuid, p_lines jsonb) - deletes the earlier detail rows of the posted lines, inserts the new ones (all three tables), checks that the sums of the rows equal the line totals (tolerance 0 after rounding), sets taskIsPosted = true and postSnapshotTaskLine on those lines, and returns the counts. Any error rolls everything back; the table shows the message and the lines stay unposted.
  7. Result: the Post button turns on (filled); a snackbar says "Posted 8 lines · 120 day rows" (or the errors).

Why the maths runs in the app and not in SQL: the distribution shapes (normal, logarithmic, epidemic) already exist as tested TypeScript; duplicating them in plpgsql would give two sources of truth. The RPC only stores and verifies.

calculateProjectBudget

A pure function kit8/pm/view/task/finances/calculateProjectBudget.ts with a SQL twin as a view / RPC for reports. It reads only posted rows.

calculateProjectBudget({
  tasks,          // the project tree (rowGUID, treePath, isStage)
  lines,          // task_line_table rows  (for the "not posted" counts)
  details,        // task_budget_line_details rows
  roleDetails, resourceDetails,
  groupBy,        // 'month' | 'week' | 'day'  (default 'month')
  dimensions,     // ['budgetItem','genus','role','resource']  (any of)
}) => {
  byTask:   { [taskGUID]:  { periods: {...}, total, postedLines, unpostedLines } },   // leaf tasks
  byStage:  { [stageGUID]: { periods: {...}, total, postedLines, unpostedLines } },   // sum of descendants (treePath)
  project:  { periods, total, costs, revenue, result, postedLines, unpostedLines },
  warnings: [ 'Task X: 2 lines not posted', 'Task Y: posted before its dates changed' ]
}
  • Stage = sum of its descendants, found by treePath (a prefix match, also in SQL); the project = the sum of the top stages. A task is never counted twice (a stage has no lines).
  • Sign / result: costs (Time, Material, Expenses genus) and revenue (Revenues genus) are summed separately; result = revenue - costs. Payments (inbound / outbound) are not budget lines in this version.
  • Currency: roll-ups use sumForBudget (one currency, the project's). sumForContract is shown per line currency and never added across currencies.
  • Periods: day rows are summed to week / month with the project's week start; an empty period is returned as 0 so the table has no holes.
  • Honesty: unposted lines are not in the numbers; each stage shows "N lines not posted" so a low budget is never silently wrong.
  • SQL twin: view project_budget_view (task × period × budget item) and an RPC pm_project_budget(project, from, to, group) that does the treePath roll-up, for exports and the dashboards; the TypeScript and SQL results are compared in a test on the same fixture.
  • Screen (phase 3): Finances view of the dashboard: a stage / the project selected in the tree shows the budget table (rows: budget items or child stages; columns: periods + total), replacing today's "select a task".

When posted data goes stale

A posted line is correct only for the dates and calendars it was posted with. Three things can break that besides editing the line:

ChangeWhat happens
Task start / finish changes (the scheduler rewrites startAt / rowDuration) SQL trigger on project_task_table: when the dates change, every line of that task gets taskIsPosted:false (the old detail rows stay until the next post, so the budget does not jump to zero, but a warning says "posted for other dates"). The trigger compares with postSnapshotTaskLine.startDay / finishDay, so a scheduler run that writes the same dates unposts nothing.
The project picks another calendarLines whose postSnapshotTaskLine.calendar… differs are shown as stale (computed, not written); "Post" re-posts them.
Days of a used calendar are editedcalendarStamp (the calendar's updated_at at posting) is older than the calendar's → stale warning; v1 does not unpost automatically (a calendar edit would touch thousands of lines).
A line is deletedIts detail rows are deleted by the FK cascade; nothing else to do.
