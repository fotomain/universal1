Initial program data - how it works

A new, empty Supabase database has the tables and the functions but no row in any catalog: no permission matrix, no budget item, no calendar. The application now makes those rows itself, from JSON files that are part of the application. It does it by itself at the first run, and a menu row does the same later.

Built 2026-11-26. Plan and decisions: INITIAL_DATA_WBS.html. Code: kit8/initial/data/code · data: kit8/initial/data/json · SQL: PART 60 of start2_sql_code.sql · README: kit8/initial/data/README.md.

1. What the application does when it starts

After a user is signed in, ONE question goes to the database (initial_data_status); the answer says what exists. Then:

The databaseWhat the user sees
Everything the application needs is thereNothing. The normal start. (This is every start after the first.)
Nothing of it exists (a new database)The window Preparing the application opens by itself and runs without asking. Only the progress is shown: a bar, the percent, "Step 3 of 15: Management genus", the table and its rows. Nothing else in the application can be used. When it is over, the exchange rates window is offered, then the home page opens.
A part exists (something was deleted, or an older database)The screen Create initial data opens as a list with a check box near each group. The user presses Create. Close stays disabled until everything required is there. When it is over the home page opens.
This user may not write the dataThe screen says who can ("ask your administrator"); Create is disabled; Check again reads the database again.
The check cannot be made (the SQL of PART 60 is not installed yet, no network)Nothing. The application is not locked; a warning is in the console.
A guest cannot be checked: the function is only for signed-in users. The check runs when a user signs in, once per user and application run (a token refresh does not ask again).

Create writes the checked groups: only what the database does not have yet, in pieces of 500 rows. A row that exists is never changed (a budget item you renamed stays renamed). While it writes the screen shows only the progress. If a step fails the message is shown and Create again goes on from there. The button Exchange rates opens the separate window of section 3.

3. Exchange rates (a separate window)

  1. Automatic. The run makes the rate in force on 31 December of the previous year for the currencies of the catalog (the base currency excluded; the check at the start looks at USD, EUR and GBP). The rates service publishes working days only, so the last published day on or before 31 December (up to 10 days back) is stored as the rate of 31 December; the day it was read from is in rowJSON.rateFromDay. A currency that already has a rate on or before that day is left alone.
  2. Offered. When the data is ready the window Exchange rates opens: Fill from 1 January to today adds every missing day for the catalog's currencies (what a currency card's "Upload all data from a date" does).
  3. Template. Download currencies_reates_import_template.csv: the columns currencyCode, startingDate, currencyRatio, rateType and a line per currency for 1 January with an empty ratio.
  4. Import. Import from CSV reads the filled file and shows a preview first: how many rates can be imported, how many lines have no ratio (skipped), which lines are wrong and why. Then Import. Rates that exist stay unless "Replace a rate that already exists" is checked.
The CSV may use , or ; between the columns, the day as 2026-01-02 or 02.01.2026, the ratio with a point or a comma; rateType is Default (or empty) or Budget. A ratio is units of the currency for 1 unit of the base currency. If the rates service cannot be reached at the first run, the screen stops at "Exchange rates" and offers Create again and Continue without rates; the next start asks again.

4. Inside

  • The list of the data is one file, initialDataDefinition.json: the groups in install order, the tables, how a row is recognised (its rowGUID, or one key of its JSON for currencies, countries and Kanban stages), what is required. The screen, the gate, the dump script and the tests all read it; a Jest test compares it with the whitelist in SQL.
  • The data is kit8/initial/data/json/NN_<table>.json, one row a line, with manifest.json (rows and sha-256). It is bundled into the application, so nothing but Supabase is needed.
  • The way in is the function initial_data_install(table, rows) (SECURITY DEFINER): a whitelist of 20 tables, at most 1 000 rows a call, INSERT ONLY (ON CONFLICT DO NOTHING plus the natural-key test), rows in the order of the file (a parent before its children). Three catalogs the client can only read (permission profiles, RACI items, languages) are written through it too, by an application administrator only.
  • The calendar days are not shipped: initial_data_fill_calendars() makes the days of last, this and next year for the five seeded calendars (the rule of start4), only for a calendar and year that has none.
  • The dump. node kit8/initial/data/code/dumpInitialData.mjs writes the JSON files from the Supabase of .env (it reads the key, never prints or writes it) and prints what changed against the files that were there. --source docker --db sqlseeds makes them from the repository seeds (kit8/docker/make_seeds_db.sh); the files in the repository now come from there. It dumps ALL rows of the listed tables: remove the user's own rows from the JSON before the files are used.

5. The first application administrator

The permission matrix is read from the database, and the only application administrator of the old database is a row of application_permission_table that nobody but SQL can write. A new database has none. The function initial_data_bootstrap_admin() makes the caller the application administrator, with the e-mail of his own session, only while nobody is one and the database has at most one registered user (the first sign-up). It is the first step of the run, before the groups that need an application administrator. A second user of a new database cannot claim it from the application: an administrator adds the e-mail in SQL (start4 PART 54 shows the row).

6. A new Supabase database

  1. SQL Editor: run start1_sql_tables.sql, then start2_sql_code.sql (PART 60 is in it), then start3_sql_pg_cron.sql if pg_cron is enabled. Not start4: the application creates the data.
  2. .env: the URL and keys of the new project; restart npx expo start --web -c.
  3. Sign in as the first user. The window "Preparing the application" runs by itself; the exchange rates window follows; then the home page opens.
An existing database needs only start2_sql_code.sql (the functions), and the menu row Create initial data works. If its data is complete the application starts as before.

7. What was tested, and what was not

Tested

  • Docker, an EMPTY database (start1 + start2): 53 checks of the five functions (insert only, whitelist, 1 000 rows, rights, the first administrator, calendars once).
  • The JSON files installed through the functions, as the first run does: 21 tables equal to the database made by start4.
  • On that database made WITHOUT start4: a demo project, a task, a Time line, Post works.
  • Jest (__tests__/initial): the model and what the application does about each state, the JSON files, the rate algorithm and the CSV, the run (order, pieces, failure), the screen, the gate, the rates window.

Not tested

  • Nothing was seen in a browser or on a phone.
  • The owner's real Supabase was not touched, and the rates service was only tested with a fake one.
  • "Take one group away and see what breaks" was not run: the proof is that the JSON alone is enough for a project and a Post. Which group is required comes from reading the code.
  • The texts of the screen and the gate are in English; the menu row is in 15 languages.
