Product entity: WooCommerce-shaped products, variants and classification in Supabase

Products are imported from the WordPress / WooCommerce shop into four defTable.md-style Supabase tables, edited in the Expo app (desktop and mobile), and written back to WooCommerce. The model copies WordPress: a product has variations, and it is classified by taxonomies (categories, tags, attributes) that hold terms.

The one idea behind the design: taxonomyTable = a WordPress taxonomy (Product categories, Tags, Color, Memory…), taxonomyTermTable = its terms (Smartphones, Food, Black, 256 GB…). The same two tables classify products and drive variant prices, so there is no separate "attributes" table to maintain. Named taxonomy, not category: a "category" is only one kind of taxonomy (and in the UI "category" means a term such as Smartphones), so categoryTable would be misleading. UI labels stay "Categories & attributes".

Domain model: WordPress → Supabase

WooCommerce stores products as posts, variations as child posts, and classification as taxonomies with terms. We keep exactly that shape, in defTable rows.

WooCommerce connection

Security: the consumer key and secret give full read/write access to the shop. Anything prefixed EXPO_PUBLIC_ or put in app.config.js extra is shipped inside the web bundle and the mobile app, so the keys must stay server-side. The keys are also written in plain text in the Google Doc "W1 PRODUCT": remove them from there and, once the proxy works, regenerate them in WooCommerce → Settings → Advanced → REST API.

Transport: Supabase Edge Function woo-proxy

  • App → supabase.functions.invoke('woo-proxy', { body: { method, path, query, data } }) with the user's JWT.
  • Function checks the user is signed in (optionally has a role from user/roles), allow-lists paths under /wp-json/wc/v3/products… and /taxes/classes, adds Basic auth, forwards, returns body + X-WP-Total / X-WP-TotalPages.
  • Also solves CORS: the browser never calls the shop directly.
  • Lives in supabase/functions/woo-proxy/index.ts (new folder at repo root).

Import and write-back

Import (Woo → Supabase), idempotent

  1. Dry run: count products / categories / attributes via X-WP-Total; show "will create N, update M, unchanged K".
  2. Taxonomies: ensure seed rows in taxonomyTable; /products/attributes → one taxonomyTable row per pa_*.
  3. Terms: /products/categories (2 passes: rows, then rowParentGUID from parent), /products/tags, /products/attributes/{id}/terms, /products/shipping_classes → taxonomyTermTable.
  4. Tax classes → taxClassTable.
  5. Products: listAll() pages of 100 → map → upsert by woo.wooId. Local edits newer than last pull (syncStatus = dirty) are not overwritten → logged as conflict.
  6. Variations of every variable product → upsert by wooId; build variantKey.
  7. Second pass: resolve grouped / upsell / cross-sell GUIDs.
  8. Write run summary to integrationSyncLogTable; realtime refreshes open lists.

Options on the screen: categories to import (e.g. only "Food"), "overwrite local changes", "include drafts".

Write-back (Supabase → Woo)

  1. Every save in ProductEditCard writes Supabase first and sets woo.syncStatus = 'dirty' (or 'localOnly' if no wooId).
  2. "Push to WooCommerce" (card button, list bulk action) → ensure terms exist in Woo (create missing attribute terms / categories and store their wooIds).
  3. Conflict check: GET product, compare date_modified_gmt with woo.wooModifiedGmt. Different → conflict; user chooses "keep app" / "take shop" with a field diff.
  4. POST (new) or PUT product with rowToWooProduct (only changed fields).
  5. Variations: POST /products/{id}/variations/batch with create / update / delete (delete only for variants the user removed).
  6. Store returned ids and date_modified_gmt; syncStatus = 'synced'; log.

Auto-push on save is a setting (default off) so the shop is never changed by accident.

Deletes: deleting in the app sets isActive = false and pushes status = 'draft'. Hard delete in Woo is not offered (orders reference products). Products removed in Woo are marked syncStatus = 'error', "missing in shop", not deleted.

Food — imported from the shop

Import with the category filter "Food" (or whatever the shop names it; the dry run lists the shop's categories). Typical shape: simple products, unit kg / g / l, tax class reduced-rate, optional food block filled in the app and pushed as _w1_food meta.

Acceptance: after import every Food product is visible in ProductListScreen filtered by the Food term, opens in ProductEditCard, a price edit pushed from the app is visible on the shop's product page, and re-running the import changes nothing (0 created, 0 updated).

If the shop has no Food category yet, the importer reports it in the dry run; then create "Food" in the app and push 3 sample products (Milk 1 l, Rye bread 500 g, Cheddar 200 g).

Tests (__tests__/catalog/product)

  • productModel: normalize (Woo strings → numbers, "" → null), validate (sale ≤ regular, SKU required for variants, variable needs ≥ 1 variation attribute).
  • variantMatrix: 3 × 3 → 9 keys; adding a value adds 3, removing one marks 3 obsolete; stable variantKey regardless of attribute order.
  • wooMappers: fixture JSON for a simple, variable, grouped and external product (from the docs' examples) → row → Woo is lossless for mapped fields; unknown meta survives.
  • wooImport with a fake transport: idempotent second run; dirty local rows not overwritten; category parent resolved regardless of page order.
  • wooPush: conflict when date_modified_gmt differs; batch split at 100.
  • SelectElementFromCatalog: extend the existing test for multi-select and tree indent.
  • SQL: run create/delete scripts on local PostgreSQL 16 with Supabase stubs (same harness as the master schema).

Decisions taken (and the alternative not taken)

QuestionDecisionNot taken, because
Table names: category or taxonomy?taxonomyTable + taxonomyTermTable (WordPress words: taxonomy → term)categoryTable + categoryValuesTable (original prompt): the table also holds tags, attributes and shipping classes, and "category" would mean the group in SQL but the value (Smartphones) in the UI
What do the two tables hold?Taxonomies and terms (WP model): product categories, tags, attributes and shipping classes in one pairSeparate attributeTable + productCategoryTable: duplicates the tree / term logic and the UI
Variants: rows or JSON array in the product?Own tableJSON array: no per-variant realtime, unique SKU index or stock rows
Who talks to Woo?Supabase Edge Function proxyDirect from app: leaks the secret, CORS on web
Source of truthSupabase for the app; Woo for orders. Explicit push with conflict checkTwo-way auto sync via webhooks: later, once push is stable (Woo webhooks "product.updated" → edge function)
Bulk import through Redux?No — repository writes directly, Redux/realtime refreshes the UIThousands of actions through the saga, slow and noisy
Prices typenumber in rowJSON, string to Woostrings everywhere: breaks sorting and validation
ImagesURLs from the Woo media libraryUploading files from the app: phase 2 (Supabase Storage → Woo src)
