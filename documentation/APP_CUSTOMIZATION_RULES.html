How one code base becomes several apps (APP_NAME = appPosts, appCC1, appOnTrend, appClothes1, appPM80) without a forest of if (app === …). First case: when APP_NAME=appPM80 the FAB of the home keeps its current items and gets three more: New Project, All Projects, Add Calendar event.

1. Verdict

The rule

Shared code (kit8/) never knows an app by name. Every app owns ONE small customization entry in apps/<app>/; a registry picks it by configurationName; the shared code asks the registry through named extension points and falls back to its built-in behavior when the app says nothing.

For the FAB

An extension point fabExtraActions: a list of actions + the routes where they show. FABAppComponent puts them under (nearest the button) what it shows today (the commands of the open screen, else its defaults), so "current items as is, plus three" holds on every screen that matches, and screens such as the project dashboard keep their own commands.

Not this

Not actions= on <FABAppComponent/> in the root layout (it replaces the commands of every screen). Not useFABContextActions in the home (it replaces the defaults and stays published when the drawer keeps the home mounted). Not process.env.APP_NAME in client code (section 9).

3. The rules

  1. One switch, read one way. The client reads the app from Constants.expoConfig.extra.configurationName (through one helper, e.g. getAppName()). Never process.env.APP_NAME in app code: the Babel plugin react-native-dotenv replaces that expression by the value of .env at build time (it also broke an assignment in a Jest test), so it is not a run-time switch.
  2. Shared code does not know the apps. kit8/ must not import from apps/ and must not compare the app name. It exposes an extension point (a prop, a hook or a registry lookup) and works without it.
  3. Data, not branches. A customization is an object in a registry (Record<AppName, AppCustomization>) with optional fields. No if (name === 'appPM80') in components. An unknown name gets the default (empty) customization.
  4. Additive by default. An extension point says what to add (extra FAB actions, extra Drawer items, extra tabs). A replacement is allowed only where the app really needs it (the home component) and is named replace…. This keeps the other screens' own behavior alive.
  5. Scope every addition. Each addition says where it shows (routes) and, if needed, who sees it (signed in / permission). A bare "everywhere" must be a decision, not an accident.
  6. Everything an app adds points to a real thing. Routes are real files of app/ (a Jest guard checks it, as for the PM80 home), labels go through the translation function, icons exist in the icon set.
  7. One file per app, one registry. apps/<app>/customization.ts default-exports the app's object; apps/appCustomization.ts maps names to objects and offers useAppCustomization() / getAppCustomization(). Adding an app = one line in the registry.
  8. Test per app and per extension point. The app gets its extras, the other apps do not, the other routes do not (if scoped). Write the test in the same round; update KNOW_HOW.md (section 1.2 / feature index) and this page.

5. The home FAB of appPM80

5.1 How the FAB decides what to show today

FABAppComponent is mounted once in app/_layout.tsx and picks the first of these that exists:

1
Prop actions - not used by the layout today. If set, it wins over everything (so it would hide the commands of the project dashboard).
2
Commands of the open screen - a screen publishes them with useFABContextActions(id, actions) (FABProvider); the last publisher wins, an unmount withdraws. The project dashboard does this (New project, Add task, Delete, Undo …).
3
Built-in defaults - Record Video, Record Audio, Scroll Top. This is what the home shows now ("current items").
Found while reading: the defaults open /record/recordvideoweb and /record/recordaudioweb, but app/record/ does not exist (the real routes are /media/record/video and /media/record/audio). The two "current" recording items therefore lead to a 404 today, in every app. "As is" must not be taken literally for them - see decision Q6.

5.3 The recommended design (C)

+
App extras (added AFTER the tiers below, nearest the button): customization.fabExtraActions filtered by the current route (usePathname(), already used by the FAB for fabHiddenOnRoute).
1
Prop actions (unchanged; wins over all, extras included - it is for tests / special screens).
2
Commands of the open screen (unchanged).
3
Built-in defaults (unchanged; routes to be corrected, Q6).

Merge rule (a pure function, mergeFabActions(base, extras, reanimated)): the extras stand nearest the button, under the base items. Default animation (a column, first item on top, last next to the button): [...base, ...extras]. Reanimated animation (stacked upward, first item next to the button): [...extras reversed, ...base] - the eye sees the same order in both. An extra whose label is already in the base is not added twice; the list may be longer than 4, and the FAB already scrolls then (manyActions).

Scope: each extra carries routes (default for appPM80: ['/home'], the home only, as asked). Making it app-wide later is one value ('*'), no code change.

What the home FAB of appPM80 shows (checked in the browser at phone width):

Record Video Record Audio Scroll Top New Project All Projects Add Calendar event +

Grey = the current items, kept. Purple = new, only while APP_NAME=appPM80 and only on the home.

8. Tests (written in the same round as the code)

  • Pure merge: extras first, then the base; no double entries; a route filter (/home matches /home and /home/, not /pm/business-order, unless asked); '*' = every route; an empty list = the base unchanged.
  • Registry: appPM80 has the three actions; appClothes1, appCC1, appOnTrend, appPosts and an unknown name have none (so their FAB is byte-for-byte what it is now).
  • FAB component (name set by mocking Constants): on /home as appPM80 the list is the three + Record Video + Record Audio + Scroll Top; on the project dashboard only the dashboard's own commands (extras are scoped to /home); as another app on /home: the old three only.
  • Real routes guard (as the PM80 home already has): /catalog/project, /user/calendar, /pm/project/dashboard exist in app/; the calendar link carries new=event.
  • New Project: pressing it requests openProjectSettings('new') and navigates to the dashboard (router mocked); a guest is sent to sign in with returnTo and no request is made (if Q5 is accepted).

9. Pitfalls found while reading the code

  • Drawer screens stay mounted. Anything a screen "publishes" while mounted (useFABContextActions) stays published after the user leaves for another drawer screen. For per-route additions use the current path (usePathname) in the shared component, not mount/unmount of the screen. If a screen must publish anyway, make the hook focus-aware (useIsFocused).
  • Last publisher wins in FABProvider: two screens publishing at once hide each other. Another reason not to put app extras there.
  • The actions prop replaces everything (extras and the dashboard's commands). Keep it for tests and special screens.
  • process.env.APP_NAME in client code is inlined from .env by the Babel dotenv plugin; read the name from expoConfig.extra.configurationName. In Jest, mock expo-constants to test another app.
  • A new window loses the in-memory store. Actions that hand something to a screen through the store (New project) must navigate inside the same window. Pure links (All Projects, the calendar deep link) may open anywhere.
  • Bundle weight. A registry that imports every app's customization pulls all of them into every bundle (as homeComponentsMap already does with the homes). Keep customization files small (data + handlers); heavy screens stay behind routes or React.lazy(() => Promise.resolve(require(...))).
  • The long FAB list. Six items scroll on phones (manyActions > 4). That works, but it is the reason to decide the order (Q4) and maybe to shorten the old items (Q6).

10. Decisions (taken with the recommended default unless it says otherwise)

Q1. Scope of the three items. Only the home (as written), or on every screen of the app? default: home only - one value in the registry changes it later.
Q2. "Current items as is." Keep all three (Record Video, Record Audio, Scroll Top) behind the new ones? default: yes, kept
Q3. All Projects / Add Calendar event: this window or a new browser window? New Project must be this window (section 6). default: this window for all three (a FAB is in-app navigation; the new-window rule stays for the circles and links of the home).
Q4. Order in the list. decided by the owner The three items stand under the default items, nearest the button: New Project, All Projects, Add Calendar event (top to bottom). Both animation variants are handled (section 5.3).
Q5. Guest pressing New Project. default: go to sign in with returnTo=/home, no request made; the alternative (open the dashboard) shows "Sign-in required".
Q6. The two recording items point to routes that do not exist. default: fix them in the same round to /media/record/video and /media/record/audio (a one-line change each in the defaults; it also repairs the other four apps) - or leave them and accept a 404.
Q7. Labels. English text through the translation function (pmT keys "New Project", "All Projects", "Add Calendar event"; other languages fall back to English until translated). default: yes
Q8. Move homeComponentsMap into the registry now? default: yes, same round - otherwise there are two places that map an app name to something.

11. How to add the next customization

  1. Add the optional field to AppCustomization (kit8/providers/AppCustomizationProvider.tsx) and let the shared component read it through useAppCustomization(); with no value it must behave exactly as before.
  2. Fill it in apps/<app>/customization.ts and list the app in apps/appCustomization.ts.
  3. Test: the app gets it, the other apps and the unknown name do not (__tests__/apps/appCustomization.test.ts), and the shared component shows it (__tests__/apps/appPM80/fab.test.tsx is the model).
  4. Update KNOW_HOW.md and this page. No SQL, no .env.
