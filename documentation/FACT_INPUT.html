Fact input built 2026-10-13

Source: Google Doc "W1 FACT INPUT". As the doc says: do not code. The business need: the user records what really happened on a task - hours worked, material delivered or used, expenses, revenues - in a document opened from the lines of the task. The posted documents feed the Monitor01 report (delivered · actually used · on-hand). This page is the scenario, the tables, the rules, the work breakdown and the questions.

Step by step

  1. Open. The menu item sits in the row menu of the Finances table (the same place as Duplicate / Delete of a line). Opening it shows the latest draft document of the task; if there is none, an empty new document (the header row is written at the first Save, so an unused window leaves nothing behind - Q5). "Previous documents" lists the earlier ones (number · kind · date · user · status).
  2. Tab. The document opens on the tab of the genus of the clicked line (last tab remembered like lastEditPlace of the task window). In strong mode the clicked line's rows are scrolled into view.
  3. Edit. Every line has an editable date (rowPeriodDatetime), quantity and unit; the other columns depend on the mode (section 4). The sums follow the money rules of the Finances table.
  4. Save writes the lines one by one (as the Finances table does). The document stays a draft: nothing reaches Monitor01.
  5. Post (section 5) checks the whole document, marks it posted, and queues the task for the summary. Posted = read only.

Strong mode: how the lines are created Q4

  • On the first Save of a new document the system proposes one fact line for every posted plan day (task_line_plan_timeline) of every line of the task that has a budget item - the date and quantity are prefilled with the plan, as a timesheet is. The user changes the real quantity and date, or deletes the lines that did not happen.
  • Lines that are not posted yet (taskIsPosted = false) have no plan days; they are named in a message ("Post the plan first") and get no fact lines.
  • [Refill from plan] adds the plan days that have no fact line in the document (the only way to get a deleted line back; it is not "adding a free line").

Free mode: what a line must have

Genus (the tab), date, quantity ≥ 0, unit. A role is recommended (Monitor01 groups by role; a line without a role lands in the "no role" row); the resource (person / equipment / product), price and note are optional.

5 - Post

  • Button: the same Post button as the Finances table, three states - Post (draft with lines) · Posted · Post needed (a posted document was unposted and changed).
  • Procedure post_task_fact_document(headerGUID) (one transaction, the answer is data): lock the document; check the owner; the document has lines; quantities ≥ 0; every date is a valid day (and not in the future - Q8); in strong mode every line has a task line of this task and the lines are consistent; set documentStatus = posted, postedAt, postedBy; queue the task for the summary. A refusal is a list of problems per line, shown like the problems of the plan Post; nothing is written.
  • Posted = read only (trigger and screen). To correct a posted document the owner uses Unpost (unpost_task_fact_document): status back to draft, the task is queued, so Monitor01 loses these numbers within 2 s; edit; Post again. unpostedAt is kept (Q9). A fact is never given a negative quantity.
  • Only posted documents count in task_line_fact_for_monitor01; a draft is invisible to every report.

6 - From the document to Monitor01

Post / Unpost of a document→ queue key (the task) → monitor01_dirty→ pg_cron, every 2 s, one procedure → task_line_fact_for_monitor01→ same run → monitor01_view (delivered · actually used · on-hand)
  • One worker, two steps, one transaction per batch: step 1 re-sums the posted task_fact_timeline rows of the claimed tasks into task_line_fact_for_monitor01 (changed rows only); step 2 is the Monitor01 aggregation, which reads this table for the fact columns. A second cron job in a chain would add another 2 s of delay; this way the end-to-end target stays under 3 s (Q11).
  • Mapping: Monitor01 delivered = Σ qtyFact of factKind = delivered; actually used = Σ qtyFact of factKind = used; on-hand = delivered − used (already in the Monitor01 plan).
  • Sum explorer: a click on delivered / used in Monitor01 lists the lines of task_fact_timeline (posted documents) with the document number; Open opens that document read only. The list total equals the cell.
  • Revenues: the document has a Revenues tab (as in the doc) and the table keeps revenue facts, but the Monitor01 plan does not show revenue (its Q4). They sit in task_line_fact_for_monitor01 for a later report.

10 - Tests

Docker (postgres:15, cd kit8/docker && ./test_sql.sh && ./test_fact_input.sh)

  • Install / delete cycle twice (idempotent).
  • Header: number and created_at are set by the database; project is filled from the task; a draft can be changed, a posted one cannot (header and lines).
  • Lines: a line of another task or project than its header is refused; strong mode refuses a line without a task line of the same task; free mode accepts NULL; negative quantity refused; two facts of one line and day are allowed.
  • Post: an empty document, a bad date and an inconsistent strong line each return a problem list and write nothing; a good document becomes posted and queues its task; Unpost returns it to draft and queues again.
  • Summary: after one worker run task_line_fact_for_monitor01 equals the sum of the posted lines by task × genus × role × unit × month × kind; drafts are not counted; an unchanged row keeps its updated_at; a deleted task or document leaves no row.
  • Policies: only the owner reads or writes; nobody writes the summary table.

Jest

  • Lines from plan days (prefilled, unposted lines named), validation twin, totals per unit, document state text.
  • Screen: strong mode has no Add line and keeps Delete / update; free mode has Add line; the date is editable in every row; the tab of the clicked line opens; Post / Unpost buttons by status.
  • Menu: the Facts input item appears in the row menu of a line and opens the document on the right tab.
