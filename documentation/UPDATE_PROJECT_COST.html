Update project cost built 2026-10-15

Request: a server side function update_project_cost_total that calculates the total cost of every task and every stage of the tree, from the register, only when the project has the cost budget on, with real time refresh, a tree column costTotalForBudget, a project switch showTotalCostOnTheGanttChart and a toolbar command before Refresh the project. Asked: "project_status_turnover or ???" and "a field of project_task_table or a separate table???" and "the fastest way".

Decisions of the owner (2026-10-15) - they replace the earlier proposals
  • CostTotal = Time + Material + Expense: costTotalForBudget is the plan in the budget currency summed over the three cost genera (answers Q1: the plan; used and invoiced are not part of version 1).
  • The server does the work only while one of the three budgets is on: Time (projectTimeCostsNeeded with a kind person / equipment) or Material (projectMaterialCostsNeeded) or Expense (projectExpenseCostsNeeded). They are the inputs under the master switch projectExpenseBudgetNeeded; the master off = the legacy project (no cost budget chosen) = no work. The rule is the same in SQL (project_cost_budget_on) and in the app (projectCostBudgetOn), and a test keeps them equal.
  • showTotalCostOnTheGanttChart is usable only while that rule is true. The other questions are answered as proposed (section 11).
  • A genus whose input switch is later turned off but that still has plan lines is still summed ("a switch never hides data", as the task tabs).
The best solution, in six lines
  1. Source: project_status_month_turnover (the user's "project_status_turnover"): column sumForBudgetPlan, already summed per task, written by the Monitor01 worker. No new source of truth.
  2. Storage: a separate narrow table project_task_cost_total (one row per task or stage that has a cost; column costTotalForBudget), not a column of project_task_table. Section 3 says why; the column is the weaker choice.
  3. Calculation: delta propagation on the ancestors read from the path labels - a task's path already contains the GUID of every stage above it, so the roll-up needs no join and no subtree scan. Measured: 500 changed tasks 14-16 ms, one task 0.3 ms. A full rebuild by the same trick: ~60-145 ms for 11 220 tasks. Section 5.
  4. Where it runs: as step 3 of monitor01_apply - the same queue, the same pg_cron tick, the same transaction as the turnover. No new job, no new trigger on the register.
  5. Real time: Supabase Realtime on the new table (a row = 5 numbers, a change of one task = about 5 small events). The client patches its cache from the event payload: no refetch of the project.
  6. Settings gate: the server does the work only while one of the Time / Material / Expense budgets is on (all off = the rows are deleted); showTotalCostOnTheGanttChart is display only and is usable only while that is true.
About the file name. The request says ./documents/UPDATE_PROJECT_COST.html. The folder documents/ does not exist; all the plan pages of this project are in documentation/, so this page is documentation/UPDATE_PROJECT_COST.html. (Say so if you want the folder documents/ made.)

Which number is "total cost"? The turnover has three: plan (sumForBudgetPlan), used (…Used, posted fact documents), invoiced (…Invoiced). costTotalForBudget = the plan in the budget currency (the budget of the task), Time + Material + Expense (decided). The same machinery gives used and invoiced for the price of one more column pair; version 1 builds the plan only.

The currency is the budget currency the plan was posted with (sumForBudget). A change of the project budget currency or rate type shows in the totals only after the tasks are reposted - exactly as in Monitor01.

4 How to calculate the stages the fastest way

A stage total = the own cost of the stage + the own cost of everything below it. The worker already knows which tasks changed (a batch) and the table stores each task's own cost, so the exact change of every stage above is newOwn − storedOwn.

#WayIdeaVerdict
1At read timeA view / RPC sums the turnover per task and rolls it up on every refresh.Whole project 300-360 ms per refresh, per client, and nothing tells the client when to refresh (no realtime signal). No.
2Recompute the stages above a changed task by a subtree sumWHERE path <@ stage.path (GiST) for each affected stage.300-690 ms for a batch of 500, ~190-200 ms even for one task: the planner scans the subtree of the top stages. No.
3Recompute with the prefixes of the path joined back to the task tableEvery prefix → join treePath = prefix.280-370 ms for 500. ltree comparisons are slow. No.
4Delta, ancestors found by a jointotal = total + delta.40-48 ms for 500. Right idea, avoidable join.
5Delta, ancestors read from the labels of the pathA label is the GUID of that ancestor: replace(label,'_','-')::uuid. One unnest(string_to_array(…)), one hash aggregate, one update by primary key.14-16 ms for 500 tasks, 0.26-0.30 ms for one. Used on the hot path.
6Full rebuild by the same label trickOwn cost of every task (a group by), then the same unnest, one pass.~58-67 ms read, ~85-146 ms with the writes, for 11 220 tasks. Used for the rare paths: the toolbar command, switch turned on, a stage moved or deleted, verify.
Why delta is safe. Money is NUMERIC(18,2): sums are exact, there is no rounding drift. The stored own cost is the reference of the delta, so a batch processed twice adds 0. A bug or an out-of-band write could still make a stage wrong: therefore way 6 exists as project_cost_verify (compares the stored totals with a rebuild, returns the differences) and as the toolbar command, and it is a test in Docker (section 10) after every scenario. Delta correctness was checked in the benchmark itself: after 500 random changes, 0 stages differ from the GiST subtree sums.

6 Design SQL, new PART 27

Post / fact / invoice→register (existing)→monitor01_dirty (existing queue)→ pg_cron 2 s: monitor01_apply→step 1 turnover→step 2 monitor01_view→ step 3 project_cost_apply (new)→project_task_cost_total→Realtime→tree column
toolbar: Update project cost→RPC update_project_cost_total(project)→flush the project's queued tasks (monitor01_apply)→project_cost_rebuild→{ tasks, projectTotal, changedRows, ms }

The table (start1, PART 27)

CREATE TABLE IF NOT EXISTS public.project_task_cost_total (
  "rowOwnerGUID"       UUID          NOT NULL REFERENCES public.project_task_table("rowGUID") ON DELETE CASCADE,  -- the task or the stage
  "rowProjectGUID"     UUID          NOT NULL,
  "rowOwnerUserGUID"   UUID,                                   -- the owner of the project: the fast realtime policy (as monitor01_view)
  "costOwnForBudget"   NUMERIC(18,2) NOT NULL DEFAULT 0,       -- the task's own lines: sum of sumForBudgetPlan of its turnover rows
  "costTotalForBudget" NUMERIC(18,2) NOT NULL DEFAULT 0,       -- own + everything below (what the tree shows)
  "updated_at"         TIMESTAMPTZ   NOT NULL DEFAULT NOW(),
  PRIMARY KEY ("rowOwnerGUID")
);
CREATE INDEX IF NOT EXISTS idx_project_task_cost_total_project ON public.project_task_cost_total ("rowProjectGUID");

Sparse: a row exists only while costOwnForBudget ≠ 0 or costTotalForBudget ≠ 0. The client treats a missing row as "no cost" (empty cell). A tiny queue project_cost_dirty("rowProjectGUID", "queuedAt") (UNLOGGED, like monitor01_dirty) carries the rare "rebuild this project" requests.

The functions and triggers (start2, PART 27)

ObjectWhat it does
project_cost_apply(p_tasks uuid[]) hot pathCalled as step 3 at the end of monitor01_apply. (1) Keeps only the tasks of projects where project_cost_budget_on(rowJSON) is true (master on and one of Time / Material / Expense on). (2) New own cost = sum of sumForBudgetPlan of the turnover of those tasks (the step before wrote it, same transaction). (3) Takes pg_advisory_xact_lock per project (sorted; serializes with a rebuild and with refresh_now, no deadlock). (4) d = newOwn − storedOwn; for the tasks with d ≠ 0: upsert own; then add d to costTotalForBudget of the task and all its ancestors (labels of subpath(treePath,1)), one grouped upsert ON CONFLICT … SET total = total + EXCLUDED.total. (5) Deletes the rows that are 0/0. Only rows whose numbers change are written (no realtime noise).
project_cost_rebuild(p_project uuid)The truth from scratch, by labels (way 6): own cost of every task of the project, totals by one unnest-and-group, upsert the changed rows, delete the rows that are no longer needed. Project switch off → deletes the rows. Returns { tasks, projectTotal, changedRows, ms } (changedRows > 0 on a project that was up to date = a drift was healed).
update_project_cost_total(p_project uuid) RPC, authenticatedThe command of the toolbar (the "updateProjectCostTotal" of the request). Checks pm_owns_project; flushes the queued tasks of this project (the same code as monitor01_refresh_now), then calls project_cost_rebuild. The result is the answer of the button. An error is not swallowed (the screen shows it).
project_cost_verify(p_project uuid)Read only: the stored totals against a rebuild, returns the differing tasks (empty = right). Used by the tests; callable by hand like monitor01_verify.
trigger on project_table (project_cost_budget_on changes its value)On → project_cost_rebuild at once (the turnover is already there). Off → DELETE of the project's rows (no worker work any more). A change of a switch that leaves the rule as it was does nothing.
statement triggers on project_task_table (treePath update = a stage moved; delete; transition tables)One row per project into project_cost_dirty; the worker rebuilds the project once at the end of its tick. A move or a delete changes the ancestors, which a delta cannot know cheaply; both are rare and the rebuild is ~0.1 s. The user's drag stays fast.
RLS · grants · realtimeRLS on, REVOKE ALL from anon, authenticated, GRANT SELECT to authenticated, policy "rowOwnerUserGUID" = app_user_guid(). REPLICA IDENTITY FULL and the table in supabase_realtime (the loop of PART 25 gets one name). The functions are SECURITY DEFINER, no execute for anon.
install backfill (start2)Every project with the budget switch on is rebuilt once (idempotent: a second install changes 0 rows).
delete_sql_structure.sqlOne new numbered part drops the table, the queue, the functions and the triggers (the numbering test is kept happy).

The hot-path statement (the shape that was measured)

-- changed: (task, project, owner, path, d) for the tasks of the batch whose own cost differs from the stored one
UPDATE/INSERT … SELECT replace(lbl, '_', '-')::uuid AS anc, c.project, c.usr, sum(c.d)
  FROM changed c
  CROSS JOIN LATERAL unnest(string_to_array(ltree2text(subpath(c.path, 1)), '.')) AS lbl   -- every label = a stage above, the last = the task itself
 GROUP BY 1, 2, 3
ON CONFLICT ("rowOwnerGUID") DO UPDATE
   SET "costTotalForBudget" = t."costTotalForBudget" + EXCLUDED."costTotalForBudget", "updated_at" = NOW();

7 Edge cases and what the design does

CaseBehaviour
All cost budgets off (master off, or Time + Material + Expense all off)No row, no work (the gate is the first line of project_cost_apply). Turning the last one off deletes the rows; turning one on rebuilds. Old projects (master never saved = off) are not touched by the install.
Task not posted, or changed after postingThe total is the last posted plan (as Monitor01). The posted-status column (green / orange check) already tells which tasks are out of date.
A stage is moved / deleted / a subtree is deletedStatement trigger queues the project → rebuilt at the end of the tick (≤ 2 s). Rows of deleted tasks go with the task (ON DELETE CASCADE).
A stage has cost lines of its ownOwn + below. The formula does not care about rowKind.
Two clients / the worker and refresh_now at onceThe per-project advisory lock serializes the cost step; the dirty queue already takes a task only once (SKIP LOCKED).
pg_cron not enabled (pitfall in KNOW_HOW)Same as Monitor01: nothing moves by itself. The toolbar command works (it flushes the queue itself). Recommended safety net: after a successful Post / Repost the app calls the RPC once (question Q6). It also removes the ≤ 2 s tick from the user's wait: the number appears about 0.1 s after Post.
Realtime silent / a socket was downThe hook refetches on reconnect (the rule of useProjectRealtime) and on the toolbar command.
Project versions, templates, import / exportNot copied (a separate table, derived data). A restored version shows no cost until its tasks are posted; the version view has no cost column.
Revenue budgetOut of scope: the register has cost genera only.
Failure inside the cost stepIt is inside monitor01_apply; the existing retry (a bad task is parked after 5 tries, the others go on) covers it. A cost error must not block Monitor01: if you want it isolated, step 3 gets its own BEGIN … EXCEPTION sub-block (decide at build time; default: isolated and logged in lastError).

10 Tests written in the same round as the code

Docker (tests/80_project_cost.sql, one transaction, rolled back)

  • Gate: master off → no row after a Post; master on with Time only / Material only / Expense only → rows; all three off → rows deleted; one on again → rebuilt; Time on but neither person nor equipment → off (same as the app).
  • Total = Time + Material + Expense lines of one task.
  • Leaf Post → own + totals of every stage above; second leaf; a change to a lower number; a task back to 0 → its row (and the stage rows that become 0/0) disappear.
  • After every scenario: project_cost_verify returns nothing and equals the GiST subtree sums (the check of the benchmark).
  • Stage move and subtree delete → project queued → rebuild gives the new totals; the old ancestors lose, the new ones gain.
  • Used and invoiced documents do not change the plan total; an unposted line is not counted.
  • Two batches over the same stage in one transaction; update_project_cost_total on a queued, never processed task; not your project → refused; RLS: another user reads 0 rows; the install twice changes 0 rows; the undo part leaves nothing.

Q6: update after Post built, debouncedAfter a successful Post of one task (useTaskPost) and after Post unposted / Repost all (useProjectPostActions: one signal for the whole run) the hook useCostRefreshDebounce hands a signal to the scheduler kit8/pm/cost/costRefreshScheduler.ts:
  • Debounce per project: every signal restarts a quiet time of COST_REFRESH_DEBOUNCE_MS = 500 ms; the RPC update_project_cost_total is called once, after the last signal.
  • One at a time: a signal that arrives while the call is running does not start a second one in parallel and is not lost - exactly one more call follows when the running one has finished.
  • Module level, not tied to a component: the Post button or the task page may be closed right after Post. Only while a cost budget is on (a later signal that says "budget off" drops the pending call). Fire and forget: the Post message never waits; an error is only logged (console.warn). The explicit command "Update project cost" cancels the pending call (it does the same work at once).
  • Cost of the debounce: the number appears about 0.5-0.6 s after the last Post (the Post itself is instant), still before the worker's 2 s tick, and it works without pg_cron.
  • What React cannot do: merge the Posts of OTHER browsers or users - each browser has its own timer. The server merges them: one queue row per task, one worker batch per 2 s, the cost step serialized per project by an advisory lock, and a rebuild that finds nothing to change writes nothing (about 0.1 s for 10 000 tasks).
