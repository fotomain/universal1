Google Drive – how it works (result of spike F0)

What the Google Drive API really does for the file attachments plan (documentation/FILE_ATTACHMENT_WBS.html): who may delete, what the narrow scope sees, what a Shared drive changes, what cannot be moved, and the limits. Written 2026-11-11 from Google's own reference pages (section 11).

Status of F0. The 8 questions of F0 were first answered from Google's documentation (sections 1–11). Way C is decided and was run live on 2026-11-11 against a real free Gmail account with only the scope drive.file: 12 of 13 lines PASS, one real finding (a folder cannot be deleted in one call; delete bottom-up) – section 12. The two-account test for way B (f0/f0_drive_spike.sh, section 10) was NOT run and is only needed if way B is ever built.
Three findings change the plan.
  1. Permanent delete in a Shared drive needs the Manager (organizer) role – not Content manager (fileOrganizer), as the plan v2–v5 wrote. A Content manager can only move a file to the trash and reorganize. (section 3, 4)
  2. The narrow scope drive.file does not see files that someone else made – access is per file and comes from the app creating it or the user picking it. So the plan's "app finds the folder of the administrator" works only with the full scope drive, which is restricted; it needs no Google verification only when the OAuth app is Internal to one Workspace domain. (section 2)
  3. A folder cannot be moved from My Drive into a Shared drive (error teamDrivesFolderMoveInNotSupported). "Move the root" between those two must copy file by file. (section 6)

A file lives in a Shared drive or in My Drive, never both. Shortcuts can point across. ownedByMe is not filled for Shared drive files.

2. Scopes and tokens

What the scopes give

ScopeGivesClass
drive.filePer-file access: the files the app created, and the files the user opened with the app (Google Picker). A file shared with the user by somebody else is not visible automatically.recommended, not restricted
drive"View and manage all your Drive files" – also Shared drives; needed for drives.createrestricted
  • Restricted scope and verification. A public app that asks for drive needs Google's verification and a security assessment. An app whose consent screen user type is Internal (only available when the Google Cloud project is owned by a Workspace organization) is used only by accounts of that domain and its restricted scopes need no review; no 100-user test limit, no "unverified app" screen. The Workspace administrator can still block or limit the app.
  • Internal means ONE domain: only the Workspace organization that owns the Google Cloud project can use an Internal app. A product used by many customer organizations (this one has organizations) cannot be Internal for all of them: it needs a public app with the restricted scope (verification + security assessment), or one Google Cloud project per customer. This is the strongest reason for way C (scope drive.file only).
  • Consequence: with drive + Internal, users with a plain Gmail account (or another domain) cannot sign in to the Drive features at all. A My Drive fallback for organizations without Workspace is therefore only possible with the narrow scope + Picker, or with a verified public app.
  • Token. The Google sign-in of Supabase asks for no Drive scope; the Drive token is a second consent (expo-auth-session, like the calendar). An access token lives about one hour; the cleanup worker and the upload queue must ask for it again.

5. Properties on files and folders (S2)

Search (files.list q)properties has { key='kit8Kind' and value='root' }appProperties has { … }

The web, iOS and Android builds of this app use different OAuth client ids, so only properties works across them. A key such as kit8TaskGUID (12 bytes) + a GUID (36) = 48 bytes, well inside the limit. With the narrow scope a search sees only the app's own files; with drive it sees every file the user may see in the drive.

6. Move and copy (S7, S11)

  • Move = files.update with addParents and removeParents (read the old parent with fields=parents). The id and the url of the file stay. Inside one Shared drive: roles fileOrganizer or organizer.
  • My Drive → Shared drive: a folder cannot be moved in (teamDrivesFolderMoveInNotSupported); a file can. Moving items out of a Shared drive needs organizer. Folder moves between two Shared drives: not stated in the reference – the live test checks it (script step 11).
  • Copy = files.copy: costs 50 quota units, counts against the 750 GB per day upload limit of the copier, the copy is owned by the copier (My Drive) or by the drive; maximum size 750 GB.
  • Revisions (S4): files.update with new media makes a revision; revisions.update with keepForever keeps an old one; a permanent delete removes them.

7. Creating a Shared drive and adding members

  • Create: drives.create with a requestId (a random UUID – the same id twice does not make two drives; an existing one gives 409). Scope drive. Not possible with a free @gmail.com account; the user's organizational unit must be allowed to create Shared drives (administrator setting). The creator becomes organizer.
  • Members: permissions.create on the drive id with supportsAllDrives=true; only an organizer adds or removes members. Limits: 600 members in all, 100 groups, 50,000 individuals through groups.
  • Outside the domain: the administrator setting "Allow users outside your organization to access files in shared drives" – unchecked, nobody outside can be a member, and managers cannot add them.
  • Domain administrators can manage any Shared drive with useDomainAdminAccess=true without being members.

12.1 Finding: with drive.file a folder cannot be deleted in one call

Observed. files.delete on kit8root answered 403 appNotAuthorizedToChild: "The user may not have granted the app … write access to all of the children of file …". Three attempts: with the copy of W11 still inside; again with only an empty folder chain left; both 403 (the app could read canDelete: true on every folder). Deleting bottom-up worked: the file (204), then files, t1, task, p1, project, kit8root – every call HTTP 204. Why the one-call delete is refused I could not establish (it may be the check of children that the narrow scope cannot see); the observed rule is enough to design against.
Consequence for the plan: the Edge Function deletes a task / project / organization tree bottom-up (list the children with files.list page by page, delete files, then folders from the deepest) – never one files.delete on the top folder. That is more calls: an organization delete walks the whole tree (S1 health check already lists it). Not tested: whether files.update trashed=true on a whole folder works with drive.file.

What the run settles and what it does not

  • Settled (free Gmail, drive.file only): find by property, nested folders, resumable upload with no token, range reads, trash / restore, replace + keep revision, copy, permanent delete of a file. Way C is possible with no restricted scope.
  • Not settled: the Edge Function itself (2 s CPU, 150 s wall clock with a large streamed download); whether the Google app needs verification before it is "In production" (the Playground used Google's own client id, not this app's three client ids); two-account behaviour (not needed for way C); the Workspace / Shared drive questions of section 10 (way B only); trashing a whole folder.

12.2 Token lifecycle: auto refresh is REQUIRED (in the Edge Function, not in the app)

Observed: the access token of the run had expires_in = 3598 seconds (one hour); the Playground request used access_type=offline and prompt=consent, which is what makes Google issue a refresh token. A way C that stops after an hour would be useless, so the refresh is part of the design:

  1. Connect (once, by the administrator): authorization-code flow with access_type=offline and prompt=consent, scope drive.file only; the redirect goes to the Edge Function, which exchanges the code (needs the client secret) and stores the refresh token encrypted in a table that no client policy can read (or Supabase Vault). The app client never sees any Google token.
  2. Every Drive call: the function asks getAccessToken(organization): a cached access token while it has more than 5 minutes left; otherwise POST https://oauth2.googleapis.com/token with grant_type=refresh_token, the client id and the client secret → a new access token (the refresh token normally stays). One refresh at a time per organization (single-flight), so ten parallel uploads do not make ten refreshes. A Drive answer 401 triggers one forced refresh and one retry.
  3. When the refresh fails with invalid_grant – the administrator revoked the app, the account password / security settings changed, the token was unused for about 6 months, or the Google app is still in "Testing" (refresh token dies after 7 days) – the function sets organizationGoogleDriveState = needsReconnect (and the error text, never the secret). The app shows a banner to the administrator and project managers: Google Drive is disconnected – reconnect; uploads and views say so; the cleanup queue and the phone upload queue simply wait.
  4. Keep-alive: a weekly pg_cron call refreshes every connected organization once, so an unused connection does not expire after 6 months, and the status banner is current.
  5. Secrets: the Google client id and client secret are Edge Function secrets (GOOGLE_DRIVE_CLIENT_ID, GOOGLE_DRIVE_CLIENT_SECRET), never EXPO_PUBLIC_… and never in the app bundle; the Google OAuth client is of type Web with the function url as the authorized redirect.
  6. In the app: nothing to refresh for Drive – the app only holds its Supabase session, which supabase-js already refreshes by itself. The resumable upload session url that the function hands out is the only Google credential a client touches; it is single-purpose and has a limited lifetime (check the exact period when building), so the upload queue (S9) asks for a new session when one is too old.

New data on the organization row: organizationGoogleDriveMode = adminProxy, organizationGoogleDriveState = ok | needsReconnect, organizationGoogleDriveLastRefreshAt, organizationGoogleDriveConnectedByGUID, organizationGoogleDriveAccountEmail. The token itself lives in its own table (planned files_google_connection_table, no client policy). Not built – this is the plan; the test above proved only the access-token half (the run used a one-hour token).
