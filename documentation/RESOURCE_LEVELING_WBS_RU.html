Оптимизация ресурсов (выравнивание и сглаживание) – структура декомпозиции работ (WBS)

Область: оптимизация ресурсов (resource optimization) в смысле PMBOK (методы выравнивание ресурсов – resource leveling и сглаживание ресурсов – resource smoothing), построенная так, чтобы все термины MS Project продолжали работать (Resource > Level, диалог Level Resources, Leveling Delay – пункт A16 файла MORE_GANTT_INPUT.html, «не построено») для диаграммы Ганта в kit8/pm. Источник: Google Doc «W1 Resource Leveling» и ответы владельца от 2026-10-27 (раздел 18). Плановый документ – без кода (проект; построение идёт по нему, см. раздел 19). Редакция 2026-10-27, второй раунд ответов в тот же день. Перевод документа RESOURCE_LEVELING_WBS.html (оригинал – английский; при расхождении верен оригинал).

1. Цель

Ресурс (человек, оборудование, партнёр – в приложении: рабочий центр) может быть записан на день на большее число часов, чем позволяет его календарь. Сегодня приложение только сообщает об этом (проверка занятости при Post, capacityModeWarn / capacityModeBlock) – ничего не двигается. Оптимизация ресурсов сдвигает (задерживает) или разрывает задачи проекта, учитывая приоритет и запас, пока ни один ресурс не будет перегружен – или точно объясняет, почему конфликт устранить нельзя. У неё два метода (PMBOK):

  • Выравнивание (Leveling) – даты могут уходить за пределы запаса; критический путь и окончание проекта могут измениться. = «Level now» в MS Project.
  • Сглаживание (Smoothing) – используется только запас; критический путь и окончание проекта не меняются; конфликт, требующий большего, остаётся и сообщается. = «Level only within available slack» в MS Project.

Владелец проекта выбирает Automatic (план оптимизируется после каждой правки) или Manual (планировщик нажимает Level now и сначала видит предпросмотр). Fast mode добавляет экранные варианты изменения данных прямо на месте (перетащить, ввести часы, исправить один конфликт одним щелчком) в наиболее удобной для пользователя форме.

Жёсткое ограничение: всё выключено, пока resourceLevelingFunctionalityEnabled ни разу не сохранялся. При выключенном ключе планировщик, диаграмма Ганта, Post, проверка занятости и все экраны работают точно как сегодня; новых кнопок, колонок и баннеров нет, сохранённые данные не меняются.

7.2 Модель: спрос, ёмкость, чужая нагрузка

  • Ключ ресурса = вид + GUID (person, equipment, workCenter) – как в resource_occupancy_x_movement. Рабочий центр-партнёр – тоже ресурс.
  • Спрос D[ресурс][день] = сумма по строкам времени (единица «часы») значений часы × коэффициент(день) с коэффициентами calculateTaskLinePlan (распределение по активным дням календаря между началом и концом задачи). Считается из строк: непроведённые строки учитываются. Строки в днях или штуках игнорируются.
  • Ёмкость C[ресурс][день] из SQL (organization_resource_capacity, часы); null = неизвестна.
  • Чужая нагрузка F[ресурс][день] = проведённые часы других проектов организации. Неподвижна.
  • Перегрузка = D + F > C (строго), в периоде resourceGrainUnit (7.9). Неизвестная ёмкость = конфликт, который сдвиг не решает внутри известных дней.
  • Горизонт: последний день, для которого у календаря есть строки (noCapacityInHorizon).

7.3 Алгоритм (идея, без кода)

1. S0 = scheduleProject(план, где все задержки выравнивания сброшены) невыровненный план 2. D = спрос(S0), C, F 7.2 3. для каждого периода t по возрастанию, для каждого ресурса r, где D[r][t] + F[r][t] > C[r][t]: претенденты = задачи, активные в t, использующие r fixed = замороженные / приоритет 1000 / ограничение соблюдается / ручные (если не разрешено) / вне области оставляем задачи (сначала fixed, затем по порядку выравнивания), пока часы помещаются; остальные "уступают" первая уступающая задача X задерживается до первого рабочего дня, где помещаются все её ресурсы (или, если можно разрывать: в t вставляется пауза, и она продолжается, когда у r есть место) предел: общий запас (Метод Smoothing), горизонт если X сдвинуть нельзя: записать нерешённый конфликт с кодом причины 4. Порядок выравнивания: idOnly – уступает задача с большим номером строки; standard – сначала больший общий запас, затем более позднее раннее начало, затем больший номер строки; priorityStandard – сначала меньший приоритет, затем стандартный. Приоритет 1000 не уступает никогда. Детерминированно: один план – один результат.

Заморожено (не двигается, но остаётся нагрузкой): progress > 0, начало раньше сегодняшнего дня, завершённая, проведённый ввод факта (использованные часы), проведённый платёжный факт по её плану платежей, неактивная, веха, этап, исходная задача подпроекта, ограничения Must Start On / Must Finish On или «всегда соблюдать», ручная задача (если не включён resourceLevelingManualTasks), приоритет 1000, задача вне области запуска; а также проведённая задача, если пользователь не выбрал её сдвиг (7.7).

Намеренно не делается: движок никогда не меняет часы, единицы, тип задачи, ресурсы строк или длительность. Он только задерживает или разрывает. (Пользователь может изменить их на месте в Fast mode, 7.6.)

7.7 Проведение и факты – проведённая задача никогда не теряет проведение молча

  • Сдвинутый день начала / окончания снимает проведение строк и платежей этой задачи (существующие триггеры). Поэтому оптимизация никогда не двигает проведённую задачу, не спросив. Когда запуску нужно сдвинуть проведённые задачи, PMResourceLevelingPostedTasksDialog перечисляет их и предлагает три выбора:
    1. Unpost and move – указанные задачи теряют проведение (строки и платежи) и сдвигаются; они остаются непроведёнными до Post (в результате предлагается пункт «Post unposted tasks» из Actions проекта).
    2. Move and post again – задачи сдвигаются и в том же шаге проводятся приложением заново обычным Post (расчёт, проверка занятости). Только если новый план проводится без конфликтов: задача, которую нельзя провести чисто, не сдвигается, и результат говорит почему. Ничего не остаётся недоделанным.
    3. Keep their dates – проведённые задачи не двигаются; они остаются нагрузкой, а вызываемый ими конфликт перечислен как нерешённый с кодом frozenPosted.
  • resourceLevelingPostedTasksAction = ask (по умолчанию) спрашивает каждый раз; unpostAndMove / moveAndPostAgain / keep применяют запомненный ответ (называется в результате). resourceLevelingPostedTasksMovementEnabled = false – то же, что keep.
  • Automatic тоже спрашивает, но не прерывая работу: он двигает только непроведённые задачи, проведённые оставляет на месте, а чип состояния показывает «N posted tasks wait for your decision»; щелчок открывает диалог.
  • Не двигаются никогда, каким бы ни был ответ: начатые задачи, завершённые задачи, задачи с проведённым вводом факта, задачи, у плана платежей которых есть проведённый платёжный факт (план без проведения под проведённым фактом сломал бы Paid / Open плана платежей – проверяется в WP1.3).
  • Undo запуска возвращает даты; вопрос задаётся снова для задач, которые были проведены заново.
  • Сдвиг дат меняет ставку контракта и курс по дням: суммы строк времени могут измениться; пользователь нажимает Recalculate, как после любого изменения дат.
  • При Post проверка занятости остаётся как есть.

7.9 Зерно: resourceGrainUnit = hour по умолчанию (R13)

У опции три значения: hour (по умолчанию), day, week. Она задаёт (а) единицу каждой величины и оси экранов ресурсов и (б) период, в котором нагрузка сравнивается с ёмкостью.

ЗначениеЕдиница на экранеСравниваемый период (v1, сегодняшние данные)
hour (по умолчанию)часы (шаг 0.25), например «11 h on 12 Mar, capacity 8 h»один рабочий день – самый мелкий период плана
dayресурсо-дни (часы ÷ часы ёмкости этого дня)один рабочий день
weekчасы (или дни)сумма недели против недельной ёмкости (более лёгкая проверка, как «week by week» в MS Project)
Ограничение, сказанное открыто. В dayByDayModel (приложение как есть) в плане нет времени суток: календарь ресурса даёт часы за день (нет от / до, нет перерывов), Post пишет строку на линию и день, планировщик считает рабочие дни. Поэтому там значения hour и day находят одни и те же конфликты (различаются единицей на экране). Настоящая почасовая оптимизация – это hourByHourModel (раздел 7.10, фаза 2): владелец решил «да, нужна модель времени суток»; она выбирается настройкой resourceOptimizationMode.

13. Критерии приёмки

  1. Главный выкл.: эталонные планы планировщика побайтово совпадают; нет нового элемента; нет нового запроса.
  2. Двум задачам нужен один человек по 8 ч в один день (ёмкость 8 ч): Leveling задерживает задачу с меньшим приоритетом на один рабочий день; после этого проверка занятости не возвращает строк.
  3. Приоритет 1000 и замороженные задачи не двигаются; конфликт перечислен с причиной.
  4. Метод Smoothing никогда не меняет окончание проекта; остаток нерешён.
  5. Преемники задержанной задачи сдвигаются; критический путь и свёртка этапов пересчитываются планировщиком.
  6. При включённых разрывах длинная задача прерывается вместо сдвига, когда это даёт меньшую задержку окончания.
  7. Manual: до Apply ничего не меняется; Cancel ничего не меняет; Apply = одна транзакция, один шаг Undo.
  8. Automatic: правка, создающая конфликт, оптимизируется после отложения; без цикла; проведённые задачи остаются на месте, а чип говорит, сколько их ждёт решения; Undo возвращает даты.
  9. Проведённая задача никогда не теряет проведение молча: диалог предлагает Unpost and move / Move and post again / Keep; «Move and post again» сдвигает задачу, только если она проводится без конфликтов; при выключенной опции или «Keep» задача заморожена и остаётся нагрузкой. Задача с проведённым вводом факта не двигается никогда.
  10. Clear leveling возвращает невыровненные даты; Undo запуска восстанавливает значения до него.
  11. Проведённая бронь того же рабочего центра в другом проекте соблюдается и не двигается.
  12. День без строки календаря сообщается, поверх него не оптимизируется.
  13. resourceGrainUnit по умолчанию hour; hour / day / week меняют единицу и период как в 7.9; экраны показывают часы. resourceOptimizationMode по умолчанию dayByDayModel, и тогда ничего не меняется.
  14. Планирование от конца проекта: те же кнопки работают; уступающие задачи двигаются раньше; предпросмотр показывает новое начало проекта.
  15. Fast mode: бюджет из 7.6 на 2 000 задач; часы, введённые в ячейке таблицы, пишут строку времени; перетащенный чип меняет ресурс; каждое действие – один шаг Undo.
  16. Все новые тексты есть в 14 словарях; окна арабского и фарси зеркальны без наложений.
  17. Базовая линия Jest: нет новых падающих наборов; скрипты Docker проходят; test_sql.sh по-прежнему проходит.

Никогда молча. Если база не может, расчёт идёт на устройстве, и предпросмотр говорит почему: planNotSupported (с причинами), serverUnavailable (PART 42 не установлена: запустите start2_sql_code.sql), serverError. Выбор никогда не игнорируется без слов.
