Выравнивание ресурсов – структура декомпозиции работ (WBS)

Область: команда MS Project Ресурс > Выровнять (Resource > Level, пункт A16 файла MORE_GANTT_INPUT.html, «не построено») для диаграммы Ганта в kit8/pm. Источник: Google Doc «W1 Resource Leveling». Плановый документ – без кода, в репозитории ничего не менялось. Перевод на русский язык документа RESOURCE_LEVELING_WBS.html (оригинал – английский; при расхождении верен оригинал).

1. Цель

Ресурс (человек, оборудование, партнёр – в приложении: рабочий центр) может быть записан на день на большее число часов, чем позволяет его календарь. Сегодня приложение только сообщает об этом (проверка занятости при Post, capacityModeWarn / capacityModeBlock) – ничего не двигается. Выравнивание ресурсов сдвигает (задерживает) или разрывает задачи проекта, учитывая приоритет и запас времени, пока ни один ресурс не будет перегружен – или точно объясняет, почему конфликт устранить нельзя.

Владелец проекта выбирает в настройках проекта: выравнивание Автоматическое (план выравнивается после каждой правки) или Ручное (планировщик нажимает Level now и сначала видит предпросмотр). Быстрый режим (Fast mode) делает так, что действия пользователя прямо на экране (перетащить полосу, изменить часы, исправить один конфликт) получают ответ мгновенно.

Жёсткое ограничение: всё выключено, пока resourceLevelingFunctionalityEnabled ни разу не сохранялся. При выключенном ключе планировщик, диаграмма Ганта, Post, проверка занятости, экспорт и все экраны работают точно как сегодня; новых кнопок, колонок и баннеров нет, сохранённые данные не меняются.

3. Что есть в приложении сегодня (проверено по коду, 2026-10-26)

ОбластьЧто естьСледствие для выравнивания
ПланировщикНа клиенте, чистый TypeScript: scheduleProject (kit8/pm/view/project/scheduling.ts) = прямой и обратный проход CPM, свёртка этапов, связи с запаздыванием, календари. Опции проекта: model/scheduleOptions.ts. Результат записывается через 800 мс функцией pm_apply_schedule.Выравнивание должно быть входом планировщика (задержка на задачу, как lag), чтобы диаграмма Ганта, критический путь, этапы и версии работали по тем же правилам. Движок может быть чистым TypeScript и тестируемым.
Спрос на ресурсСтрока времени (Time line) задачи имеет ресурс (человек / оборудование / рабочий центр, taskResourceItem), количество в часах и распределение. Post раскладывает часы по рабочим дням задачи (calculateTaskLinePlan) в task_line_plan_movements (строка на линию и день).До Post спрос по дням можно посчитать из строк той же функцией (для выравнивания Post не нужен). После Post проведённые строки других проектов – это чужая нагрузка.
Ёмкость (capacity)Календарь ресурса = часы в день (PART 21, organization_resource_capacity); календари человека / оборудования / рабочего центра / контракта; день без строки календаря «неизвестен», его не угадывают.Единственный источник ёмкости. Выравнивание читает её через RPC; правила календарей не дублируются в TypeScript.
Проверка занятостиPART 22: resource_occupancy_x_movement (абстрактная занятость), organization_resource_busy_check(task, organization), режим организации resourceCapacityStrongMode (capacityModeOff / Warn / Block), окно BusyConflictsWindow. «Равно – не занято».То же определение перегрузки (занято > ёмкость). Выровненный план обязан проходить эту проверку при Post. Проверка остаётся главной.
Поля задачи (Gantt Extended)A15 приоритет taskPriority (0–1000, по умолчанию 500); A12 разрывы taskSplits; A1 ручные задачи; A3 ограничения; A5 крайний срок; A6 тип задачи / работа / единицы; A10 / A11 календари; A14 неактивные; A2 расчёт Manual (F9); запас totalFloatDays / slackDays.Выравнивание читает их, когда функция включена, и игнорирует, когда выключена.
Реакции на сдвиг датыИзменение дня начала / окончания снимает проведение строк и платежей задачи (task_line_plan_unpost_on_dates, task_payment_plan_unpost_on_dates) и переписывает запись в календаре пользователя.Самый опасный побочный эффект. Выравнивание не должно молча снимать проведение: правила заморозки и предпросмотр (7.7).
Само выравниваниеНичего нет. MORE_GANTT_INPUT.html A16: «Missing … nothing is moved».Новая функция.

4. Определения – глоссарий Microsoft Project и что он значит здесь (R2)

Каждый термин функции выравнивания MS Project (диалог Ресурс > Выровнять ресурсы, поля, представления) и его смысл в приложении.

#Термин MS ProjectЗначение в MS ProjectВ приложении
DОсновные термины
D1Resource leveling (выравнивание ресурсов)Задержка или разрыв задач, чтобы ни один ресурс не работал больше своей доступности.Новое движок этого документа.
D2Overallocation / overallocated resource (перегрузка)Ресурсу назначено в периоде больше работы, чем он может сделать (единицы > max units).Соответствует занятые часы дня > часы его календаря в этот день (то же правило, что в проверке занятости; равно – не перегрузка).
D3Max units / resource availability (доступность)% полной занятости, в котором ресурс доступен.Соответствует ёмкость в часах в день календаря ресурса (неполная неделя = меньше часов). Единицы в % нет.
D4Peak units / Peak (пик)Наибольшая нагрузка ресурса в периоде.Новое «Peak hours» на ресурс и на запуск, в виде Resource Load.
D5Assignment / assignment units (назначение)Ресурс на задаче с % его времени.Соответствует строка времени задачи (ресурс + часы). Часы в день = часы × вес дня по распределению. Единицы units из A6 в этой версии выравниванием не используются.
D6Work / remaining work (работа / оставшаяся работа)Часы задачи / ещё не выполненные часы.Соответствует часы строк времени. Оставшаяся работа не строится: начатая задача (progress > 0) заморожена (7.3).
D7Resource calendar (календарь ресурса)Рабочие дни / часы одного ресурса.Есть PART 21 (календари человека, оборудования, рабочего центра, контракта).
D8Resource pool (пул ресурсов)Ресурсы, общие для нескольких проектов.Есть организация: её проекты делят рабочие центры; чужая нагрузка – проведённые брони других проектов.
D9Booking type (предложенный / утверждённый)Предложенный ресурс выравнивание может игнорировать.Соответствует типа брони нет. Свои непроведённые строки считаются всегда; чужая нагрузка = проведённые строки. Не строится как отдельная опция.
FПоля задачи
D10Leveling Delay (задержка выравнивания)Задержка (продолжительность), которую выравнивание поставило перед задачей.Новое taskLevelingDelayDays в рабочих днях календаря задачи; только целые дни (во времени нет времени суток).
D11Leveling Can Split (можно разрывать)Выравнивание может прерывать эту задачу.Новое taskLevelingCanSplit (по умолчанию да); использует разрывы A12 (taskSplits).
D12Priority (0–1000)Важность задачи; 1000 = никогда не выравнивать; низкий приоритет задерживается первым.Есть A15 taskPriority (по умолчанию 500). Новое смысл: 1000 = не выравнивать.
D13Slack (общий / свободный резерв)На сколько задача может сдвинуться, не двигая конец проекта / преемника.Есть totalFloatDays, slackDays (A3).
D14Critical task / critical path (критический путь)Задачи без запаса.Есть. Выравнивание может создать новый критический путь (задержка входит в путь).
D15Constraint (ограничение)Правило даты задачи.Есть A3. Задачи «Must start/finish on» и «всегда соблюдать» задерживать нельзя (сообщается).
D16Manually scheduled task (задача вручную)Задача, даты которой вводит планировщик.Есть A1. Не выравнивается, пока не включён resourceLevelingManualTasks.
D17Split task (разорванная задача)Задача с паузой в работе.Есть A12.
D18Task type / effort driven (тип задачи)Фиксированные единицы / длительность / работа.Есть A6; не используется выравниванием (оно не меняет работу и единицы).
D19Level assignments («Leveling can adjust individual assignments on a task»)Задерживать одно назначение, а не всю задачу.Не строится у строки времени нет собственных дат; двигается вся задача (вопрос Q6).
D20Deadline, baseline, status dateКонтрольная дата / сохранённый план / «сегодня» отчёта.Есть A5, C1, C3. Выравнивание молча не сдвигает задачу за крайний срок: сорванный срок показан в предпросмотре.

D22Look for overallocations on a [minute / hour / day / week / month] basisПериод, в котором нагрузка сравнивается с ёмкостью.Новое resourceLevelingGrain = day (по умолчанию) или week. Час и минута: невозможно – у проведённых дней нет времени суток (как в проверке занятости).

7.2 Модель: спрос, ёмкость, чужая нагрузка

  • Ключ ресурса = вид + GUID (person, equipment, workCenter) – тот же ключ, что в resource_occupancy_x_movement. Рабочий центр-партнёр – тоже ресурс.
  • Спрос D[ресурс][день] = сумма по строкам времени задач проекта (в единице «часы») значений часы × коэффициент(день), где коэффициенты – из calculateTaskLinePlan (распределение по активным дням календаря между началом и концом задачи). Считается из строк, поэтому непроведённые строки учитываются. Строка в днях или штуках игнорируется (как в представлении занятости).
  • Ёмкость C[ресурс][день] из SQL (organization_resource_capacity); null = неизвестна.
  • Чужая нагрузка F[ресурс][день] = проведённые часы других проектов организации (представление занятости без этого проекта). Неподвижна.
  • Перегрузка = D + F > C (строго); при grain week: суммы недели. Неизвестная ёмкость = конфликт, который нельзя решить сдвигом задачи внутри известных дней.
  • Горизонт: последний день, для которого у календаря есть строки (задержка никогда не выходит за него: noCapacityInHorizon).

7.3 Алгоритм выравнивания (идея, без кода)

1. S0 = scheduleProject(план, где все задержки выравнивания сброшены) невыровненный план 2. D = спрос(S0), C, F 7.2 3. для каждого дня t по возрастанию, для каждого ресурса r, где D[r][t] + F[r][t] > C[r][t]: претенденты = задачи, активные в день t, использующие r fixed = замороженные / приоритет 1000 / ограничение соблюдается / ручные (если не разрешено) / вне области оставляем задачи (сначала fixed, затем по порядку выравнивания), пока часы помещаются; остальные "уступают" первая уступающая задача X задерживается до первого рабочего дня, где помещаются все её ресурсы (или, если можно разрывать: в день t вставляется пауза, и она продолжается, когда у r есть место) предел: общий запас (опция «только в пределах запаса»), горизонт если X сдвинуть нельзя: записать нерешённый конфликт с кодом причины 4. S1 = scheduleProject(план с новыми задержками) преемники, этапы, критический путь, окончание следуют 5. повтор с шага 2 только для изменившихся ресурсов и дней, пока не будет новых сдвигов (каждый сдвиг увеличивает задержку или добавляет паузу: цикл конечен; страховочный счётчик останавливает запуск и сообщает об этом) 6. результат = по задачам: задержка, разрывы, причина; по ресурсам: конфликты до / после; окончание проекта до / после

Порядок выравнивания (какая задача конфликта уступает первой): idOnly – задача с большим номером строки; standard – сначала больший общий запас, затем более позднее раннее начало, затем больший номер строки; priorityStandard – сначала меньший приоритет, затем стандартный порядок. Приоритет 1000 не уступает никогда. Детерминированно: один и тот же план даёт один и тот же результат.

Заморожено (не двигается, но остаётся нагрузкой): проведённая задача (если не включён resourceLevelingMovePostedTasks), progress > 0, начало раньше сегодняшнего дня, завершённая, неактивная, веха, этап (суммарная строка), исходная задача подпроекта, задача с ограничением Must Start On / Must Finish On или с «всегда соблюдать» ограничениями, ручная задача (если не включён resourceLevelingManualTasks), приоритет 1000, задача вне области запуска.

Намеренно не делается: движок никогда не меняет часы, единицы, тип задачи, ресурсы строк или длительность. Он только задерживает или разрывает.

7.4 Где живёт результат

  • На задаче (project_task_table.rowJSON): taskLevelingDelayDays (число ≥ 0, отсутствует = 0) и taskLevelingCanSplit (boolean, по умолчанию true; приоритет – существующий taskPriority). Разрывы, сделанные выравниванием, пишутся в существующий taskSplits с пометкой, чтобы «Clear leveling» убирал только их (taskSplitsByLeveling).
  • Планировщик читает задержку как lag: начало = max(начало по связям, ограничения) + задержка в календаре задачи (ручная задача: только когда разрешено). Подпись A2 (calcSignature.ts) включает её, поэтому расчёт Manual видит изменённую задержку как ожидающую правку.

7.7 Проведение и факты

  • Сдвинутая дата снимает проведение строк и платежей этой задачи (существующие триггеры). Поэтому Automatic никогда не двигает проведённую задачу; Manual с resourceLevelingMovePostedTasks перечисляет в предпросмотре задачи, у которых будет снято проведение, и спрашивает.
  • Задачи с проведённым фактом / счётом (в регистре есть строки used / invoiced) заморожены независимо от переключателя.
  • После запуска планировщик нажимает Post unposted tasks (Actions проекта), как после любого изменения дат; предпросмотр и toast об этом говорят. Итоги стоимости и Monitor01 идут обычным путём. Сдвиг меняет ставку и курс по дням (контракты и ставки – по дате): суммы строк времени могут измениться; пользователь нажимает Recalculate, как после любого изменения дат.
  • При Post проверка занятости (capacityModeWarn / Block) остаётся как есть.

Триггер на строках задач отклоняет отрицательную задержку и задержку на этапе, вехе или исходной задаче подпроекта. task_template_clean_task убирает новые ключи.

13. Критерии приёмки

  1. При выключенном главном переключателе прогон Jest планировщика на эталонных планах даёт побайтово одинаковые результаты; ни один новый элемент не отрисовывается; новых запросов нет.
  2. План с двумя задачами, которым нужен один человек по 8 ч в один день (ёмкость 8 ч), выравнивается задержкой задачи с меньшим приоритетом на один рабочий день; после этого проверка занятости не возвращает строк.
  3. Приоритет 1000 и замороженные задачи не двигаются никогда; конфликт перечислен с кодом причины.
  4. «Только в пределах запаса» никогда не меняет конец проекта; остаток нерешён.
  5. Преемники задержанной задачи сдвигаются; критический путь и свёртка этапов пересчитываются планировщиком.
  6. При включённых разрывах длинная задача прерывается вместо сдвига, когда это решает конфликт с меньшей задержкой окончания.
  7. Manual: до Apply ничего не меняется; Cancel ничего не меняет; Apply – одна транзакция и один шаг Undo.
  8. Automatic: правка, создающая конфликт, выравнивается после отложения; без цикла; проведённые задачи не двигаются.
  9. Clear leveling возвращает даты невыровненного плана; Undo запуска восстанавливает значения до этого запуска.
  10. Проведённая бронь того же рабочего центра в другом проекте соблюдается и не двигается.
  11. День без строки календаря сообщается, поверх него не выравнивается.
  12. Fast mode: числа из 7.6 выдержаны на 2 000 задач (бенчмарк).
  13. Экспорт MS Project содержит LevelingDelay, LevelingCanSplit, Priority только при включённой функции; импорт их восстанавливает.
  14. Все новые тексты есть в 14 словарях; окна арабского и фарси зеркальны без наложений.
  15. Базовая линия Jest не показывает новых падающих наборов; скрипты Docker проходят; test_sql.sh по-прежнему проходит (установка дважды, delete ничего не оставляет).
