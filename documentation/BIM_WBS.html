BIM: import an IFC model as a project WBS and show it in 3D

A user imports a BIM model (IFC). The application makes a project with the stages and tasks only (no costs, no lines), keeps the 3D geometry in a compact binary form, and shows a 3D view next to the task tree. A press on a task lights its parts in 3D; a press on a part in 3D scrolls the tree to its task or stage. It must work on web, iOS and Android.

The examples folder is kit8/pm/bim/examples (the request said kit8/kit8/bim/examples: taken as a typo).
Where the build differs from the plan below: (1) the web SQLite runs in a dedicated worker, not a SharedWorker - OPFS synchronous access exists in dedicated workers only; the leader window (Web Lock) owns the worker, other windows use a BroadcastChannel (tested with two browser tabs); (2) the tables have rowProjectGUID on every table, the model has no chunkHash column on storeys; (3) projectIsBIMBased is always switchable by the user (owner 2026-11-20, Project settings -> BIM; no guard trigger; the import sets it too) - this replaces the read-only rule of section 4; (4) the converter server uploads the chunks with the user's own token (the Storage policy decides, no service key on the server) and the app writes the rows through RPCs - the model, tasks and rows are not one SQL transaction: a failure after the tasks were written deletes them again (runBimImport); (5) not built: instancing, normals, meshopt / brotli on the wire, ID-buffer picking, the BIM view of a version; (6) nothing was tried on a real phone and the Supabase mode of the converter was not run against a real Supabase.
Measured on example 1: 4 of 12 storeys hold walls (Elevator Pit 31, L1_35_Low 5, L1_37_Med 5, L1_43_High 17 = 58), 4 stages + 58 tasks, 58 property rows, 4 chunks = 37 088 bytes (IFC 446 971 bytes), model 59.8 x 28.6 x 70.9 m, unit scale 0.3048 applied, worst difference chunk vs IFC 0.45 mm; 10 000 elements save into the local database in about 0.5 s (sql.js); in the browser the 58 walls render, a press on a stage lights its walls and dims the rest, a press on a wall selects its row and shows its properties.

Short answers to the "if it is a good idea" questions (reasons in the sections):
  • Local database name kit8bimdb_<organization GUID>: yes, wiped at sign out. The big binary chunks are FILES next to it, not rows.
  • Separate tables per project: no. One set of bim_ tables with a project column (section 9).
  • Qdrant: not as the store of the model (no row security, no blobs, no joins to the tasks). Yes, later, as an optional semantic search / matching index behind an Edge Function (sections 8 and 12).
  • Web SQLite: official SQLite WASM with OPFS, the opfs-sahpool VFS inside a SharedWorker, because the application opens many browser windows (section 7).

  • "Scroll to a task" already exists: usePMStore.getState().requestFocus(guid) expands the parents, selects the row and scrolls (used by the timeline strip, the deep link, the last task). The 3D view only calls it.

The shared chat (claude.ai/share/9855157f...)

The page shows three answers. Its conclusions, which this plan follows:

  • No native IFC plugin for Expo; web-ifc (WASM) does not run in React Native's native runtime.
  • Parse once on the server (IfcOpenShell geometry iterator, many threads), do not write an IFC parser; dedupe repeated shapes (one mesh + many transforms); compress; properties separate, keyed by GlobalId, plus the spatial tree site > building > storey > element.
  • Chunk by storey, cache by content hash, load the first view fast.
  • Client: merge meshes per material with an element id, few draw calls, frameloop="demand", lazy properties.
  • Mobile: the same r3f scene through expo-gl; lighter geometry, pixel ratio cap 2, no antialiasing / shadows; BVH raycast picking (ID buffer readPixels is slow on native); load by storey; offline cache with expo-file-system + expo-sqlite; bottom sheets, big touch targets, tap-based tools; never parse IFC on the device.
The "Fastest options, in order of impact / Quantized binary buffers + ..." list of the request is not on that page (it ends at the mobile answer). Section 6 builds that list from the same idea (send less, in a GPU-ready format) and adds what the chat did not say: Hermes has no WebAssembly, so meshopt / Draco decode only on web.

3. IFC to project WBS (the minimum data)

Only stages and tasks. No lines, no costs, no resources, no links between tasks.

IFCBecomesRule
IfcProjectthe project (name, projectIsBIMBased)the project GUID is given by the importer (fixed for the two examples)
IfcBuildingStoreya stage, sorted by elevation (lowest first = the order of building)a storey with no element is skipped (Q4); elevation in metres after the unit scale; the stage text = the storey name
an element (IfcWall, slab, column, beam, door, window ...)a task inside its storey stagegranularity auto (Q2): one task per element up to 1 500 elements in the model, else one task per (storey, IFC class, type name) with all its elements; text = element name, else type name + tag
element without storey (site, roof on building)a task in a stage "Building / Site"one extra stage only when needed
IfcSite / IfcBuildingnothingonly the spatial tree of the model; not a row
Property sets, materials, quantitiesnothing (phase 3)"minimum data"
  • Dates (IFC has none unless it carries a work schedule): project start = the day of the import (a value the user can set in the importer); a stage starts when the previous stage finishes; the tasks of a stage run one after the other, one working day each, in the order of the element ids; every row is pinned (manualStartAt) like BUDGET1 / CAKE2 so the result is the same on every run. The user re-plans later - the BIM view does not care about dates.
  • Link element to task: bim_element_table.taskGUID (the truth, one task per element) and a short copy in the task row rowJSON.bimIfcGuid (single element) or rowJSON.bimGroupKey (a grouped task) so a task knows its origin without a join. A stage keeps rowJSON.bimStoreyGuid.
  • The tasks go through the existing project_import_tasks (chunks of 500, no per-row progress recalculation). 58 walls = 58 tasks + the stages of the storeys that hold them.
  • A stage / task copied, templated or versioned loses the bim* keys (task_template_clean_task strips them); the BIM view of a project version is not built.

6. The fastest exchange client / server

Principle of the shared study: send less data, in the format the GPU already uses. The IFC never travels to a device; a device receives only the derived chunks of the storeys it looks at.

7. Local SQLite (web and devices)

Name and content

  • kit8bimdb_<organizationGUID>: a good idea. The app has users with many organizations; one file per organization keeps data apart, a switch of organization opens another file, leaving an organization deletes one file. (The existing sqlite_<userId> database of the undo store stays as it is.)
  • Content: the same bim_ tables as the cloud (storeys, elements, chunks) + bim_cache_state_table (model, revision, chunks present, last opened). It is a read cache: the cloud is the truth; a new revision replaces the rows of the model in one transaction.
  • Chunk binaries are not rows. Native: files in the app document folder bim/<org>/<project>/<hash>.bimc (expo-file-system). Web: OPFS files. The row bim_chunk_table.localPath points to the file. This keeps the database small, VACUUM cheap and lets the OS stream a file into memory.
  • Security: the cache is wiped at sign out and when the user stops being a member of the organization; at every open the app asks the cloud bim_model_manifest (RLS) - a refused answer deletes the cached project. The cache is not encrypted at rest (the OS sandbox / browser origin is the protection): say so in the README.

Web: official SQLite WASM + OPFS

  • Package @sqlite.org/sqlite-wasm, run inside a worker (OPFS synchronous access works only in workers).
  • Two OPFS VFS: opfs (needs the page to be cross-origin isolated: Cross-Origin-Opener-Policy: same-origin + Cross-Origin-Embedder-Policy: require-corp) and opfs-sahpool (no special headers, but one connection at a time).
  • Recommendation: opfs-sahpool inside a SharedWorker. The app opens task windows and routes in new browser windows (openTaskEditWindow, pm80OpenRoute): a plain sahpool database would be locked by the first window. A SharedWorker owns the one connection and every window talks to it through a message port. Fallback where SharedWorker is missing: Web Locks leader election + BroadcastChannel; a second window without the lock reads through the leader.
  • Why not opfs: COEP require-corp blocks every cross-origin resource without CORP / CORS headers (Google sign-in pieces, fonts, images) and the hosting must be able to send the headers; too risky for the whole site. Re-evaluate if the site becomes cross-origin isolated for another reason.
  • Spike A2 proves: Metro bundles the .wasm, the worker script loads on the EAS web hosting, Safari / Firefox / Chrome work.

Phone: expo-sqlite

  • Already installed; openDatabaseAsync('kit8bimdb_<org>') on first use of a BIM project. WAL on, one writer.
  • The two implementations hide behind BimLocalDb (.native.ts / .web.ts, the project's twin file rule; a .web.ts must not import types from its twin - types in bimLocalTypes.ts).
  • expo-sqlite also has a web build; it is not used because the owner asked for the official SQLite WASM + OPFS.

9. Tables (prefix bim_, SQL PART 55)

New tables follow the owner's naming rule: xxx_table / xxx_catalog, camelCase columns like the rest. Tables go to start1_sql_tables.sql; policies, RPCs, triggers to start2_sql_code.sql; the drop to delete_sql_structure.sql.

TableRowsMain columns (minimum)

Separate tables for each project: no

  • Runtime CREATE TABLE per project means DDL by users, one RLS policy set per table, the permission matrix and the PostgREST schema cache changing at run time, a migration that must touch thousands of tables, and tests that cannot name them. The app's rule is the opposite: ONE table, a project column, RLS (perm_projects).
  • Isolation and speed come from indexes: (rowProjectGUID, rowModelGUID), (taskGUID), (rowModelGUID, ifcGuid). 50 000 elements x 1 000 projects = 50 million small rows is normal for Postgres; if it ever hurts, list-partition bim_element_table by organization (a later, invisible change).
  • One thing IS separated per project: the chunk files (folder per project / model), so a project can be deleted and evicted by deleting a folder. On the device: one database per organization, files per project (section 7).
  • Rules: a client only READS the bim tables (SELECT policies); every write is a bim_ RPC (as documents and chat do). A project that is read-only (PART 51) refuses the import and the removal; a deleted project deletes its rows and queues its storage objects. A new table needs a row in permission_matrix.py and in the PART 51 lists.
  • bim_import_commit runs the task import and the bim rows in one transaction: the project is either fully BIM based with all links, or unchanged.

10. The 3D viewer

  • Libraries: three + @react-three/fiber (web) / @react-three/fiber/native + expo-gl (phone): one scene code for all platforms, as the study recommends. A thin platform shell per target (BimCanvas.tsx / BimCanvas.web.tsx). @react-three/drei is not needed (a small own orbit control on react-native-gesture-handler); three-mesh-bvh for picking. All native: a dev build.
  • Why not Skia: the application's Skia is 2D (Gantt); a 3D scene would need another renderer anyway.
  • Scene: one merged mesh per (chunk, material), instanced meshes for repeated types; the position attribute is Uint16 normalized, the chunk's origin + size sit in the object matrix; element index as a vertex attribute; the per-element state texture drives colour / dimming in the shader. Draw calls in the tens.
  • Load order: manifest -> bounding boxes of all storeys drawn at once (cheap) -> chunk of the selected / lowest storey -> the rest by distance. An element of a storey whose chunk is not yet loaded still highlights as its box.
  • Render on demand (frameloop="demand"): a frame only on a gesture, a selection or a chunk arrival. Pixel ratio at most 2; no antialiasing and no shadows on phones; flat shading by derivatives (no normals in the file).
  • Camera: orbit (one finger / left mouse), pan (two fingers / right mouse), pinch / wheel zoom, fit to model, fit to selection; a "reset view" button; Z up of IFC converted to the Y up of three once in the converter.
  • Controls drawn as ordinary buttons of the design system: Fit, Dim the rest, Zoom to selection, Storey filter (later). Touch targets 44 px.
  • Empty / error states in words: no WebGL, chunk missing (retry), model removed.
