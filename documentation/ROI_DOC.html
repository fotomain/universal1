ROI per task and per project

A design proposal - nothing is built. Four kinds of return on investment (plan / fact combinations of costs and revenues), a project-settings tab TabROI that says which taxes count, a switch roiForTasksFunctionalityEnabled (OFF by default) that decides whether ROI is calculated and shown per task, and a new view in Monitor01 with one line per task (when the switch is ON) and project totals in the footer. This page answers: is the idea good, what is missing in the data, and the best way to calculate.

1. Verdict: is it good?

Yes - the idea is sound and fits the system. Three of the four numbers already exist in monitor01_view (plan cost, vendor invoice, customer invoice), the VAT components are already stored, and Monitor01 already has a footer (TotalsRow). Two things must be fixed before it is built.
GAP 1 There is no planned revenue in the register.
PART 25 deliberately lets the Revenue (Deliverable) genus into the report only through posted customer invoices (project_status_register_plan reads the cost genera only; project_status_fresh_turnover keeps a revenue movement only when its kind is sold). So "Revenues Planned" (ROI1, ROI2) has no source until the plan of the Revenue lines is registered - in its own columns, so the Budget / Planned columns of the old report stay as they are (section 5).
GAP 2 "FactRevenues" (ROI2) does not exist.
The only fact of a revenue is the posted customer invoice - and that is exactly ROI3's "Customer invoice data". Today ROI2 and ROI3 would show the same number. A second revenue fact (revenue recognised on delivery, or cash received) needs a document that is not built. Decision Q1.
NOTE ROI4 costs = vendor invoices only.
Time of your own employees is never invoiced: it is a fact input (sumForBudgetUsed). ROI4 as written leaves it out, so ROI4 is too good for a project with much internal work. Decision Q2.
NOTE Plan cost against partial revenue.
ROI2 and ROI3 divide a part of the revenue (what is delivered / invoiced so far) by the whole plan cost. Early in a project they are strongly negative by construction. That is correct as a "so far" number, but the screen must say so (header tip) and it follows the period filter. Section 5.4.

2. Project settings - TabROI

New tab after Customer (kit8/pm/view/project/settings/PMProjectROITab.tsx), also in Organization edit → Projects → Settings (defaults of a new project, like the Product tab). Same pattern as PMProjectCustomerTab: a roiValuesOf() that reads a missing value as the default.

Key (rowJSON)DefaultMeaning
roiForTasksFunctionalityEnabled NEWfalseROI for tasks. OFF: ROI is calculated and shown for the project only (Monitor01 ROI tab: one line per project, no task lines; the per-task calculation does not run). ON: it is also calculated and shown per task. The three tax switches below apply to both levels.
projectROIIncludeAllTaxesfalseMaster switch. ON = both VAT switches below are ON and shown locked (one click for the cash view). OFF = the two switches are free.
projectROIIncludeSaleVATfalseON: the VAT of the customer invoice / planned revenue is added to the revenue. OFF: revenue is net.
projectROIIncludePurchaseVATfalseON: all VAT of the vendor invoice / planned cost is added to the cost. OFF: cost = net + the VAT that is cost (not recoverable) - the IFRS / GAAP cost, same as the default basis of every other report.
The new switch, in short. Name and default follow the other functionality switches (customerInvoiceFunctionalityEnabled, subprojectsFunctionalityEnabled), but the default is false: a missing value is read as OFF - the opposite of the Customer switch. In SQL that is vendor_project_setting_on(project, key) (FALSE unless stored true), not vendor_project_setting (see the pitfall in KNOW_HOW.md section 7). In TypeScript roiValuesOf() reads j?.roiForTasksFunctionalityEnabled === true.
The tab shows the switch first, with the hint "On: Monitor01 → ROI has a line per task. Off: one line per project." The project switch belongs in the Organization defaults too (defaultProjectSettings), so a new project starts as the organization wants. No SQL is needed to store it.
"All taxes" means VAT. The system stores no other tax (no income tax, duty, withholding). The label of the master switch should say "VAT" to avoid a promise the numbers cannot keep: Include all taxes (VAT).
Why OFF by default. Recoverable VAT is a receivable / payable to the tax authority, not a cost and not revenue (IFRS / GAAP, see the VAT basis in kit8/pm/vat/README.md). ROI on the default setting is therefore the accounting ROI. ON is a cash view. Both are legitimate, so the choice is the project's.

These switches belong to the project, not to the user: they replace the global Cost | Net | With VAT choice (VatBasisSelect) inside the ROI view only. Two competing selectors on one screen would give two answers to the same question; the ROI header tip states the basis used.

3. The four ROI kinds

All money is in the budget currency (sumForBudget family), net of VAT before the VAT rules of section 4. C = cost, R = revenue.

What each kind answers

  • ROI1 - is the project worth starting? Available the moment the plan is posted. Changes when the plan is re-posted.
  • ROI2 - given the plan cost, what did the delivered work earn? (needs a revenue fact other than the invoice)
  • ROI3 - what has the customer been billed, against what we plan to spend? Meaningful at the end of the project or with a period filter.
  • ROI4 - what really happened: money invoiced to the customer against money invoiced by vendors. The honest "so far" result.
Do not average the ROI of tasks. The ROI of a project is Σ profit / Σ cost of its tasks, never the mean of the task ROIs (a small task with ROI 400 % would drag a large one). The footer is computed from sums, so it is also correct when the tasks shown are filtered.

4. Taxes - how the two switches change C and R

The register already stores every amount as components: net · VAT · VAT that is cost (vat_basis_amount / amountOfVatBasis). ROI only picks the components; it adds no new VAT logic.

SideIncludePurchaseVAT / IncludeSaleVATAmount used
Cost (plan, vendor invoice)OFF (default)net + VAT that is cost  = basis cost
ONnet + all VAT  = basis gross
Revenue (planned, customer invoice)OFF (default)net
ONnet + VAT (a customer invoice's VAT is never cost, it has no "in cost" part)

The two switches are independent on purpose. Typical case: a company that cannot recover input VAT (non-recoverable → already in the default cost) but is asked "what is the ROI incl. the VAT I invoice" turns on SaleVAT only.

If every VAT rate has the same recoverable share on both sides, switching both on changes C and R by the same factor - the ROI ratio stays, the profit amount grows. The ROI differs only when the rates / recoverable shares differ between purchases and sales. The calculator (section 7) shows both effects.

5. The best way to calculate

The question is where the ratio is computed. Short answer: store additive money in the database, compute the ratio in one pure function.

OptionVerdictWhy
A. Store ROI in monitor01_view (a column per row)NOA ratio is not additive. The table is incremental (the worker rewrites changed rows only), a row is one genus × role × month, and the tree subtotals add rows up: a stored ROI would be wrong in every subtotal and every filter.
B. SQL view / RPC that returns ROI per taskonly as a checkCorrect, but one more round trip, no Realtime, and it ignores the filters of the bar (period, role, unit) that the screen applies.
C. Store the money (additive) + compute the ratio on the client from the rows Monitor01 already holdsYESZero new queries, follows Realtime and the filters for free, the footer is the same code as the task line. The same pattern as monitor01Totals (sums of rows, nothing else).

5.1 What is stored (SQL, additive)

  • Cost plan, vendor invoice, customer invoice: nothing new, the columns exist in monitor01_view.
  • Planned revenue NEW: project_status_register_plan also registers the plan movements of the Revenue lines; project_status_fresh_turnover puts them into new turnover columns sumForBudgetRevenuePlan, vatForBudgetRevenuePlan, and monitor01_view gets sumRevenuePlan, vatRevenuePlan (NET and VAT, like every money pair). They are not written into sumForBudgetPlan: the Budget / Planned / Contracted columns of the old report stay byte-for-byte what they are (decision Q4 of Monitor01 stays true for those columns).
  • Nothing else. No stored ROI, no stored profit.

5.2 The pure function (one place, TypeScript)

// kit8/pm/reports/monitor01/roi/roiModel.ts - pure, no React, no I/O
export interface RoiSettings { includeSaleVat: boolean; includePurchaseVat: boolean }   // from roiValuesOf(project.rowJSON)

const cost = (net: number, vat: number, vatInCost: number, s: RoiSettings) =>
  net + (s.includePurchaseVat ? vat : vatInCost);                    // amountOfVatBasis(..., 'gross' | 'cost')
const revenue = (net: number, vat: number, s: RoiSettings) =>
  net + (s.includeSaleVat ? vat : 0);

/** the ratio. cost = 0 → null (shown "–"): never 0, never Infinity */
export const roiRatio = (r: number, c: number): number | null =>
  c === 0 ? null : (r - c) / c;

export function roiOfRows(rows: Monitor01Row[], s: RoiSettings): RoiLine {
  const sum = (f: (x: Monitor01Row) => number) => rows.reduce((a, x) => a + f(x), 0);
  const planCost  = sum(x => isCostGenus(x.genusGUID) ? cost(x.sumForBudget, x.vatBudget ?? 0, x.vatInCostBudget ?? 0, s) : 0);
  const factCost  = sum(x => cost(x.sumVendorInvoiced, x.vatVendorInvoiced ?? 0, x.vatInCostVendorInvoiced ?? 0, s));
  const planRev   = sum(x => revenue(x.sumRevenuePlan ?? 0, x.vatRevenuePlan ?? 0, s));
  const factRev   = sum(x => revenue(x.sumCustomerInvoiced, x.vatCustomerInvoiced ?? 0, s));
  return {
    planCost, factCost, planRev, factRev,
    roi1: roiRatio(planRev, planCost),
    roi2: null,                                    // Q1 - no second revenue fact yet
    roi3: roiRatio(factRev, planCost),
    roi4: roiRatio(factRev, factCost),
  };
}

The task line is roiOfRows(rows of ONE task); a stage / project line is the same call on the rows of its tasks - never on the ROIs. The footer is the same call on all rows shown.

The switch roiForTasksFunctionalityEnabled gates the task level

// the screen asks for lines; the switch of EACH project decides whether it gets task lines
export function roiLinesOf(rows: Monitor01Row[], settingsOf: (projectGUID: string) => RoiProjectSettings): RoiLine[] {
  const out: RoiLine[] = [];
  for (const [projectGUID, projectRows] of groupBy(rows, r => r.rowProjectGUID)) {
    const s = settingsOf(projectGUID);                        // { includeSaleVat, includePurchaseVat, forTasks }
    if (s.forTasks) {                                         // ON: one line per task - the only place that calculates a task
      for (const [taskGUID, taskRows] of groupBy(projectRows, r => r.rowOwnerGUID)) {
        out.push({ level: 'task', projectGUID, taskGUID, ...roiOfRows(taskRows, s) });
      }
    }
    out.push({ level: 'project', projectGUID, ...roiOfRows(projectRows, s) });   // always: the footer / the one line of a project
  }
  return out;
}

With the switch OFF the code never groups by task, so there is nothing to compute, to render or to drill into. The project level is the same call on the same rows, so turning the switch ON changes only which lines exist - never a project number.

5.4 Rules that keep the numbers right

  1. Sum first, divide last. Round only the displayed percent (1 decimal); the sums keep the cents of the rows.
  2. C = 0 gives "–", not 0 % and not ∞. Profit is still shown.
  3. Units: money has no unit, so ROI adds across hours and pieces without the per-unit split Monitor01 uses for quantities.
  4. Genus: C takes only Time / Material / Expense rows, R only the Revenue rows. A task line therefore needs the rows of all genera of the task - the ROI view ignores the genus tabs (Time / Material / …).
  5. Subprojects: Monitor01 can show a subproject's cost in the origin task (radio Projects / Subprojects / All). The ROI view takes the rows as filtered by that radio, so a footer never counts the same subproject twice; the tip of the header says which radio is on.
  6. Corrections / credit notes are negative movements and sum naturally. A negative R is allowed.
  7. Period: the bar's start / finish dates filter the months of the rows, so ROI3 / ROI4 become "ROI of the period". Plan cost in ROI3 is then the plan cost of the same months.

6. Monitor01 - what is shown

"Show all ROI1-4, per task and per project in the footer" - the task level only for projects that have roiForTasksFunctionalityEnabled ON.

A Monitor01 row is one genus × role × unit × month of a task. A ROI column on that row would be meaningless (a Time row has no revenue). So ROI is a new tab "ROI" (after Deliverable, before All) with a different table: one line per task (project switch ON), project totals in the footer. The existing tabs and columns are unchanged.

Switch ON (below). Switch OFF (default): the same table has no task lines - one line per project, the numbers of the footer; the tab hint says "ROI per task: Project settings → ROI → ROI for tasks". 7. Worked example

One task. Numbers are the base of the example in the table above ("Design"); change them and switch the taxes. VAT amounts are given as a percent of the net.

With the defaults (both OFF): ROI1 50.0 %, ROI3 20.0 %, ROI4 33.3 %. Switch only SaleVAT on: ROI1 80.0 %, ROI3 44.0 %, ROI4 60.0 %. Only PurchaseVAT on (VAT 20 %, 100 % recoverable): ROI1 25.0 %, ROI3 0.0 %, ROI4 11.1 %.
