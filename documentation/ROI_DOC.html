ROI: month totals, Monitor02 (now), Monitor03 (history) BUILT 2026-10-20

Built (SQL PARTs 33 + 34, kit8/pm/reports/roi, monitor02, monitor03; READMEs there). Four kinds of return on investment (ROI1-4); the additive money in project_status_roi_task_month (task × month) and project_status_month_totals (project × month); the report Monitor02_ROINow; the append-only project_status_roi_history behind the project switch roiHistoryFunctionalityEnabled and the report Monitor03_ROIHistory. Monitor01 got a strip (section 7.1). ROI2 uses the fact input of the Revenue lines; ROI4 counts the cost that is never invoiced. Where the built system differs from the first design of this page, the text below says what is built.

1. Verdict

The design holds, and both variants fit together. The month totals are the one source of truth for the project level (now, history, footers); the monitor01 rows stay the source for the task level. Nothing stores a ratio except what a view computes.
GAP 1 No planned revenue in the register.
project_status_register_plan reads the cost genera only, and project_status_fresh_turnover keeps a revenue movement only when its kind is sold (PART 25, decision Q4 of Monitor01). ROI1 / ROI2 need the plan of the Revenue lines - registered into new columns, so Budget / Planned / Contracted of Monitor01 do not change.
RESOLVED ROI2 = plan cost against the fact input of the Revenue lines.
Found in the code: the fact input document already creates lines for all four genera (task_fact_document_create joins revenueGenus), but project_status_register_fact drops them (genusGUID IN (timeGenus, materialGenus, expenseGenus)). So the revenue fact is typed in today and never reaches a report. It is registered as kind used into new revenue columns. ROI2 is then different from ROI3 (customer invoice) - the old Gap 2 is gone.
DECIDED ROI4 cost = vendor invoices + the cost that is never invoiced.
Own staff time is never invoiced (it is a fact input). Rule built: the posted fact input of a cost line that has no vendor (no vendor on its contract / on the line / main vendor of its equipment or product) is "own cost" and is added to the vendor invoices. A cost line with a vendor counts when its invoice is posted (a fact input that waits for its invoice is not in ROI4 yet). Decision Q2.
NOTE Part of the revenue against the whole plan cost.
ROI2 and ROI3 divide a part of the revenue (entered / invoiced so far) by the whole plan cost: early in a project they are strongly negative by construction. The header tip says so; they follow the period filter. Section 6.4.

2. Project settings - tab ROI

New tab ROI after Subprojects (kit8/pm/view/project/settings/PMProjectRoiTab.tsx), also in Organization edit → Projects → Settings (defaults of a new project, defaultProjectSettings). The keys live in project_table.rowJSON; all five default to false - a missing value is OFF. In SQL read them with vendor_project_setting_on(project, key) (FALSE unless stored true), not vendor_project_setting (pitfall, KNOW_HOW section 7); in TypeScript roiValuesOf() tests === true.

Key (rowJSON)DefaultMeaning
roiForTasksFunctionalityEnabledfalseROI per task. ON: Monitor02 shows the project, with a line per task. OFF: the project is not in Monitor02 at all and no task is calculated (roi_task_lines returns no rows). The project ROI itself is the same either way (Monitor03 and the strip of Monitor01 do not depend on this switch). Decided: Monitor02 is for the projects with the switch ON only.
roiHistoryFunctionalityEnabled NEWfalseROI history. ON: the Monitor01 worker writes a snapshot row into project_status_roi_history whenever the project's totals change (section 5.3), and Monitor03 offers the "as seen on" curve. OFF: nothing is written. Turning it OFF keeps the rows already written (they are never deleted by a switch); turning it ON again continues the history, and the gap is drawn dashed.
projectROIIncludeAllTaxesfalseMaster: ON = both VAT switches ON and locked. Label it "Include all taxes (VAT)": the system stores no other tax.
projectROIIncludeSaleVATfalseON: the VAT of the revenue side (planned revenue, fact input, customer invoice) is added to the revenue. OFF: revenue is net.
projectROIIncludePurchaseVATfalseON: all VAT of the cost side (plan, vendor invoice) is added. OFF: cost = net + the VAT that is cost (not recoverable) - the IFRS / GAAP cost, the default of every other report.
The tax switches change only the view of the numbers, never the stored ones. The tables hold net · VAT · VAT that is cost; the switches choose which components are added. Changing a switch therefore redraws the whole history consistently and invalidates nothing.

These switches replace the global Cost | Net | With VAT choice (VatBasisSelect) inside the ROI reports only; their header tips state the basis used.

3. The four ROI kinds

Budget currency (sumForBudget family), VAT rules of section 4. C = cost, R = revenue.

Profit = R − C     ROI = (R − C) / C     (C = 0 → no value, shown "–")
KindCost CRevenue RAnswers
ROI1 plan - planplan cost (Time + Material + Expense)planned revenue NEW columnIs the project worth it on paper? Moves when the plan is re-posted.
ROI2 plan - factplan costfact input of the Revenue lines (posted fact documents, kind used) NEW columnGiven the plan cost, what did the entered (delivered) work earn?
ROI3 plan - invoicedplan costposted customer invoicesWhat has the customer been billed against what we plan to spend?
ROI4 fact - factposted vendor invoices + the cost that is never invoiced (Q2)posted customer invoicesWhat really happened in invoiced money.
Never average the ROI of tasks or months. The ROI of a project (or of a period) is Σ profit / Σ cost - the money is added first, the ratio is taken last. This is also why month totals hold money only.

4. Taxes - which components are added

SideSwitchAmount used
Cost (plan, vendor invoice)IncludePurchaseVAT OFFnet + VAT that is cost (= basis cost)
ONnet + all VAT (= basis gross)
Revenue (planned, fact input, customer invoice)IncludeSaleVAT OFFnet
ONnet + VAT (the VAT of a revenue is never cost: no "in cost" part)
With equal rates and fully recoverable VAT on both sides, switching both ON changes C and R by the same factor: the ROI stays, the profit grows. The ROI differs only when rates or recoverable shares differ. Section 8 shows both effects.

5. Data: what is stored

Rule: store money, never ratios. The tables below hold 15 additive components; the ratios come from roiOfMoney() (app) and roi_ratio() (SQL views), always under the project's current tax switches.

5.1 The register learns the Revenue lines and the "own cost" (SQL PART 33)

  • Plan of the Revenue lines: project_status_register_plan also registers their plan movements. Fact input of the Revenue lines: project_status_register_fact also registers their used movements (before, the filter dropped them).
  • Own cost: a used movement of a cost line carries rowJSON.ownCost = the line has no vendor (pm_line_has_vendor(genus, json): the rule of vendor_invoice_candidates, read from the JSON the fact line copied from its task line - in the default FREE fact mode the fact line has no task line GUID). Set at Post; an unpost + post refreshes it.
  • Monitor01 does not change: project_status_fresh_turnover still keeps a revenue movement only when its kind is sold; the stale flag of monitor01_fresh_rows counts the cost plan only (both definitions). monitor01_view and the turnover got no new column (the first design had four): the ROI money has its own tables.
  • On an existing database the install re-registers the posted fact documents that have no ownCost yet or have Revenue lines, and queues every task with a plan or a movement; the worker (or Refresh) fills the ROI tables.

5.3 project_status_roi_history - the log of what was seen (switch roiHistoryFunctionalityEnabled)

The curve of the month totals shows the past as the data stands today: after a plan re-post the old months change too. The log keeps what the project looked like on each day.

  • Key (project, day): at most one row per project per day (the day's last state wins; the reasons of the day are joined). No pg_cron: a day without a change has no row and the chart draws a step line.
  • Columns: the 15 components (the project's Σ at that moment) + reason (history on · plan · fact input · vendor invoice · customer invoice, found by comparing with the newest row). Components, not percentages: a change of a tax switch redraws the whole log.
  • Written only for projects with the switch ON and only when the totals differ from the project's newest row. Turning the switch ON writes the first row at once (a trigger on project_table); history exists only from that day; switching OFF stops writing and keeps the rows.
  • Project level only. The one table that cannot be rebuilt: start5 never touches it, delete_sql_structure.sql drops it with its data.

Where the ratio is computedVerdictWhy
Stored in a table (monitor01_view, the month totals, the log)NONot additive: wrong in every subtotal, filter and period; depends on the tax switches.

6.1 The function (TypeScript, kit8/pm/reports/roi/roiModel.ts)

/** the 15 additive components; ONE bundle = a project-month, a task, a snapshot, or any SUM of them */
export type RoiMoney = Record<'costPlanNet' | 'costPlanVat' | 'costPlanVatInCost'
  | 'revenuePlanNet' | 'revenuePlanVat' | 'revenueUsedNet' | 'revenueUsedVat'
  | 'costOwnNet' | 'costOwnVat' | 'costOwnVatInCost'
  | 'costInvoicedNet' | 'costInvoicedVat' | 'costInvoicedVatInCost'
  | 'revenueInvoicedNet' | 'revenueInvoicedVat', number>;

const cost = (net, vat, inCost, includeVat) => net + (includeVat ? vat : inCost);
const revenue = (net, vat, includeVat) => net + (includeVat ? vat : 0);

/** cost = 0 → null (shown "-"): never 0, never Infinity */
export const roiRatio = (r: number, c: number) => (c === 0 ? null : (r - c) / c);

export function roiOfMoney(m: RoiMoney, tax: RoiTaxSettings): RoiLine {
  const planCost  = cost(m.costPlanNet, m.costPlanVat, m.costPlanVatInCost, tax.includePurchaseVat);
  const factCost  = cost(m.costInvoicedNet, m.costInvoicedVat, m.costInvoicedVatInCost, tax.includePurchaseVat)
                  + cost(m.costOwnNet, m.costOwnVat, m.costOwnVatInCost, tax.includePurchaseVat);   // vendor invoices + the cost never invoiced
  const planRev   = revenue(m.revenuePlanNet, m.revenuePlanVat, tax.includeSaleVat);
  const usedRev   = revenue(m.revenueUsedNet, m.revenueUsedVat, tax.includeSaleVat);                 // the fact input of the Revenue lines
  const billedRev = revenue(m.revenueInvoicedNet, m.revenueInvoicedVat, tax.includeSaleVat);
  return { /* the five values, */ roi1: roiRatio(planRev, planCost), roi2: roiRatio(usedRev, planCost),
           roi3: roiRatio(billedRev, planCost), roi4: roiRatio(billedRev, factCost) };
}

Every line of every report is roiOfMoney(Σ bundles): a task = its task-month rows for the period, a project = Σ of its month totals, a footer = the sum of the project lines' values (each already under its own project's switches) with the ratios taken of the sums, a history point = one snapshot. The task lines exist only for projects with roiForTasksFunctionalityEnabled; the code never groups by task otherwise.

6.4 Rules that keep the numbers right

  1. Sum first, divide last; round only the displayed percent (1 decimal).
  2. C = 0 gives "–" (grey), not 0 % and not ∞; the profit amount is still shown.
  3. Money has no unit: ROI adds across hours and pieces.
  4. Genus: cost = Time / Material / Expense only, revenue = the Revenue genus only. The ROI reports have no genus tabs.
  5. Subprojects: month totals count a project's own tasks. The task lines of Monitor02 take the rows as the radio of Monitor01 filters them; the header tip names the radio. A footer never adds a subproject twice.
  6. Corrections / credit notes are negative movements and sum naturally; a negative R is allowed.
  7. Period: months in range. ROI2 / ROI3 / ROI4 become "ROI of the period" and the plan cost is the plan cost of the same months.
