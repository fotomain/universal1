ReusableList

One list component for iOS, Android and the web that does everything ReusableTable does (create, edit, delete, search, sort, filter, select, export, folders, menus, Post ...) and stays fast with a very big number of rows.

FIRST SLICE BUILT 2026-11-13 (the owner answered Q5: drag reorder on a phone is needed; both data modes as the parameter reusableListDataMode). Code kit8/ui/components/list/reusable (README there) · demo route /demo/list/reusable (media posts) · no SQL. Built: engine, client + server data modes, FlashList body, drag reorder (grip, ghost, drop line, auto scroll), selection store, bar, row menu, export, 68 Jest tests. Not built yet: folders tree, Post button, column fill, W11 views / RPCs per register, device numbers (W1 / W12). Found while building: (1) a browser cannot scroll a list taller than 33 554 428 px (Chrome) / 17 895 697 px (Firefox): 500 000 rows of 72 px lose their last ~34 000 rows on the web - above ~236 000 rows use serverDataMode; (2) FlashList follows the first visible item when items move above it (maintainVisibleContentPosition): it is switched off, or a dropped item scrolls away under the finger; (3) FlashList v2 renders on react-native-web: 21 items mounted for 10 000 and 100 000 rows (S1 partly answered, Chrome only).

The request (owner, in order)

  1. This document: documentation/ReusableList_WBS.html. No code now.
  2. It must work on devices (iOS, Android) and on the web.
  3. It must have the same functionality as ReusableTable.
  4. It must work with a big list of items.
  5. Use the best plugins, or prove that a custom approach is better - with a table (section 4).
Result in one paragraph. The best engine on the shelf is FlashList v2 (@shopify/flash-list 2.0.2 is already in package.json and not used by any screen). It scores highest of all candidates that run on all three platforms (51 of 60, section 4), and a custom list loses on every point except "no dependency" (35 of 60). The one open cell is the web: FlashList v2 claims react-native-web support and reorder-by-drag on the web has to be proven with @hello-pangea/dnd, so the first work package is a 2 day spike with pass / fail numbers (W1) that decides between FlashList everywhere (expected) and FlashList on devices + a DOM virtual list on the web (fallback). The plan has the same parts in both cases because the engine sits behind one small adapter (section 6).
What "list" means here (change me if wrong): a ReusableTable shows one row as cells in columns; a ReusableList shows one row as one item (a card or a line, chosen by renderItem, or built from the same visualColumns by default). Everything around the rows - data, CRUD, search, sort, filter, selection, menus, export, folders - is the same. A table of 100 000 rows and a list of 100 000 rows read the same data and the same columns.

3. What "big" means, and what it costs

Rendering is only one of five costs. A fast virtual list on top of a slow data layer is still slow.

Targets (to confirm, question Q1)

SizeUseModeMust hold
up to 1 000all today's tablesclientNo visible difference from today; opens in < 150 ms.
10 000big catalogs, movements, partner balance linesclientFirst items in < 300 ms; scroll without blank areas at 55+ fps on the floor device; search / sort / filter answer in < 150 ms.
100 000registers, logsclient (memory test) or serverScroll stays smooth; search / sort in < 500 ms with a progress hint; select all is instant.
200 000 - 500 000the tree demo sizeserver modeOnly the loaded pages are in memory; search / sort / filter run in the database.

Floor device for the numbers: the Samsung SM_A336B (Galaxy A33) the owner already uses for Android runs (KNOW_HOW section 7), plus Chrome on the Mac and the iPhone simulator. A fast Mac says nothing about a phone.

The five costs

#CostTodayPlan
1Rows on screen (mount, layout, memory)All rows are mounted.A virtualized engine mounts only the screen plus a margin and recycles the cells (FlashList) - section 4.
2Cost of one item (a table row has ~10 cells, each a TextInput / picker)Every cell is an editor from the start.An item is display only until tapped (text, no inputs). One heavy editor mounts for one field of one item, never for all.

Above 100 000 rows: server mode.
4Selection and re-renderArray, O(selected x rows); a selection change re-renders every row.Set + "all matching except" flag; each item subscribes to its own selected state (useSyncExternalStore), so one tap re-renders one item.
5Data in memory and on the wireOne page of 1000, array replaced on read; (to check in W2: does an edit copy the whole array in the slice?).Section 6: client up to ~100 000, server pages beyond; realtime patches batched (100 - 250 ms) and applied by rowGUID.

The proof that custom is not better (requested)

A custom list has to match what the winner gives. The question is: what would it cost us to build it, and where could it beat FlashList?

Capability needed by the listFlashList v2Custom virtualizerCustom wins?

Reuse cells while scrollingbuilt in (recycling)write a view pool with its own leak rulesno
Fixed height rows (the table-like case)fasttrivial math, the fastest possibletie: FlatList + getItemLayout already does it, with no new code

The only place a custom approach ties is fixed-height rows, and there the existing FlatList with getItemLayout is the "custom" solution already - no new virtualizer is needed. Conclusion: no custom virtualizer. We write custom code only where no library exists: the shared engine (data, search, selection, menus), the recycling-safe item state and the reorder handles.

Also seen, not scored: virtua (a virtual list for React and React Native) and react-native-big-list - not evaluated in depth; both are cheap extras to try in W1 if FlashList fails on the web.

6. Architecture

Screen passes the same props as a ReusableTable: entityName, listOwnerGUID, visualColumns, foldersTree ... plus renderItem / uxuiList (optional).
ReusableList (bar, summary, folders tree, menus, windows) · the bar is the same component family as the table's bar.
Collection engine (no UI): data source -> rows -> search -> filter -> sort -> view (array of rowGUID + a Map to the row), selection store, drafts store, summary. First it reuses the pure helpers of the table; when the list is proven, it is extracted as useReusableCollection and ReusableTable becomes its second user (W13: a virtualized "big mode" for the table too).
ListBody adapter: { data: rowGUID[], renderItem, itemHeight?, getKey, scrollToIndex, onEndReached, header, footer, empty } → FlashListBody (default) · FlatListBody (fixed height + tests) · DomListBody.web (only if W1 says so).
Data source: redux entity (as today) · local rows · server pages (new, W11) - all give the engine the same { rows, total, loading, loadMore, patch }.

Decisions with reasons

#DecisionReason
D1The list first imports useReusableTableCrud, tableRows, tableFilter, tableExport*, tablePdf, useSearchHistory; the orchestration is written once in the engine hook and copied from nowhere.Zero risk for the live tables now (the 31 baseline test failures stay as they are); the extraction into useReusableCollection happens at W13 with the table's own tests as the net.
D2The list data to the body is an array of rowGUID plus a stable Map<rowGUID, row>; renderItem receives one row, memoized by row object identity.A realtime patch of one row changes one object and re-renders one item. Recycling needs stable keys.
D3No state inside an item that must survive recycling: selection, open editor, draft text, menu open, swipe position live in stores keyed by rowGUID; the item reads them with useSyncExternalStore. FlashList's useRecyclingState only for pure view state (a collapsed block).A recycled cell is the same React component for another row; local state would show on the wrong item (test S4).
D4An item is display only; one editor mounts on tap for one field. Heavy cells (catalog picker, date picker) are never mounted per item.Cost 2 of section 3: a table row with 10 inputs is what makes 1000 rows slow today.
D5The default item is built from visualColumns by a new optional column key listRole: title · subtitle · meta · badge · hidden (default: first text column = title, next 3 = meta, others hidden). renderItem replaces it.Any existing table becomes a list in one prop; a catalog screen can show a list on a phone and a table on a desktop with the same columns.
D6Layouts: line (default, one column), card, grid (numColumns), masonry. Responsive: the layout may differ per width (a phone = line, desktop = grid).FlashList supports columns and masonry; the table cannot do this.
D7The bar, the CRUD panel, the menus, the windows and the folders tree are shared components, not rendered by the body. Only the scrolling items are in the body; header = search / sort chips (sticky), footer = summary.The body re-renders rarely; the bar can use ordinary React state.
D8Realtime patches go through applyPatches(rows, patches) batched every 100 - 250 ms.A burst of 500 realtime rows must not mean 500 renders.

7. Data for a big list

Three sources behind the same engine contract. The first two are today's behavior.

ModeHowGood forCost / limit
client (default)All rows of the scope are read (pages of 1000 until done, with a count first) and held in the redux entity; search / sort / filter in the engine.up to ~100 000 rows (memory test in the bench, W12)First load time; one array in memory. Realtime works as today.
server (new, W11)The list asks for a page (range), a search text, a sort, filters, and a total; PostgREST count (estimated for large tables) gives the number; the engine keeps loaded pages only, onEndReached loads the next. local rowsAs today; the screen holds the array.Settings listsClient mode limits.

If yes the entity keeps an index Map and patches by key. Same check for crudMoment triggering a full selector run in every list.

12. Risks

RiskWhy it mattersAnswer
FlashList on the web is claimed by the docs but not proven hereThe one cell of the score table we did not measure.W1 S1 first; the DOM body is in the plan as fallback.
Drag reorder with a virtual listThe library documents mode="virtual" with react-window; with FlashList on the web it is untested. Needs overscan ≥ 1 and has no window auto-scroll during a drag.S3; reorder also by menu; reorder is off under sort / filter / search anyway.
Recycled cell shows another row's stateA typed text, an open menu or a selection mark appears on the wrong item.D3: no per-row state in the item; test S4 and a regression test.
Reanimated 4.5.1 with react-native-draggable-flatlist 4.0.3The package's peer range is >=2.8.0, but it was published long before Reanimated 4; not checked here.Use it only for lists under 500 rows and only after a smoke test in W9.
Only page 0 (1000 rows) is read todayA "big" list that shows 1000 rows is not big.Section 7: pages until done (client) or server mode; decided by Q1 / Q2.
Export of a big listA PDF of 100 000 rows is not practical (memory, size).JSON / CSV stream from the data in chunks; PDF has a row limit with a clear message (Q8).
Browser find (Ctrl+F) sees only mounted itemsA normal limit of every virtual list.The search box is the answer; say so in the README.
Variable heights and the scrollbar sizeThe scrollbar length is an estimate until items are measured.A itemHeight option for fixed lists; accepted for variable ones.
Refactor of ReusableTable (W13)29 suites already fail at baseline; a new break could hide in them.Done last, after the list is proven; compare the FAIL lines before and after (KNOW_HOW section 5).
Beta / young libraries (LegendList v3)API and bug risk.Not a base; only in the spike if FlashList fails.

13. Not in scope (first version)

  • A custom virtualizer, a Skia list.
  • A generic "any table, any column" server RPC (security and speed; each big register gets its own view or RPC in W11).
  • Hour-by-hour or tree-in-list (a tree is FolderTreeReusable + the list beside it).
  • Offline cache of a big list on the device.
  • Replacing the Gantt tree, Monitor01 or the Monitor07 report tables (they have their own FlatList bodies; they may adopt the adapter later).
  • Translation of the new texts beyond English (the fallback covers the rest).
