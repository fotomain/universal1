Permissions – Work Breakdown Structure

Scope: who may see and change what – organization members, administrators, invitations, RACI on the Time lines, permission profiles, CRUD matrix per table, interface permissions, task versions. Planning document – no implementation yet. Status: 2026-11-02, first version, written from the Google Doc “W1 PERMISSIONS”. Everything marked proposal is my reading and is not confirmed; the questions are in section 13, each with a recommended answer.

Two things to know before reading.

  • The Google Sheet linked in the doc (“Rows: table names, Columns: role names”) was empty when I read it (Sheet1, A1:Z200 returned no values). The matrix in section 9 is therefore my proposal, not your sheet. If you fill the sheet, I will read it again and replace section 9.
  • Today a project is visible only to its owner: the policies of project_table, project_task_table, task_line_table and the documents are built on pm_owns_project() (99 uses in start2_sql_code.sql, 204 policies in all). Giving a second person access to a project is therefore not “one more table” – it is a change of the rule that every PM table is read by (section 10). This is the biggest part of the work and the biggest risk.

1. Goal

One consistent answer to “may this user do this operation (Create / Read / Update / Delete) on this table or screen in this project?”, decided in the database (so the API cannot be used around the screen), shown in the interface (hidden / read only buttons), and driven by three things:

  1. Organization level – who is a member of the organization, who is its administrator.
  2. Project level – the permission profile(s) the user was given in a project (manager, read only, sponsor, curator, investor).
  3. Task level – derived, never typed: a person on a Time line of a task with a RACI item (Responsible …) gives the linked user the rights of a task manager on that one task.

Not in this document: the money rules, the register, the reports – they only get their access rule from here.

2. Answers to the direct questions of the document

“managementRACIGenus – is it good?” No. In this application a genus is a classifier of money / work lines (managementGenusTable: Time · Material · Expense · Revenue · Payments …; managementActivityGenusTable: operating / investing / financing). RACI is not a kind of line – it is the role of a person on a task. A genus table also brings folders, catalog screens and seeds for four values that PMBOK will never change. Recommended: a code enum with the four names you gave, copied into a SQL check, titles through the language files (same technique as the budget item key matrix: one TypeScript constant, one SQL function, a Jest test that compares them). See section 5.

“Show me the list of the tables.” Section 3 (current) and 3.2 (new).

“Make enum or another code.” Section 5.

6. Users, persons, organizations

6.1 Rules from the document

  1. A user is unique by e-mail and may work in many organizations. At the first login one organization is created automatically (as today).
  2. A person is unique by e-mail and independent from organizations; it may exist with no user, and a user may exist with no person. The user can create his person from his profile; the administrator can create it from the card of the user in the users list.
  3. An organization administrator does not take part in projects and tasks (no person is needed); he administrates catalogs, users and permissions.

6.3 Many organizations without rewriting the SQL proposal

Today userTable.rowJSON.userOrganization is read by organization_of_current_user(), project_table.rowParentGUID, the capacity check, RLS of the documents … A user in several organizations needs “the organization I am working in now”. Recommended: keep userOrganization as exactly that – the ACTIVE organization – and add an RPC organization_switch(org) that changes it only to an organization the user is a member of (the trigger that protects the key already exists: kit8.user_organization_change). The member table lists all memberships; nothing that reads userOrganization changes. A “switch organization” item goes in the pinned part of the Drawer; project lists already filter by the organization.

6.4 Administrator rules (database, not only screen)

  • An administrator can mark / unmark any other member as administrator.
  • An administrator cannot delete himself from the table – only another administrator can. The same trigger refuses to unmark himself while he is the last administrator, and refuses any change that leaves the organization with no administrator. Q13
  • Deleting a member row removes the user’s access in that organization only (his projects and documents stay; the owner column is not rewritten) – what happens to the projects he owns is a question: Q9b (recommended: ownership moves to the oldest administrator by an explicit action; the delete is refused while he owns open projects).

6.5 Invitations

  • An administrator presses Invite, types userEmailForInvitation; the e-mail is checked against the member rows of this organization (already invited / member → message). The member row invited is created with invitedAt.
  • organizationInvitationTable + its RPCs (organization_invite_user, _revoke_invitation, _accept_invitation) already do this. Recommended: one mechanism – the member row replaces the invitation row; the RPC names stay (the client code and tests keep working); the old rows are migrated once and the old table is dropped in delete_sql_structure.sql in the same PART.
  • “Via Supabase”: sending a real e-mail is auth.admin.inviteUserByEmail, which needs the service role key – it cannot be called from the app. Phase 1 stays as today: the invited person signs up with the same e-mail and organization_ensure_user finds the pending row. A real invitation e-mail = an Edge Function that you deploy by hand (later, Q15).

6.6 User ↔ person

  • The link is the e-mail (personTable.rowJSON.personEmail = userTable.rowOwnerGUID) – as in PART 36. activeUserState.rowJSON.personGUID is the cached link for the client; the database always recomputes it from the e-mail (no stored foreign key, so it cannot go stale).
  • Change from PART 36: today organization_ensure_user makes a person for every user. With the rules above it makes one only if autoCreatePerson is true (the default). Existing users keep their persons.
  • The person is independent from organizations but his contracts, rates, calendars and variants are organization data – see risk R3 in section 11.

9. Enforcement

9.1 Database (the law)

  1. Project access function pm_can_access_project(project, op) replaces the owner test in the read policies: owner OR member (profile row) OR administrator of the project’s organization (read). The 99 places that call pm_owns_project are split: ownership uses stay (changing the owner, deleting the project); access uses are replaced. Each is listed in the work package so none is forgotten.
  2. RESTRICTIVE policies (CREATE POLICY … AS RESTRICTIVE) per table that the matrix describes: they are AND-ed with the existing policies, so the existing rules stay as the floor and the matrix only narrows or – for the project/task tables, where the floor is replaced in step 1 – applies on top. Added in start2 in the PART of the table; no existing policy is rewritten twice.
  3. RPCs (SECURITY DEFINER, they ignore RLS): every document RPC (post_*, unpost_*, create_*, delete_*, set header / line) begins with perm_require(table, op, project). The list of RPCs is generated by a query on pg_proc and checked by a test, so a new RPC without the call fails the test.
  4. Field/action locks and the “not himself” rule: triggers (7.5).
  5. Realtime: the PM tables are on the realtime publication; Supabase applies the SELECT policy to each change, so the broader read rule also widens who receives events – desired, but the policy must be cheap (R4).

9.2 Interface

  • One hook usePermissions(projectGUID, taskGUID?) reading perm_my_matrix; helpers can('project_task_table','U'), canUi('permissionVendorInvoice','C').
  • Hidden: a tab / menu item the user may not even read. Disabled with a tip: a button he may read but not use (Post, Delete, “+”, Create based on). ReusableTable gets addEnabled / editable / deleteEnabled from the hook (it already has addEnabled and read only modes).
  • The screen never decides alone: when the database refuses, the existing ErrorModalWindow shows the refusal text (SQLSTATE 42501 → “No permission: table, operation”, translated).
  • A “My permissions” window (profile list + the matrix rows that apply) for support: invaluable when a user says “I cannot press Post”.

10. Task versions: task_line_history (“??? TESTIT” in your doc)

  • Project settings → Task tab: taskVersionsFunctionalityEnabled (master, OFF by default like every new master switch) and taskVersionsAutoSave (true by default). Also in the Organization defaults (defaultProjectSettings).
  • A version = one row of task_line_history: rowOwnerGUID = task, rowParentGUID = project, rowJSON { versionNo, savedAt, savedBy, reason (autosave / manual / before post / before restore), task (the task row), lines (all its task_line_table rows) }.
  • When Q17: with auto save on – before a change of a posted task’s lines and at every Post; plus a manual “Save version” in the task menu. Restore = a new version first (“before restore”), then the task and its lines are replaced, the task is unposted (the posting must not stay silent – same principle as resource leveling).
  • Limit: you wrote .env MAX_TASK_VERSIONS NUMBER=30. SQL cannot read .env (the same lesson as the base currency of the rate book). Two parts: the client variable must be EXPO_PUBLIC_MAX_TASK_VERSIONS=30 (Expo exposes only the EXPO_PUBLIC_ prefix) and is only the default of a project setting taskVersionsMax; the SQL trigger prunes the oldest versions above the setting (30 when missing). You edit .env yourself – I give you the line when it is built.
  • Size: 30 versions × the lines of a big task are JSON; capped by the limit and by a max of 500 lines per version (a bigger task is refused with a visible reason, like task templates).
  • Permission: reading versions = R on the task; restore = U with no lock on the changed keys (a locked Responsible cannot restore a name he cannot edit).
  • Tests: Docker (save at post, prune at 31, restore round trip, bulk fill does not create 2000 versions), Jest (settings tab, restore modal).
