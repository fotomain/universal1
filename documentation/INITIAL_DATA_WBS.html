Initial program data

An empty Supabase database has the tables and the functions but no row in any catalog. The application cannot be used then: no budget item, no calendar, no permission matrix. The plan below gives the application its own "Create initial data" function: it finds out what is missing, shows it as a list with check boxes and writes the rows from JSON files that are part of the application.

BUILT 2026-11-26 (the plan of the same day was accepted with the owner's answers to Q2, Q4 and Q5, section 10; what changed while building is in section 12). Source: the Google Doc "W1 Initial Program Data". Code in kit8/initial/data/code, JSON files in kit8/initial/data/json, SQL PART 60, Docker kit8/docker/test_initial_data.sh, Jest __tests__/initial, README kit8/initial/data/README.md, how it works: documentation/INITIAL_DATA_HOW_IT_WORKS.html.

The request (from the Google Doc, in order)

  1. Make this WBS. Check the current state of the data the application needs at least to work, improve the requirements.
  2. The screen is CreateInitialProgramData.tsx. Hamburger menu -> System settings -> Create initial data.
  3. Code in kit8/initial/data/code. The current data is dumped into JSON files in kit8/initial/data/json.
  4. The list the screen shows: "part A of the current chat" (the minimum set found in this chat on 2026-11-23, section 3, tier A) plus cfrTypeTable, the business units table, countryTable, language_catalog, files_document_type_catalog, budgetScenarioTable.
  5. A ReusableTable with a check box near each element. Buttons Close and Create.
  6. It runs at the first application run: if some data does not exist it opens CreateInitialProgramData, locks all other functionality until the process is finished, then opens the home page.
  7. Then INITIAL_DATA_HOW_IT_WORKS.html (after the build).

1. Current state (checked in the code on 2026-11-26)

Read from start1 / start2 / start4 and the TypeScript. Nothing was run against a real database; the Docker proof is work item A0.

Where the data comes from today

Only start4_sql_insert_missing.sql (and its upsert twin start5) puts rows into the catalogs: 7 562 lines, 47 tables, about 9 000 rows (4 104 of them exchange rates, about 2 000 the demo product catalog). The owner pastes it into the Supabase SQL Editor by hand. The application itself has no way to create them and no check that they exist: a new database simply shows empty lists and fails at the first Post.

Who may write the catalogs from the app

The ~57 generic catalogs have write policies that call perm_can(table, letter) (PART 47). With an empty permission matrix the organization administrator still has CRUD (perm_default_set), and a new user is made the administrator of his own organization at the first sign-in (organization_for_email). So the first signed-in user can write most catalogs through the normal client. Not all:

  • language_catalog, managementRACIGenusTable, project_permission_profile_catalog: SELECT only for the client.
  • application_permission_table: no client access at all.
  • managementCalendarDaysTable: made by the function fill_management_calendar, not by hand.

The chicken and the egg

The only application administrator is a row of application_permission_table, and start4 seeds exactly one e-mail (the owner's). In a new database nobody is an application administrator, and the table cannot be written by the app. The request does not say who becomes the first one. See Q2.

The code already depends on the seed ids

By name, in TypeScript: workingDaysCalendar (project default), standardWorkWeekCalendar (capacity fallback), uniformDistribution, unit_hour, raciResponsibleGUID, the genus ids (timeGenus in 18 files), the budget folders costsBudgetFolder ..., the Kanban stage codes, planScenarioProject1. A JSON copy of these rows must therefore keep their rowGUID.

What the folders hold now: kit8/initial/data/code and kit8/initial/data/json exist, both empty. No route, no menu row, no gate.

3. What the request missed (improvements)

  1. The list in the request is not enough to start. Its six extra tables are all tier B; the application-administrator row is in none of them and must be made by a function (Q2).
  2. Three tables cannot be written by the client and one is generated. The screen therefore calls two SECURITY DEFINER functions (section 6) and never writes those tables itself.
  3. Row ids. Currencies, countries and Kanban stages are created without a fixed id (matched by currencyCode / countryCode / stageCode); the code ids (timeGenus, workingDaysCalendar ...) are fixed. A dump of a live database carries whatever ids it has: each table in the model gets a natural key, and an existing row with the same natural key counts as "exists" (never a duplicate).
  4. Never overwrite. Create only INSERTs what is missing. A seed row the user has edited (a renamed budget item) stays as the user left it. (Refreshing to the repository values is start5, a different job.)
  5. "Dump current data" must not dump the user's own work. Business units, budget items, countries and scenarios are also made by users. The dump script lists, per table, the rows that are in the seed files and the rows that are not, and the owner decides (Q3). It also never writes a secret or an e-mail into a JSON file (the admin e-mail of start4 is dropped).
  6. The calendar days are not data to ship. They are generated for last / this / next year at Create time (as start4 does), so the file does not go stale on 1 January. Years after next year are added by the existing calendar screen.
  7. "Check if any data does not exist" needs a definition: per group, the row count AND the required keys (for example workingDaysCalendar exists and has days for the current year). A count alone says "ok" for a database that has one stray row.
  8. Who is locked in? A guest cannot write anything; a plain member cannot write the catalogs. The gate shows each of them a message that says what to do (sign in / ask the administrator) instead of an unusable Create button.
  9. The check runs once per sign-in, not at every start, and costs one RPC call (initial_data_status); the result is kept in memory, so a normal start of a ready database shows no screen.
  10. Safe to stop. Create works group by group in dependency order; a failure stops at that group, keeps what was written, shows the message and the next run continues from there (insert-only, so repeating is harmless).

4. The first run

  1. Where it runs: a component InitialDataGate in the root layout, above the Drawer, after the sign-in is known (a guest sees the sign-in card, then the same check).
  2. The lock: while the required (tier A) groups are incomplete the gate covers the whole window: no Drawer, no FAB, no deep link works. Close is disabled (it only closes the screen when it was opened from the menu, or when nothing required is missing).
  3. The end: when the status says every tier A group is complete the gate unlocks and goes to the home page (/home). Tier B groups the user left unchecked do not block.
  4. The menu row (System settings -> Create initial data) opens the same screen at any time to add what is missing or was deleted (an administrator only). It does not lock anything.

5. The screen CreateInitialProgramData

One ReusableTable in local rows mode (as the Monitor01 fields tab): no Supabase table behind it, the rows come from the model. A check box near each row (the table's own selection column), the groups of section 2 as folders.

Code placement. The expo-router route is a thin file app/system/initialdata.tsx (the router needs it there); everything else is in kit8/initial/data/code. A new screen needs its <Drawer.Screen name="system/initialdata"> in app/_layout.tsx or the menu opens Home (KNOW_HOW section 7) and the menu key drawer.createInitialData in all 15 languages.

6. The JSON files

  • One file per table in kit8/initial/data/json, named with the install order: 10_managementGenusTable.json ... plus manifest.json (order, group, tier, natural key, row counts, sha-256 of each file, dump time and the source: "database" or "start4").
  • File content: { "format": "kit8.initialdata", "version": 1, "table": "...", "naturalKey": [...], "rows": [ { rowGUID, rowOwnerGUID, rowParentGUID, rowFolderGUID, orderInList, rowJSON } ] }. No created_at / updated_at.
  • The files are bundled into the application with a fixed require map (loadInitialJson.ts), so the first run works offline of any server except Supabase. The 4 104-row rates file is required lazily, only when its group is checked (Q5).
  • The dump is dumpInitialData.mjs (Node, in the code folder): reads the owner's Supabase with the key of .env (never printed, never written), writes the files, then prints a report against start4: rows added, rows missing, rows changed. A second mode builds the files from start4 itself, for an owner who has no database to dump yet. Run by the owner in the terminal; I do not run it against the owner's Supabase.
  • A Jest test keeps the files honest: every table is in the model whitelist, counts equal the manifest, hashes match, tier A rows equal the rows of start4 (ids and keys), no e-mail address appears in any file.

7. SQL - PART 60 (planned)

Tables: none (no table is added). Functions go to start2_sql_code.sql PART 60, the drop to delete_sql_structure.sql, a PART 60 banner in start1 only if a table is added later. All SECURITY DEFINER with a fixed search_path, granted to authenticated only.

FunctionWhat it does
initial_data_status()One call, one JSON answer: per group the row count, the required keys that are missing, the days of the calendars, canCreate (the caller may write) and needsAdmin (the bootstrap case). Cheap: counts and key lookups only.
initial_data_install(p_group text, p_rows jsonb)Inserts the rows of ONE whitelisted table, ON CONFLICT DO NOTHING plus the natural-key test; never updates, never deletes. Refuses any table not in the whitelist, any caller who is not an organization administrator or application administrator (or the bootstrap case), and a chunk of more than 1 000 rows. Returns inserted / skipped. It is the only writer of the three read-only tables.
initial_data_fill_calendars()Calls fill_management_calendar for the seeded calendars for last / this / next year when they have no days (the same rule as start4).
initial_data_bootstrap_admin()Makes the caller an application administrator only when application_permission_table is empty (Q2 sets the extra condition). Returns false otherwise. Writes the e-mail of the JWT, never a value sent by the client.
Why one RPC and not the normal table writes? Three tables have no client write path, and one function gives one place for the whitelist, the "insert only" rule and the order. The generic catalogs could also be written through the client, but then the 1 000-row and permission behaviour would differ per table; a single path is easier to test.

12. As built (2026-11-26) - what differs from the plan

  • The gate (InitialDataGate, a Modal over the whole window): nothing exists -> the screen runs by itself, only the progress (a bar, "Step n of m", the table and rows); a part exists -> the list opens, the user presses Create; everything required exists -> nothing is shown. "Nothing exists" = no key of any table of the list, no calendar day, no administrator (isCompletelyEmpty).
  • Required is a smaller set than "everything in the file" (required in initialDataDefinition.json): the genus, the keys, the RACI items, the profiles, the Kanban stages in full; of the budget items the 3 folders, the 6 genus items and the two standard payment items; of the currencies EUR, USD, GBP; calendars workingDaysCalendar and standardWorkWeekCalendar with their days of this year; VAT vat_0; units unit_hour and unit_pcs; uniformDistribution; at least one CRUD and one UXUI row of the matrix. A user who deletes a budget item nobody needs does not bring the first-run screen back at every start.
  • Exchange rates (Q5): group rates = the rate IN FORCE on 31 December of the previous year for USD, EUR, GBP (the base currency excluded). The service publishes working days only: the last published day on or before 31 December (up to 10 days back) is stored as the rate OF 31 December (rowJSON.rateFromDay says where it was read). A currency that has a Default rate on or before the day is not touched. After the data is ready the window ExchangeRatesWindow offers: fill 1 January - today, download currencies_reates_import_template.csv, import a CSV (a preview first; , or ;, 2026-01-02 or 02.01.2026, a line with an empty ratio is skipped, rates that exist stay unless the box is checked).
  • If the rates service cannot be reached the run stops at "rates" with the message, Create again, and Continue without rates (first run only). The next start asks again.
  • If the check itself fails (SQL PART 60 not installed yet, no network) the application is not locked (a warning in the console).
  • The first administrator keeps the default of Q2 above: the first user of an empty database (nobody is an application administrator and the database has at most one registered user), made by the run itself before the groups that only an application administrator may write.
  • Tests on an empty database are NOT in tests/: test_time_genus.sh and test_fact_monitor01.sh run every tests/NNN_*.sql on a database that has start4, which would break them. kit8/docker/test_initial_data.sh does: 53 SQL checks, the JSON installed through the functions, 21 tables equal to the database of start4, a smoke (demo project, task, Time line, Post) on the database made WITHOUT start4.
  • Counts corrected: the permission matrix is 11 + 1 694 + 297 rows (the CRUD and UXUI rows are made by a SELECT in start4, the first count looked only at literal rows); measure units 11.
  • Not done / not seen: nothing was seen in a browser or on a phone; the real Supabase of the owner was not touched (the dump script reads it when the owner runs it: node kit8/initial/data/code/dumpInitialData.mjs; the JSON files in the repository are from start4 in Docker); the removal experiment of A0 (take one group away and see what breaks) was not run: the proof is "the JSON alone is enough for a project and a Post", not "each group is necessary" - the tier of a group comes from reading the code.

11. Install (when it is built)

  1. Run start2_sql_code.sql (PART 60 functions). No tables, so start1 and start4 are not needed. On a NEW database run start1, start2 and start3 (if pg_cron), NOT start4: the application creates the data itself.
  2. Run the dump once if the JSON files are to be refreshed from your database (a command will be given with the build).
  3. Reload the app. On a new database it opens the screen by itself; on a ready database nothing changes except the new menu row.
