5 - Realtime and incremental calculation

5.1 Options compared

5.2 The worker

  1. A posting writes its movements and marks the keys (project, task line, month) dirty (statement-level trigger on the movements, keys only - as monitor01_dirty does with tasks today).
  2. pg_cron (every 2 s, the existing job renamed) takes a batch with FOR UPDATE SKIP LOCKED, re-aggregates, writes only changed rows, logs the lag.
  3. Supabase realtime delivers the changed turnover rows to the open report; the screen patches them by key (as useMonitor01Rows does).
  4. …_refresh_now(project) stays: the Refresh button and an empty first look recompute at once when the cron is not running.

5.3 Posting = rewrite by registrator

Post: DELETE FROM movements WHERE rowRegistratorGUID = X then INSERT … SELECT from the document lines, in the posting transaction. Unpost / delete: the delete only. One rule, the same for every document type, idempotent.

9 - 0333Effect my reading - please confirm, Q1

The doc does not define "0333Effect". The project already has Correct033: the plan algorithm that makes the rounded rows add up to the exact total by putting the cent difference into the last row. I read 0333Effect as the same rule applied to a vendor invoice, where the vendor printed totals and the sum of the rounded lines differs by a few cents.

Rule

  1. Header special sums: T_sum (before VAT) and T_vat. The button "fill based on document" sets them to Σ lines.
  2. Discrepancy: D_sum = T_sum − Σ sumForContract, D_vat = T_vat − Σ vatForContract.
  3. If T = 0 that sum is not corrected (the doc: "if 0 = any special sum, no correction of this sum").
  4. Otherwise D is added to the last line of the document (the last by orderInList, independent of the tab shown).
  5. Safety: if |D| > 0.01 × number of lines (default) the document is refused with a message, not corrected silently: a wrong total must not be hidden in one line.

Example

lineqty × pricesumVAT 21%
11 × 10.0110.012.10
21 × 10.0110.012.10
31 × 10.0110.012.10
Σ30.036.30
vendor prints30.046.31
D+0.01+0.01
line 3 becomes10.022.11

The rule is a pure function written twice (TypeScript for the form's live preview, SQL for the posting trigger) and tested to give the same answer - the way Correct033 and the fact sums already are. Open: which sum is "for accounting" before or after VAT (I take before VAT, VAT separate) and whether the correction is per tab (I take: whole document).
