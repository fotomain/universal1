Part A - the platform (chapter 13)

13.1 Basic concepts

A business process (БизнесПроцесс) joins separate operations into a chain of linked actions that reaches one goal - e.g. "invoice, take cash, release the goods" as the process Sale for cash. It formalizes how events of the organization are handled and brings the performers into the handling. The strongest effect comes from key processes that start and end outside the organization.

  • The chain is drawn as a route map (карта маршрута): the whole life cycle from the start point to the end point as a diagram of linked route points (точки маршрута).
  • Passing along the chain is called the movement of the process.
  • A route point is one stage of the life cycle, normally one automatic or manual operation.
  • A task (Задача) is an assignment to a performer. Tasks show how a process advances over its route points; they can also be created by other objects or by users directly, without any process.

13.2 Objects of the mechanism

Four configuration objects make the mechanism, plus the reference catalogs used as address dimensions:

ObjectRole
Business processesmain object: holds the route map, creates tasks, moves along the route
Tasksmain object: the assignments; completing one pushes its process to the next point
Information register (Адресация)auxiliary: maps performers to roles / departments / ... (see 13.4)
Session parameterauxiliary: the current performer, used to filter "my tasks"
Catalogs (employees, roles, departments)auxiliary: predefined values used as address values in route points
  • Business process and task talk to each other: the process creates tasks, a finished task advances the process.
  • The auxiliary objects do not use each other or the main objects. The route map takes predefined values (roles, departments) from the catalogs; the process reads the register to handle group points; tasks read the register with the session parameter to select tasks of the current performer.

13.3 Kinds of routing

KindMeaning
Rigid (жесткая)strict map without conditions or parallel branches; fixed performers for every point
Free (свободная)performers of a point are not set in the map; they are chosen by code or interactively during the life cycle
Conditional (условная)the map checks conditions and takes a branch; binary (yes / no) or multiple (choice of a variant)
Parallel (параллельная)the process splits into branches that advance independently and may be joined (waited for) later

Real maps usually mix all four.

13.4 Addressing system

The key idea of the mechanism: tasks can be addressed not only to a person but to a role (role routing, ролевая адресация) - a set of rules in the metadata that finds the final performer from his roles, department and other addressing attributes.

Vocabulary

  • Addressing attributes of a task (реквизиты адресации): the dimensions of the address space of the business domain (employee, role, department ...).
  • Main addressing attribute (основной реквизит адресации): the one attribute that means the concrete performer (the employee).
  • Dereferencing (разыменование): finding the main attribute from the other attributes.
  • Addressing register (Адресация): an information register that stores the current match of performers to departments, work groups, functions ... i.e. to all the other attributes.
  • A concrete performer is determined by three task properties: Addressing, Main addressing attribute, Current performer.

Idea in one example

Register rows: Cashier - Ivanov, Manager - Petrov. A process point "Take cash payment" is addressed only to the role Cashier: one task is created (name = point name, role = Cashier, employee = empty). When Ivanov opens his task list he sees it (the register says Ivanov has the role Cashier); Petrov does not.

Setting it up - 13 steps of the manual

  1. Choose a 3-dimensional address system: employee, role, department.
  2. Create a catalog for each dimension (Employees, Roles, Departments) and fill predefined values (e.g. Ivanov / Petrov / Sidorov; Cashier / Manager / Head of department / Storekeeper; Accounting / Sales / Warehouse).
  3. Create the information register with one dimension per catalog, each typed as a reference to that catalog.
  4. Create the session parameter CurrentPerformer typed as a reference to Employees.
  5. Initialise that parameter at system start (look the employee up by the user name; the handler is УстановкаПараметровСеанса).
  6. Create the task.
  7. Put the register into the task property Addressing.
  8. Add the addressing attributes to the task (Employee, Role, Department).
  9. Type each as a reference to its catalog and link it to the matching register dimension.
  10. Make Employee the main addressing attribute.
  11. Create the first business process, set its Task property, draw its route map choosing address values for the points from the predefined catalog data (Fig. 460 of the original shows such a map).
  12. Create the next process pointing at the same task.
  13. Draw its map, and so on.
Rule: a task type is usually created once and shared by all business processes of the configuration.

13.5 Starting a business process

A process starts by the method Start() (Старт) or by the form button "Start and close". A process can be written without being started (e.g. when the start is triggered later by an event). Programmatic pattern: create the object, fill the date, Write(), Start().

13.7 Fork and join

  • Fork point (точка разделения): one input, any number of outputs; the outputs run in parallel and independently.
  • Join point (точка слияния): the process does not go past it until all incoming branches are finished; it is a stage where all tasks of the forked branches must be done.
  • Nesting is allowed: each join synchronizes only the branches of its own fork.
  • A fork without a join is allowed (several parallel branches until the end).
  • A join without a fork is not allowed; the route map check reports that not all lines entering the join came from a fork.

13.8 Manual control

The "finished" flag of a process and the "executed" flag of a task can be set by hand, bypassing the mechanism. Do it only when all the consequences below are understood.

13.8.1 "Finished" flag of a process

  • Setting it makes the process finished even if its tasks are open; completing those tasks later no longer moves the process.
  • It can be set on a not started process: it can then never be started.
  • Clearing it on a finished process does not reopen its tasks: the process is open but has no open task, and it cannot be started again (it counts as started because tasks exist). To really go back, clear the "executed" flag of the right tasks so the process returns to the wanted point.

13.8.2 "Executed" flag of a task

  • Setting it by hand does not advance the process and does not call BeforeExecute / OnExecute of the task or of its route point. The process may stall: not finished, no open task.
  • Clearing it can create a parallel flow: a process with one done and one open task gets two open tasks; each one then moves the process on from its own point; the process finishes when all tasks of both branches are done.
  • Clearing it on a task of an already finished process makes the task show as open in lists, but executing it does not move the process.

13.8.3 Deleting tasks

  • Deleting the open tasks of an unfinished process may stall it (not finished, nothing active).
  • Tasks are used to draw the real route map (passed and active points), so deleting them makes the picture wrong or contradictory.
  • Deleting all tasks of an unfinished process turns it back into "not started".

13.8.4 Adding tasks

  • A task added to a finished process: the process stays finished; executing the task does not move it.
  • A task added to a not started process: the process becomes "started", and executing the task advances it along the map.
  • A task added to a started, unfinished process: the process becomes parallel.
Manual actionResult
Set "finished" on a processstops it; open tasks no longer move it; no handler but BeforeWrite / OnWrite runs
Clear "finished"process open, tasks stay done: stalled unless "executed" is also cleared on a task
Set "executed" on a taskno movement, no handlers

13.9 Conditional transition

A conditional point branches the process by a yes / no result. The handler Condition check (ПроверкаУсловия) is mandatory; the route map check warns if it is missing. The handler sets Result: True goes by the "Yes" branch, otherwise by "No"; the default is False. Typical body: compare two values and set the result accordingly (the original example limits an invoice discount against the usual discount). For many outcomes, a chain of conditional points works but the choice point (13.10) is better.

13.10 Choice of a variant

A choice point (точка выбора варианта) picks one of several paths. The handler Choice of variant (ВыборВарианта) is mandatory; the map check warns when it is missing. The handler must set Result to one of the variants declared in the point (e.g. by payment kind: cash, non-cash, offset, credit; the kind is an attribute of the process). If Result is not set, an error is raised and the transaction in which the choice ran is rolled back.

13.11 Creating tasks

  • Tasks are created only when the process enters an action point or a nested process point. Other points (condition, fork, join, processing ...) run their action and pass on at once.
  • A point can create one or many tasks. Many tasks are made when the point has the flag group (групповая): the process selects all rows of the Addressing register that match the point's attributes and creates one task per row. Example: point addressed to the role Cashier, register has two Cashier rows (Ivanov, Petrov) -> two tasks, each with both role and final performer set. So, for group points the role routing is applied only once, at the moment the list of tasks is built.
#Platform doesYour handler
1begin transaction
2BeforeCreateTasks (ПередСозданиемЗадач)
3build the list of tasks
4OnCreateTasks (ПриСозданииЗадач)
5write all created tasks
6BeforeWrite of each task
7write the task
8OnWrite of each task
9commit
  • Step 2: the handler gets an empty array, so you can fill it yourself and set StandardProcessing = False to skip the standard way.
  • Step 3: if StandardProcessing is still True, the process dereferences the point's addressing attributes and builds one task (or a list, for group points, e.g. all employees of a department).
  • Step 4: tasks are not written yet - tune them here (deadline, priority, extra attributes) or add more tasks.
  • Step 5: if Cancel = True was returned, task creation is interrupted and an exception is thrown - for Start() this cancels the start. Otherwise every task is written (steps 6-8).

Attributes filled automatically: name = name of the route point; reference to the process instance; reference to the route point; addressing attributes copied from the point.

13.12 Execution check

Tasks may be completed by automatic procedures, not only by users (e.g. a task "post the document" is closed when a watcher sees the document posted). The task method CheckExecution() (ПроверитьВыполнение) and its handlers serve this. Typical use: if the check returns True, call ExecuteTask().

#Platform doesYour handler
1handle the call
2ExecutionCheckProcessing of the task (ОбработкаПроверкиВыполнения); if Result = False the method returns False at once
3the same handler of the route point
4return the result of step 3; if True, ExecuteTask() may be called

13.13 Executing nested processes

A route map may start nested business processes. The parent waits until the nested one ends, only then moves to the next point. Entering a "nested business process" point:

#Platform doesYour handler
1begin transaction
2BeforeCreateNestedProcesses
3BeforeCreateTasks of the point
4if StandardProcessing, build the tasks array
5OnCreateTasks
6write the tasks; create the array of nested processes
7OnCreateNestedProcesses
8write and start the nested processes
9commit
  • Step 2: the array of processes arrives empty; adding your own processes cancels the standard generation.
  • Step 3: an empty array of tasks arrives. If standard processing is kept, it is cleared and refilled - one task per started nested process, with name, process reference and route point set.
  • Step 5: tune or add tasks.
  • Step 6: tasks are written, then for each task a nested process of the type set in the point is created, with date and a reference to the leading task (ведущая задача).
  • Step 7: tune, delete or add nested processes; they are written after the handler ends. Their number equals the number of tasks after step 5.

13.14 Finishing a business process

  • The process becomes finished (Finished = True) automatically when it reaches an end point and has no open tasks.
  • A nested process (has a leading task) marks the leading task as executed when it finishes, which moves the parent on.
  • On entering the end point the handler OnFinish (ПриЗавершении) runs. With Cancel = True (e.g. conditions not met) processing stops and the task whose execution led to the end point stays open.
  • Setting Finished = True by code or interactively aborts a process or removes it from the list of active ones. Only BeforeWrite and OnWrite run; the leading task is not executed.

13.16 Business processes with several start points

  • Several start points mean the start point is chosen by conditions outside the process. If the process itself has all the information, use one start point followed by a condition or choice point.
  • With several start points, Start() must get the concrete point, otherwise an error is raised. So: (1) define interactive start commands that pass the right point; (2) if the process is nested in others, write the OnCreateNestedProcesses handler of those points so that it writes and starts every created process from the needed point (loop over the array: write, then start with the chosen point, e.g. a "simplified approval" point).
  • Otherwise they work like ordinary processes.

13.17 Feedback from other objects

Documents, catalog items and other objects can take part in processes and influence them: e.g. posting a document must execute the waiting task automatically (also: setting a discount on an invoice, reserving goods). The mechanism does not need big changes of the applied solution: the reaction is configured without changing those objects much.

The manual's example, for "the task needs a posted document":

  1. The document form notifies of the posting (after write, if it was a posting, send a notification with the document reference).
  2. Register a notification handler at system start (in the managed application module).
  3. The handler calls a server common module method (e.g. WorkWithBusinessProcesses) that queries the tasks of that document (Task.Task.TasksByPerformer, filter by the document attribute), and for each runs CheckExecution() and, if True, ExecuteTask().

Another way: a scheduled job that selects tasks of a performer on a schedule, checks them and executes the ones that pass.

13.18 Route map

The map describes the logic and whole life cycle from start to end as a diagram of linked route points. It is edited in the configurator: tab Other of the process editor -> button Route map. Details are in Chapter 31 "Development tools" of the guide (link in the original; not read here).

Route point kinds met in this chapter: start, action, condition, choice of variant, fork, join, nested process, processing (automatic), end.

13.20 Configuring a task

Part B - 1C:Document Management (an application on the platform)

Source: the "Processes and tasks" article of the 1C:Document Management developer guide (PROF / CORP / DGU, dated 2016-02-20). Part A explains the platform; here is how a big product turns it into something usable. Names of metadata objects are given in English with the original in grey.

B0 Overview and workplaces

The block automates how users cooperate. It offers a set of simple typical processes from which bigger ones are built. Every simple process creates tasks; executing the tasks moves the process along its route map; the process is finished when all its tasks are done.

Simple, one performerone task for one person
Simple, several performerssome of them allow an order of execution: it decides when the task of a given performer is created (steps; performers of one step work in parallel)
Complex (КомплексныйПроцесс)built from simple processes, with a configurable order and conditions, in the "Enterprise" mode
Composite (составной)built from simple processes too, but the order is fixed and cannot be changed by the user. Three exist: handling of internal, incoming and outgoing documents

The simple processes of the product (translated): Execution, Assignment, Familiarization, Invitation, Review, Registration, Agreement, Sign-off, plus "Solving questions of task execution" and the three composite document-handling processes. One task object serves all of them (PerformerTask).

B1 How the processes work

Behaviour of every process is defined by its route map; each route point has handlers with the code. See Part A for the platform side.

Deliberate break of the platform logic - Familiarization tasks. For Invitation, Review, Registration, Agreement and Sign-off the "familiarize with the result" task may be created after the process finished, which the platform logic does not expect. Reason: if the result is positive (e.g. all agreed, no remarks) the author has nothing more to do with the subjects, and when the process is only a step of a complex process, its positive end must not wait for the author - the complex process must go to its next step at once.
  • How it is done: in the handler BeforeCreateTasks of the Familiarization point the standard processing is switched off; when the result is "agreed" and the process is nested in a complex process (the type of the leading task's process says so), the handler just returns. The task is then created in OnFinish of the End point under the opposite condition: agreed + nested in a complex process -> create the task, add a row to the table of familiarization results (with the iteration number), write the process in "simple write" mode.
  • Tip from the guide: to switch the familiarization task off completely during an implementation, comment out the code that creates it.

B2 Complex processes

  • The route map of a complex process only makes it finish when all sub-actions are done. The order in which actions are created lives outside the map.
  • Starting of sub-actions is decided by the procedure StartNewActions (СтартоватьНовыеДействия) in the object module of the complex process. It is called first on entering the route point "Execute all actions of the process", and later each time the leading task of an action is executed (event subscription ComplexProcessTaskOnExecute, ЗадачаКомплексногоПроцессаПриВыполнении).
  • That procedure picks the next actions according to the configured order and routing conditions (B7).
Advice of the guide: do not change the standard behaviour of complex processes - the logic is intricate.

B3 Role routing

  • A performer can be a user or a role. Each role can have several performers.
  • When a process starts for a role, one task is created; all performers of the role see it, any one may execute it.
  • Roles are edited in a dedicated form: Process management - Performer roles.
  • Each role may have up to two addressing objects - an extra cut of data (organization, department ...) so the same role can be used for different organizations. A role task that has addressing objects can be executed only by performers of the role with the same objects. Example: a task for role "Secretary" and organization "Mercury Project LLC" cannot be done by a Secretary of another organization or by one without an object.

B4 Process templates

  • A template is the settings from which a process is started. Almost every process has templates. Workplace: Process management - Process templates.
  • A template can be assigned to several kinds of documents; when a process is created from a document those templates are shown as recommended in the assistant.
  • Templates sit in catalogs Templates<ProcessName>. The same catalogs hold hidden service templates - the settings of the actions inside complex-process templates. So a list may show 1 complex template while a query returns thousands of rows.
  • Filling a process from a template: FillFromTemplate (ЗаполнитьПоШаблону) in the object module; used (1) by the creation assistant, (2) at interactive start, (3) by "fill from template" in the process card. Other fill logic (from a project, a project task) lives in FillingProcessing (ОбработкаЗаполнения). To understand a case, put a breakpoint into FillFromTemplate and read the call stack.
  • Extra method FillFromTemplateAndSubject: unused in the standard configuration, meant for creating processes by code in your own extensions.

B5 Subjects of processes and tasks

The data that people work on, or that is the result of the work, are called subjects (предметы). Any number per process or task. Each subject has a role for the process:

Subject roleBehaviour
Maincannot be deleted in tasks
Auxiliarythe role that every subject added in a task gets; can be deleted in the task card
Fillablecan be cleared in the task card
  • Subjects can be added to a process, a template or a task. In a process any role allowed for that subject type may be chosen (allowed roles are set in code). In a template a subject is only a setting (no concrete object reference).
  • Visibility of subjects in tasks is set in the template and copied to the process: a subject can be visible in the process card but hidden in the task.
  • Adding a subject to a process passes it to the open sub-tasks. In a complex process it is not passed to already started actions; all the other actions start with the new set; visibility can be configured for not started actions.
  • Adding a subject to a task passes it only to its own process and that process's tasks; a process created from a task inherits the task's subjects.
  • Files added from disk are inseparable from the process and its tasks and are never passed to other processes. To pass a file on, first put it into the file storage and add it from there.

B6 Starting processes

  1. General command Main - Create - Process.
  2. From an object or a task: menus Send or Subtasks in lists and cards.
  3. Interactive start: while doing an action in a document card; a special form shows only the processes assigned to the kind of that document.
  4. Fully automatic start on events, with no user (mechanism of business events; rules in register BusinessProcessAutoStartRules).

Ways 1 and 2 use the process creation assistant (common form CreateBusinessProcess); its client entry is OpenMainProcessCreationAssistant in the client common module WorkWithBusinessProcessesClient. The guide points to separate articles "Business processes" and "Auto-start of business processes" for details (not linked from the page; not read).

B7 Routing conditions

When setting the order of actions of a complex process, or the performers of a multi-performer process, one often needs to include or exclude an action or a performer at run time. For that there are routing conditions, set up by the person responsible for processes, in the Enterprise mode.

  • A condition can be built with a constructor (data composition), written as 1C code, or combined from other conditions.
  • Complex process: checked during routing; a failed condition means the sub-process (action) is not created.
  • Simple multi-performer process: checked when the process is created; a failed condition removes that performer.
  • Storage: catalog RoutingConditions; checking: common module WorkWithRoutingConditions.

B8 Background execution

To keep the program responsive there are three background mechanisms, each switched by a constant and served by a scheduled job:

MechanismQueueJobSwitch
Background start of processesregister ProcessesToStartProcessStart; deferred start: StartDeferredProcessesconstant UseBackgroundProcessStart
Background task executionregister TasksToExecuteTaskExecutionconstant UseBackgroundTaskExecution
Background routing of complex processesregister ComplexProcessRoutingQueueBackgroundComplexProcessRoutingconstant UseBackgroundComplexProcessRouting
  • Start: the user creates and writes the process and it is put in the queue; the server job starts it. On success it leaves the queue; on failure the user gets an application notification. Procedures are in common modules ProcessStart<...>.
  • Task execution: same idea; procedures in TaskExecution<...>.
  • Complex routing is different: after each action finishes (task executed) a fictitious task (no performers, never shown) is created for the parent complex process, which stops it, and the action is put in the queue (done in the subscription ComplexProcessTaskOnExecute). The job, for every queue row, finds and starts the next actions, executes the fictitious task (so the complex process can finish if nothing is left), deletes it directly, and removes the queue row.

Troubleshooting (guide's advice)

  • Errors reach the author / performer as application notifications, so they can tell the administrator in time. Causes range from a code bug to a wrongly designed action of a complex process; the message usually says what is wrong.
  • To diagnose: disable the scheduled job, write a data processor that calls the job's procedure, run it in a full-rights user session, investigate in the Configurator.
  • To keep working while investigating: switch the background constants off - new processes and tasks then run in user sessions - and run the job code by hand.
  • Background execution works only in the client-server mode; background task execution may also be used in the file mode when a distributed infobase is used.

B9 Executing tasks by e-mail

  1. The user gets a notification of a new task; it contains special links, one for each result button of the task.
  2. Clicking a link opens a new letter (address filled in); the user writes a comment and sends it.
  3. The program receives the letter, finds the task from its content and executes it.
  • Notifications use the standard notification mechanism; special subject and text (built in WorkWithNotifications, search for TaskExecutionByMailServer).
  • Procedures: common modules TaskExecutionByMail<...>. Replies are processed by job TaskExecutionByMail; each result is logged in register TaskExecutionByMailLog (results in enumeration TaskByMailExecutionResult). Constant: maximum size of attachments in such notifications.
  • To customize: the text is made by FormTaskNotificationTextWithMailExecution in module TaskExecutionByMailServer; the answer variants by functions AnswerVariantsForTaskExecutionByMail in the process object modules.

B10 Processes in a distributed infobase (RIB)

With the exchange plan Full, processes and tasks are exchanged in a special way.

General rules

  • Every process has a master node - the node where it was created and started. Stored in the attribute ExchangeNode (a unique node id, equal to NodeID of the exchange plan).
  • Progress (executing tasks and routing complex processes, which hangs on leading tasks) happens only at the master node. This removes collisions and hung processes when tasks are executed in different nodes.
  • Data is merged by custom logic; the standard collision handling of the platform is switched off.

Limits and side effects

  • The process card can be edited only at the master node.
  • A change of performers is stored only in the node where it was made, and becomes current in all nodes after the task is executed at the master.
  • If a task is executed in two nodes, the result that reaches the master first and gets processed wins.
  • Deleted subjects can come back (a subject can appear again after deletion); for Agreement and Invitation also excluded performers can be restored.

How it works

  • A node id is created on the first write of the node of plan Full. A process gets ExchangeNode on its first write, in the subscription BeforeBusinessProcessWrite.
  • Background start: processed by the jobs ProcessStart and StartDeferredProcesses only at the master; the current node is found by ThisExchangeNodeForProcessHandling in WorkWithBusinessProcesses. Without background start a process starts at once.
  • Tasks are always executed by the background mechanism; jobs TaskExecution and TaskExecutionByMail skip tasks whose process belongs to another node. The same for BusinessProcessRepeat and BackgroundComplexProcessRouting.
  • Receiving data from the main and from a subordinate node is handled the same way (overridden in OnReceiveDataFromMaster / OnReceiveDataFromSlave of plan Full), with a per-process procedure HandleRIBProcessReceive in each process's manager module.
Where the process is receivedRule
Master nodeincoming data is ignored, except that subjects the local process lacks are added (changes are then registered for all known nodes). Otherwise the incoming process is compared with the local one, ignoring attributes with performers (and in some processes the Author); any difference makes the master register its own data for the other nodes. So the master rejects foreign changes and re-publishes its own data.
Other nodeaccepted fully if the process is finished; accepted fully except controller attributes if the iteration changed; otherwise all data except performers and subjects: subjects are merged, performers are kept (in the execution point) or taken, with the execution result, from the object that is at the check point (the existing one is preferred).
Task (any node)the same, but tasks have no iteration and no route points: performers from other nodes are taken only when the task is executed

Execution at a non-master node: the actual result, performer etc. travel through the background mechanism. When the task is put into TasksToExecute, the execution parameters are stored with it (a structure packed into a value storage in the resource Parameters); the master unpacks them in TaskExecutionServer.ExecuteTaskWithParameters, HandleBeforeTaskExecution, HandleAfterTaskExecution (process manager module) and in BeforeWrite of the process object (search for CurrentTask).

Possible problem

Before version 2.0.8 processes in RIB were not tied to nodes. On upgrade, node ids are filled and processes are mapped to the current node by the author: if the author has an infobase user, all his processes go to the current node. If one directory user has infobase users in two or more nodes (an error in itself: one directory user must map to exactly one infobase user), the same processes get tied to two nodes and cannot run. Fix: delete the extra infobase users and update ExchangeNode of the processes in all nodes by your own code; use FillExchangeNodeInProcesses in the common module DocumentManagementInfobaseUpdate as a base.

Advice of the guide: do not change the standard behaviour of process execution in RIB.

  • Rights to the action templates of a complex template follow the top-level template; action templates of a complex process are open to all its current and former participants.
  • Read access to processes and tasks is derived from the register ProcessParticipants (УчастникиПроцессов), which lists all current and past participants.
  • Propagation by hierarchy. A new process (once) gives access to the participants of its parent processes that "influence access to subordinates" (decided by the procedure ProcessParticipantsAffectingAccessToSubordinateObjects of each process manager). On every write, new participants get access to the parent processes. So in a complex process the participants of one sub-process may not see another.
  • Role performers, delegates and managers by hierarchy see processes and tasks only while that right (role, delegation, management) is in force; excluded from the role = access lost.
  • To give access to specific people for all processes of a document kind, department etc., write code that puts those users / roles into the register (via business events or a scheduled job); the same works for giving all participants of a complex process access to all its sub-actions.
