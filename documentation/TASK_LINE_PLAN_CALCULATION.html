Task line plan calculation built

Source: Google Doc "W1 Post Task" (Part 1 task posting, Part 2 Correct033 effect). A task line has totals (qtyTaskLine, sumForBudget, sumForContract) and a distribution (distributionForBudgetTaskLine), but no dates. Post turns every line with a budget item into one row per day in the new table task_line_plan; a new Plan view shows these rows (read-only).

1. Calculate

calculateTaskLinePlan (pure TypeScript): task days × calendar × distribution → a coefficient per day, normalized to baseOfDistribution.

2. Post

One Supabase procedure create_task_line_plan(taskLinePlanJSON), one SQL transaction: replace the rows, multiply, round to 2 digits, run Correct033, verify, set taskIsPosted.

3. Look

PMTaskLinePlanView = a Plan button after Finances on the Gantt toolbar and the route /pm/project/task/plan. All lines of the task in one table, no CRUD.

This page replaces the "Post" part of PROJECT_BUDGET_CALCULATION.html (my first plan, written from the first version of the doc). The role / resource detail tables, calendarForBudgetPlan and the project roll-up are not in the new document, so they are left out here; the first page stays as a later step. Part 2 (Correct033) follows the separate Google Doc "0333 Effect" (see that section).

Part 1.1 - postTask

Budget item column and the posted flag (PMProjectTaskFinancesCRUD)

  • First column budgetItemTaskLine = a catalog column on budgetItemTable (first in taskLineColumns.tsx, before the Errors column). The table is built like managementGenusTable (folders + items, rowOwnerGUID='budgetItemCatalog', rowJSON { title, description, managementGenusItem }); its default rows are made by SQL from the genus rows (one item per genus item), so a new line gets the item of its tab at once and the list per tab is filtered by managementGenusItem.   • The new line keys: budgetItemTaskLine, taskIsPosted, baseOfDistribution (written by the procedure, see below).

Post button in ReusableTable (generic)

  • Prop postDataNeeded, false by default, true for the task-line table. If true: the first button of the toolbar panel (before the CRUD panel), icon always, text only on a wide window (useWindowDimensions, already used in the file).
  • Helper props: postedField (default 'taskIsPosted'), onPost(rows), postButtonColor. The table stays generic; the parent gives the state. Texts (your answer 7): Post on the first edit (never posted) · Posted after a finished post · Post needed when the data changed afterwards. Pressing the button runs onPost in every state.
  • Colour: project.uxuiSettings.postButtonBackgroundColor, light fuchsia by default (#F0ABFC): a new key in PMUxUiSettings, a default in uxuiSettingsOf(), a colour picker in the project UX/UI settings (as taskProgressLineColor).
  • Because the Finances table shows one genus per tab, Post posts the whole task (all tabs), not only the visible tab. The button state counts all lines of the task that have a budget item.

What Post does

  1. Take every line of the task with budgetItemTaskLine not empty. Lines without one are skipped (and counted in the snackbar); if such a line already has plan rows, the procedure deletes them.
  2. For each line: the distribution of the line (distributionForBudgetTaskLine; manual is not used now: such a line is refused with a message; new lines already default to uniform) is applied to sumForBudget, sumForContract, qtyTaskLine over the days taskStartDate → taskFinishDate (schedule[taskGUID].startMs inclusive → finishMs exclusive) that are active in the project calendar.
  3. Call create_task_line_plan(taskLinePlanJSON) once for the task. On success: snackbar "Posted N lines · M days"; the button is on. On any error: nothing is written, the message names the line.

calculateTaskLinePlan (pure, tested)

kit8/pm/view/task/plan/calculateTaskLinePlan.ts - no React, no network. It only prepares the minimum the procedure needs.

calculateTaskLinePlan({
  task:          { startMs, finishMs },            // from the scheduler (finish exclusive)
  lines:         TaskLineRow[],                    // the lines of the task
  calendarDays:  { day: 'YYYY-MM-DD', isActive }[],// calendarForTaskPlan
  distributions: DefRow[],                         // distributionGenericTable
}) => {
  taskLinePlanJSON: { taskGUID, lines: [{ lineGUID, qtyTaskLine, sumForBudget, sumForContract,
                                          baseOfDistribution, days: [{ d: '2026-10-12', c: 0.0833333333 }, …] }] },
  skipped: [{ lineGUID, reason: 'noBudgetItem' }],
  errors:  [{ lineGUID, message }],                // manual distribution, no days, no calendar year, no totals…
}
  1. Periods = the active calendar days from the first to the last day of the task. None → error for every line.
  2. Weights = distributionShares(code, periods.length, params) (already in distributionModel.ts; the shapes stay in TypeScript, one source of truth). The timeline is the active days only: the excluded days are removed and the shape is stretched over what is left (the other reading - the shape on the calendar span, the excluded days zeroed - is in Open points).
  3. Normalize: c_i = round(w_i / Σw, 10); the difference to baseOfDistribution = 1 goes to the last day with a non-zero weight (the same rule as Correct033, in coefficients).
  4. Pass the totals as they are on the line (null stays null; no 0 is invented). The multiplication, rounding and Correct033 are done by SQL, in the transaction, so the stored rows can never be a different calculation than the one that checked them.
  5. A preview of the amounts (same rule, integer cents) is available for the UI/tests; the database is the judge.

Part 2 - Correct033 effect

What the "0333 Effect" document says

  • Cause: each calculated row is rounded independently, so the sum of the rounded parts differs from the total.
  • Example: an invoice of $100.00 on three rows with coefficient 1/3 (33.333…%) each. The exact part is $33.3333…, rounded to 2 decimals $33.33 (the 3rd digit, 3, is below 5, so every row rounds down). Distributed total = 33.33 + 33.33 + 33.33 = $99.99; the lost fractions add up to a visible $0.01 "penny variance" (the document writes the difference as −$0.01, i.e. distributed minus original; below d is original minus distributed, so it is +0.01).
  • Remedy named in the document: accounting systems either add a separate "Rounding Adjustment" line or force the final row to absorb the remainder ($33.34). Part 1 of the task document asks for the second one - the last row inserted into task_line_plan - so that is what is implemented.
  • The document ends by offering a SQL query that balances the discrepancy on the last row; that is the procedure step below.

Splitting 100.00 into three equal days gives 33.33 + 33.33 + 33.33 = 99.99. The SQL algorithm adds the missing 0.01 to the last inserted row so the total is 100.00. The general rule (the 0.01 is the usual case, not a constant):

  1. For a line and a measure m (qtyTaskLine, sumForBudget, sumForContract) with total T (rounded to 2): a_i = round(T × c_i, 2) for every row; the money is handled as numeric / integer cents, never float.
  2. d = T − Σ a_i (the discrepancy; 0.01 for 100.00 over 3 days, -0.03 for 100.00 over 7, 0 when nothing was lost).
  3. d ≠ 0 → a_last = a_last + d, where "last" = the last row of the distribution with a non-zero coefficient (a curve with a zero tail never receives money on a day it was told to skip). Rows are ordered by rowPeriodDatetime.
  4. Safety check: |d| must not exceed n × 0.005 (the largest possible total rounding error); more is a bug → RAISE EXCEPTION, the whole transaction rolls back.
  5. The same for rowCoefficient against baseOfDistribution, to 10 digits (3 days: 0.3333333333 ×3 = 0.9999999999 → the last is 0.3333333334).
  6. Null total → null in every row, no correction. Total 0 → zeros.

Why not a "Rounding Adjustment" line. An extra row would have no day (rowPeriodDatetime) and would break "one row per active day", the view and the per-day reports. The last day absorbs the remainder instead, as in the document's $33.34.
Know the side effect. "Everything on the last row" is exact but the last day absorbs the whole error; over a long task it can drift by several cents (random-walk of the roundings) - the 7-day example already moves 3 cents. The alternative (largest remainder: give the missing cents one by one to the rows with the biggest rounding loss) keeps every row within ±0.01. I follow the document (last row); the largest-remainder mode is not built.

The SQL procedure create_task_line_plan(taskLinePlanJSON)

Supabase RPC (plpgsql, SECURITY INVOKER, so RLS and pm_owns_project apply). One call = one transaction: any error rolls back everything, the table never holds half a post.

  1. Lock the task row (FOR UPDATE) so two Post presses cannot interleave; check pm_owns_project.
  2. Validate the JSON: every lineGUID is a line of this task; days strictly ascending; coefficients ≥ 0 and Σ within 1e-6 of 1; at least one day.
  3. Delete the old rows of the task's lines that are in the JSON and of lines of the task that are not (their budget item was cleared).
  4. Insert one row per line and day (generate_series / jsonb_array_elements … WITH ORDINALITY, one set-based INSERT): rowProjectGUID and rowOwnerGUID from the task, rowParentGUID = the line, the three amounts = round(T × c, 2).
  5. Correct033 per line and measure (previous section), also on rowCoefficient.
  6. Verify: Σ rows = T for each measure and Σ rowCoefficient = baseOfDistribution → else exception.
  7. Mark: task_line_table.rowJSON = rowJSON || { taskIsPosted: true, baseOfDistribution } for the posted lines (a merge, so no other key is lost).
  8. Return { lines, rows }.

Staleness: a trigger on project_task_table sets taskIsPosted:false on the lines of a task when its start / finish day changes (the scheduler rewrites them), so Post turns off after a re-plan. A calendar edit does not unpost anything in this version.
