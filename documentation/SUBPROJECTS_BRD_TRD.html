Subprojects built 2026-10-16 BRD + TRD

A project can be used as a subproject of a task of another project. The task (the origin task) takes its start and finish from the subproject and follows it automatically, and - when the owner switches it on - Monitor01 shows the Time, Material and Expense plan / fact of the subproject on the origin task too. The subproject is a normal project: nothing new is stored for its data, so the Gantt, Finances, Fact input, vendor documents and Monitor01 work in it unchanged. Everything is OFF by default, so no existing project changes.

What is new

  • 6 project switches (tab TabSubprojects): the master, autoChangeOriginTaskBasedOnSubprojects and its four children (dates, Time, Material, Expense)
  • 2 task fields: taskIsSubproject, taskSubprojectGUID
  • 1 table project_subproject_link, 0 new columns
  • 24 new SQL functions, 7 triggers; 4 older functions got one line each; monitor01_fresh_rows is replaced
  • Monitor01: aggregation of the subproject into the origin task + radio Projects | Subprojects | All

The rules

  1. No recursion: A in B in A is refused when chosen and cannot be posted.
  2. One project may be the subproject of many tasks, in any projects.
  3. Subproject dates change = origin task dates change (autoChangeStartAndFinishDatesForOriginTask), through several levels.
  4. The child switches are shown only while the switch above them is on.
  5. Aggregation (aggregateTime / Material / Expence...) is per genus and OFF by default.
  6. The Monitor01 radio appears only if a project of the organization has the functionality on.

Status

SQL PART 29 is tested on Postgres 15 (tests/90_subprojects.sql, 80 checks, plus the whole install / delete / re-install and all older SQL tests). The screens are tested with Jest. Not seen in a real browser and not run on the owner's Supabase. Section 12 lists the decisions and what is not built.

2 The user scenario (from the Google Doc)

  1. The project manager enters tasks as today.
  2. In Project settings - Subprojects he switches subprojectsFunctionalityEnabled on (false by default). Only then the switch autoChangeOriginTaskBasedOnSubprojects (true by default) is shown, and only while that is on its four children: autoChangeStartAndFinishDatesForOriginTask (true), aggregateTimeFromSubprojectToTheOriginTask, aggregateMaterialFromSubprojectToTheOriginTask, aggregateExpenceFromSubprojectToTheOriginTask (false).
  3. On a task he sets the flag taskIsSubproject. With the flag on he picks the project from a list: rowJSON.taskSubprojectGUID. A recursive definition is refused with an error.
  4. The origin task now has the start and finish of the subproject. The manager works in the subproject as in any project; when its start or end moves, the origin task moves.
  5. In Monitor01 the origin task shows the Time / Material / Expense of its subproject for every aggregate switch that is on; he can show projects, subprojects, or all (the radio appears only when the functionality is in use in the organization). By default only projects are shown, so each plan is seen once: on the origin task.
Project A (origin)→Task T1 taskIsSubproject→ taskSubprojectGUID →Project B (subproject, a normal project)
B: start / finish changes→ subproject_propagate_dates →T1: startAt / finish = B→A is re-scheduled (successors of T1 move)
Far away (the Doc, "for coding of this document"): subprojects will carry all CRM processes as Gantt tree tasks. Nothing is built for it now; the design only has to not block it. It does not: a CRM process is an ordinary project used as a subproject (BR-10).

7.1 Date algorithm, step by step (subproject_sync_origin_task)

  1. S = the subproject of the task (from project_subproject_link); O = the origin project.
  2. (start, finish) = subproject_dates_of(S). If either is NULL: stop (S was never scheduled).
  3. Write linkStartAt, linkFinishAt, linkSyncedAt when they differ.
  4. If subproject_dates_on(O) is false (the functionality, the follow switch or the dates switch is off): stop - the origin task keeps its own dates.
  5. days = GREATEST(1, subproject_work_days(start, finish, O.skipWeekends)) - the calendar of the ORIGIN project, because its CPM turns days into a finish.
  6. If manualStartAt, durationDays, startAt, rowDuration of the task already equal the new values: stop (return false).
  7. UPDATE the task. The existing trigger trg_task_line_plan_unpost_on_dates unposts the lines of that task if a DAY changed (see edge cases).
  8. The caller (subproject_propagate_dates) now looks at the project of the origin task: its dates changed, so the origin tasks that point at O follow in the same transaction. The open dashboard of O re-runs CPM from the new manualStartAt / durationDays and writes back; that write calls the propagation again and corrects anything the CPM changed (successors of the origin task).

7.2 Aggregation, step by step (monitor01_fresh_rows)

  1. For the tasks to apply (a batch of the worker) take subproject_agg_sources: for an origin task O with link to S, every task of S for every genus G with subproject_aggregate_on(O.project, G); then, for each such task that is itself an origin task X (link to S2), every task of S2 for G if subproject_aggregate_on(X.project, G); repeat.
  2. Read the register turnover once for all the tasks involved (project_status_fresh_turnover).
  3. Own rows: (task, every genus). Aggregated rows: (O, G) from the sources. Sum by (O, genus, role, unit, month); the stale flag is the "or" of the plan lines.
  4. Name, project and user of the row are those of O. monitor01_apply then upserts changed rows only and deletes the rows that are gone (a switch turned off removes the aggregated rows).

9 Edge cases

  • Self reference (A in A): refused by the CHECK of the table and by subproject_creates_cycle.
  • Indirect cycle (A→B→C→A): refused at the moment the last task is linked; the message names the chain (tested: "Project B -> Project A -> Project B").
  • Cycle from a restore / import: a version restore or an import writes rowJSON too, so the trigger fires there. A cycle that still got in is stopped at Post (subproject_assert_no_cycle); the propagation has a depth limit and the aggregation uses UNION.
  • Subproject never scheduled: its dates are NULL; the origin task keeps its own dates.
  • Zero length: durationDays is at least 1; the origin task is never turned into a milestone.
  • Different calendars (origin skips weekends, sub does not): the start / finish are copied; durationDays is counted in the origin calendar (tested: 18 calendar days = 14 working days).
  • The CPM clamps: the client CPM never starts a task before the start of its own project, and a predecessor can push the origin task later than the subproject. Then the bar of the origin task differs from the subproject until the predecessor is changed; the database copies the subproject dates anyway and the CPM write-back corrects them. The warning is built: the tree row and the Gantt bar show it (section 8).
  • Posted lines of the origin task: a changed day unposts them (the existing rule); the Post button shows.
  • Permissions: the propagation and the aggregation are SECURITY DEFINER, so an origin task in a project of another user of the organization is updated although the editor of the subproject cannot edit it. The picker and the link table follow the visibility rule of project_table.
  • Double counting: the default Monitor01 view (Projects) hides the subproject, so the aggregated numbers are seen once. Choosing "All" shows both the subproject and the aggregate on the origin task - that is by design, and the owner chooses it.
  • Many origins, one subproject: each link is its own row; each origin task aggregates the same subproject separately.
  • Templates and versions: NOT handled yet: "create template from project" copies the two task keys as plain JSON. A template used in another project could then point at a real project; the trigger checks it when the task is written (the project must be visible and no cycle), but a copy does not clear the keys.
  • Performance: every lookup is by an index on project_subproject_link; with no link the added work of monitor01_apply and monitor01_fresh_rows is one empty index probe. The task triggers fire only for rows that have one of the two task keys. The Monitor01 bench was not re-run.
