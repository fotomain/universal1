3 - Data flow

task_line_plan_movements+ task_line_contract_movements+ task_line_fact_movements
↓ statement-level triggers: only write the task key
monitor01_dirty (one row per task)
↓ pg_cron every 2 s · procedure · batches of 500 tasks · SKIP LOCKED
monitor01_view (rewrites only rows whose numbers changed)→monitor01_refresh_log
↓ Supabase Realtime (postgres_changes, filter by project)
hook useMonitor01Rows → patch by key → Monitor01Dashboard→ click a sum →SumExplorerListReusable → source tables
Why a queue and not a trigger that updates the view directly: a Post inserts hundreds of movement rows in one transaction and the Time-genus check writes them twice (planMovementStatus false, then true). A direct trigger would re-aggregate for every statement inside the user's transaction and make Post slower. The trigger only writes a task key (one cheap insert, duplicates ignored); the heavy work is done outside the user's transaction, once per task and tick.

Latency budget: commit → ≤ 2 s until the next tick → ~50-300 ms batch → ~100 ms realtime → screen. Target: under 3 s end to end, under 2.5 s on a quiet system.

6 - The worker (pg_cron, every 2 seconds)

"Incremental, in batches" of the doc = only the tasks that changed, 500 at a time, only the rows whose numbers changed.

  1. Fast exit: if monitor01_dirty is empty, return (no snapshot of the big tables, a fraction of a millisecond). Most ticks end here.
  2. Claim: take up to 500 queue rows, oldest first, with FOR UPDATE SKIP LOCKED and delete them in the same statement. Two workers (a slow tick plus the next one) never take the same task.
  3. Aggregate once: one set-based statement reads the three sources for the claimed tasks only (indexes on task), joins the lines for genus / role / unit and the project for names and owner, groups by the five key columns and the month.
  4. Apply the difference: upsert the fresh rows only where a number or a name differs (IS DISTINCT FROM), delete the rows of the claimed tasks that no longer have a source. Unchanged rows are not touched, so they produce no WAL and no realtime event.
  5. Commit per batch: a procedure (not a function) commits after every batch and loops while the queue is not empty and less than ~1.5 s has passed, so one tick never overlaps the next and a big import drains in several ticks.
  6. Log: one row in monitor01_refresh_log if anything was done.

Correctness details

  • Race: a change committed while the worker runs queues its key again after the worker's commit; the next tick reads it. A key can be processed twice, never lost.
  • Failure: a failing batch rolls back (the keys return to the queue), attempts grows, after 5 the task is parked and the log shows it; the rest of the queue continues.
  • Safety net: monitor01_verify(sample) (daily, and on demand) recomputes a sample of tasks, compares with the view and queues the differences - it covers anything that bypassed the triggers (TRUNCATE, bulk import with triggers off). monitor01_rebuild queues all tasks of a project or of everything.
  • Install on an existing database: the install only queues all tasks that have lines; the worker fills the view in the following ticks (no heavy statement inside the install transaction). Old projects need no change.
  • pg_cron needs: the extension enabled (Supabase dashboard) and a version that accepts the seconds form ('2 seconds', pg_cron 1.5 or newer) - please check it in the dashboard (Q14). If not available, the fallback is one minute cron + the app calling the worker on demand (not recommended).

8 - Navigate from any sum to the source transactions

SumExplorerListReusable.tsx - one reusable component; Monitor01 is only its first user (the Costs / Revenues reports can use it later).

What the user sees

  • Tap a number → a window titled with the cell ("Data Analyst · 2026-10 · task01 · planned = 24 h")
  • Under it the list of the source transactions that make the sum, paged, newest first: day · line · quantity · unit · who / document
  • At the bottom a check line: "list total 24.00 = cell 24.00 ✓" - or the difference and "the view is about 2 s behind"
  • Each transaction has Open: jumps to its task line in the Plan view (app/pm/project/task/plan) or the contract card
  • On a derived cell (rest to contract, on-hand) two lists, one per operand, each with its subtotal

How it is reusable

  • Props: title, sum (value + unit), filter (a bag of keys: project, task, genus, role, unit, month, from / to), sources[]
  • A source = name · columns · fetchPage(filter, page) · onOpen(row) · sign (+ / −)
  • The component knows nothing about Monitor01: Monitor01 passes its sources, another report passes its own
  • Used for cells, group subtotals and the total row: fewer keys in filter = a bigger list

Where the rows come from

  • One RPC monitor01_sum_sources(measure, filter, page) (SECURITY INVOKER, so the project policy applies) returns the page, the row count and the exact sum
  • Indexed by task / project / line role; for the total row by project and month
  • Reads the source tables, never monitor01_view: the list is the proof of the sum

13 - Tests

Docker (postgres:15, cd kit8/docker && ./test_sql.sh && ./test_monitor01.sh)

  • Install / delete cycle passes twice (idempotent); the drop removes tables, triggers, functions, cron jobs.
  • The example of the sheet: after one worker run monitor01_view equals the sheet row by row (24/24/0/20/16/4, 24/0/24, 100/65/35/50/30/20, 200/80/120).
  • A new movement, a deleted line, a changed role / unit / genus, a renamed task / project / role: each ends in the right row after one run.
  • Only changed rows are written (updated_at of an unchanged row stays); a deleted task leaves no row.
  • Empty queue: the run changes nothing and writes no log. Burst: 10 000 writes to one task = one queue row.
  • Batching: 1200 queued tasks drain in three batches; two concurrent workers never process the same task; a poisoned task is parked after 5 attempts and the rest continues.
  • Race: a commit during a worker run is picked up on the next one (two-session script, like test_time_genus_race.sh).
  • planMovementStatus = false rows are not counted; a stale line is counted and flagged (Q3).
  • Policies: the owner reads only own projects; nobody writes monitor01_view; the source tables follow their policies.
  • monitor01_sum_sources: for every cell the list total equals the cell; monitor01_verify finds a manually damaged row.
  • Speed (100 000 movements): batch and empty-tick times from section 7 are printed.

Jest

  • Tree builder, subtotals, totals per unit, filters (dates, contains), colour rules, key patching (insert / update / delete event), reconnect refetch, data-age text.
  • Sum explorer: paging, check line, derived cell with two lists, Open action. Toggle shows the button and the dashboard; route renders with a project selector.
