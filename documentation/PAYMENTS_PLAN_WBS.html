Payments Plan – Work Breakdown Structure

W1 PLAN PAYMENTS. Scope: a new first-level tab TabPayments in the Finances view of a task (PMProjectTaskInputCRUD) where the project manager plans the payments (money out / money in) of the task for his forecast: table task_payment_plan_lines, a Post step, and an empty Cash flow sub-tab kept for a later report. Built 2026-10-23 (section 10). Sources: the Google Doc “W1 PLAN PAYMENTS” and the owner’s answers of 2026-10-21 and 2026-10-23 (section 8). Version 4.

1. Goal

Today a task plans its costs and revenue (Time, Material, Expenses, Deliverable lines → posted plan days → Monitor01). That is the amount and the day of the work, not the day the money moves. W1 adds the second view: for the same task the project manager plans when and how much is paid out (Outbound) or received (Inbound), to whom (a partner or a person + a contract), under which budget item and business unit, in which currency, with the three sums sumForContract · sumForAccounting · sumForBudget.

The payment day is a positive shift in days after the start or after the end of the task (a select field on the payment says which). The shift is taken from the contract, else from the partner’s payment terms – both optional, the manager may overwrite it – or the date is typed by hand; the two are always kept consistent. The budget item of a payment is taken from the contract (a new input on partner and person contracts) and can be edited on the payment line. Buttons fill / refresh propose the payments from the task’s Time, Material, Expense (Outbound) and Deliverable (Inbound) lines. Post turns the payments into posted rows that a later cash-flow report will read.

Hard constraint (as for every feature of this app): nothing existing changes. A project that never opens TabPayments works exactly as before; the Time / Material / Expenses / Deliverable tabs, the posted plan days, Post of the task lines, the register and Monitor01 are not touched. The payment plan is a separate table with its own Post that nothing else reads in W1.

4. Proposed data model (to confirm)

One table, every domain field in rowJSON, one row = one payment. No plan group and no header total (dropped by the owner).

task_payment_plan_lines                (PART 37)
  rowGUID          uuid  PK
  rowProjectGUID   uuid  -> project_table       (RLS: pm_owns_project)
  rowOwnerGUID     uuid  -> project_task_table  (ON DELETE CASCADE)   the task
  rowParentGUID    text  'inbound' | 'outbound'                       the direction (like the genus of a task line) = the sub-tab
  orderInList, created_at, updated_at
  rowJSON {
    paymentPlanPaymentDirection     'inbound' | 'outbound'           (= rowParentGUID, kept equal)
    paymentPlanBudgetItem           budgetItemTable.rowGUID          (payments genus, direction as above; default = paymentBudgetItem of the contract; EDITABLE)
    paymentPlanBudgetItemSource     'contract' | 'line'              (taken from the contract / chosen by the user; while 'contract' it follows a change of the contract)
    paymentPlanBusinessUnit         businessUnitTable.rowGUID        (default: the unit of the source line, else businessUnitAssigned of the contract)
    paymentPlanPartner              partnerTable.rowGUID             (the payee when it is a partner)
    paymentPlanPerson               personTable.rowGUID              (the payee when it is a person; Outbound only; exactly one of partner / person)
    paymentPlanContract             contractTable.rowGUID            (of that partner / person)
    paymentPlanCurrency             ISO code (default: currency of the contract, else of the project)
    paymentPlanTimelineAnchor       'taskStart' | 'taskEnd'          (what the shift is counted from; default 'taskStart')
    paymentPlanTimelineShiftDays    number >= 0                      (default chain: contract -> partner terms -> 0)
    paymentPlannedTransactionDate   'YYYY-MM-DD'                     (typed, or anchor date + shift)
    paymentPlanDateSource           'shift' | 'date'                 (which of the two the user typed last)
    sumForContract                  number, WITH VAT, typed, in paymentPlanCurrency
    sumForAccounting, sumForBudget  numbers, WITH VAT, snapshot made with the rate of paymentPlannedTransactionDate (fxSnapshot, like a task line)
    paymentPlanSource               null (hand made) | { genus, taskLineGUIDs[] }   (what a fill button made; what refresh replaces)
    paymentIsPosted                 boolean; any change sets false, only the Post RPC sets true
  }

task_payment_plan_movements            (PART 37)   the POSTED payments: one row per payment, written by post_task_payment_plan
  rowGUID, rowProjectGUID, rowOwnerGUID (task), rowParentGUID (the payment line, cascade)
  periodDay (= planned date), direction, budgetItem, businessUnit, partner, person, contract, currency,
  sumForContract, sumForAccounting, sumForBudget (WITH VAT)

contractTable.rowJSON.paymentTimelineShiftDays                       number >= 0, optional   (new key, no SQL; partner AND person contracts)
contractTable.rowJSON.paymentBudgetItemOutbound                      budgetItemTable.rowGUID of the OUTBOUND payments genus, optional   (new key, no SQL; partner AND person contracts)
contractTable.rowJSON.paymentBudgetItemInbound                       budgetItemTable.rowGUID of the INBOUND payments genus, optional    (new key, no SQL; a person has none)
partnerTable.rowJSON.supplierData.paymentTimelineShiftDays           number >= 0, optional   (new key, no SQL)
partnerTable.rowJSON.customerData.paymentTimelineShiftDays           number >= 0, optional   (new key, no SQL)

Rules

  • Date. Date = (start or end of the task, by paymentPlanTimelineAnchor) + shift days. Typing the date sets the shift = date − anchor date. The date can never be before the task start; with the project switch OFF it can also not be after the task end – so with the anchor Task end and the switch off only shift 0 is possible. A typed date before the chosen anchor (shift would be negative) is an error that says “choose the anchor Task start”.
  • Shift default. Contract value → else the partner’s value (supplier data for Outbound, customer data for Inbound; a person has none) → else 0. “Not set” is not 0: only a missing value falls to the next step.
  • Budget item. A new payment takes paymentBudgetItem of its contract, when its direction equals the sub-tab (a contract with both roles can have an item of one direction only); otherwise it is empty and the Errors column asks for one. The user can change it in the cell (R13): the choice lists the payments-genus items of the direction of the sub-tab. A line the user edited (paymentPlanBudgetItemSource = 'line') keeps its item when the contract changes; a refresh by a fill button never overwrites it.
  • Contract form. The input “Payment budget item” (and the shift) is on partner contracts and on person contracts: for a person contract the list is outbound items; for a partner contract the outbound items when it has the supplier role, the inbound items when it has the customer role (both roles: both lists).
  • Payee. Outbound: a supplier partner or a person. Inbound: a customer partner. A person Time line pays the person: paymentPlanPerson and the person’s contract.
  • Rate day. The planned transaction date; without a rate on that day the latest earlier rate of the book, as the existing code does; no rate at all = the cell stays empty and the Errors column says why.
  • Post. Needs per payment: budget item (payments genus, direction right), payee, contract, currency, date (rules above), sum, the three sums converted.

6. Sequence, dependencies and acceptance criteria

  1. 1 Decisions – 1.3 (seeds) is checked first. 2, 3.1, 3.3 and 4 can start at once.
  2. 2 SQL and 3 pure rules – independent of each other; both before 5 and 6.
  3. 4 Contract / partner keys and the Payments settings tab – before 3.4 / 6.3 (they read them).
  4. 5 Redux entity and tab, then 6 table, then 7 fill buttons.
  5. 8 Quality – tests are written with each step, as always.

Acceptance criteria

  • The task Finances view has the tab Payments with three sub-tabs Outbound · Inbound · Cash flow; Cash flow is empty (a placeholder, no data read). A stage shows the usual note. A project that never uses the tab shows no change anywhere else.
  • The project settings have a separate tab Payments with the switch (true by default); the Organization defaults have it too.
  • The contract form of a partner contract and of a person contract has the optional inputs “Payment budget item” and “Payment timeline shift (days)”; the partner card has the optional shift in its supplier and customer payment terms; none of them is lost when the form is saved.
  • A payment can be added on Outbound and on Inbound; payee, contract, budget item, business unit and currency are chosen as in 6.2 and saved in rowJSON of task_payment_plan_lines. There is no header total and no total check.
  • A new payment takes the budget item of its contract when the direction fits. The user can change the budget item on the payment line (any payments-genus item of the direction); the changed item stays when the contract is changed or the payment is refreshed by a fill button.
  • The payment has the select Anchor: Task start | Task end (default Task start). Typing the shift days (≥ 0 only; a negative value is refused by the number input) fills the planned date = anchor date + shift; typing the date fills the shift; changing the anchor recalculates the date (shift-source) or the shift (date-source). A date before the task start is an error; with the switch off a date after the task end is an error; with it on (default) it is allowed.
  • A new payment takes the shift of its contract; without one the shift of the partner’s payment terms (supplier data for Outbound, customer data for Inbound); without both 0. The manager can overwrite it.
  • When the task start or end moves, payments with a shift follow it; payments with a typed date keep the date and show the new shift (⚠ if negative).
  • The three sums include VAT; sumForAccounting / sumForBudget are calculated from sumForContract with the rate of the planned date; without a rate the cell is empty and the line says why.
  • The fill buttons create one payment per group for the genus of the button, only on the matching sub-tab, including persons’ Time lines; pressing one twice gives the same rows; hand made payments and hand edits are not touched.
  • The Post button shows Post needed after any change and Posted after Post; Post writes one movement per payment in one transaction, twice gives the same rows; an incomplete payment refuses the Post with a list; changing or deleting a posted payment unposts it.
  • Deleting the task deletes its payments and movements; another user cannot read them.
  • test_sql.sh passes (install twice, delete, install); the new Docker test and the new Jest tests pass; no new FAIL against the Jest baseline.

11. Decisions taken while building

  • Which of shift / date was typed is found by comparing the row with paymentPlanDateSnapshot (the table gives computeRowJSON only the new row). A typed date before the chosen anchor leaves the shift empty and the line says “choose the anchor Task start”.
  • The budget item follows the contract while it is empty or still the item the app took last time (paymentPlanBudgetItemAuto); anything else is the user’s choice and stays (also at a refresh of a fill). An item the catalog does not know as a payment item of the direction is not taken from the contract.
  • The payee is two columns (Supplier / Customer, and Person on Outbound); both set = the one that was not the payee before is the new choice. A contract chosen first gives its payee.
  • Post checks everything, also the converted sums while the project has an accounting / budget currency; the days of the task come from the scheduler of the app (its time zone). paymentEverPosted makes “Post needed” (not “Post”) of a payment that was posted once.
  • A refresh matches groups to made payments by the lines they share, so a payment whose payee or contract the user changed keeps living; a made payment with no group any more is removed after a confirmation.
  • The task moves: the screen (while the task is open) brings every payment in line (usePaymentPlanFollowsTask); the database unposts the payments of a task whose start or end day changed.
