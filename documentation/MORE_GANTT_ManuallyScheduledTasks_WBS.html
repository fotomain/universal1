Manually Scheduled Tasks – Work Breakdown Structure

Scope: add the MS Project Task Mode (Auto Scheduled | Manually Scheduled) to the Gantt chart of kit8/pm. Item A1 of MORE_GANTT_INPUT.html. Planning document – no implementation, nothing in the code was changed.

1. Goal

Today every task is placed by the scheduler: its start is the latest of the project start, its “start no earlier than” date and what its predecessors force. A planner who knows better (“the crane arrives on 14 March, whatever the plan says”) can only type a start no earlier than date, and a predecessor that finishes late still pushes the task away.

A manually scheduled task has a start and a duration that the user types and that no link, calendar or project start ever moves. Links to and from it stay drawn and stay valid for the other tasks; when a predecessor would push the task later than the user placed it, the app only warns. This is how MS Project 2010+ plans early, rough or externally fixed work.

Hard constraint: a project that does not use the feature schedules exactly as today (same dates, same critical path, same write-back). Everything new is behind a project switch that is OFF while never saved, and the scheduler is unchanged for a task without the new keys.

2. Requirements overview

#RequirementNote
R1A project without the feature behaves exactly as before.Master switch OFF by default; a task without the new keys is auto.
R2A task (task or milestone) has a mode: Auto (default) or Manual.Stages (summary rows) and subproject tasks stay auto in this version.
R3A manual task keeps its typed start. Duration, calendar and links never move it; finish = start + duration in the project calendar.The only thing that changes a manual start is the user.
R4Links of a manual task remain: its finish still drives its successors (FS / SS / FF / SF + lag), its predecessors no longer drive it.Critical path, float and stage roll-up include it.
R5When a predecessor would place a manual task later than it is, the task shows a conflict warning (bar and tree). Nothing is moved.Same idea as the MS Project “scheduling conflict” indicator.
R6The mode is switched in four places: a tree column (click), the row / bar menu, the task window, and the project setting “new tasks are manual”.One command, one undo step.
R7A manual bar looks different from an auto bar (outline style + pin), and a drag of a manual bar writes the manual start, not a constraint.Tooltips explain both.
R8Switching Auto → Manual keeps the dates the task has now. Switching Manual → Auto removes the manual start; the task returns to ASAP.Confirm with the owner (Q3).
R9Every reader of the schedule honors the mode: the client scheduler, project versions, the network view, Post of task lines, the user calendar, templates, JSON and MS Project XML export.Section 3 lists them with the place in the code.
R10Turning the project switch OFF makes every task auto again, without deleting the stored manual dates (turning it ON restores them).Same “hidden is not deleted” rule as the cost input switches.

3. What already exists (checked in the code, 2026-10-26)

  • Scheduler view/project/scheduling.ts scheduleProject() – pure; forward pass: es = projectStart, then max(es, manualStartAt), then every predecessor constraint (FS / SS / FF / SF + lag), then nextWorkDay; backward pass gives totalFloatDays and isCritical; stages roll up min start / max finish. Called by store/storeDerive.ts derive() and by version/model/versionCompare.ts scheduleVersion().
  • rowJSON.manualStartAt is today a start no earlier than constraint (ASAP when empty). It is written by the inline Start cell (setStartConstraint), the task window, TaskDatesBar / taskDatesModel.ts, a bar drag (applyBarEdit “move” and “resize-start”) and, for the origin task of a subproject, by SQL subproject_sync_origin_task. The MS Project XML export writes it as constraint type 4.
  • Write-back crud/queries.ts useScheduleWriteBack → RPC pm_apply_schedule stores the computed rowJSON.startAt and rowDuration (finish) – so SQL, the user calendar and Monitor reports read real dates. Posted task lines and payments are unposted when the start or finish day changes (task_line_plan_unpost_on_dates, task_payment_plan_unpost_on_dates).
  • Task window PMTaskEditModal (Start “no earlier than”, Finish, Duration, hour / minute / second fields), tree columns taskStartDate / taskFinishDate / taskDuration, row menu PMTaskRowMenu, Task info page (“start ≥ …” with a clear button), taskShare.ts text.
  • Copies of a plan: project templates shift startAt / manualStartAt by the new project start (crud/api/templateApi.ts); task templates strip them (task_template_clean_task, test 98_task_template.sql); project versions copy the whole rowJSON.
  • Subprojects: the origin task follows the subproject dates and gets taskIsSubproject; taskDatesReadOnlyReason() already blocks date editing for it.
  • Settings pattern: project switches live in project_table.rowJSON (PMRowJSON in model/types.ts), organization defaults in rowJSON.defaultProjectSettings; a switch that was never saved reads as its default.
Important: because a bar drag already writes manualStartAt, an auto task that was dragged today is pinned only from the left – a late predecessor still pushes it. That stays as it is (it is the MS Project auto behavior too). The manual mode needs its own key; reusing manualStartAt would turn every dragged task into a manual one.

4. Proposed model and rules (to confirm)

4.1 Keys

WhereKeyMeaning
project_task_table.rowJSONtaskScheduleMode'auto' | 'manual'; absent = auto.
project_task_table.rowJSONtaskManualStartAtISO timestamptz of the typed start (same format as manualStartAt, may carry hour / minute / second). Only read while the mode is manual. Absent on a manual task = the engine’s start at the moment of the switch is used and stored on the first save (so a manual task always has a start).
project_task_table.rowJSONdurationDaysUnchanged – the duration, working days of the project calendar.
project_table.rowJSONmanualSchedulingFunctionalityEnabledMaster switch, OFF while never saved (=== true in TS).
project_table.rowJSONnewTasksAreManuallyScheduledDefault mode of a new task; false while never saved; works only while the master switch is on.
PMScheduledRow (client, not stored)isManual, engineStartMs, linkConflictMode used for the row, where the links alone would start it, and engineStartMs > startMs for a manual row.

No new table and no SQL column: the keys live in the existing JSONB, the write-back (pm_apply_schedule) already stores what the scheduler computes. SQL changes are limited to one function (task template cleaning, work package 9.5).

4.2 Scheduler rules (forward pass)

  1. A leaf row is manual when the master switch is on, taskScheduleMode = 'manual', it is not a summary row and it is not a subproject task (taskIsSubproject !== true). Everything else is auto and takes the existing code path unchanged.
  2. Manual: es = taskManualStartAt (the typed instant, not moved to the next work day and not limited by the project start); ef = addWorkDays(es, duration). Predecessor links are not applied to es; they are evaluated once more only to fill engineStartMs and linkConflict.
  3. Successors read the manual row’s ES / EF exactly like those of an auto row (the loop already reads the aggregate of the predecessor).
  4. Backward pass: unchanged formula on the manual dates. A manual task that finishes later than its successors allow gets zero float and is critical (negative float is clamped to 0 as today).
  5. Stage roll-up, project finish, project progress: unchanged – they read the rows. projectStartMs stays the project start; a manual task before it is allowed and widens the Gantt time line (see risk Z2).
  6. Cycles: the topological sort and cycle detection still run on all links, a link into a manual task counts. (A manual task can still be part of a cycle error – the user fixes the link.)

4.4 Display

  • Gantt bar: manual = outlined bar with a lighter fill and square end brackets (the MS Project look), a small pin glyph at the start; auto bars unchanged. With linkConflict a warning triangle at the start and a tip “A predecessor ends after this task starts (links would start it on …)”. Critical-path color still applies to a critical manual bar.
  • Tree: optional built-in column taskMode (title “Mode”, icon only, 36 px, hidden by default and offered only while the switch is on; click toggles; tip says what the click does). The Task name cell shows the warning icon on a conflict even when the column is hidden.
  • Tip / Task info page / share text: “Manually scheduled: start 2026-03-14” instead of “start ≥ …”.

6. Sequence and dependencies

  1. 1 Decisions – before code.
  2. 2 Model – blocks everything.
  3. 3 Scheduler (with its tests) – needs 2; the heart of the feature, can be finished and tested alone, no UI.
  4. 4 Commands – needs 2 (and 3 for the checks).
  5. 5 Tree, 6 Gantt, 7 Task window, 8 Settings – need 4; independent of each other, so they can go in parallel. 8 first if the UI is to be tried early (nothing is visible while the switch is off).
  6. 9 Other readers – 9.1, 9.3, 9.4 after 3; 9.5 and 9.6 independent (9.5 is the only SQL).
  7. 10 Quality – last; test cases are drafted from step 3 onward.

7. Acceptance criteria

  • A project without the switch (or with it on and no manual task) shows the same dates, float and critical path as before, and writes nothing new.
  • A task switched to Manual keeps its dates; moving its predecessor later or changing the project start does not move it; its successors still follow its finish.
  • When the predecessor would start the manual task later than it is, the warning shows on the bar and in the tree and disappears when the user moves the task or the predecessor.
  • Dragging a manual bar leaves it where it was dropped; dragging an auto bar behaves as today.
  • Switching Manual → Auto returns the task to the engine’s position (after the confirm decision Q3); Undo restores the manual state in one step.
  • A stage and a subproject task cannot be made manual and say why.
  • Turning the switch OFF asks when manual tasks exist, makes every task auto, and turning it ON again restores the manual starts.
  • The posted task lines of a manual task are unposted only when its start or finish day changes (existing behavior of the write-back).
  • A version, a project created from a template, a JSON export / import and the MS Project XML keep the mode; the XML opens in MS Project with the task manually scheduled.

8. Questions for the owner (the answers change the design)

#QuestionProposal
Q1Master switch per project, OFF by default (like ROI), or always on?Per project, OFF by default; organization default through “Save settings to organization”.
Q2Should a new task be manual by default?No – auto by default; setting “New tasks are scheduled manually” for those who want it (MS Project 2010+ defaults to manual; the app’s existing plans are all auto).
Q3Manual → Auto: forget the manual start (ASAP) or turn it into a start no earlier than constraint?Forget it (ASAP): the user chose “let the plan decide”. A constraint would silently keep the task late.
Q4Manual stages (summary rows with their own dates)?Not in this version. It needs a second set of dates on summaries and a decision about roll-up; plan it as a later package.
Q5Independent Finish and blank dates on a manual task (MS Project allows start, finish and duration to disagree, or to be text)?No – start + duration, finish derived. A manual task always has a valid start.
Q6Link conflict: warn only, or also offer “Respect links” (move the task to where the links put it)?Warn only in V1; “Respect links” is one command (setScheduleMode auto then manual again) and can come next.
Q7May a manual task start before the project start?Yes (MS Project allows it); the Gantt time line is widened to it.
Q8Milestones: manual too?Yes – a manual milestone is a fixed date (a delivery date, a gate).

9. Out of scope

  • Manual summary tasks (Q4), blank or text dates, independent finish (Q5).
  • The other constraint types (Must Start On, Finish No Later Than …) and the deadline date – items A3 / A5 of MORE_GANTT_INPUT.html; the conflict marker built here is reused for them.
  • The indicators column of the table (E11) – the conflict icon sits in the Task name cell until then.
  • Resource and cost behavior: Time, Material and Expense lines follow the dates of the task as today.

10. Risks

#RiskHandling
Z1Two keys with “manual start” in the name confuse the code and the users (manualStartAt = no earlier than, taskManualStartAt = fixed).Comments on both keys in types.ts, the README paragraph (10.3), different tips in the UI; a grep-able test that both are never written together by one command.
Z2A manual task before the project start (or far after the finish) breaks the Gantt time-line range or the “Fit to screen” span.Check how PMGanttSurface takes the range (projectStartMs, projectFinishMs, version overlays widen it) and widen it by the earliest manual start; test with a manual task one year earlier.
Z3Changing the schedule write-back changes startAt of many rows and unposts their lines and payments.Not triggered by the feature itself: the write-back runs only when a computed day differs, and an auto task keeps its result. A test with the switch ON / OFF on a plan with posted lines checks that nothing is unposted.
Z4MS Project XML element order (schema) – a wrong order makes MS Project refuse the file.9.6 includes opening the file in MS Project; fallback: export a manual task as an auto task with a constraint (type 4) and say so in the export window.
Z5The other ends read startAt from the write-back, which lags the client scheduler by a moment.Unchanged behavior; a manual task is simply stable earlier because its dates do not depend on other rows.

11. Update steps when it is built (preview)

  1. Run start2_sql_code.sql in the Supabase SQL Editor (only the one function of 9.5 changes; no table, no seed, no pg_cron).
  2. Restart Expo with a cleared cache; no .env change.
  3. Project settings → Main → Scheduling → turn on “Manually scheduled tasks”; right-click a task → “Schedule manually”.
