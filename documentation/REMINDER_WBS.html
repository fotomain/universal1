Reminder (idle mode) Phase 1 built 2026-10-20

Decisions of the owner (2026-10-20): build Phase 1; no Phase 2 (no server push); the calendar code lives in kit8/ui/calendar (screens + data/), the reminder code in kit8/ui/reminder; the web gets a service worker (public/reminder-sw.js). Built differently from this plan: (1) no own Kotlin module: the source of expo-notifications 57 uses setExactAndAllowWhileIdle when exact alarms are allowed and has a boot receiver (still to be confirmed on real phones, WP0); (2) the expo-notifications config plugin is not used (it forces the iOS push entitlement); (3) the background top-up task is not built, the list is topped up when the app is open; (4) the web shows reminders only while the browser is open: a closed browser needs a push server (= Phase 2). See kit8/ui/reminder/README.md.

Source: the note "W1 REMINDER IDLE": no code, this WBS document needed; calendar task reminder; only for logged in users; it must work in idle mode also, when the application is in the background on Android and Apple - that is why native code is needed. Nothing is built. This page is the plan.

The answer in four lines

  • The reminders already exist (notifications of a calendar entry) but fire only while the app runs (UserCalendarNotifier, a 30 s timer).
  • Phase 1 = the phone's OS fires them: we hand the next reminders to the OS as local scheduled notifications (Android alarm, iOS notification center). Works with the app closed, the phone locked, in Doze, offline.
  • Phase 2 (optional) = a server push (FCM / APNs) as the long range and cross-device safety net.
  • Logged in only: schedule after sign in, wipe everything at sign out / user change.

What is NOT in this plan

  • Web / browser (no idle mode there; the existing in-app modal + browser Notification stay as they are).
  • New reminder fields: the calendar editor already has them (amount, unit, all-day time).
  • Code. The next round builds Phase 1 after the spike (WP0), see section 10.

2 Rules

  1. Only for logged in users. No session = no scheduled reminder and no push token on the server (section 6).
  2. Idle mode: a reminder is shown on time when the app is closed (swiped away), in the background, the screen is locked, the phone is in Doze / Low power mode and has no network at that moment.
  3. The source of truth stays user_calendar_event_table. The OS schedule is a cache of it: it can be wiped and rebuilt at any time (idempotent sync).
  4. One reminder = one OS notification with a stable key ${rowGUID}:${YYYY-MM-DD}:${index} (the key dueReminders already uses). A reminder is never shown twice (OS notification + in-app modal): the shown-keys store decides.
  5. A tap opens the entry (/user/calendar?eventGUID&date); the in-app modal does not open a second time for the same key.
  6. Done tasks do not remind (same rule as dueReminders); an edit / delete / "done" removes or moves the scheduled notification at the next sync.
  7. Times follow the phone's local clock and time zone (travel, summer time): an all-day reminder "09:00" is 09:00 where the phone is.
  8. The user can switch reminders off per device, and sees clearly when the OS blocks them (no permission, exact alarms off, battery saver) - section 9.

3 Why native code is needed - the OS limits

A JavaScript timer (setInterval) is frozen or killed when the app is in the background. Only the operating system can wake the phone at a time.

Consequence: the reminder itself must be a notification that the OS owns (local scheduled or push). Code that runs "at 09:00" cannot be trusted on either platform. "Native code" here means: notification channel + exact alarm + boot re-schedule on Android, notification center + categories on iOS, FCM / APNs registration for phase 2 - see section 7 for how much of it a library already gives us.

4 Architecture

user_calendar_event_table
notifications[], recurrence, done→ React Query + realtime
already loaded by the Notifier→ planner (pure TS)
next 60 reminders = "the plan"→ sync (diff)
schedule / cancel by key→ OS alarm / notification center
fires with the app dead

Phase 1 - local schedule required

  • Planner (pure function, no OS): input = event rows, now, limit (60, below the iOS 64; one slot is kept free for a test notification), output = the plan: list of {key, fireAtMs, title, body, data:{ownerGUID, eventGUID, date}}, nearest first, only the future, done tasks removed. Built on expandEvents / notificationTimeMs, so the in-app modal and the OS use the same times.
  • Scheduler (adapter): reads the OS list of pending notifications, compares with the plan by key and fire time, cancels what is gone or changed, schedules what is new. Idempotent: run it as often as needed.
  • When it runs: after sign in; whenever the calendar rows change (the realtime hook is already mounted); app start; app returns to foreground; a time zone / clock change; permission change; after a boot (Android, by the OS re-delivering the alarms or our boot receiver); best-effort by a background task (daily) to top up when the user does not open the app for days.
  • Horizon: the plan holds the next 60 reminders. A phone with few entries is covered for months. A phone with many entries (every day a reminder) is covered for about 2 months on Android and, with 60 on iOS, for the nearest 60 reminders: when the user does not open the app, the window empties. That hole is what phase 2 closes.

Phase 2 - server push optional, decide in question 2

  • Long range: reminders behind the local window; cross-device: an entry changed on the web while the phone's app was closed.
  • Needs: a device table with the push token, the due reminders computed in SQL, a sender (pg_cron → Edge Function → FCM / APNs), credentials per app variant. Section 8.
  • De-duplication rule: the server pushes a reminder to a device only when the reminder is behind that device's local horizon (the device reports localHorizonAt at every sync). The push is therefore never a second copy of a local one.
Recommendation: build Phase 1 first. It alone fulfils "works in idle mode in the background on Android and Apple". Phase 2 adds infrastructure (Firebase project, APNs key, Edge Function, secrets) and is only worth it if users do not open the app for weeks or edit on several devices.

5 Flows

5.1 Set a reminder (any screen)

user saves an entry with "10 minutes before"→row saved (existing code)→realtime / cache change→sync: plan, diff, schedule→OS holds it

First reminder ever: the permission prompt appears here (not at the app start), with a short explanation card first. If the user refuses, the entry is saved and the calendar shows "Reminders are blocked on this phone".

5.2 The reminder fires with the app closed

OS shows the notification (title = entry, body = when + label)→user taps→app starts, session restored (SecureStore)→deep link /user/calendar?eventGUID&date→quick view opens, key marked as shown

5.3 Edit / delete / done / move

Any change is just a new plan: the diff cancels the old key and schedules the new one. A project task that moves (the SQL trigger rewrites the copy's dates) changes the plan the same way - when the phone sees the realtime event or at the next app start. If the app is not running when the project plan changes, the old alarm fires at the old time (section 12, risk 4).

5.4 Foreground

While the app is open the existing modal remains the way to show a reminder. The OS notification for the same key is suppressed in the foreground handler (shouldShowAlert=false) when the in-app modal takes it, so there is one reminder, never two.

5.5 Reboot, update, time zone

Android: alarms are cleared at reboot - the boot receiver (library or ours) re-creates them from the saved plan; the app also re-syncs at its next start. iOS: nothing to do. Time zone change: re-plan (all-day reminders are wall-clock times).

12 Risks

  1. OEM battery killers (Samsung, Xiaomi, Huawei) kill alarms. Mitigation: status + guide in section 9; cannot be removed by code.
  2. Android exact alarm policy: USE_EXACT_ALARM is for apps whose core function is an alarm or a calendar. If Play review does not accept this app as one, use SCHEDULE_EXACT_ALARM (the user switches it on) and fall back to inexact. Question 3.
  3. iOS 64 limit: top-up on every app start / foreground; phase 2 for the long range.
  4. Stale alarm: an entry changed on another device (or by the project plan) while this phone's app is closed: the old alarm fires at the old time. Mitigation: re-sync at every start, silent push (WP7.4). A reminder of a deleted entry may still show once; a tap finds nothing and says so.
  5. Force stop / force quit: Android force stop cancels alarms and push until the next launch; iOS force quit stops silent pushes but keeps local notifications.
  6. Time zones: an all-day reminder follows the phone clock; the server (phase 2) uses the zone last reported by the device.
  7. Native build: a new plugin needs expo run:android|ios; Expo Go cannot test it (same lesson as the media libraries). Four variants: every variant has its own bundle id, so its own push credentials.
  8. Library versions: expo-notifications must match SDK 57; do not add a second notification library (like the camera / video clashes in KNOW_HOW section 7).
  9. Privacy: a notification text is visible on the lock screen. Option "hide the title on the lock screen" (question 4).

13 Tests

Jest (written with the code)

  • Planner: single / repeating entries, all-day with atTime, several reminders per entry, exDates, done task, past reminders, limit 60 nearest, stable keys, time zone and summer time cases.
  • Diff: nothing changed = no calls; moved reminder = cancel + schedule; deleted entry = cancel.
  • Scheduler with a mocked OS module: permission denied = no schedule and status "blocked"; sign out = cancel all and clear keys; user change = A's notifications cancelled before B's are scheduled; not signed in = no calls.
  • Notifier: a tapped OS notification marks the key as shown, no second modal; the foreground handler suppresses the OS banner when the modal shows.
  • Same guard test as the SQL files: app.config.js lists the plugin and the permissions (a file test).

On devices (manual checklist, cannot be automated here)

  • Android: app swiped away, screen off 10 min, Doze forced, reboot, airplane mode, battery saver, exact alarm switch off, "Force stop" (documented as lost), time zone change.
  • iPhone: locked, Focus on, force-quit, 70 reminders (the 64 limit), time zone change, notification permission denied then allowed in Settings.
  • Both: sign out then wait for a due time = nothing shows; sign in as another user = only that user's reminders.

Docker (phase 2 only)

tests/93_reminder_push.sql: the SQL expansion equals the TypeScript golden cases; the horizon rule; RLS (a user cannot read another's device row); unregister; the tick sends each reminder once. Added to test_fact_monitor01.sh.
