Schedule From Project Finish Date – Work Breakdown Structure

Scope: the MS Project setting Project Information > Schedule From: Project Start Date | Project Finish Date for the Gantt chart of kit8/pm. Item A4 of MORE_GANTT_INPUT.html. Planning document – no implementation, nothing in the code was changed.

1. Goal

A plan today is always built forward from the project start date: the finish is the result. Many real projects work the other way: the opening, the delivery, the audit date is fixed and the question is “when must we start?”.

In MS Project the planner chooses Schedule From Project Finish Date, types the finish date, and the engine plans backward: every task is placed as late as its successors allow (new tasks default to As Late As Possible), the project start date becomes a result, and a start that would already lie in the past is the early warning that the date is not reachable. This feature adds that mode. The project window already has a field “Project Finish Date (projectFinishDate)”; today it is only a note, the scheduler never reads it.

Hard constraint: a project that is scheduled from the start (the default, and every existing project) behaves exactly as today: same dates, same critical path, same write-back, and the existing Finish Date field keeps its present (inert) behavior.

3. What already exists (checked in the code, 2026-10-26)

  • Scheduler view/project/scheduling.ts scheduleProject(): forward pass from projectStartMs (nextWorkDay of the start); project finish = the largest EF; backward pass over the leaves in reverse topological order with lf = projectFinishMs as the initial bound, FS / SS / FF / SF limits of the successors, then ls = subtractWorkDays(lf, d). Today these late dates are used only for totalFloatDays and isCritical. This is exactly the placement the new mode needs, with projectFinishMs fixed to the typed date instead of computed.
  • Start input: store/storeDerive.ts derive() reads project.rowJSON.projectStartAt (else created_at, else today) and skipWeekends; versionCompare.ts scheduleVersion() does the same for a version.
  • Finish today: the project window (PMRecentProjectsToolbar) has the editable field “Project Finish Date (projectFinishDate)” saved in rowJSON.projectFinishDate; for a new project it also sets rowDuration, which the write-back overwrites with the computed finish. The scheduler never reads it, so on existing projects it is a free-text memo that may be old or empty.
  • Write-back useScheduleWriteBack → pm_apply_schedule stores startAt / rowDuration per task and the project rowDuration (finish) and progress; a changed day unposts posted task lines and payments (task_line_plan_unpost_on_dates, task_payment_plan_unpost_on_dates).
  • Readers of the project start / finish: Gantt time line (PMGanttSurface range, PMProjectGanttChart project band and Fit), period window, network view (useNetworkView, networkModel), PDF header, MS Project XML (msProjectXml.ts), project cards / catalog (ProjectCard, projectCatalogModel), createProject (projectApi.ts), create-from-template (templateApi.ts: every date shifted by target start − template start), SQL user_calendar_project_task_json (fallback date).
  • Constraints today: only manualStartAt = start no earlier than; a bar drag and the inline Start cell write it. In a backward-planned project that key would mean something else (section 4.4).
Build order: the dragged-bar meaning, the “as late as possible” default of a task and the conflict markers need the constraint types of MORE_GANTT_The8ConstraintTypes.html (item A3: ALAP, Finish No Later Than, Must Finish On, the conflict flag, negative slack). This feature should be built after A3; without it the mode could be offered only as a read-only plan with no way to pin a task.

No new table and no SQL column. Under the proposal there is no SQL change at all (section 11).

4.2 The algorithm

  1. Fixed finish. F = nextBackWorkDay(projectFinishDate) + 1 day (exclusive). A finish on a non-working day is moved to the previous working day, with a tip.
  2. Backward placement (the new first pass). Reverse topological order over the leaf graph. For each leaf: lf = F, then the minimum over its successors’ constraints using the successors’ placed dates: FS lf ≤ shift(succ.ls, −lag), SS ls ≤ shift(succ.ls, −lag), FF lf ≤ shift(succ.lf, −lag), SF ls ≤ shift(succ.lf, −lag); then ls = subtractWorkDays(lf, d). These are the formulas of today’s backward pass; the code is moved to a shared function and used for both purposes. Milestones: ls = lf.
  3. Constraints in the mirror. Fixed rows (R8) take their own dates and bound their predecessors. A date constraint of A3 is applied as in its table (MSO / MFO fix the date; Finish No Later Than bounds lf; Start No Earlier Than bounds ls ≥ D and is a conflict when the links would need earlier).
  4. Calculated start. S = min(ls) over all leaves (the stages roll up as today). projectStartInPast = S < today.
  5. Early dates for float. The existing forward pass runs from S (with the same constraints) to give earlyStartMs / EF; totalFloatDays = work days between early and late start; critical when it is 0. The longest chain starts exactly at S, so it is the critical path.
  6. Output. startMs / finishMs of a leaf = the late (placed) dates; projectStartMs = S, projectFinishMs = F; stage roll-up, progress and cycle handling unchanged.

In start mode none of this runs: step 2 is the existing backward pass, used for float only, as today.

4.3 The stored start and the write-back

In finish mode the write-back, besides the task rows, writes the calculated start into the project row (projectStartAt and projectStartDate) with the normal project update (no new RPC; no loop, because in finish mode derive() does not read projectStartAt). From then on every reader that still looks at projectStartAt – cards, the calendar fallback, versions, exports, a switch back to start mode – sees the real start. When the calculated start changes by a day the project row is rewritten once.

4.5 Switching the mode

  • Start → Finish: the window proposes the finish date of the current plan (the last day, inclusive) so that, at the switch, the project length is unchanged; tasks then move to their late dates (into their free slack).
  • Finish → Start: the start field takes the calculated start; tasks move to their early dates. The typed finish date stays in projectFinishDate as the memo it is today.
  • Preview (R7): before Save, the app runs both schedules on the current data (a dry run, no write) and shows “N tasks change their dates; the posted lines and payments of M of them will need a new Post”. Cancel leaves everything as it was.
  • An existing projectFinishDate is not adopted silently: when the user selects “Finish date” the field is pre-filled with the plan’s finish, whatever the old memo says (decision Q3).

4.6 Display

  • Project window (PMRecentProjectsToolbar, Main tab): a SegmentButtonsApp “Schedule from: Start date | Finish date” above the two date fields; in finish mode the start field is read-only with the label “Project Start Date (calculated)”, in start mode the finish keeps today’s behavior.
  • Gantt: a vertical line with the date at the fixed finish (light and dark palette), a header chip “Scheduled from finish · 2026-12-31”, and the orange warning of R5 when the start lies in the past (also in the project card).
  • Task window / task info: the float text says “late start / early start” where it helps; no new fields.

7. Acceptance criteria

  • A project never switched shows the same dates, float, critical path and write-back as before; its Finish Date field still has no effect.
  • For a chain of three 5-day tasks and the finish 2026-12-31 (Mon–Fri), the last task ends on 31 Dec, the first starts 10 working days before the start of the second, and the project start is the first task’s start, shown read-only and stored in the project row.
  • A shorter parallel branch is placed late (its finish meets its successor) and shows its float; the longest chain is critical.
  • Changing the finish date moves every task that has no fixed date; changing a duration moves predecessors, not successors.
  • When the calculated start is before today the warning shows with both dates; nothing is moved.
  • A manually scheduled task and a subproject origin task stay on their dates and bound their predecessors.
  • Switching the mode shows the preview with the task counts and the Post warning, and does nothing on Cancel; switching back gives the early dates with the calculated start as the start date.
  • A version, a project from a template, the network view, the JSON / PDF export and the MS Project XML are correct for a finish-mode project.

10. Out of scope and risks

  • Out of scope: the start / finish of a single stage as a driving date; “schedule from finish” for a subproject independently of its parent; the deadline date (A5); resource leveling; a project calendar with holidays (A11) – the backward pass uses the existing Mon–Fri / 7-day calendar.
