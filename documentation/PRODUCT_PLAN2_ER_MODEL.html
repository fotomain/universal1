Product storage ER model, laid out as a waterfall

Every table sits on a numbered level, and every arrow points down. A table only ever depends on levels above it. Data falls from reference data through the WooCommerce product model, the rebuild queue and the read model, down to the RPCs the web shop calls.

Generated from the actual shop schema in the PostgreSQL 16 test database used for the Plan 2 benchmark: tables, columns, primary keys, foreign keys, unique indexes and triggers. Laid out with ELK's layered algorithm with one partition per level, so no table can move above a table it depends on.

Create / drop order

CREATE (top → bottom)

unit → tax_class → shipping_class → media → tag → category → attribute → attribute_term → product → variant → product_category → product_tag → product_attribute → product_media → product_link → review → download → dirty → listing → variant_facet → page → category_facet

DROP (bottom → top)

category_facet → page → variant_facet → listing → dirty → download → review → product_link → product_media → product_attribute → product_tag → product_category → variant → product → attribute_term → attribute → category → tag → media → shipping_class → tax_class → unit

The WooCommerce import follows the same order: taxonomies and terms first, then products, then variations and links. Every foreign key then resolves on the first pass, except category.parent_id and product.parent_id (self references), which are filled in a second pass.

Read-model tables (listing, variant_facet, page, category_facet) have no foreign keys on purpose. They are rebuilt rather than referenced. Deleting a product queues it in dirty, and rebuild_product() then removes its read-model rows. Products are normally archived (status = 'draft'), not deleted, because Woo orders reference them.
