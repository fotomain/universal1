Record media - how it works

Hamburger menu Record -> Video, Audio, Photo. Every recording is kept on the device / in the browser, becomes a media post, and its file is uploaded by itself to the organization's file storage (Google Drive, or OneDrive when the organization chose it). The post stores the address of the file in the storage. The player uses the file of the device first when it exists, and the file in the storage when it does not - a browser always plays from the storage.

BUILT 2026-11-26. Tried in Jest and in the Docker database (30 SQL checks) only. NOT tried on a real phone, in a real browser, or against the real Google Drive.

1. What happens when the user records

  1. The user records a video / audio / photo and presses Save. The file is copied out of the cache: phone = a file in the app's document folder (file:///...kit8video_*.mp4), browser = IndexedDB (kit8media://...).
  2. The media post is written to mediaPostTable (rowJSON.recordingFolder = video | audio | photo). The screen says "saved" at once.
  3. In the background (useUploadRecordingToDrive): every part of the recording is sent to the storage through the Edge Function files-drive (scope recording): a session is opened, the bytes go in 5 MiB pieces straight to Google / Microsoft, the function finds and verifies the file and the database writes a file row.
  4. The post is updated: googleDriveURLToFile, mediaDriveFiles, mediaDriveState = uploaded. A message tells the user: "Saved to the file storage: media/video/<post guid>".

2. Where the files are

In the storage of the organization, under the folder kit8root the application made:

RecordingFolderFile name
Videokit8root/media/video<media post guid>.<ext>; a video cut in parts: <guid>-2.<ext>, <guid>-3.<ext> ...
Audiokit8root/media/audio
Photokit8root/media/photo

The folders carry the marks of the other file folders (kit8Kind = media / media-video ...). There is no files sub folder. The folder id is cached in files_folder_table (key recording:video).

Which storage: ONE for the whole organization, set in Organization edit -> Files (Google Drive or OneDrive). An organization that is not connected gets no upload: the recording stays on the device (see "When it fails").

3. What the media post stores

Key in rowJSONMeaning
recordingFoldervideo | audio | photo - set when the post is made; the database lets files be added to the post only with it, and only its author
mediaPostOrigin, mediaSegments[].urithe file of the device / browser (unchanged: the local copy stays)
googleDriveURLToFilethe address of the (first) file in the storage, e.g. https://drive.google.com/file/d/<id>/view (OneDrive: its web address - the key name is kept)
mediaDriveFiles[{ fileRowGUID, googleDriveURLToFile }], one per part, in the order of the parts
mediaDriveStateuploaded | failed (missing = not tried: an older post or a screen with no database)
mediaDriveErrorthe reason, when failed
Why two keys: a Google Drive page address needs a Google login, a <video> cannot play it and the users of the organization have no Google login. The player therefore asks the function for a link with fileRowGUID: the function signs a link that works for 10 minutes and streams the file (Range works, so seeking works). googleDriveURLToFile is the address for people and for "open in Drive".

The file rows (fileSourceKind = recording, parent = the post) are private to the author: no other member of the organization, not even the administrator, sees them or the organization file list. They are not cards in the Media Posts list.

4. Playing: which file is used

WhereFirstThen
Browser (web)the file in the storage (mediaDriveFiles)the copy of THIS browser (IndexedDB) when the storage cannot be reached
iPhone / Androidthe file of the device, if it existsthe file in the storage - when the file is gone (reinstall, a post made on another device) or the file does not play
Post with no file in the storageits own address, as before (a post made on a phone cannot be played in a browser: the message says so)

The rule is one pure function, resolvePlaySource (play/playSource.ts); MediaPlayer calls it and, when the player reports an error for the local file, tries the storage once before the user sees a red text. Used by the Media Posts list, the "Recording saved" window and every MediaPlayerModal given driveFiles.

5. The server side

SQL (start2_sql_code.sql, PART 49)

  • files_authorize: new scope recording; p_guid = the post; allowed only for its author and only with recordingFolder; answers the folder in idKind; files never move.
  • files_list: scope recording; the organization list hides these rows.
  • Policy mediaPost_select (two copies: PART 49 and PART 50): the rows are visible to their uploader only.
  • Delete: the trigger on the post (files_on_identification_post_delete, also for recordingFolder) deletes the file rows and queues the storage files for deletion.
  • No new table, no new column.

Edge Function files-drive

  • chainFor: media / <audio|video|photo>; scopeKeyFor: recording:<folder>.
  • upload_session: the file type must fit the folder (a photo = an image, a video = video/*, an audio = audio/* or webm / ogg); the name must start with the post guid.
  • Limits that already exist: 100 MB a file, the storage limit of the organization.
  • It must be redeployed (see UPDATE STEP-BY-STEP).

6. When the upload does not work

The recording is never lost: it is on the device first. The post gets mediaDriveState = failed + mediaDriveError and a message says why.

CauseWhat the user sees
The organization has no connected storage"... saved on this device but NOT uploaded: Google Drive is not connected."
A file above 100 MB (a long video)"The file is bigger than 100 MB."
The storage limit of the organizationthe limit message of the function
No network / the browser tab was closed during the uploadthe recording stays; no post update (state missing)
A video in parts: part 2 failsall or nothing: the parts that went are removed again
Important: a web recording that failed to upload exists only in that browser (IndexedDB). A phone recording that failed exists only on that phone - and a browser cannot play it ("This recording is a file on the phone that made it ...").

8. Not built (honest list)

  • Retry of a failed upload (no queue, no "Upload again" button, nothing at the next app start). A failed recording stays on the device.
  • Recordings made before this change are not uploaded; they play as before (their phone files cannot be played in a browser).
  • Files above 100 MB: phase 1 reads the whole file into memory (the same limit as the Files tab).
  • Photo cards still draw the local picture; a photo that exists only in the storage (made on another device) is not drawn in the list, and the browser does not draw the photo of a phone. The photo IS uploaded and its address is stored.
  • Upload progress is not shown (one message at the end).
  • The local copy is never deleted after the upload (web: IndexedDB keeps it as the fallback; phone: the file is the first choice).
  • Not seen on a real phone, in a real browser, or against a real Google Drive.
