The rules behind the fields

1 · One stamp, decided once

The class is NOT stored on the budget item (its activity already is the default: operating = OpEx, investing = CapEx, financing = Financing). It is decided on the plan line (default from the item, override with a reason), copied to each document line, and frozen on every register row at Post.

2 · Registers are pure

A line may be mixed (a capital share %), but a register row never is: Post writes two rows (capex part, opex part) in the same transaction. Every report then sums, filters and drills down without a rule.

3 · History does not move

A policy or budget item change never touches posted rows. Only an expenditure_reclassification document moves money: it appends a minus row and a plus row, with a reason and a user. The register stays append-only.

4 · Real column or rowJSON

The existing pattern decides: the register and document tables have real columns (indexed, grouped, CHECKed); the catalog and plan-line tables keep their fields in rowJSON (task_line_table, the generic catalogs, project_table, organizationTable). A rowJSON key must also go into the normalizer of its form.

5 · Money is never added by a new column

A new money column goes through the VAT basis (kit8/pm/vat) and, for movements, has its consolidation twin by the list of PART 52. The VAT that is cost (recoverable share) stays what makes the capital cost: net + VAT that is cost.

6 · Names

New tables follow KNOW_HOW section 2.2: xxx_catalog (справочник), xxx_table (non-periodic information register), xxx_history (append-only / periodic), documents _header / _lines. Columns are camelCase quoted, like the neighbours.

Only the new (+) and changed (~) fields are drawn; the full field tables are further down. Read top to bottom: the key and the budget item give the default, the plan line decides, the document lines copy, Post freezes it in the registers, the worker carries it into the reports.

Constraints and guards the fields need

  • CHECK on every register / document column: expenditureClass IN ('capex','opex','financing') (registers) and ... 'mixed' (lines and plan); capitalSharePercent NOT NULL and strictly between 0 and 100 exactly when class = mixed.
  • Purpose follows class: capex → growth | sustaining | regulatory, opex → run | change, financing → empty (trigger; a CHECK across the JSON key and the item key is not possible).
  • Override needs a reason (CHECK on the task line, CASE WHEN jsonb_typeof style).
  • Registers are append-only for the class: a BEFORE UPDATE trigger refuses a change of expenditureClass (like partner_balance_movements_no_update); the reclassification passes with a flag that only its Post sets, as app.consolidation_apply does.
  • Freeze of document lines: the trigger that today allows only qty / price / VAT % also allows class / share / request while the header is a draft.
  • Capitalised own labour only on a development / construction stage with the criteria date reached, and only while capitaliseOwnLabour is on (time sheet Post guard).
  • Read-only project (PART 51): every new project-data table gets a row in one of the two DO lists; the new RPCs that only write derived rows call project_readonly_check.
  • Permissions (PARTs 46 - 47): every new table is a row of permission_matrix.py, every write RPC calls perm_can_in / perm_require (Docker test 53 lists the ones that do not).
  • Consolidation twin: asset_movements is added to the three lists of PART 52 (consolidation_apply, _rebuild, _verify).
  • Delete file: every new table is dropped in delete_sql_structure.sql (numbered part, reverse order).

Decisions for the data model (recommended default in each)

#QuestionRecommended default
Q-ER1Where is a mixed line split?At Post, into two pure register rows. The line stays one (what the user typed, what the invoice shows). Alternative: split at entry into two lines - rejected, it breaks the one-to-one of invoice line and vendor document.
Q-ER2Class on the header or on the lines?On the lines. A header class would force one class per document; one invoice routinely has a machine and its service.
Q-ER3Class stored on the budget item?No. The activity of the existing key is the class; a second stored value could disagree with it. A function derives it.
Q-ER4Class in the key of the aggregates, or parallel columns?In the key. Parallel columns (qtyPlanCapex, ...) would double 20 columns in the turnover and 16 in the month totals; the key change costs one rebuild and the verifiers prove it.
Q-ER5Is the IAS 7 activity of cash stored?No, derived (capex = investing, opex = operating, financing = financing). One more stored value would be one more thing to reclassify.
Q-ER6Class on a paymentCopied from the source line (plan line / invoice line); the payment budget item of the Payments genus is NOT the class.
Q-ER7Revenue in the class reportsExcluded: the class filter applies to the cost side; the Revenue register rows keep opex by convention and the screens say so.
Q-ER8Project-side asset register or ERPProject side only (WBS Q3). asset_catalog is a project asset; the statutory register stays in the ERP.
