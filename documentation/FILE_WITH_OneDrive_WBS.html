W2 File attachments on Microsoft OneDrive – Work Breakdown Structure (v4)

The file attachments (documentation/FILE_ATTACHMENT_WBS.html, built on Google Drive, way C) get a SECOND storage: Microsoft OneDrive (personal accounts and work / school accounts), through Microsoft Graph. A project chooses where ITS files live with one new setting, projectFilesStorageProvider. Everything above the storage stays as it is: the Files tab, the permissions, the viewer, the database rows, the delete rules, the Edge Function files-drive (its actions, its signed links, its cleanup queue).

Status: PLAN ONLY – no code (2026-11-11). v4: OD1-OD6 are BUILT (2026-11-11); OD7 (the live test) waits for the SQL on the owner's database and the Web redirect uri. v3: the spike OD0 was RUN on a personal account (2026-11-11): CORS passes, the browser uploads straight to OneDrive, folder permanentDelete works in one call – see documentation/OneDrive/ONEDRIVE_HOW_IT_WORKS.html; sections 3.7, 3.13, 3A, 4, 9, 10 are updated. v2: the owner accepted all recommended answers (section 14 = decisions) and the open facts were investigated (section 3A = investigation log). Facts from Microsoft's documentation are marked with their source (section 15); what is NOT proven on a real account is listed as the spike OD0 (section 10) – the same way the Google plan started. Items marked verify are still unproven on a real account (the spike).

About "Sign in with Microsoft is ready". The repository has no Microsoft sign-in code today (searched kit8, app, supabase, package.json: only the MS Project XML export mentions Microsoft). I read your sentence as: the Microsoft Entra app registration exists. Sign-in of USERS and the connection of the STORAGE are two different OAuth flows (section 5), so the plan lists exactly what I need from that registration (section 5.2).

1.1 What happens when the choice changes

  • Every file row remembers its storage (rowJSON.fileStorageProvider). View, Replace, Move, Delete and the cleanup of an OLD file always use the provider OF THE ROW, never the current setting of the project.
  • New uploads go to the provider chosen NOW. A project can therefore hold files of both storages for a while; the Files tab shows a small badge (Google Drive / OneDrive) on a row only while the project holds both.
  • On a change, when the project already has files, a window asks: "N files stay in Google Drive. New files will be stored in Microsoft OneDrive." (Cancel / Change). No file is moved. A tool "Move all files to the other storage" is NOT part of this plan Q1 decided.
  • If the new provider is not connected yet, the choice is saved, the tab shows "Connect Microsoft OneDrive to add files" and Add is disabled – the same words and behaviour as for an unconnected Google Drive today.
  • Files with no project (the organization's files and the document files) use the ORGANIZATION default of the same key Q2 decided.
  • The right to change the setting is the right to change Project settings (project manager); the right to CONNECT a storage is projectFileManager (administrator + project manager by default) – unchanged.

2. Architecture – one function, two storage adapters

Way C stays: the administrator signs in to the storage ONCE; the Edge Function files-drive keeps the encrypted refresh token, refreshes the access token by itself, checks the permission (files_authorize) and does every storage call. Members never see a Microsoft (or Google) screen. The app never holds a storage token.

2.1 The provider interface (inside supabase/functions/files-drive)

The handler already talks to a small object (createDrive). It is made explicit as StorageProvider and the handler asks providerFor(row | project) for it:

interface StorageProvider {
  id: 'googleDrive' | 'oneDrive';
  authUrl(state, redirectUri): string;                 // consent
  exchangeCode(code, redirectUri): Tokens;             // code -> refresh + access (+ account email)
  refresh(refreshToken): Tokens;                       // OneDrive: returns a NEW refresh token every time
  revoke(token): void;                                 // best effort
  findOrCreateRoot(token, org): Item;                  // kit8root
  ensureFolderChain(token, rootId, chain): Item[];     // organization/project/task/... /files
  openUploadSession(token, folder, name, mime, size, origin): { sessionUrl, ... };
  openUpdateSession(token, itemId, ...): { sessionUrl };       // replace = a new version
  getItem(token, id) / listChildren(token, folderId);
  openMedia(token, id, range): Response;               // streamed to the browser
  moveItem(token, id, newParentId);
  deleteItem(token, id);                               // permanent (see 3.7)
  versions(token, id) / keepVersion(token, id, v);
  quota(token): { used, total };                       // S8 storage line
}

The Google adapter is the present code moved behind the interface with NO change of behaviour (its Jest tests stay green). The OneDrive adapter is new. The handler's actions keep their names (connect_start, status, upload_session, upload_finish, download_url, delete_file, cleanup, disconnect, replace_session / _finish, move, health …); the body gets an optional provider (default: the project's, resolved by the database through files_authorize, which now also returns it).

2.2 What does not change

  • The Files tab, the panel, the viewer route /files/view, the permissions projectFileManager / projectMediaPostManager, the row rules of mediaPostTable, the cleanup queue and its pg_cron tick, the signed download links (HMAC) and Range streaming.
  • Upload still goes straight from the app to the storage (resumable session); the bytes do not pass the function (fallback in 10, check 1).

3. Microsoft facts the plan relies on

From Microsoft Learn (links in section 15). Everything marked verify is a claim I could not confirm from the documentation and is a step of the spike OD0.

#TopicFact
3.1EndpointsMicrosoft identity platform v2: authorize and token at https://login.microsoftonline.com/{tenant}/oauth2/v2.0/…; {tenant} = common (personal + work/school), organizations, consumers or one directory id. Files API: https://graph.microsoft.com/v1.0/me/drive/… (OneDrive of the signed-in user).
3.2Permission (scope)Delegated Files.ReadWrite is the least privileged permission for upload sessions, delete and (with Files.Read being enough for download) works for BOTH a personal Microsoft account and a work / school account. Plus offline_access (to get a refresh token) and User.Read (the account's e-mail / name). No admin consent is required for Files.ReadWrite (OneDrive permission reference); only a tenant policy or the publisher rule (3.17) can still require an administrator. Careful: on a PERSONAL account Files.ReadWrite also grants access to files shared with the signed-in user – the app must never browse outside kit8root.
3.3No "only my files" scopeGoogle's drive.file sees only the files the app made. Microsoft has no equivalent for a user's drive: Files.ReadWrite can reach the WHOLE OneDrive of that account. Files.ReadWrite.AppFolder limits the app to its own folder Apps/<app name> but is valid for personal accounts only (not OneDrive for Business / SharePoint) and is still labelled preview in Microsoft's reference. See section 4 for what we do about it.
3.4Refresh tokenDefault lifetime 90 days (24 hours only for a single-page app redirect URI – ours is a server redirect, so 90). A refresh token replaces itself on every use: the answer of the token endpoint carries a NEW refresh token, which must be stored (Google's does not rotate). It can be revoked at any time: the user revokes it, an admin revokes all tokens, an admin resets the password (for confidential clients too). → state needsReconnect exactly like Google's invalid_grant.
3.5Upload sessionPOST /me/drive/items/{parentId}:/{name}:/createUploadSession (body: item.@microsoft.graph.conflictBehavior fail | replace | rename, optional deferCommit) → uploadUrl (pre-authenticated). Fragments by PUT with Content-Range, in order. Each fragment must be a multiple of 320 KiB (327 680 bytes), under 60 MiB; 5–10 MiB recommended. Answer 202 + nextExpectedRanges while more is expected, 200 / 201 + the driveItem at the end. Do NOT send an Authorization header to the uploadUrl (it can cause 401). GET on the uploadUrl = which ranges are missing (resume); DELETE = cancel; a session expires after inactivity (every fragment extends it); a lost session = 404 = start again. A name conflict at the end = 409 nameAlreadyExists. Use sessions above 10 MiB (below that a plain PUT would do; we always use sessions: one code path).
3.6DownloadGET …/content answers 302 to a pre-authenticated, short-lived (minutes) URL (= the property @microsoft.graph.downloadUrl); no Authorization header on it; Range works on that URL (206), not on /content. Our function reads ?select=@microsoft.graph.downloadUrl for EVERY view request (never cached) and streams it with the browser's Range – so the signed-link model of the Files tab is unchanged.
3.7DeleteDELETE /me/drive/items/{id} moves to the recycle bin (204), it is NOT permanent. Permanent delete exists in v1.0: POST /drives/{driveId}/items/{itemId}/permanentDelete, no body, 204, "permanently removed, not sent to the recycle bin, cannot be restored"; permission delegated Files.ReadWrite for BOTH account types. (Needs the driveId: kept in the connection row.) Spike: it deletes a FOLDER with content in one call (204, then 404) on a personal account, so the OneDrive adapter needs no bottom-up order; work accounts still to be confirmed.
3.8VersionsOneDrive keeps version history itself: a new upload session on an EXISTING item id makes a new version; GET /items/{id}/versions lists them. How many are kept: work / school accounts – default 500 major versions, never expiring (the organization setting for NEW libraries / OneDrive accounts; an administrator can change it). Personal accounts – no current figure in Microsoft's documentation (old forum answers say 25 versions or 30 days) verify. So "an old version is kept forever" can be promised for work accounts only; the Replace window says so. (Google needed keepForever.)
3.9No custom propertiesA driveItem has no free key / value bag like Google's properties (description exists for personal accounts only). The "is this file ours" mark is therefore NOT on the file: the database holds every item id and every id the function uses comes from a database row (never from the client); a check compares the item's parentReference.id with the folder the database recorded.
3.10Names and pathsID addressing is stable (an item's id survives rename and move) – every stored reference is an id; a path is used only to find kit8root and its first folders, and each path segment is percent-encoded. Reserved characters in names: / \ * < > ? : |, and for OneDrive for Business also # and %; a folder name cannot end with .; a business name cannot begin with ~. Rule for the adapter: each of these (and a leading ~, a trailing .) becomes _ in the NAME on OneDrive; the real title stays in the database row. The planned paths are about 150 characters (the exact path limit per account type is not in the pages read verify).
3.11QuotaGET /me/drive → quota { total, used, remaining, state } (personal free tier is small, a work account usually has 1 TB). The storage line (S8) shows it and the upload refuses when remaining is smaller than the file.
3.12ThrottlingGraph answers 429 Too Many Requests with a Retry-After header (seconds). Microsoft: wait exactly that long, never retry at once (every request counts against the limit), repeat until it succeeds; no header = exponential back-off; writes are throttled earlier than reads. The adapter waits Retry-After (bounded by the function's time budget, 3.14), then answers the app "try again"; the cleanup queue retries later. No polling loops (the health check reads folders only on request).
3.13CORS of the upload URLResolved by the spike (personal account): the preflight for PUT with Content-Range to my.microsoftpersonalcontent.com passes, the 202 answer and the final 201 driveItem are readable by the browser. A work / school account uses another upload host (SharePoint) and is still to be checked verify (work). So the browser uploads straight to OneDrive; the fallback through the function is kept only for a work tenant that fails.
3.14Limits of the Supabase function256 MB memory, 400 s wall clock on paid plans (150 s free), 2 s CPU per request (waiting for I/O is not counted), 150 s idle timeout, function size 20 MB (CLI bundle). A maximum request body size is not documented verify. Consequences: streaming a download is fine (the body is piped, never held); the fallback "fragment through the function" must keep fragments small (5 MiB fits the memory) and its body limit is measured in the spike; a 100 MB file through the function takes minutes, still under 400 s.
3.15When the account goes awayWork account: a deleted user's OneDrive is kept 30 days by default (an administrator can set 30–3650), then 93 days in a "deleted" state that only a global / SharePoint administrator can restore. And a NEW Microsoft rule (message MC1381110, in force from July 2026): the OneDrive of an unlicensed account becomes read-only after 60 days, is archived after 93 days (users cannot reach it) and may be deleted after about 365 unlicensed days; a licence or pay-as-you-go billing stops it. So a service account must keep a licence that includes OneDrive. A personal Microsoft account has none of this.
3.16Client secret lifetimeThe admin center allows at most 24 months; Microsoft recommends less than 12. The plan: 12 months, the expiry date written into the status of the function (warning 30 days before) and into the connection note.
3.17Publisher verification / consent in OTHER tenantsSince November 2020, where risk-based step-up consent is on, users of a tenant other than the app's home tenant cannot consent to a multi-tenant app that is NOT publisher verified and asks for more than basic sign-in (our Files.ReadWrite is more) – they see a warning and an administrator of that tenant must approve once. Personal accounts and the owner's own tenant are not affected. Verification is free but needs a verified Microsoft AI Cloud Partner Program account, an app registered with a WORK / SCHOOL account (an app registered with a personal Microsoft account cannot be verified) and a publisher domain that is not *.onmicrosoft.com. Plan: not needed for the first release; documented for customers' administrators.

5. Connection and "Sign in with Microsoft"

5.1 Two different flows

  • Sign in of users (Supabase Auth with the Azure / Microsoft provider, or another way): proves WHO a person is. It gives the app no durable access to anyone's OneDrive, and a user who signs in with Microsoft does not thereby connect a storage.
  • Storage connection (this plan): the administrator presses "Connect Microsoft OneDrive" in Project settings → Files, is sent to the consent page, comes back to /user/files?filesConnect=ok (the route built for Google), the function stores the encrypted refresh token. Exactly the Google flow; only the endpoints and the scope differ.

7. Data and SQL (a new PART 50, written when the spike is green)

Rule of the owner (2026-11-02): new tables are snake_case files_…; old tables are not renamed. Nothing below changes a Google row.

The helper fileItemIdOf(row) hides the difference from the app and the function.

  • Upload pending (files_upload_pending_table): provider + the folder id + name for the "one open upload per folder and name" rule of the finish step.
  • Organization row keys, next to the organizationGoogleDrive… ones: organizationOneDriveState, …AccountEmail, …RootFolderUrl, …LastRefreshAt, …RootFolderId.
  • Functions (start2, PART 50, same names, REPLACED copies where a function exists): files_authorize returns the provider of the scope (project setting → organization default); files_add / _update / _move / _replace accept and keep fileStorageProvider; files_org_facts / files_connection_status take a provider; files_folder_get / _set, files_cleanup_*, files_upload_pending_* carry it; files_health_rows lists files per provider; a trigger refuses a change of fileStorageProvider of an existing file row (a file does not change storage by an update).
  • Seeds / permissions: the permission matrix needs the new table (permission_matrix.py → the seed is regenerated: the count of tables goes up by one; the two Jest / Docker tests that count tables are updated in the same round). No new profile.
  • start3 (pg_cron): one more job files_provider_keepalive (daily) that asks the function to refresh the OneDrive token (section 4) – only when the OneDrive table has a row.
  • delete_sql_structure.sql: drops the new table, the new job and the new functions.
The Docker tests 55 / 56 / 57 stay as they are (Google); a new 58_files_onedrive.sql repeats the provider-neutral checks for a OneDrive project (rows, folders, cleanup, permissions, the provider trigger).

10. Spike OD0 – what is checked (no product code) – RUN 2026-11-11, results in documentation/OneDrive/ONEDRIVE_HOW_IT_WORKS.html

Run on a personal account: checks 1, 2, 4 (personal), 5 (file and folder permanentDelete), 6, 7, 8, 9 are done; 3 only partly (SPA flow); 10 (disconnect screens), 11 (shared files) are manual; everything for a work / school account, the 90-day sliding token and the 100 MB stream through the function are still open (OD7).

A script and a small HTML page like documentation/Goolge/f0/, run with your Microsoft account in the browser (you sign in and consent; I never type passwords). Tokens are never written to a file and are revoked at the end.

  1. CORS of the upload URL (decides the design): create a session, PUT a fragment from a page served at http://localhost:8088 with Content-Range; does the preflight pass? Can the browser read the answer (202 / 201 body)? Fallback if not: the app sends each fragment to the function and the function forwards it – then MEASURE the function's request body limit (not documented) with 1, 5, 10 and 20 MiB; if 5 MiB is refused a smaller common chunk is needed for both providers (the common multiple of 256 KiB and 320 KiB is 1280 KiB, e.g. 2.5 MiB).
  2. Fragment rules: 5 MiB fragments, last fragment shorter, wrong order refused, resume with GET on the uploadUrl, the effect of an Authorization header on the PUT.
  3. Refresh token rotation: use it twice; does the old one still work for a while? Is the 90 days window sliding (use after 1 day → new 90 days)? Personal vs work account.
  4. Scopes: does Files.ReadWrite consent work for a personal account and for a work account without an administrator? What does the tenant's "user consent" policy do for an unverified multi-tenant app?
  5. Delete: permanentDelete of a file on a personal and on a work account (documented: 204; confirm the recycle bin stays empty); of a FOLDER with content (one call or bottom-up?); plain DELETE for comparison.
  6. Download: @microsoft.graph.downloadUrl lifetime, Range 206, content type of an image / pdf / md as returned, streaming 100 MB through the function (memory, time limit – the same F0b item 2 as Google).
  7. Versions: update session on an item id → /versions list; the number kept on a PERSONAL account (work: 500 by default, 3.8).
  8. Names: a file name with spaces, accents, #, %, a leading ~, 120 characters; a path of 150 and of 400 characters (find the limit); the conflictBehavior=fail answer; the sanitising rule of 3.10.
  9. Quota answer on both account types; 429 behaviour is read from the documentation only (not provoked).
  10. Disconnect: how the administrator removes the app's access (personal, work); what the old refresh token does afterwards.
  11. Sharing: with a personal account, confirm that the app never lists anything outside kit8root (a test file shared WITH the account must not appear in any function answer).

12. Acceptance criteria

  1. Project settings → Files shows the radio 1. Google Drive / 2. Microsoft OneDrive; it is disabled while filesFunctionalityEnabled is off and enabled when it is on; a project saved before this feature shows Google Drive selected.
  2. With OneDrive chosen and connected, Add file stores the file in kit8root/…/files of the connected Microsoft account; View shows image / pdf / text / audio / video in the browser (never a download); Download is a button.
  3. Replace makes a new OneDrive version; Versions lists them; Move changes the folder; Delete removes the file permanently (or says before that it cannot).
  4. A project on Google and a project on OneDrive work side by side in one organization; after a provider change the OLD files still open, replace and delete with THEIR provider.
  5. Disconnect then Connect again works and ends on "Microsoft OneDrive is connected"; a revoked token shows "Reconnect Microsoft OneDrive" and nothing else breaks.
  6. Every existing Google test passes unchanged except the chunk size; the new OneDrive suite and Docker test 58 pass; KNOW_HOW and the READMEs are updated in the same round.
