Resource Leveling – Work Breakdown Structure

Scope: the MS Project command Resource > Level (item A16 of MORE_GANTT_INPUT.html, “not built”) for the Gantt chart of kit8/pm. Source: the Google Doc “W1 Resource Leveling”. Planning document – no code, nothing in the repository was changed. Russian translation: RESOURCE_LEVELING_WBS_RU.html.

1. Goal

A resource (a person, an equipment, a partner – in the app: a work center) can be booked for more hours on a day than its calendar allows. Today the app only reports this (the busy check at Post, capacityModeWarn / capacityModeBlock) – nothing is moved. Resource leveling moves (delays) or splits the tasks of the project, by priority and slack, until no resource is over-allocated – or tells exactly why a conflict cannot be removed.

The project owner chooses in the project settings whether leveling is Automatic (the plan is leveled after every edit) or Manual (the planner presses Level now and sees a preview first), and a Fast mode makes the in-line, on-screen user actions (drag a bar, edit an hour, fix one conflict) answer at once.

Hard constraint: everything is off while resourceLevelingFunctionalityEnabled was never saved. With it off the scheduler, the Gantt chart, Post, the busy check, the exports and every screen work exactly as today; no new button, column or banner is shown and no stored data changes.

7.2 The model: demand, capacity, foreign load

  • Resource key = kind + GUID (person, equipment, workCenter) – the same key as resource_occupancy_x_movement. A partner work center is a resource too.
  • Demand D[resource][day] = the sum over the Time lines of the project’s tasks (in the hours unit) of hours × coefficient(day), where the coefficients are those of calculateTaskLinePlan (distribution over the active days of the calendar between the task start and finish). Computed from the lines, so unposted lines count. A line in days or pieces is ignored (as in the occupancy view).
  • Capacity C[resource][day] from SQL (organization_resource_capacity); null = unknown.
  • Foreign load F[resource][day] = posted hours of the other projects of the organization (the occupancy view without this project). Fixed.
  • Over-allocation = D + F > C (strictly); with grain week: the sums of the week. Unknown capacity = a conflict that cannot be solved by moving a task within the known days.
  • Horizon: the last day for which the calendar has rows (a delay never goes beyond it: noCapacityInHorizon).

7.3 The leveling algorithm (concept, no code)

1. S0 = scheduleProject(plan with every leveling delay cleared) the unleveled plan 2. D = demand(S0), C, F 7.2 3. for each day t ascending, for each resource r with D[r][t] + F[r][t] > C[r][t]: contenders = tasks active on t that use r fixed = frozen / priority 1000 / constraint-honored / manual (unless allowed) / out of scope keep tasks (fixed first, then by the leveling order) while the hours fit; the rest "yield" the first yielding task X is delayed to the first working day where all its resources fit (or, if it may split: a gap is inserted at t and it continues when r has room) limit: total slack (option within slack only), the horizon if X cannot be moved: record the unresolved conflict with its reason code 4. S1 = scheduleProject(plan with the new delays) successors, stages, critical path, finish follow 5. repeat from 2 for the changed resources and days only, until no new move is made (each move increases a delay or adds a gap: it ends; a safety counter stops a run and reports it) 6. result = per task: delay, splits, reason; per resource: conflicts before / after; project finish before / after

Leveling order (which task yields first in a conflict): idOnly – the task with the higher row number; standard – more total slack first, then the later early start, then the higher row number; priorityStandard – the lower priority first, then the standard order. Priority 1000 never yields. Deterministic: the same plan gives the same result.

Frozen (not moved, but still load): posted task (unless resourceLevelingMovePostedTasks), progress > 0, start before today, finished, inactive, milestone, stage (summary), subproject origin task, a task with a constraint Must Start On / Must Finish On or with “always honor” constraints, a manual task (unless resourceLevelingManualTasks), priority 1000, a task out of the run scope.

Not done on purpose: the engine never changes hours, units, task type, resources of the lines or the duration. It only delays or splits.

7.4 Where the result lives

  • On the task (project_task_table.rowJSON): taskLevelingDelayDays (number ≥ 0, absent = 0) and taskLevelingCanSplit (boolean, default true; priority is the existing taskPriority). Splits made by leveling are written into the existing taskSplits with a mark so that “Clear leveling” removes only them (taskSplitsByLeveling).
  • The scheduler reads the delay like a lag: start = max(start from the links, constraints) + delay in the calendar of the task (a manual task: only when allowed). The signature of A2 (calcSignature.ts) includes it, so Calculation Manual sees a changed delay as a pending edit.
  • History: tables of section 8.

7.6 Fast mode (R11) – reading to confirm (Q2)

“Most online and in-line user action patterns needed” is read as: the leveling answers the actions of the user on the screen, at once, without a dialog and without waiting for the server. Switch resourceLevelingFunctionalityFastModeEnabled (needs the master). What it changes:

PatternNormal modeFast mode
EngineFull run over the scope; iterates until no move is left; report.Incremental: only the resources and the days that the edit changed; a single greedy pass from the changed day forward; the full run stays available as a button.
Drag a bar / change a durationOver-allocation is shown after the drop.While dragging, the ghost over-allocation of the touched resources is drawn live (indicator 006, graph 009); on drop the leveling result of the neighbors is shown at once.

Fast mode works in both Manual and Automatic mode; in Manual mode it only gives the live indicator and the in-line fixes (nothing is moved without a click).

7.7 Posting and facts

  • A moved date unposts the lines and payments of that task (existing triggers). Therefore Automatic mode never moves a posted task; Manual mode with resourceLevelingMovePostedTasks lists the tasks that will be unposted in the preview and asks.
  • Tasks with a posted fact input / invoice (the register has used / invoiced rows) are frozen whatever the switch says.
  • After a run the planner presses Post unposted tasks (project Actions) as after any date change; the preview and the toast say so. The cost totals and Monitor01 follow the usual path. A move changes the rate and exchange rate of the days (contracts and rates are by date): the sums of the Time lines may change; the user presses Recalculate as after any date change.
  • At Post the busy check (capacityModeWarn / Block) stays as it is.

13. Acceptance criteria

  1. With the master off, a Jest run of the scheduler on golden plans gives byte-identical results; no new element is rendered; no new request is made.
  2. A plan with two tasks that need one person for 8 h each on the same day (capacity 8 h) is leveled by delaying the lower-priority task by one working day; after it the busy check returns no rows.
  3. Priority 1000 and frozen tasks are never moved; the conflict is listed with its reason code.
  4. “Within slack only” never changes the project finish; the remainder is unresolved.
  5. Successors of a delayed task move; the critical path and the stage roll-up are recalculated by the scheduler.
  6. With splits on, a long task is interrupted instead of moved when this solves the conflict with a smaller finish delay.
  7. Manual mode: nothing changes before Apply; Cancel changes nothing; Apply is one transaction and one Undo step.
  8. Automatic mode: an edit that creates a conflict is leveled after the debounce; no loop; posted tasks are not moved.
  9. Clear leveling returns the dates of the unleveled plan; Undo of a run restores the values before that run.
  10. Another project’s posted booking of the same work center is respected and is not moved.
  11. A day without a calendar row is reported, never leveled over.
  12. Fast mode: the numbers of 7.6 are met on 2 000 tasks (bench).
  13. MS Project export contains LevelingDelay, LevelingCanSplit, Priority only while the function is on; import restores them.
  14. All new texts exist in the 14 dictionaries; Arabic and Farsi windows are mirrored without overlaps.
  15. The Jest baseline shows no new failing suite; the Docker scripts pass; test_sql.sh still passes (install twice, delete leaves nothing).

15. Out of scope (this version)
