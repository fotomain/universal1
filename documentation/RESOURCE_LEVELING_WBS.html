Resource Optimization (leveling and smoothing) – Work Breakdown Structure

Scope: resource optimization in the PMBOK sense (the techniques resource leveling and resource smoothing), built so that every MS Project term still works (Resource > Level, the Level Resources dialog, Leveling Delay – item A16 of MORE_GANTT_INPUT.html, “not built”) for the Gantt chart of kit8/pm. Source: the Google Doc “W1 Resource Leveling” and the owner’s answers of 2026-10-27 (section 18). Planning document – no code (the design; the build follows it, see section 19). Revised 2026-10-27, second round of answers the same day. Russian translation: RESOURCE_LEVELING_WBS_RU.html.

1. Goal

A resource (a person, an equipment, a partner – in the app: a work center) can be booked for more hours on a day than its calendar allows. Today the app only reports this (the busy check at Post, capacityModeWarn / capacityModeBlock) – nothing is moved. Resource optimization moves (delays) or splits the tasks of the project, by priority and slack, until no resource is over-allocated – or tells exactly why a conflict cannot be removed. It has two methods (PMBOK):

  • Leveling – dates may move beyond the slack; the critical path and the project finish may change. = MS Project “Level now”.
  • Smoothing – only the slack is used; the critical path and the project finish do not change; a conflict that needs more stays and is reported. = MS Project “Level only within available slack”.

The project owner chooses Automatic (the plan is optimized after every edit) or Manual (the planner presses Level now and sees a preview first). A Fast mode adds on-screen, in-place options to change the data (drag, edit hours, fix one conflict with one click) in the form that is the most comfortable for the user.

Hard constraint: everything is off while resourceLevelingFunctionalityEnabled was never saved. With it off the scheduler, the Gantt chart, Post, the busy check and every screen work exactly as today; no new button, column or banner is shown and no stored data changes.

7.2 The model: demand, capacity, foreign load

  • Resource key = kind + GUID (person, equipment, workCenter) – as in resource_occupancy_x_movement. A partner work center is a resource too.
  • Demand D[resource][day] = the sum over the Time lines (hours unit) of hours × coefficient(day), with the coefficients of calculateTaskLinePlan (distribution over the active days of the calendar between the task start and finish). Calculated from the lines: unposted lines count. Lines in days or pieces are ignored.
  • Capacity C[resource][day] from SQL (organization_resource_capacity, hours); null = unknown.
  • Foreign load F[resource][day] = posted hours of the other projects of the organization. Fixed.
  • Over-allocation = D + F > C (strictly), in the period of resourceGrainUnit (7.9). Unknown capacity = a conflict that moving cannot solve inside the known days.
  • Horizon: the last day for which the calendar has rows (noCapacityInHorizon).

7.3 The algorithm (concept, no code)

1. S0 = scheduleProject(plan with every leveling delay cleared) the unleveled plan 2. D = demand(S0), C, F 7.2 3. for each period t ascending, for each resource r with D[r][t] + F[r][t] > C[r][t]: contenders = tasks active in t that use r fixed = frozen / priority 1000 / constraint-honored / manual (unless allowed) / out of scope keep tasks (fixed first, then by the leveling order) while the hours fit; the rest "yield" the first yielding task X is delayed to the first working day where all its resources fit (or, if it may split: a gap is inserted at t and it continues when r has room) limit: total slack (Method Smoothing), the horizon if X cannot be moved: record the unresolved conflict with its reason code 4. S1 = scheduleProject(plan with the new delays) successors, stages, critical path, finish follow 5. repeat from 2 for the changed resources and days only, until no new move is made (each move increases a delay or adds a gap: it ends; a safety counter stops a run and reports it) 6. result = per task: delay, splits, reason; per resource: conflicts before / after; project finish before / after

Leveling order: idOnly – the task with the higher row number yields; standard – more total slack first, then the later early start, then the higher row number; priorityStandard – the lower priority first, then standard. Priority 1000 never yields. Deterministic: the same plan gives the same result.

Frozen (not moved, but still load): progress > 0, start before today, finished, a posted fact input (used hours), a posted payment fact on its payment plan, inactive, milestone, stage, subproject origin task, Must Start On / Must Finish On or “always honor” constraints, a manual task (unless resourceLevelingManualTasks), priority 1000, a task out of the run scope; and a posted task unless the user chose to move it (7.7).

Not done on purpose: the engine never changes hours, units, task type, the resources of the lines or the duration. It only delays or splits. (The user may change them in place in Fast mode, 7.6.)

7.4 Where the result lives

  • On the task (project_task_table.rowJSON): taskLevelingDelayDays (≥ 0, working days; absent = 0) and taskLevelingCanSplit (default true; priority = taskPriority). Splits made by leveling go into taskSplits with a mark (taskSplitsByLeveling) so Clear leveling removes only them.
  • The scheduler reads the delay like a lag: start = max(links, constraints) + delay in the calendar of the task. The A2 signature (calcSignature.ts) includes it.
  • History: section 8.

7.7 Posting and facts – a posted task never loses its posting silently

  • A moved start / finish day unposts the lines and payments of that task (existing triggers). Therefore the optimization never moves a posted task without asking. When a run needs to move posted tasks, PMResourceLevelingPostedTasksDialog lists them and offers three choices:
    1. Unpost and move – the listed tasks are unposted (lines and payments) and moved; they stay unposted until Post (the item “Post unposted tasks” of the project Actions is offered in the result).
    2. Move and post again – the tasks are moved and posted again by the app in the same step with the normal Post (calculation, busy check). Only if the new plan posts without conflicts: a task that cannot be posted cleanly is not moved, and the result says why. Nothing is left half done.
    3. Keep their dates – the posted tasks are not moved; they stay as load and the conflict they cause is listed as unresolved with the code frozenPosted.
  • resourceLevelingPostedTasksAction = ask (default) asks every time; unpostAndMove / moveAndPostAgain / keep apply a remembered answer (named in the result). resourceLevelingPostedTasksMovementEnabled = false is the same as keep.
  • Automatic mode asks without interrupting: it moves only the unposted tasks, leaves the posted ones where they are, and the status chip shows “N posted tasks wait for your decision”; a click opens the dialog.
  • Never moved whatever the answer: tasks that have started, finished tasks, tasks with a posted fact input, tasks whose payment plan has a posted payment fact (an unposted plan under a posted fact would break the Paid / Open of the payment plan – checked in WP1.3).
  • Undo of a run restores the dates; the question is asked again for the tasks that were posted again.
  • Moving dates changes the contract rate and the exchange rate of the days: the sums of Time lines may change; the user presses Recalculate as after any date change.
  • At Post the busy check stays as it is.

7.9 The grain: resourceGrainUnit = hour by default (R13)

The option has three values: hour (default), day, week. It sets (a) the unit of every amount and axis of the resource screens and (b) the period in which load is compared with capacity.

ValueUnit shownPeriod compared (v1, today’s data)
hour (default)hours (0.25 step), e.g. “11 h on 12 Mar, capacity 8 h”one working day – the finest period the plan has
dayresource-days (hours ÷ the capacity hours of that day)one working day
weekhours (or days)the sum of the week against the weekly capacity (a lighter check, as MS Project “week by week”)
Limit, stated openly. In the dayByDayModel (the app as it is) the plan has no time of day: the resource calendar gives hours per day (no from / to, no breaks), Post writes one row per line and day, the scheduler counts working days. Therefore there the values hour and day find the same conflicts (they differ in the unit shown). True hour-by-hour optimization is the hourByHourModel (section 7.10, phase 2): the owner decided “yes, it needs a time-of-day model”, selected by resourceOptimizationMode.

13. Acceptance criteria

  1. Master off: scheduler golden plans byte-identical; no new element; no new request.
  2. Two tasks need one person 8 h each on the same day (capacity 8 h): Leveling delays the lower-priority task by one working day; afterwards the busy check returns no rows.
  3. Priority 1000 and frozen tasks never move; the conflict is listed with its reason.
  4. Method Smoothing never changes the project finish; the rest is unresolved.
  5. Successors of a delayed task move; critical path and stage roll-up are recalculated by the scheduler.
  6. With splits on, a long task is interrupted instead of moved when this gives a smaller finish delay.
  7. Manual: nothing changes before Apply; Cancel changes nothing; Apply = one transaction, one Undo step.
  8. Automatic: an edit that creates a conflict is optimized after the debounce; no loop; posted tasks are left and the chip says how many wait for a decision; Undo restores the dates.
  9. A posted task is never unposted silently: the dialog offers Unpost and move / Move and post again / Keep; “Move and post again” moves a task only if it posts without conflicts; with the option off or “Keep” the task is frozen and still load. A task with a posted fact input is never moved.
  10. Clear leveling returns the unleveled dates; Undo of a run restores the values before it.
  11. A posted booking of the same work center in another project is respected and not moved.
  12. A day without a calendar row is reported, never optimized over.
  13. resourceGrainUnit defaults to hour; hour / day / week change the unit and period as in 7.9; the screens show hours. resourceOptimizationMode defaults to dayByDayModel and then nothing changes.
  14. Schedule from the project finish: the same buttons work; yielding tasks move earlier; the preview shows the new project start.
  15. Fast mode: the budget of 7.6 on 2 000 tasks; hours typed in a grid cell write the Time line; a dragged chip changes its resource; each action is one Undo step.
  16. All new texts exist in the 14 dictionaries; Arabic and Farsi windows mirror without overlap.
  17. Jest baseline: no new failing suite; Docker scripts pass; test_sql.sh still passes.

How a server side run goes. (1) The device prepares the run as before and builds the problem (resourceLevelingServerProblem.ts: leaves in topological order with hours per resource, links with lag, stage members, start delays, the range of the capacity). (2) project_resource_leveling_server_plan(project, problem) searches in the database (set-based, per resource and period) and returns the delays, the moves with their reasons, the conflicts it could not solve, and the finish. It writes nothing. (3) The device continues from the proposal with its own engine (seed): what is right stays, a conflict the database left is solved here. (4) The preview is the usual one and carries a note: Calculated by the database and checked on this device (+ how many tasks were adjusted). Apply, Undo and history are unchanged.

The database takes a plan planned from the start, in one calendar (Monday to Friday, or every day), with FS / SS / FF / SF links with a lag in working days (also to or from a stage), uniform distribution, at most 3000 tasks and 20000 links. Not taken (the reason is shown in the preview): direction (planned from the finish), calendar, taskCalendar, constraint, manual, splits, elapsed, external, inactive, subproject, distribution, cycle, size, timeout.

Never silent. If the database cannot do it, the run is calculated on the device and the preview says why: planNotSupported (with the reasons), serverUnavailable (PART 42 not installed: run start2_sql_code.sql), serverError. A choice is never ignored without a word.

Exactness. The SQL functions repeat the arithmetic of the TypeScript engine (the working-day maths, the order of the tasks, the periods that decide who yields). They were compared with the engine on 469 random plans (leveling and smoothing, the three orders, day and week, stage links, started and frozen tasks, start delays): the same delays. The engine of the device stays the authority: a wrong proposal can only cost time, never produce a wrong plan.

Other algorithms improved with the switch. Effective settings: Fast mode needs the client side (fastModeNeedsClientSide; its switch is disabled with the reason). The engine compares with the plan the run started from (baselineDelays) while it continues from a seed, and knows from the database why a task was not placed (failureHints). scheduling.ts gives one shared graph (leafGraphOf) to the scheduler and to the problem builder.
