Time Genus Timeline Control & Collision Detection WBS Specification

W1 BEFORE POST architectural specification and Work Breakdown Structure (WBS).
Source: Google Doc "W1 BEFORE POST". Architectural Blueprint • No Application Code Modified (Do Not Coding)

Directive Compliance: "Do not coding." This document establishes the complete architectural plan, abstract entity designs, state transition models, and Work Breakdown Structure (WBS) for checking resource busy status on the timeline prior to committing plan movements.
1. The Need

Prevent Double-Booking

Human resources and equipment (classified under timeGenus) have physical, non-elastic availability. The system must verify whether a resource is already booked on overlapping timeline intervals before committing plan movements.

2. The Method

Optimistic Calculation & Purge

Execute task line plan calculations optimistically into task_line_plan_movements. Check every line against timeline availability. If any resource is occupied, atomically purge all generated movements and report collision diagnostics.

3. The Architecture

Abstract & Multi-Scale

Decouple timeline conflict control from single tables. Utilize an abstract timeline occupancy model supporting flexible granularities (Day, Hour, Minute) reusable across projects, work orders, and rentals.

1. Business Need & Timeline Concurrency Problem

Why timeGenus is fundamentally different from Material, Expense, and Revenue lines.

In UNIVERSAL1 Project Management, resources belong to distinct management genuses:

  • Material Genus (materialGenus): Storable inventory items. Multi-allocation is permitted up to available inventory; they do not occupy time slots.
  • Expense Genus (expenseGenus) & Revenue Genus (revenueGenus): Financial entries and invoices. Pure accounting figures with no operational exclusivity.
  • Time Genus (timeGenus): People (Human Resources booked by hour/day) and Machines/Tools (Equipment Resources). Time cannot be inventoried. A human developer or a 20-ton crane cannot physically execute two disjoint activities simultaneously during the exact same hour or minute.
TIMELINE COLLISION SCENARIO: ============================ Calendar Day: 2026-10-15 [09:00 - 18:00] Resource: "John Doe (Senior Backend Dev)" [Max Capacity: 1.0 FTE / 8.0 hrs/day] Task #101 (Already Posted): [======== 6.0 Hours Allocated (09:00 - 15:00) ========] Task #102 (Attempting to Post): [======== 4.0 Hours Allocated (13:00 - 17:00) ========] ^^^ OVERLAP COLLISION! ^^^ Total Load on 2026-10-15: 10.0 Hours > 8.0 Max Capacity (Overload = 2.0 hrs) ACTION REQUIRED: Detect collision BEFORE post finalize → Block Task #102 → Rollback/Delete!
Core Business Requirement: Before a task's financial plan is accepted as posted (taskIsPosted: true), every line carrying a timeGenus resource must be validated against all concurrent timeline allocations. If the resource is already occupied, the post action must fail with explicit conflict reporting.

3. Strategy Analysis & The Optimistic Variant

Evaluation of execution paths: Optimistic Purge vs Pessimistic Pre-Check.

User-Specified Variant

Variant 1: Optimistic Posting with Automatic Purge

Workflow:

  1. Calculate full distribution for the task lines.
  2. Insert the resulting daily/hourly rows directly into task_line_plan_movements.
  3. Run collision check across all inserted lines of timeGenus resources.
  4. Decision Gate:
    • If Clear: Keep rows, update timeline register, mark taskIsPosted = true, commit.
    • If Resource Busy: Immediately execute:
      DELETE FROM task_line_plan_movements WHERE "rowOwnerGUID" = taskGUID;
      Mark taskIsPosted = false, raise collision exception with conflicting task ID and period.
Why this is advantageous: Reuses existing distribution math, normalization, and Correct033 logic without writing a duplicate "shadow dry-run" engine. The database SQL engine performs set-based collision checks directly against indexed rows.
Alternative Variant

Variant 2: Pessimistic Dry-Run Pre-Check

Workflow:

  1. Calculate distribution in memory (TypeScript or temporary PostgreSQL CTE/unlogged table).
  2. Query timeline occupancy register for busy collisions before writing any rows to task_line_plan_movements.
  3. If collision detected: abort immediately with error without writing any database records.
  4. If clear: proceed with persistent insert into task_line_plan_movements.
Tradeoff: Avoids write-then-delete IO churn on database tables, but requires maintaining two execution paths (dry-run validator vs actual inserter) or uncommitted transaction rollbacks.

Detailed Comparison Matrix

Evaluation Criteria Variant 1: Optimistic Purge (Specified) Variant 2: Pessimistic Pre-Check Variant 3: Transactional Savepoint Rollback

4. Control Periods: Day, Hour, Minute

The document specifies: "Minimum control periods maybe: Day, hour, minute."

Different tasks and resources operate on different operational timeframes. A construction worker or crane might be scheduled in full days, a machine operator or senior consultant in hours, and high-contention surgical equipment, testing benches, or drones in minute slots.

Period 1

Day Granularity

rowGranularity = 'day'

  • Period Format: YYYY-MM-DD 00:00:00+TZ
  • Duration: 1 full calendar day (or project work day, e.g., 8 hours).
  • Collision Rule:
    Binary: Resource assigned to another task on same date.
    Or Cumulative: Total hours across tasks on day > daily working capacity (e.g., > 8h).
  • Use Case: High-level Gantt tasks, milestone allocations.
Period 2

Hour Granularity

rowGranularity = 'hour'

  • Period Format: YYYY-MM-DD HH:00:00+TZ
  • Duration: 1 hour block (60 minutes).
  • Collision Rule:
    Direct slot overlap:
    (start_a < end_b AND end_a > start_b)
    No two tasks can book the same resource during the same clock hour.
  • Use Case: Shift work, equipment rental, technician visits.
Period 3

Minute Granularity

rowGranularity = 'minute'

  • Period Format: YYYY-MM-DD HH:MM:00+TZ
  • Duration: Discrete minute interval (e.g., 1 min, 15 min, 30 min).
  • Collision Rule:
    Precise range intersection using PostgreSQL tstzrange GiST exclusion constraint:
    period_range && existing_range
  • Use Case: Lab testing benches, drone flights, meeting rooms, tight micro-tasks.

Interval Math & Range Overlap Formulation

MATHEMATICAL COLLISION FORMULA: =============================== Given two allocations A and B for the same physical resource R: A = [A.startDatetime, A.endDatetime) B = [B.startDatetime, B.endDatetime) Collision Condition: (A.startDatetime < B.endDatetime) AND (A.endDatetime > B.startDatetime) Capacity Check (for Non-Exclusive or Shared Resources): For any time point t in [A.start, A.end]: Σ allocatedCapacity(R, t) ≤ maxCapacity(R) If Σ allocatedCapacity > maxCapacity → COLLISION!

Entity Schema Definition: abstract_resource_occupancy_movements

-- Abstract reusable resource timeline occupancy register
CREATE TABLE IF NOT EXISTS public.abstract_resource_occupancy_movements (
  "rowGUID"              UUID          NOT NULL DEFAULT gen_random_uuid(),
  "rowProjectGUID"       UUID          NOT NULL REFERENCES public.project_table("rowGUID") ON DELETE CASCADE,
  "rowOwnerGUID"         UUID          NOT NULL, -- Polymorphic: task, work order, rental
  "rowOwnerTable"        TEXT          NOT NULL DEFAULT 'project_task_table',
  "rowLineGUID"          UUID          REFERENCES public.task_line_table("rowGUID") ON DELETE CASCADE,
  "resourceGUID"         TEXT          NOT NULL, -- Person GUID, Equipment GUID, etc.
  "resourceRoleGUID"     TEXT,
  "resourceKind"         TEXT          NOT NULL DEFAULT 'person', -- 'person' | 'equipment' | 'room'
  "periodStartDatetime"  TIMESTAMPTZ   NOT NULL,
  "periodEndDatetime"    TIMESTAMPTZ   NOT NULL,
  "periodGranularity"    TEXT          NOT NULL DEFAULT 'day', -- 'day' | 'hour' | 'minute'
  "allocatedCapacity"    NUMERIC(10,4) NOT NULL DEFAULT 1.0000,
  "maxCapacity"          NUMERIC(10,4) NOT NULL DEFAULT 1.0000,
  "isExclusive"          BOOLEAN       NOT NULL DEFAULT TRUE,
  "rowJSON"              JSONB         NOT NULL DEFAULT '{}'::jsonb,
  "created_at"           TIMESTAMPTZ   NOT NULL DEFAULT NOW(),
  "updated_at"           TIMESTAMPTZ   NOT NULL DEFAULT NOW(),
  PRIMARY KEY ("rowGUID"),
  CONSTRAINT abstract_occupancy_period_chk CHECK ("periodEndDatetime" > "periodStartDatetime"),
  CONSTRAINT abstract_occupancy_granularity_chk CHECK ("periodGranularity" IN ('day', 'hour', 'minute'))
);

6. SQL Mechanics: Optimistic Post & Automatic Collision Purge

Step-by-step implementation of the optimistic check and delete mechanism.

Inside the enhanced posting procedure (create_task_line_plan / create_abstract_task_plan), the workflow executes as follows:

  1. Delete Old Rows: Purge existing movements of the task being re-posted (so a re-post doesn't collide with itself).
  2. Insert Proposed Rows: Insert new rows into task_line_plan_movements with normalized coefficients and Correct033 applied.
  3. Synchronize Abstract Movements: For every line where rowParentGUID = 'timeGenus' and a concrete resource is assigned (taskResourceItem not empty), insert corresponding records into abstract_resource_occupancy_movements.
  4. Run Set-Based Collision Check: Query whether any of the newly inserted timeGenus periods overlap with existing occupied periods for the same resource owned by other tasks/owners.
  5. Evaluate Collision Decision:
    • NO COLLISION: Proceed to update timeline register, mark task_line_table.rowJSON.taskIsPosted = true, and return success.
    • COLLISION DETECTED:
      PURGE ALL LINES: Execute: 
      DELETE FROM public.task_line_plan_movements WHERE "rowOwnerGUID" = v_task;
DELETE FROM public.abstract_resource_occupancy_movements WHERE "rowOwnerGUID" = v_task;
UPDATE public.task_line_table 
   SET "rowJSON" = "rowJSON" || '{"taskIsPosted": false}'::jsonb 
 WHERE "rowOwnerGUID" = v_task;

      RAISE EXCEPTION: Abort the transaction with structured JSON error details identifying the colliding resource, conflicting task title, and overlapping period.

SQL Stored Procedure Implementation Blueprint

-- Blueprint: Set-based resource collision validator
CREATE OR REPLACE FUNCTION public.check_resource_timeline_collision(
  p_task_guid        UUID,
  p_project_guid     UUID
) RETURNS TABLE (
  has_collision      BOOLEAN,
  colliding_resource TEXT,
  conflicting_owner  UUID,
  conflict_start     TIMESTAMPTZ,
  conflict_end       TIMESTAMPTZ,
  error_message      TEXT
) LANGUAGE plpgsql SECURITY INVOKER AS $$
BEGIN
  RETURN QUERY
  SELECT 
    TRUE AS has_collision,
    new_occ."resourceGUID" AS colliding_resource,
    exist_occ."rowOwnerGUID" AS conflicting_owner,
    GREATEST(new_occ."periodStartDatetime", exist_occ."periodStartDatetime") AS conflict_start,
    LEAST(new_occ."periodEndDatetime", exist_occ."periodEndDatetime") AS conflict_end,
    format('Resource %s is already busy on task %s from %s to %s',
           new_occ."resourceGUID", exist_occ."rowOwnerGUID", 
           GREATEST(new_occ."periodStartDatetime", exist_occ."periodStartDatetime"),
           LEAST(new_occ."periodEndDatetime", exist_occ."periodEndDatetime")) AS error_message
    FROM public.abstract_resource_occupancy_movements new_occ
    JOIN public.abstract_resource_occupancy_movements exist_occ
      ON new_occ."resourceGUID" = exist_occ."resourceGUID"
     AND new_occ."rowOwnerGUID" <> exist_occ."rowOwnerGUID" -- Don't collide with self
     -- Overlap interval intersection:
     AND new_occ."periodStartDatetime" < exist_occ."periodEndDatetime"
     AND new_occ."periodEndDatetime"   > exist_occ."periodStartDatetime"
   WHERE new_occ."rowOwnerGUID" = p_task_guid
   LIMIT 1;
END;
$$;
