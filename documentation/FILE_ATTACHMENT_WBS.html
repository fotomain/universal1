W1 File attachments – Work Breakdown Structure (v5)

Files (documents, scans, audio, video, links) can be attached to an organization, a project, a stage, a task and to documents (invoices, orders …). The file lives in Google Drive, inside ONE root folder of the organization (kit8root, inside a Google Shared drive); the app stores the Drive url and the data around it in a mediaPost row. Project setting filesFunctionalityEnabled (TRUE by default) switches the feature.

Status: PLAN ONLY – no code. v5 written 2026-11-11 after the owner's answers to Q14 and Q15 (v4: Q1, Q10, Q11, Findings 2 and 5; v3: Q3–Q5 and all of S1–S11). Items marked Q are open questions with a recommended default (section 15); the plan is built on the defaults.

What is new in v5.
  • Q14: yes – every member of the organization reads the files of every project.
  • Q15: a media post that is outside a project (recordings, links, intent posts) is visible, changeable and deletable by its author only.
  • Permission renamed: mediaPostManager is gone; projectMediaPostManager takes its place and lets its holder create, read, update and delete any post of a project (project, stage, task scope). projectFileManager (Q11) stays for the organization-level and document files and for the Drive administration (root url, set up, health check, move the root). Both are true by default for the administrator and the project manager – this default is my reading, see Q18.
  • Finding 5 is rewritten as three row rules (section 12); a check of the code shows that old posts do not all carry a real author (section 12, Q19).
  • Kept from v4: Shared drive root, no Picker, everyone = organization members, Q10, permanent delete, S1–S11, tables files_…, PART 49, Docker test 55.

4. The root folder of the organization (N1–N4)

One value per organization: organizationGoogleDriveRootFolderUrl, the url of a Google Drive folder (https://drive.google.com/drive/folders/<id>). It is stored on the organization row (organizationTable.rowJSON, next to defaultProjectSettings) together with the parsed organizationGoogleDriveRootFolderId and the Shared drive id organizationGoogleDriveRootDriveId (empty for the My Drive fallback). It is NOT a project default: "Save settings to organization" does not copy it. The field is shown on Project settings → Files (as requested) and on Organization edit → Files; both show and change the SAME organization value, and the project tab says so in one line.

Who / whenWhat happens
Scenario 1 – the administrator signs in with Google and the url is empty
  1. The sign-in creates the organization and makes this user its administrator (organization_ensure_user, existing).
  2. The client sees: administrator ∧ signed in with Google ∧ url empty → it asks ONE tap "Connect Google Drive" (a Drive token, section 8) and goes on by itself. Q2
  3. The Shared drive: the client lists the user's Shared drives. If there is exactly one it is used; if there are several the administrator picks one from a list (one choice, no folder picking); if there is none the button Create Shared drive "kit8" makes one when Google allows it (F0 question 4, Q15), else the window says "ask your Google Workspace administrator for a Shared drive".
  4. The folder: the app looks in that Shared drive for a folder titled kit8root that carries its properties mark (S2) – it is found and used if it exists, so a second try or a second administrator never makes a duplicate – and creates it with that exact title only when it is missing.
  5. Everyone: the members of the organization are added to the Shared drive (see below).
  6. The url is saved through the RPC files_root_set (also the Shared drive id and the shared e-mails). From now on every member's app takes the folder from the organization row – nobody searches or picks again.
  7. A failure shows ErrorModalWindow and the button Set up Google Drive stays on the Files tab to try again.
Scenario 2 – the user signs in without GoogleThe field is a TextInputApp on the Files tab. The user (project manager or administrator) pastes the url of a folder that already exists and that the uploaders can write to. The url is checked as text (a Google Drive folder url with a valid id); when a Drive token is available it is also checked in Drive (readable, is a folder, writable) and the folder title is shown. A user without Google can change the url but cannot upload (R10). A bare Shared drive is refused as a root (a drive cannot be deleted like a folder); the url must be a folder, in a Shared drive or in My Drive.

Change of the url laterA window asks: Move the files already stored to the new folder? – Move (S7: the app moves its folders organization, project, document, template) or Leave (stored files stay where they are and keep working; new files go to the new folder). Nothing is deleted either way.

"Full CRUD access for everyone" – decided: (A)

Everyone = every member of the organization (organizationMemberTable), nobody else. In the Shared drive each member is added by e-mail with the role that may add, edit and delete files made by others – Content manager (fileOrganizer) is expected, to be confirmed in F0 (the lower role Contributor may not delete). New members are added by the administrator's client (a Share with members button, and automatically when the administrator opens the app and finds members that are not yet added – the list is kept in organizationGoogleDriveRootSharedWith); a removed member is removed from the Shared drive the same way. The option "anyone who has the link" is not built.
Limits: a member with a Google account outside the Workspace domain can be refused by the domain's sharing rules (F0 question 5, Q16); then that member cannot upload and sees the reason. Having Drive access is not the same as the app permission: inside the app only a holder of projectFileManager sees the add / edit / delete buttons (section 12).

  • The folder names organization, project, task, document, template, files are fixed words; the GUIDs are the lower case uuids of the rows. The file keeps the name the user gave it (the Drive file id, not the name, identifies it, so two files with the same name are possible – the list shows a warning on the second one).
  • A folder is found or created by name inside its parent. Two users could create the same folder at the same moment and Drive would keep both, so the folder ids are recorded in files_folder_table (section 12): the first writer wins, the loser deletes its empty duplicate and uses the winner's id. The same table tells the delete step which folder to remove (section 6).
  • The path is also information on the row (googleDriveRelativePath). A task moved to another project leaves its Drive folder where it is; the links keep working.
  • S2: every folder the app makes gets a readable description and properties (GUIDs) so a person browsing Drive – and the health check – can tell what it is.

6. Delete rules (N7, A2, A3)

Delete is PERMANENT (Q4 answered). The app uses the Drive call files.delete, which skips the Drive trash: nothing can be restored, not by the person, not by the administrator (only a Google Workspace administrator can restore for a short time, and a Shared drive has its own trash rules). So every delete window says it plainly: "N files will be deleted from Google Drive permanently." and a deleted task or project names the number of files in it (files_count_for_delete).
The database cannot delete a file in Google Drive – it has no Drive token. A trigger can delete the rows and remember what has to be removed; the removal itself must be done by an app client that holds a Drive token. The plan therefore has two layers, so that the files do not stay behind when a task disappears in any way.
Shared drive: no owner problem; My Drive fallback: only the owner deletes. In a Shared drive the files belong to the drive, so any member with the Content manager role can delete any file – the cleanup of one client is enough (F0 question 2 confirms the role). In the My Drive fallback (an organization without Workspace) files.delete removes only what the caller owns, so the queue then holds ONE line per file with the owner's e-mail (driveOwnerEmail) and the cleanup worker of each user deletes that user's files.
EventWhat happens
One file deleted in the listThe row is deleted by files_delete and the Drive file is removed at once (owner), else the queue line waits for the owner's client. Allowed for a holder of projectFileManager (administrator, project manager).
A task / stage is deleted in the app
  1. Layer 1 (client, before the delete): the confirmation window gets one more line – "N files will be deleted from Google Drive permanently" (files_count_for_delete counts the task and everything under it). On OK the client removes what it can – its own files and the task/<taskGUID> folder of every deleted task it owns – then deletes the task.
  2. Layer 2 (database, always): a statement trigger on project_task_table DELETE (transition table, as the task tree is deleted in one statement) deletes the file rows of every removed task and, for every Drive file and folder it knew, writes a line into files_drive_cleanup_table (with the owner's e-mail). This runs also when the task is deleted by a path that has no Drive token (another user, a project delete, the REST API).
  3. The cleanup worker (client): when the app opens, after a delete and every few minutes while a Drive token exists, the client reads files_cleanup_pending() (the lines it may do: owner = my Google e-mail, or I own the folder, or I am an administrator of the organization), deletes the Drive items, and calls files_cleanup_done. A Drive "not found" counts as done. A refusal ("no permission") stays in the queue with the reason and the attempts, and is shown to the administrator on the Files tab: Google Drive cleanup: 3 waiting, 1 failed, with a retry.
A project is deletedSame two layers for the folder project/<projectGUID> (it holds the project files and all task folders) and its file rows.
A draft document is deleted (S6)The document RPCs (delete_vendor_invoice …) delete the draft; a statement trigger on each of the seven document headers removes the file rows and queues document/<kind>/<documentGUID>. A posted document cannot be deleted (unpost first), so its files stay.
A task template is deleted (S11)A trigger on the template header queues template/<templateGUID> and deletes its files_template_file_table rows. "Fill with Replace" deletes the old tasks of the target: their files go by the task rule above.
An organization is deleted (Q5, Q10 answered: remove the folder named in the url)
  1. The window asks the administrator to type the organization name and says: "The Google Drive folder named in the root url (kit8root) and ALL files in it will be deleted permanently." It shows the number of files and the used storage (S8).
  2. Layer 1 (client, before the delete): the client deletes the folder named in organizationGoogleDriveRootFolderUrl with everything inside it – always, whoever made it and whatever it is called (Q10). A Shared drive itself is never deleted: the root is always a folder inside it.
  3. Layer 2 (database): a statement trigger on organizationTable DELETE queues the root folder and deletes all file rows, folder rows and version rows of the organization. The queue line carries the organization GUID as plain text (no foreign key), and the members lose access with the organization, so the line is read by the user who requested the delete and by any member of the same Shared drive (files_cleanup_pending).
  4. In the My Drive fallback files owned by other people are removed by their owners' clients (owner rule above).
A file is replaced (S4)Nothing is deleted: Drive keeps the old revision (kept forever) and the row notes the new version. A permanent delete of the file deletes its revisions too.

Not covered by the delete: files of a project version (a version is a plan copy and carries no files), and "orphan" files that exist in Drive without a row – the health check (S1) finds those.

8. Google Drive access – findings

Finding 1 – the app has no Drive access today. The sign-in (signInWithOAuth({ provider: 'google' }), kit8/hooks/useAuth.*) asks for no Drive scope and the code never reads provider_token. The Drive helpers in kit8/google/drive (create file / folder with folderPath + findIfExists, list, delete, progress) exist and only need a token. So R10 means: signed in with Google and a Drive token.

Getting the token

Same pattern as the calendar (useGoogleCalendarConnect): expo-auth-session Google provider, the three client ids already in .env, one tap "Connect Google Drive", the token kept in memory for its lifetime (~1 h). The hook is generalised to useGoogleConnect(scopes). Alternative for Scenario 1: ask the Drive scope in the sign-in itself (scopes in signInWithOAuth) – then "automatic" is truly zero taps, but EVERY user of the app sees the Drive consent at login, and Supabase gives the Google token (provider_token) only in the session right after the login, with no refresh. Recommended: the one tap (Q2). Google Cloud needs the Drive API enabled and the scope on the consent screen.

Finding 2 – decided: the app finds or creates the folder, nobody picks it. The narrow scope drive.file gives the app access to files it created or the user opened – Google: Choose Drive API scopes. It is not confirmed that the app of member B can see a folder made by member A. The plan has ONE answer for it, tested in F0 question 1: if drive.file is enough, it is used; if not, the app uses the scope drive (full Drive). That scope is restricted, but an app whose OAuth consent screen is Internal to the Workspace domain needs no Google verification. The Google Picker is not used. Consequence of the internal app: every user must have an account in that domain (see Q16).
Finding 3 – ownership: solved by the Shared drive. In "My Drive" the uploader owns the file (it counts against that person's storage, goes with that person's account, and only that person can delete it). In a Shared drive the organization owns every file, so none of this applies. The My Drive fallback keeps the owner rules of section 6.
Finding 4 – properties, not appProperties. The key-value marks of S2 must be Drive properties (visible to every app). appProperties are private to ONE OAuth client, and the web, iOS and Android builds of this app use different client ids, so a mark written on the web would be invisible on a phone. F0 question 6 confirms it.

Upload (R15, N5, N6)

  1. The user drops / picks a file → a row appears at once with a progress bar (client side only; on a phone it first goes into the queue of S9).
  2. The client checks the storage limit (S8) and gets or creates the folders of section 5 (ids from files_folder_table, created in Drive only when missing, with description and properties of S2).
  3. Upload with progress and a Cancel (abort signal). On success files_add writes the row with the Drive id and url. On failure NO row is written and ErrorModalWindow says why.
  4. Size: 100 MB per file in phase 1 (the helper uploads multipart, the whole file in memory); resumable upload later (Q6).

11. The suggestions S1–S11 – design (all are built)

All eleven are part of the plan (A4). Each one lists what it does, how, and its limits. The work package is in brackets.

S1 Health check "Check files" (F7)

A button on the Files tab and in the dashboard menu (administrator and project managers; for the organization scope it walks the whole root, for a project or task only that part). It is read only until the user presses Repair on selected lines, and the result can be copied.

  1. files_health_rows(scope) returns the file rows with their Drive ids and the GUIDs of the tasks / projects / documents that still exist.
  2. The client lists the Drive folders by id (files.list, '<folderId>' in parents, paged) with a progress bar and a Cancel.
  3. Findings and repairs: A a row whose Drive file is missing → delete the row (or keep). B a Drive file in a files folder without a row (orphan) → Adopt (makes a row, uploader "unknown") or delete permanently. C a folder of a task / project / document that no longer exists → delete permanently (after a confirmation with the count). D a folder in Drive that is not in files_folder_table (record lost) → register it, found through the properties of S2. E the same folder name twice in one parent → move the children into the recorded one, delete the empty duplicate. F root problems: not writable, title not kit8root, members not yet shared (compare with files_members_emails) → Share. G rows under another root (S7) → Move.

Limits: it can only see what the user's token sees (drive.file, Finding 2) – the result says "checked as <e-mail>"; it never repairs on its own.

S2 Readable folders (F7)

When the app creates a folder it sets the description (kit8 · Project "Bridge" · 11111…, for a task its name and project) and the properties kit8Kind, kit8OrganizationGUID, kit8ProjectGUID, kit8TaskGUID … (a GUID fits the key + value size limit of Drive, to confirm in F0). The folder NAME stays the GUID (stable, never renamed). The description is refreshed at the next upload after a rename and by the health check ("Refresh folder descriptions"). The marks are what Scenario 1 uses to find an existing kit8root. Use properties, not appProperties (Finding 4).

S3 Shared drive as the root (F3, F7) – the main design

Needs Google Workspace (a Shared drive does not exist for a free Gmail account). Scenario 1 (section 4) picks or creates the Shared drive and the folder kit8root in it; Scenario 2 accepts any folder url, also one inside a Shared drive. Every Drive call carries supportsAllDrives=true (and includeItemsFromAllDrives / driveId for lists). Members: access is the Shared drive's member list, so Share with members compares the organization members with the drive's members and adds / removes them (role: Content manager, to be confirmed in F0; needs the user to be a manager of the drive). Gains: the files belong to the organization – no quota problem, no files lost with an account, and permanent delete works for every Content manager. Rows keep googleDriveDriveId; googleDriveOwnerEmail is empty. Fallback: an organization without Workspace uses a My Drive folder (Scenario 2 or the same button) with the owner rules of section 6.

S4 Replace file + versions (F8)

Row / card menu Replace…: pick a new file; the client uploads it over the same Drive file (files.update with media), so the Drive id, the url, the row, the paper place and the document type stay and Drive creates a new revision. The client marks the old revision keepForever (otherwise Drive may drop old revisions) and calls files_replace: size, MIME, kind, fileVersionNumber + 1 on the row and one line into files_version_history (the OLD version: revision id, size, name, who replaced, when). The Versions panel of the viewer lists them; Open / Download of an old revision uses revisions.get; Restore = download that revision and replace with it (a new version, nothing is lost). Rights: the same as edit. Limits: Drive keeps revisions only for binary files and for Google-native files in other forms; old revisions count in the storage (S8). A delete removes every revision for good.

S5 Document types (F8)

Catalog files_document_type_catalog (universal columns; owner empty = seeded rows for everybody, owner = organization for its own types). Seeds in start4 / start5: Contract, Invoice, Specification, Drawing, Photo, Report, Minutes, Certificate, Other. Screen Catalogs → File document types (administrator CRUD; others read; a seeded row is read only). The file row stores fileDocumentTypeGUID; the dashboard has the column, the filter and an inline edit; the add window can ask for the type; a link opens a viewer with the type shown. Check in F2 that kit8_setup_def_table and SystemMetaData accept a snake_case table name; if not, the table is set up like the PM tables.

S6 Files on documents (F9)

Scope document for the seven documents: vendor invoice, purchase order, product receipt, customer invoice, payment fact, fact input, time sheet (fileSourceKind = document, fileDocumentKind, parent = the document GUID). Drive path document/<kind>/<documentGUID>/files/ (a document may span several projects, so there is no project folder). A paperclip button with the count sits in the form bar and in the row menu of each list. Rights (Q11 answered): reading = every member of the organization that may read the document; add / edit / replace / move / delete = a holder of projectFileManager (administrator, project manager) – nothing more is asked of the document. Files can be added to a POSTED document (the scan of the paper invoice arrives after posting) – the posting does not freeze files. A draft document that is deleted removes its files (section 6); a posted one cannot be deleted. The RPCs call perm_require on the interface permission projectFileManager.

S7 Move a file / move the root (F8)

Move a file: row / card menu Move to… opens the project dashboard as a picker (the existing PMProjectDashboard picker: project → task, or the organization / a document) and calls files_move after the client has moved the Drive file (files.update with addParents / removeParents, so the Drive id and the url stay). Both folders must be writable by the user; a Drive refusal leaves the row unchanged. The row gets the new parent, kind, project, folder id and path. On web an optional drag of a row onto a task row of the open tree can call the same code if the Skia hit test allows it (a nice-to-have, not a requirement).

Move to a new root: when the root url changes (section 4) the window offers it, and the Files tab shows Move files to the root while rows exist whose googleDriveRootFolderId differs from the current root. Same Drive (or the same Shared drive): the client MOVES the folders organization, project, document, template of the old root into the new one (a few calls; every id and url stays), then files_root_moved(oldId, newId) updates the rows and the folder table. Different Drives (My Drive → Shared drive, or another owner): a move is not allowed by Drive in general (F0 question 8), so the client copies each file (files.copy) into the new structure, updates the row, and queues the old file for delete; this runs file by file, shows progress, can be stopped and continues from the rows still under the old root (the to-do list is in the data, no job table). Copies are owned by the copier. The old root folder itself is never deleted by the move.

S8 Storage used + limit (F10)

files_storage_used(scope) sums fileSizeBytes (links count 0; old revisions of S4 are added from files_version_history) per organization, project and uploader's e-mail. Shown on the Files tab, in the footer of the dashboard and in the organization delete window. Optional organization limit filesStorageLimitMegabytes (empty = none): files_storage_check(size) is asked BEFORE the upload (so no file is uploaded and then refused) and files_add checks it again; the refusal says how much is used. The numbers are the app's own bookkeeping, not Google's quota (Google counts per owner Drive, or the Shared drive).

S9 Upload queue with retry on phones (F10)

On iOS / Android a file that is picked is first copied into the app's document folder (expo-file-system) and listed in a queue stored on the device (AsyncStorage: id, scope, local uri, name, MIME, size, attempts, state, last error). A worker uploads when there is a connection (network state – check whether @react-native-community/netinfo or expo-network is already installed; otherwise a failed request is the signal) and a Drive token; it retries with a growing pause (3 attempts in a row, then failed with Retry), survives a restart, and removes the local copy after the row is written. A queued file is visible in the dashboard (section 9), so the user knows it is not lost; a queue size cap (default 500 MB) refuses new picks with a message. When the Drive token has expired the queue waits and the dashboard shows "Connect Google Drive". Web: the browser cannot keep a file handle after a reload, so the web queue lives while the page is open (retry button only); IndexedDB storage of blobs is possible later. The permanent decisions (folder, limit) are taken when the queue item is uploaded, not when it is picked.

S10 Attach a recording (F9)

In the result screen of the media recorder (app/media/record/*) a button Attach to… opens the same picker as S7 (project → task, project, organization, document). The recording file is put into the queue of S9 (so a lost connection is not a lost recording) and becomes a normal file row in that scope (kind audio / video, title = the recording title, the original recording row stays in the recordings list). Web recordings (a blob) are uploaded at once.

S11 Copy files with task templates (F11)

Templates (PART 40) are shared by the whole organization and survive their source task, so they must not point at files that can be deleted. Save to template… gets a check box Include files (default off). When on, the client COPIES each Drive file of the saved tasks into template/<templateGUID>/task/<templateTaskGUID>/files/ (files.copy) and records them in files_template_file_table (template, template task, Drive id of the copy, name, MIME, size, paper place, document type, order). Fill from template… gets Copy files (default on when the template has files): after task_template_fill the client copies each template file into the new task's folder and writes the file rows. This needs the map from template task to created task: F11 checks that task_template_fill returns it and adds it to the result if not (the fill keeps its transaction and its speed). Deleting a template removes its folder (section 6). Not copied: files of a project version (a version is a plan snapshot) and the files of "Replace what the row has now" targets (they are deleted with their tasks). A "copy project" function does not exist today; when it is built it calls the same copy code. The copies count in the storage of the person who filled (S8) and a missing source file is skipped with a report line.

Finding 5 – decided: three row rules on mediaPostTable. Today its policies are USING (true) for anon and authenticated (the loop at the top of start2_sql_code.sql) and the matrix lists it only as an "own" table. The plan separates the rows:
  1. A post outside a project (no fileSourceKind and no project / task parent: recordings, links, intent posts) – visible, changeable and deletable by its author only (rowOwnerGUID = the signed-in user, Q15). No permission is involved; anon sees nothing.
  2. A post of a project (file rows of the scope project / stage / task, and any other post whose parent is a project or task) – read by every member of the organization (Q14); created, changed and deleted by a holder of projectMediaPostManager only, who may do it for any post of the project.
  3. A file of the organization or of a document – read by every member (documents: the members that may read the document); written by a holder of projectFileManager.
File rows are written only by the SECURITY DEFINER RPCs, which ask the permission; the policies carry the read rules.

start1 – tables

  • files_folder_table – one row per Drive folder pair: organization, scopeKey (organization | project:<g> | task:<g> | document:<kind>:<g> | template:<g>:<taskG>), project GUID, driveFolderId (the GUID folder), driveFilesFolderId (its files folder), root folder id, Drive id (Shared drive), created by, date. Unique on (organization, scopeKey) – the first writer wins (section 5).
  • files_drive_cleanup_table – what has to be removed in Drive: organization GUID (plain text, no foreign key), Drive item id, item kind (file | folder), driveOwnerEmail, why (file deleted | task deleted | project deleted | document deleted | template deleted | organization deleted | moved), requested by, attempts, last error, state (waiting | done | failed).
  • files_document_type_catalog – S5 (universal columns; rowOwnerGUID = empty for seeded rows, else the organization).
  • files_version_history – S4: one row per replaced version: file row GUID, organization, Drive revision id, version number, name, size, MIME, replaced by, replaced at.
  • files_template_file_table – S11: template GUID, template task GUID, Drive id of the template copy, name, MIME, size, paper place, document type, order.

14. Acceptance criteria

  1. A new project has filesFunctionalityEnabled TRUE; OFF hides the tree column, tabs and Add actions; ON brings the files back.
  2. Scenario 1: a new organization on Google Workspace, the administrator signs in with Google, taps "Connect Google Drive" once → a folder titled exactly kit8root exists in the Shared drive, every organization member is a member of the drive with the delete-capable role, and its url is in Project settings → Files. Signing in again, or a second administrator, finds the same folder and makes no second one. Nobody is asked to pick a folder.
  3. Scenario 2: a user without Google sees the url field as text, a holder of projectFileManager can change it, a plain member sees it read only and the RPC refuses a direct call. A bad url, or a bare Shared drive, is refused with a message.
  4. A PDF dropped on a task (web) appears with progress and lands in kit8root/project/<projectGUID>/task/<taskGUID>/files/; a file added to the project lands in …/project/<projectGUID>/files/; a file of the organization lands in kit8root/organization/files/. The row has the Drive url and the tree shows the name at once.
  5. A second uploader in the same task reuses the same folders (no duplicate folders, also when two users start at the same moment); the folders carry the readable description and marks (S2).
  6. Deleting a task with files: the confirmation says how many files will be deleted from Google Drive permanently; afterwards the task folder is gone from Drive (not in the trash), the rows are gone, the queue line is done. Deleting it from another user's session (no token) leaves a waiting queue line that the next client with the right Drive access completes; files owned by another person are removed by that person's client (or, in a Shared drive, at once).
  7. Deleting an organization removes the folder named in its root url from Drive (permanently); the file, folder and version rows are gone and the queue line exists.
  8. Cards by default on a phone and a portrait tablet, table on a desktop; the icon button switches both ways; reorder by drag survives a reload; paper place typed in the table shows on the card.
  9. The organization card lists the files of all its projects, finds by part of a name, the task link opens the task; the project card shows only that project.
  10. View opens text, .md, PDF, image, audio, video each in the right route; unknown types show the info page.
  11. S1 the health check finds a file deleted by hand in Drive, an orphan file, a folder of a deleted task and a lost folder record, and repairs each only after a click. S4 Replace keeps the url and the row, the Versions panel shows the old version and Restore makes a new one. S5 a file gets a type, the filter finds it. S6 a posted vendor invoice gets a scan; deleting a draft invoice removes its files. S7 a moved file keeps its Drive url; changing the root and pressing Move leaves no row under the old root. S8 an upload over the limit is refused before it starts. S9 a file picked with no connection uploads later by itself, also after the app was closed. S10 a recording is attached to a task. S11 a template saved with files fills a new task with its own copies of them.
  12. A plain member reads every file but has no add / edit / delete button and the RPCs refuse; the administrator and the project manager can do all. Recordings and other posts outside a project are seen by their author only; a project manager can change any post of a project.
  13. A user of ANOTHER organization cannot read, add, change or delete these rows; old posts (recordings, YouTube) still work; test_sql.sh and test 55 pass; no new failing Jest suite.
