W1 File attachments – Work Breakdown Structure

Files (documents, scans, audio, video, links) can be attached to an organization, a project, a stage and a task. The file itself lives in the user's Google Drive; the app stores only its Drive url and the data around it in a mediaPost row. Project setting filesFunctionalityEnabled (TRUE by default) switches the whole feature.

Status: PLAN ONLY – no code (the Google Doc "W1 FILE ATTACHEMENTS" says "Do not code"). Written 2026-11-02 from that document and from a read of the code (mediaPost, Google Drive helpers, the tree, the media player routes, the generic table rules). Items marked Q are open questions with a recommended default (section 11); the plan is built on the defaults.

3. Data: a file is a mediaPost row

No new table. The existing mediaPostTable (generic schema, kit8/redux/SystemMetaData.ts entity mediaPostReusable) holds the file rows next to the recordings and links it already has. A file row is recognised by rowJSON.fileSourceKind; every other row (recordings, YouTube posts) is untouched.

Decision, not stored in the task. The "first file" of the tree column is NOT copied into project_task_table.rowJSON: one RPC (file_attachment_first_per_task) returns the first file and the count per task of a project and the tree caches it. So task save, task templates, project versions and MS Project export are not touched.

4. Google Drive (the part with the real risks)

Finding 1 – the app has no Drive access today. The sign-in (supabase.auth.signInWithOAuth({ provider: 'google' }), kit8/hooks/useAuth.*) asks for no Drive scope and the code never reads provider_token. The Drive helpers in kit8/google/drive (create file / folder, list, delete, progress, folderPath with findIfExists) exist and only need an access token. R10 therefore means: signed in with Google and a Drive token.

Token

Same pattern as the calendar (useGoogleCalendarConnect): expo-auth-session Google provider, the three client ids already in .env, the token is kept in memory for its lifetime (~1 h), one tap "Connect Google Drive" when it is missing or expired. The hook is generalised into a shared useGoogleConnect(scopes); the Drive scope is drive.file (the app sees only the files it created – a non-restricted scope, no Google security review of the whole Drive). The Google Cloud project needs the Drive API enabled and the scope on the consent screen.

Not signed in with Google (or the client id of the platform missing): the Add buttons are disabled with a visible reason; the list of the files (rows) is still readable, because the rows are in the database.

Upload (R15)

  1. The user drops / picks a file → a row appears at once in the list with a progress bar (state uploading, client side only – nothing is in the database yet).
  2. Folders: FILES_KIT8_ / project_<projectGUID> / task_<taskGUID> (task and stage), FILES_KIT8_/project_<projectGUID> for a file of the project itself Q3, FILES_KIT8_/organization_<organizationGUID> for the organization. Created with createFolder(... findIfExists), so a second file reuses the folder.
  3. Upload with progress and an abort signal (the Cancel button). On success the RPC file_attachment_add writes the row with the Drive id and webViewLink. On failure NO row is written and an ErrorModalWindow tells why (not a snackbar).
  4. Sharing: see Q2.
Finding 2 – "my Drive" is private. A file uploaded to the Drive of user A cannot be opened by user B of the same organization unless A shares it. Default (Q2): after the upload the app grants the reader role to the e-mail of every member of the organization (the drive.file scope allows it on files the app created), and the row has the button Share with organization to repeat it for members who joined later. An organization switch "anyone with the link" is possible but OFF (a leaked link = access).
Finding 3 – size. The helper uploads multipart (the whole file in memory). A limit of 100 MB per file in phase 1 with a clear message; the Drive resumable upload (large video) is a later step Q5.

Delete

Deleting a row asks: Remove from the list only (default) or Also move the file to the Google Drive trash (only for the uploader). The app never deletes permanently. Deleting a task / project / organization deletes its file ROWS by a trigger; the Drive files stay (nobody is told silently that a file vanished).

5. Switch and visibility

  • filesFunctionalityEnabled: project level, TRUE unless stored false (SQL vendor_project_setting(project, key) – the pattern of the Vendor switches; TS !== false). Project settings → new tab Files; the Organization defaults (Organization edit → Projects → Settings) and "Save settings to organization" carry it like every other key.
  • OFF: the tree column, the Files views / tabs, the Task menu item and the Add actions are hidden; the rows stay in the database and come back when the switch is turned on.
  • The organization's own files (organization card) follow the switch of the Organization defaults.

7. File view (R13)

A button View (eye) on every row / card, in the tree cell and in the Task menu. It always goes to ONE route, /files/view?postGUID=…; that route reads the row and replaces itself with the standard route of the kind, so a viewer can be opened from anywhere (and linked) without the caller knowing the kind.

8. SQL (PART 44 – file attachments)

Rules of the project apply: tables / indexes in start1_sql_tables.sql, everything else in start2_sql_code.sql (same PART number), drops in delete_sql_structure.sql; idempotent; tested in Docker before it is handed over. No seed rows, no pg_cron.

Finding 4 – mediaPostTable is open to everybody today. Its policies are USING (true) for anon and authenticated (the loop in start2_sql_code.sql, "Allow anon select / insert / update / sql_for_delete"). Left as it is, the files of every organization would be readable and writable by anybody with the public key. The plan fixes it for file rows only, without touching the recordings.

start1 – tables

  • Partial index on mediaPostTable ("rowOwnerGUID", "rowParentGUID", "orderInList") WHERE "rowJSON" ? 'fileSourceKind' and one on (rowJSON->>'fileSourceProjectGUID') for the project list. No column is added (the table is generic).

start2 – code

  • RLS (restrictive policies) on mediaPostTable: SELECT of a file row only when its rowOwnerGUID is the organization of the user (app_user_guid() → userTable.rowJSON.userOrganization); INSERT / UPDATE / DELETE of a file row by a client is refused. Rows without fileSourceKind pass as before. The RPCs are SECURITY DEFINER (documents rule: written only by RPCs).
  • RPC file_attachment_list(p_scope, p_guid, p_search) – the rows with task name, task kind, project name, project GUID; organization scope = all projects of the organization; search by name / paper place / task name (ILIKE on the extracted fields).
  • RPC file_attachment_add(p_scope, p_parent, p_json) – checks the parent belongs to the user's organization, fills rowOwnerGUID, fileSourceKind, fileSourceProjectGUID, fileUploadedBy / At, orderInList; refuses while the project switch is OFF.
  • RPC file_attachment_update(p_guid, p_patch) (name, description, paper place only), file_attachment_reorder(p_guid[], …), file_attachment_delete(p_guid) (uploader or organization administrator), file_attachment_first_per_task(p_project), file_attachment_members_emails() (for sharing).
  • Triggers: deleting a task / stage / project (and an organization) deletes its file rows; a statement-level safety check that a file row is never moved to another organization.
  • Pitfall kept in mind: vendor_project_setting is TRUE unless stored false – the right helper for filesFunctionalityEnabled.

delete file

A numbered part drops the functions, the policies and the two indexes; the table and its rows stay (the table belongs to another feature). The numbering test scans ^-- PART (\d+): – the comment style of the other parts is used.

Docker test tests/46_file_attachment.sql

Add to each scope, the organization of another user cannot read (use tt.rows_of(sql): RLS filters silently), a client INSERT / UPDATE / DELETE of a file row is refused, a recording row still works for the old policies, update of only the three allowed fields, reorder, delete rights, cascade on task delete, first-per-task with the count, switch OFF refuses add. test_sql.sh keeps passing (install twice, delete leaves nothing).

10. Acceptance criteria

  1. A new project has filesFunctionalityEnabled TRUE; turning it off hides the tree column, the tabs and the Add actions; turning it on brings the files back.
  2. A user signed in with Google drops a PDF on the task Files tab (web): the file appears with progress, lands in Drive in FILES_KIT8_/project_<GUID>/task_<GUID>, the row has the Drive url, and the tree shows its name at once.
  3. The same on a phone with the + button; the card list is the default on a phone and a portrait tablet, the table on a desktop; the icon button switches both ways.
  4. A user without Google sign-in sees the list but the Add buttons say why they are off.
  5. The organization card lists the files of all its projects, finds a file by part of its name, and the task link opens the task. The project card shows only that project's files.
  6. Reordering by drag changes the order and survives a reload.
  7. Paper place typed in the table is shown on the card and the other way round.
  8. View opens text, .md, PDF, image, audio and video each in the right standard route; an unknown type shows the info page with Open in Google Drive.
  9. A user of ANOTHER organization cannot read, add, change or delete these rows (Docker test and a real second account).
  10. Old posts (recordings, YouTube) still work; no old project changes; test_sql.sh and the new Docker test pass; Jest has no new failing suite.

Not in this plan

  • Version history of a file, full-text search inside the files, thumbnails / OCR, an organization-wide Drive owned by a service account, copying files when a project or template is copied (task templates, project versions and the MS Project export do not carry files), push notification of a new file.
  • Uploading what the media recorder produced straight from the recorder screen ("attach this recording to a task") – the file row type allows it (R12), the button is a later small step.
