W1 File attachments – Work Breakdown Structure (v7, way C)

Files (documents, scans, audio, video, links) can be attached to an organization, a project, a stage, a task and to documents (invoices, orders …). The file lives in Google Drive inside ONE root folder kit8root of the organization. Way C: the organization's administrator connects ONE Google account once; a Supabase Edge Function keeps that account's token, refreshes it by itself and does every Drive call after checking the app permission. Members and project managers never sign in to Google. The app stores the Drive url and the data around it in a mediaPost row. Project setting filesFunctionalityEnabled (TRUE by default) switches the feature.

Status: BUILT in 3 slices on 2026-11-11 (upload / list / view / delete, replace + versions, move, document types, storage, health check; see kit8/files/README.md for what is still open). v7 written 2026-11-11: the whole plan rewritten for way C after the live spike (documentation/Goolge/GOOGLE_DRIVE_HOW_IT_WORKS.html, section 12: 12 of 13 steps PASS on a free Gmail account with only drive.file). Items marked Q are open questions with a recommended default (section 16).

What is new in v7 (way C replaces way B).
  • One Google account per organization (the administrator's, a free Gmail is enough). No Google sign-in for members, no Drive sharing, no per-user Drive tokens, no Workspace, no Shared drive, no Internal OAuth app, no Picker. The scope is only drive.file – one Google app serves all customer organizations.
  • All Drive work is on the server (Edge Function files-drive, section 13): connect, find / create folders, resumable upload sessions, streamed downloads, delete, move, copy, health check, cleanup. The database can now trigger deletes (pg_cron → the function), so the cleanup queue no longer waits for an open app.
  • Token auto refresh is built into the function (access token = one hour; refresh token kept server-side, encrypted). When Google refuses the refresh the organization becomes needs reconnect and the administrator sees a banner (section 4).
  • Uploads: the function opens a resumable session; the app sends the bytes straight to Google with no token (tested, W6). Downloads: the function streams them, with Range (tested, W7); players use a short-lived signed url.
  • Delete is bottom-up (tested: one files.delete on a folder gives 403 appNotAuthorizedToChild; deleting leaf first works, W12).
  • Permissions as decided: projectFileManager (organization / document files, root, Drive administration) and projectMediaPostManager (any post of a project), both true by default for the administrator and the project manager; all members read; a post outside a project is visible to its author only.
  • All eleven suggestions S1–S11 stay; S3 (Shared drive) is no longer needed. Tables files_…, PART 49, Docker test 55 stay.

QuestionAnswer in way C
Who talks to Google?Only the Edge Function, as the administrator's account, with the narrow scope drive.file. Every file and folder is made by the app, so the narrow scope sees all of it (W3, W6).
Who needs a Google account?Only the administrator who connects it (once). It can be a free Gmail. Members and project managers sign in to the app as today.
Where are rights decided?In the app's permission system. The function calls a SQL function (files_authorize, section 12) with the caller's JWT; the Drive account is never exposed to the caller.
Who owns the files in Drive?The connected account – one owner, one 15 GB free quota (a Workspace account has more). Permanent delete always works (the owner deletes).
How do the bytes move?Upload: the function opens a resumable session (it writes an uploadId into the file properties) and returns its url; the client sends the file directly to Google in chunks with Content-Range (multiples of 256 KB; the url itself carries the authorization – W6). F0b: a single PUT of the whole body reaches Google but a browser cannot read its answer; chunks are fully readable. The file is found again by the uploadId (upload_finish). Download / view: the function streams it, passing Range (W7). The function never buffers a file.
What can the database do?pg_cron + pg_net call the function with an internal secret: the cleanup of deleted tasks / projects / documents / organizations runs by itself, with no client open.
What happens when Google refuses?See section 4 (reconnect banner); files in Drive and rows in the database are untouched.
Three limits that follow from drive.file (decisions, not options).
  1. Only what the app made. The connected account's app sees ONLY the folders and files this app created. A foreign folder typed into the url field is invisible to it (Q24).
  2. Never change the Google OAuth client id. drive.file access is per file and per client id: a new client id would lose sight of every existing file. One Web client, used only by the Edge Function.
  3. One account. If the administrator's account is closed, the files go with it. A transfer to another account is a manual Google step (a Workspace account is better for a company). The health check (S1) shows who the connected account is.

4. The connection and the root folder (N1–N4, D1)

Values on the organization row (organizationTable.rowJSON, next to defaultProjectSettings; not project defaults – "Save settings to organization" does not copy them): organizationGoogleDriveMode (adminProxy), organizationGoogleDriveState (notConnected | ok | needsReconnect), organizationGoogleDriveAccountEmail, organizationGoogleDriveConnectedByGUID, organizationGoogleDriveLastRefreshAt, organizationGoogleDriveRootFolderUrl, organizationGoogleDriveRootFolderId. The token is not there: it is in files_google_connection_table (no client policy at all).

Step / caseWhat happens
Connect (Scenario 1)
  1. The administrator (any app login method – Google login is NOT needed) sees Connect Google Drive in Project settings → Files; after the first sign-in of a new organization a one-time prompt offers it. Only a holder of projectFileManager sees it.
  2. The button opens Google's consent page (authorization-code flow, access_type=offline, prompt=consent, scope drive.file only). The user picks which Google account to connect – a free Gmail is enough.
  3. Google returns to the Edge Function, which exchanges the code, stores the refresh token (encrypted) and the account e-mail, and sets …State = ok.
  4. The folder: the function looks for a folder titled kit8root carrying its properties mark (S2) – found and used when it exists (a reconnect never makes a duplicate) – and creates it only when it is missing. It stores the url and the id on the organization row.
  5. A failure shows ErrorModalWindow; the button stays.
The root url field (Scenario 2)A TextInputApp on the Files tab shows the url (read only for a user without projectFileManager, with the reason as a tip). A holder may paste another url; the function checks it with the connected account (files.get): it must be a folder the app can see – in practice a folder this app made (limit 1 of section 3). Otherwise: "Google lets this app use only folders it created. Use Set up to create a new kit8root, or reconnect the account that made this folder." A user who signs in without Google can still change the field (it is a database value); only the check needs the connection.
Who may connect / changeA holder of projectFileManager – by default the administrator and the project manager (Q11). Enforced in the function and in the RPCs, not only in the interface.
Token auto refresh (required)
  1. An access token lives about one hour (observed 3598 s). The function asks getAccessToken(organization) for every Drive call: a cached token while it has more than 5 minutes left, otherwise POST oauth2.googleapis.com/token with grant_type=refresh_token (client id + secret from the function secrets). One refresh at a time per organization; a Drive 401 forces one refresh and one retry.
  2. invalid_grant (the administrator revoked the app, security settings changed, unused about 6 months, or the Google app is still in "Testing" – 7 days) → …State = needsReconnect with the error text (never the secret). The app shows a banner to holders of projectFileManager: Google Drive is disconnected – reconnect. Uploads and views say so; the cleanup queue waits.
  3. A weekly pg_cron call refreshes every connected organization once (no expiry from non-use; a current status).
  4. In the app nothing refreshes: the client holds only its Supabase session, which supabase-js refreshes by itself. The resumable session url handed out by the function is the only Google credential a client touches; it has a limited lifetime, so a queued upload asks for a new one when needed.
Change of the account laterReconnect with a different Google account: the old folder is invisible to the new account (limits 1 and 2), so the window says: Files stay in the old account. Move them first (S7) or accept that the old files can no longer be opened. The supported path: connect the new account, then S7 "move the root" copies the files across accounts (section 11).
DisconnectButton Disconnect: the function revokes the token at Google and deletes the stored token; rows and Drive files stay. State notConnected.
Empty / not connectedThe Add buttons are off with the reason "Google Drive is not connected – ask the administrator" (a holder sees Connect Google Drive instead). Reading files already stored needs the connection too (files are streamed through the function).

  • The folder names organization, project, task, document, template, files are fixed words; the GUIDs are the lower case uuids of the rows. The file keeps the name the user gave it (the Drive file id identifies it, so two files with the same name are possible – the list warns on the second one).
  • The whole chain is made on the first upload by the function (tested, W4: five levels); a folder is found by its properties mark or by name inside its parent. Two uploads at the same moment could make the same folder twice, so the ids are recorded in files_folder_table (section 12): first writer wins, the function removes its empty duplicate. The same table tells the delete step what to remove.
  • The path is also information on the row (googleDriveRelativePath). A task moved to another project leaves its Drive folder where it is; the links keep working.
  • S2: every folder gets a readable description and properties (GUIDs; key + value ≤ 124 bytes – tested, W5) so a person browsing Drive – and the health check – can tell what it is.

6. Delete rules (N7, A2, A3, Q10)

Delete is PERMANENT and BOTTOM-UP. The function uses files.delete (no Drive trash; nothing can be restored). A delete window says: "N files will be deleted from Google Drive permanently." Tested: files.delete on a folder with children gave 403 appNotAuthorizedToChild in the full test (twice) but HTTP 204 in ten smaller trials (F0b) – the cause is not known, so the function deletes files first, then folders from the deepest (every call HTTP 204, always worked), and may try one call first with this as the fallback. Slower – the cleanup is a background job. Trashing a whole folder in one call works (HTTP 200).
EventWhat happens
One file deleted in the listThe client calls the function (delete); it checks the permission (projectMediaPostManager for project / stage / task files, projectFileManager for organization / document files), deletes the Drive file, then files_delete removes the row. A Drive "not found" counts as done.
A task / stage is deleted in the app
  1. The confirmation window gets one more line – "N files will be deleted from Google Drive permanently" (files_count_for_delete counts the task and everything under it).
  2. Database, always: a statement trigger on project_task_table DELETE (transition table; the task tree goes in one statement) deletes the file rows of every removed task and writes lines into files_drive_cleanup_table (the folder task/<taskGUID> and the known file ids). This runs for any delete path: another user, a project delete, the REST API.
  3. The cleanup tick: pg_cron (files_cleanup_tick, every minute) calls the function through pg_net with the internal secret; the function takes the waiting lines, deletes bottom-up with the organization's token, marks them done (a Drive "not found" = done) or failed with the reason and the attempts. The client additionally pokes the function right after a delete so the user does not wait a minute. Without pg_net the poke and a button Run cleanup (Files tab) do the same.
  4. The administrator sees Google Drive cleanup: 3 waiting, 1 failed on the Files tab, with Retry. While the state is needsReconnect the lines wait.
A project is deletedSame for the folder project/<projectGUID> (project files and all task folders) and its file rows.
A draft document is deleted (S6)The document RPCs (delete_vendor_invoice …) delete the draft; a statement trigger on each of the seven document headers removes the file rows and queues document/<kind>/<documentGUID>. A posted document cannot be deleted (unpost first), so its files stay.
A task template is deleted (S11)A trigger on the template header queues template/<templateGUID> and deletes its files_template_file_table rows. "Fill with Replace" deletes the old tasks of the target: their files go by the task rule.
An organization is deleted (Q5, Q10)
  1. The window asks the administrator to type the organization name and says: "The Google Drive folder named in the root url (kit8root) and ALL files in it will be deleted permanently." It shows the number of files and the used storage (S8).
  2. A statement trigger on organizationTable DELETE queues the root folder (the one named in the url – always, whoever made it, Q10) and deletes all file, folder and version rows. The queue line carries the organization GUID as plain text (no foreign key), and files_google_connection_table keeps the token until the queue of that organization is done.
  3. The function deletes the tree bottom-up, then the root folder, then revokes the token at Google and deletes the stored token.
A file is replaced (S4)Nothing is deleted: Drive keeps the old revision (kept forever) and the row notes the new version. A permanent delete of the file deletes its revisions too.

Not covered: files of a project version (a version is a plan copy and carries no files), and "orphan" files that exist in Drive without a row – the health check (S1) finds those.

11. The suggestions S1–S11 – design (all are built)

All eleven are part of the plan (A4); under way C each runs in the Edge Function. The work package is in brackets.

S1 Health check "Check files" (F7)

A button on the Files tab and in the dashboard menu (holders of projectFileManager; the organization scope walks the whole root, a project or task only that part). Read only until the user presses Repair on selected lines; the result can be copied. The function does the walk (page by page, with progress through repeated calls and a Cancel):

  1. files_health_rows(scope) returns the file rows with their Drive ids and the GUIDs of the tasks / projects / documents that still exist.
  2. The function lists the Drive folders by id (files.list, '<folderId>' in parents).
  3. Findings and repairs: A a row whose Drive file is missing → delete the row (or keep). B a Drive file in a files folder without a row (orphan) → Adopt or delete permanently. C a folder of a task / project / document that no longer exists → delete (bottom-up) after a confirmation with the count. D a folder not in files_folder_table (record lost) → register it through its properties (S2). E the same folder name twice in one parent → move the children into the recorded one, delete the empty duplicate. F connection problems: state needsReconnect, root not found, account e-mail changed. G rows under another root / account (S7) → Move. H the Drive storage quota nearly full.

Limit: it sees only what the app made (limit 1). It never repairs on its own.

S2 Readable folders (F7)

When the function creates a folder it sets the description (kit8 · Project "Bridge" · 11111…, for a task its name and project) and the properties kit8Kind, kit8OrganizationGUID, kit8ProjectGUID, kit8TaskGUID … (key + value ≤ 124 bytes, tested W5). The folder NAME stays the GUID (stable, never renamed). The description is refreshed at the next upload after a rename and by the health check. The marks are what the connect step uses to find an existing kit8root. Use properties, not appProperties (fact 5).

S3 Shared drive as the root – not needed

Way C gives what a Shared drive was for: one owner of every file, delete that always works, no per-member Drive access. A Workspace account can still be the connected account (more storage, company-owned). A root inside a Shared drive would work only if the connected account's app creates it there (supportsAllDrives=true) – untested and not planned.

S4 Replace file + versions (F8)

Row / card menu Replace…: the function opens an update session for the same Drive file (PATCH with uploadType=resumable), the client sends the new bytes, the function finishes: it marks the old revision keepForever (W10) and calls files_replace – size, MIME, kind, fileVersionNumber + 1 and one line in files_version_history (the OLD version: revision id, size, name, who, when). The Drive id, the url, the row, the paper place and the document type stay (W9). The Versions panel lists them; Open / Download of an old revision by revisions.get; Restore = download that revision and replace with it (a new version, nothing is lost). Rights: as edit. Old revisions count in the storage (S8). A delete removes every revision for good.

S5 Document types (F8)

Catalog files_document_type_catalog (universal columns; owner empty = seeded rows for everybody, owner = organization for its own types). Seeds in start4 / start5: Contract, Invoice, Specification, Drawing, Photo, Report, Minutes, Certificate, Other. Screen Catalogs → File document types (administrator CRUD; others read; a seeded row is read only). The file row stores fileDocumentTypeGUID; the dashboard has the column, the filter and an inline edit; the add window can ask for the type. Check in F2 that kit8_setup_def_table and SystemMetaData accept a snake_case table name; if not, the table is set up like the PM tables.

S6 Files on documents (F9)

Scope document for the seven documents: vendor invoice, purchase order, product receipt, customer invoice, payment fact, fact input, time sheet (fileSourceKind = document, fileDocumentKind, parent = the document GUID). Drive path document/<kind>/<documentGUID>/files/. A paperclip button with the count sits in the form bar and in the row menu of each list. Rights (Q11): reading = every member that may read the document; add / edit / replace / move / delete = a holder of projectFileManager. Files can be added to a POSTED document (the scan of the paper invoice arrives after posting). A draft document that is deleted removes its files (section 6); a posted one cannot be deleted.

S7 Move a file / move the root (F8)

Move a file: row / card menu Move to… opens the project dashboard as a picker (PMProjectDashboard picker: project → task, or the organization / a document); the function moves the Drive file (files.update with addParents / removeParents; the id and url stay) and calls files_move – the row gets the new parent, kind, project, folder id and path. On web an optional drag of a row onto a task row of the open tree can call the same code if the Skia hit test allows it (nice-to-have).

Move the root: the account is the same → the function MOVES the folders organization, project, document, template into the new root (a few calls; every id stays), then files_root_moved(old, new) updates the rows and the folder table. A different account (after a reconnect with another Google account): Drive cannot move between owners, so the function copies – downloads from the old account and uploads to the new one, streamed through the function, resumable, file by file, with progress, stop and continue; the to-do list is in the data (rows whose googleDriveAccountEmail or root differs from the current one). It needs both tokens during the move, so the old connection is kept until the move finishes (files_google_connection_table holds two rows for that time). Copies are owned by the new account.

S8 Storage used + limit (F10)

files_storage_used(scope) sums fileSizeBytes (links count 0; old revisions of S4 from files_version_history) per organization, project and uploader. The function also reads the account's Drive quota (about.get?fields=storageQuota) so the Files tab shows used / free in Google. Optional limit filesStorageLimitMegabytes (empty = none): files_storage_check(size) is asked BEFORE an upload session is opened, and files_add checks again. A free account fills at 15 GB: the Files tab warns at 90 % (finding H of S1).

S9 Upload queue with retry on phones (F10)

A picked file is first copied into the app's document folder (expo-file-system) and listed in a queue on the device (AsyncStorage: id, scope, local uri, name, MIME, size, attempts, state, last error). A worker uploads when there is a connection (check whether @react-native-community/netinfo or expo-network is installed; otherwise a failed request is the signal): it asks the function for a session, sends the chunks, asks the function to finish. It retries with a growing pause (3 in a row, then failed with Retry), survives a restart, and removes the local copy after the row is written. Way C makes this simpler: it needs only the Supabase session (no one-hour Drive token to renew). A session url that is too old is replaced by a new one. A queued file is visible in the dashboard; a size cap (default 500 MB) refuses new picks. Web: the queue lives while the page is open (a browser keeps no file handle after a reload); IndexedDB later.

S10 Attach a recording (F9)

In the result screen of the media recorder (app/media/record/*) a button Attach to… opens the same picker as S7 (project → task, project, organization, document; only for a holder of the matching permission). The recording file goes into the queue of S9 and becomes a normal file row in that scope (kind audio / video, title = the recording title; the original recording row stays in the recordings list, visible to its author only). Web recordings (a blob) are uploaded at once.

S11 Copy files with task templates (F11)

Templates (PART 40) are shared by the whole organization and survive their source task, so they must not point at files that can be deleted. Save to template… gets Include files (default off): the function COPIES each Drive file of the saved tasks into template/<templateGUID>/task/<templateTaskGUID>/files/ (files.copy, W11; server side, no bytes through the client) and records them in files_template_file_table. Fill from template… gets Copy files (default on when the template has files): after task_template_fill the function copies each template file into the new task's folder and writes the file rows. This needs the map from template task to created task: F11 checks that task_template_fill returns it and adds it if not (the fill keeps its transaction and speed). Deleting a template removes its folder (section 6). Not copied: files of a project version, and the files of "Replace what the row has now" targets (deleted with their tasks). A missing source file is skipped with a report line. Copies count in the storage (S8).

12. SQL (PART 49 – files)

Rules of the project: tables / indexes in start1_sql_tables.sql, everything else in start2_sql_code.sql (same PART), the cleanup schedule in start3_sql_pg_cron.sql, seeds in start4 / start5, drops in delete_sql_structure.sql; idempotent; tested in Docker before it is handed over. New tables are files_…, snake_case (_catalog = справочник, _table = register, _history = periodic).

Row rules on mediaPostTable (Finding 5, decided). Today its policies are USING (true) for anon and authenticated. The plan separates the rows:
  1. A post outside a project (no fileSourceKind and no project / task parent: recordings, links, intent posts) – visible, changeable and deletable by its author only (rowOwnerGUID = the signed-in user, Q15). No permission is involved; anon sees nothing. Old rows with no real author are removed by del_old_mediaPost.sql (Q19: not actual).
  2. A post of a project (file rows of the scope project / stage / task, and any other post whose parent is a project or task) – read by every member of the organization (Q14); created, changed and deleted by a holder of projectMediaPostManager only – for any post of the project.
  3. A file of the organization or of a document – read by every member (documents: the members that may read the document); written by a holder of projectFileManager.
File rows are written only by the SECURITY DEFINER RPCs, which ask the permission; the policies carry the read rules.

start1 – tables

  • files_google_connection_table – the connection secret: organization GUID (plain text), account e-mail, refreshTokenEncrypted, state, last refresh, last error, connected by, created. RLS on, NO policy for any client role; read and written only by the function (service role) and SECURITY DEFINER status functions that return no secret. Encrypted with a key held in the function secrets (FILES_TOKEN_KEY, AES-GCM in the function) – the database never sees the plain token.
  • files_folder_table – one row per Drive folder pair: organization, scopeKey (organization | project:<g> | task:<g> | document:<kind>:<g> | template:<g>:<taskG>), project GUID, driveFolderId, driveFilesFolderId, root folder id, account e-mail, created by, date. Unique on (organization, scopeKey) – first writer wins.
  • files_drive_cleanup_table – what has to be removed: organization GUID (plain text, no foreign key), Drive item id, item kind (file | folder | tree), why (file deleted | task deleted | project deleted | document deleted | template deleted | organization deleted | moved), requested by, attempts, last error, state (waiting | running | done | failed), timestamps.
  • files_upload_pending_table – binds an upload to its finish: session id, organization, scope, parent, name, MIME, size, requested by, expires. files_add accepts a row only for a pending upload the function has verified in Drive.
  • files_document_type_catalog (S5), files_version_history (S4), files_template_file_table (S11) as described in section 11.
  • Partial index on mediaPostTable ("rowOwnerGUID", "rowParentGUID", "orderInList") WHERE "rowJSON" ? 'fileSourceKind' and one on ("rowJSON"->>'fileSourceProjectGUID').

15. Acceptance criteria

  1. A new project has filesFunctionalityEnabled TRUE; OFF hides the tree column, tabs and Add actions; ON brings the files back.
  2. Connect: the administrator (signed in WITHOUT Google) taps Connect Google Drive, chooses a free Gmail account, and a folder titled exactly kit8root exists in that Drive and its url is in Project settings → Files; the state shows Connected as …. Connecting again, or a second administrator, finds the same folder and makes no second one. Nobody picks a folder.
  3. Members need nothing from Google: a project manager and a plain member, signed in with e-mail and password only, add (project manager) and open (both) files without any Google dialog.
  4. Auto refresh: after the access token expired (more than an hour) an upload and a view still work with no user action; after the administrator revokes the app in Google, the state becomes needs reconnect, the banner shows to the holders of projectFileManager, uploads say why, and Reconnect restores everything.
  5. A PDF dropped on a task (web) appears with progress and lands in kit8root/project/<projectGUID>/task/<taskGUID>/files/ – the bytes go from the browser straight to Google; a file added to the project lands in …/project/<projectGUID>/files/; a file of the organization lands in kit8root/organization/files/. The row has the Drive id and the tree shows the name at once.
  6. Two uploads at the same moment reuse the same folders (no duplicate folders); the folders carry the readable description and marks (S2).
  7. Deleting a task with files: the confirmation says how many files will be deleted from Google Drive permanently; within a minute (or at once after the poke) the task folder is gone from Drive – deleted bottom-up, not in the trash – the rows are gone and the queue line is done, also when the task was deleted by another user or by SQL.
  8. Deleting an organization deletes the folder named in its root url from Drive (permanently), revokes the token and removes the stored token; the file, folder and version rows are gone.
  9. Cards by default on a phone and a portrait tablet, table on a desktop; the icon button switches both ways; reorder by drag survives a reload; paper place typed in the table shows on the card.
  10. The organization card lists the files of all its projects, finds by part of a name, the task link opens the task; the project card shows only that project.
  11. View opens text, .md, PDF, image, audio (seekable), video (seekable) each in the right route through the signed url; unknown types show the info page; a signed url stops working after its lifetime.
  12. S1 the health check finds a file deleted by hand in Drive, an orphan file, a folder of a deleted task and a lost folder record, and repairs each only after a click. S4 Replace keeps the url and the row, Versions shows the old version, Restore makes a new one. S5 a file gets a type, the filter finds it. S6 a posted vendor invoice gets a scan; deleting a draft invoice removes its files. S7 a moved file keeps its Drive id; changing the root and pressing Move leaves no row under the old root. S8 an upload over the limit is refused before it starts. S9 a file picked with no connection uploads later by itself, also after the app was closed. S10 a recording is attached to a task. S11 a template saved with files fills a new task with its own copies.
  13. A plain member reads every file but has no add / edit / delete button and the RPCs and the function refuse; the administrator and the project manager can do all. Recordings and other posts outside a project are seen by their author only; a project manager can change any post of a project. A user of ANOTHER organization cannot read, add, change or delete these rows; no client role can read files_google_connection_table; test_sql.sh and test 55 pass; no new failing Jest suite.
