Consolidation

Every project may have its own currencies. The organization has ONE more currency, the currency for consolidation, and every money amount that a report adds up across projects is also kept in that currency, in a new sum sumForConsolidation that lives next to sumForBudget and is calculated by the database alone.

BUILT 2026-11-17 (C1-C6 and C8; C7 and the parts listed in “Built vs plan” are NOT built) · SQL PART 52 (start1_sql_tables.sql tables, start2_sql_code.sql code, start3_sql_pg_cron.sql the tick) · modules kit8/pm/reports/consolidation (Monitor08), kit8/catalog/organization/consolidation, kit8/catalog/organization/currencies · Docker test tests/100_consolidation.sql (75 checks)

The request (owner, 2026-11-17)

  1. Make all currencies editable for each project.
  2. An organization-only setting currencyForConsolidation. It must consolidate the data of all projects.
  3. sumForConsolidation must work in parallel to sumForBudget and the other sums.
  4. sumForConsolidation must be auto calculable.
  5. sumForConsolidation is not visible and not editable in the documents; it appears in the reports only.

Improvement of 2026-11-17 (second round)

  1. Q7 decided: currencyForConsolidation is obligatory: consolidation is never off (sections 2, 3 and 5, decisions Q7 / Q12 changed).
  2. Two new organization settings: Include purchase VAT into consolidation and Include sale VAT into consolidation (section 2, decision Q11).

Why it is needed, and the rules

The problem point 1 creates

Project A budgets in EUR, project B in USD. A report that adds the two (the footer of Monitor02, the totals of Monitor01 over "all projects", Monitor07 per partner) would add euros to dollars. Today the project currencies are the same inside an organization, so it never showed. Once they are free, a sum over several projects is only meaningful in one currency: that is the consolidation currency.

Rules

  1. Convert at the finest grain, add afterwards. The conversion is made per movement (its own day); totals are sums of converted movements, never a conversion of a total.
  2. Project currencies are never added to each other; a report that spans projects with different budget currencies is forced to the consolidation basis (or says "mixed").
  3. Same shape as the budget sum: net · VAT · VAT that is cost are stored; what a report adds is chosen at read time by the two organization switches consolidationIncludePurchaseVAT / consolidationIncludeSaleVAT (section 2).
  4. currencyForConsolidation is obligatory: consolidation is never off, so a cross-project total always has a currency to be added in.
  5. Only the database writes it. The client never sends it; the Post transaction and the worker are the only writers.
  6. Posting is never refused because of consolidation (a reporting layer): a missing rate is a gap that the worker closes later.
  7. Same currency = no conversion: when the budget currency of the project IS the consolidation currency, sumForConsolidation = sumForBudget exactly.

1 · Currencies editable for each project

What changes

  • Project settings → Budgets → Main: currencyForBudget, currencyForAccounting, currencyForContract are editable fields again (PMProjectBudgetsTab: currenciesEditable default becomes true; the read only message CURRENCIES_ORGANIZATION_MESSAGE goes away). The two rate types per project (exchangeRateTypeForAccounting / ForBudget) stay as they are.
  • The organization screen keeps the three currencies as defaults: a new project starts from them; the existing window "Change the currencies of the organization?" (Yes = recalculate all projects, No = save only, Cancel) stays, and its text says that Yes overwrites the own currencies of the projects.
  • A project whose currencies differ from the organization's shows a small mark "own currencies" in the settings window (information only).

A change of ONE project

  1. The user edits a currency and presses Save. An approval window (askPMApprove) lists the change: Yes = save and recalculate this project; Cancel = save nothing. There is no "save only" here: old lines in the old currency under a new project currency would be wrong sums.
  2. Recalculate = the algorithm of the organization run for ONE project: the core of recalculateOrganizationProjects.ts is split into recalculateProject(env, project) (the organization loop calls it for each project; no behavior change), the task lines are converted again (recalculateLineFx), the posted tasks are posted again (runTaskPost), the cost totals are refreshed, then the project is queued for consolidation (section 3-4).
  3. A read only project is refused (only the read only switch changes).
  4. Right: the project manager (update right on project_table), the same as other project settings.
The one real danger (decision Q1). The organization recalculation re-posts the tasks but does not touch the lines of posted documents (invoices, orders, receipts, fact input, time sheets, payment facts): their sumForBudget / sumForAccounting were frozen in the old currency. After a change of the budget or accounting currency the register of that project would hold old and new currencies together. Recommended: a database guard (project_currency_guard, BEFORE UPDATE on project_table) refuses a change of currencyForBudget / currencyForAccounting while the project has any posted document and says how many of which kind ("unpost them first"); currencyForContract (only the default of a new line) is always free. A later package can add "rebuild the posted documents" (touch each line so the line trigger recalculates, then re-register).

The two VAT switches

  • Purchase side = the plan, order, receipt, fact and vendor invoice rows of Time / Material / Expense. Sale side = the customer invoice rows (kind sold) and the Revenue lines of the plan and the fact input.
  • The switches change only what a report ADDS, never what is stored: the twins keep the three components (sumForConsolidation = net, vatForConsolidation, vatInCostForConsolidation) and the database function consolidation_amount(net, vat, vat_in_cost, side) (the sibling of vat_basis_amount) picks the amount from the two switches. So a change of a switch needs no recalculation: it is saved at once and every report shows the new figures.
  • Consolidation is ONE number for the organization, so in the consolidation currency basis the two organization switches replace the VAT basis selector of the report (the selector shows "set by the organization"). In the project currency basis the VAT basis selector works as before.
  • Rows that are already with VAT by their nature are outside the switches: payments (task_payment_plan_movements), the cash ledger and the partner balance store the gross amount; their twin is the gross amount converted, with no VAT components.
  • ROI (phase 2) uses the same two organization switches for the all-project totals; the project ROI switches (projectROIInclude…) stay for the ROI of one project.
  • The block says in words what each switch does, and every report header that shows the consolidation basis prints the two states ("VAT: purchase without, sale without").

The screen

  • Organization edit gets a block Consolidation (next to the currencies, outside the project defaults): a currency select (no Clear: the field is obligatory, a save without a currency is refused with a message), a rate type select, the two VAT switches, the state badge, the number of gaps, a "Refresh now" button. Visible and editable for the administrator only (organization_is_admin); the others do not see the block.
  • A change of the currency or of the rate type asks an approval window (the VAT switches do not: see above): Yes = save and recalculate every project of the organization (a database job, below); Cancel = nothing. There is no "No": half of the book in the old currency would be wrong.
  • Pure rules in kit8/catalog/organization/consolidation/consolidationModel.ts (codes, changed?, words of the window) like organizationCurrenciesModel.ts; tested without a screen.

In SQL

  • fx_consolidation_currency() and fx_consolidation_rate_type(): like fx_base_currency(), they read the row of organization_of_current_user(). A variant with the organization as an argument serves the worker (no user).
  • Obligatory in the database too (Q7): a trigger on organizationTable refuses a row whose currencyForConsolidation is empty, is not a code of currencyTable, or whose rate type is empty, for every writer except the install backfill; organization_for_email (the organization made at the first sign in) sets it at creation to USD (owner decision 2026-11-17; the budget currency of a new organization is USD too). Any other insert that sends none gets the default of the trigger (budget currency of its default project settings, else the base currency, else EUR). The two switches are booleans, a missing value is read as OFF (=== true in TS, vendor_project_setting_on style in SQL).
  • A trigger on organizationTable (change of the currency or the rate type, not of the switches) writes one row per project of the organization into consolidation_dirty and sets consolidationState = 'recalculating'. Only the administrator can change the row (the organization guard of PART 45); the keys consolidationState are protected from a client write by the same trigger.

3 & 4 · sumForConsolidation, parallel and automatic

How it is calculated

consolidation_convert(p_amount, p_project, p_day) =

  • source = the budget sum of the movement and the currencyForBudget of its project (decision Q2: every table already has the budget sum and the project, so one rule fits all of them; converting from the contract sum would need a currency column in each table);
  • target = currencyForConsolidation of the organization of the project, rate type exchangeRateTypeForConsolidation;
  • day = the day of the movement (periodDay / the date of rowTurnoverMoment / the document date) - the same day the budget sum was made;
  • same currency → the amount itself; otherwise fx_convert(...) (the existing D365-style pair rate with the "latest rate on or before the day" rule, rounded to the decimals of the target currency); no rate → a gap (below).

The same function converts the VAT and the VAT that is cost, so the three components keep net + VAT consistent in the consolidation currency.

Where the column lives (parallel to sumForBudget)

Rule: a table gets a twin when it is a register or a report table (written by Post / a worker, read by reports). A table that holds the lines the user types does not (section 5). The exact list is made at C3 by scanning the sumForBudget… columns; a Jest test (consolidationTwinsSql.test.ts) fails when a table of the first group has one without its twin.

Auto calculation (point 4)

EventWhat happens
Post / Unpost of any documentThe register function writes the movement WITH its consolidation sum in the same statement (Unpost deletes it with the movement). Frozen at Post like the budget sum (decision Q3).
Consolidation currency or rate type changesTrigger on the organization row queues every project → worker recalculates the consolidation columns of all register / report tables, project by project; state recalculating then ready.
A project currency changes (point 1)The recalculation of that project re-registers it; the trigger on project_table (currency keys) queues the project.
A rate is missing at PostThe movement is written with 0 and one row in consolidation_gap_table (movement, from, to, rate type, day, reason noExchangeRate / noBudgetCurrency; there is no "no consolidation currency" reason: it is obligatory); Post goes through (decision Q5). State gaps, reports show the number.
The missing rate is entered (ECB seed, a user)A trigger on currencyExchangeRateTable (the pattern of trg_cash_ledger_rate: it does nothing while there are no gaps) wakes the worker for the gaps of that currency; the gap closes, the sums are filled.
Anything else (safety net)pg_cron job consolidation_tick (10 s, start3_sql_pg_cron.sql) calls consolidation_process_dirty(); the button "Refresh now" = consolidation_refresh_now(org) works without pg_cron, like "Refresh rests" of the money accounts.

5 · Not visible and not editable in the documents; reports only

Documents

  • No table of the "NOT stored" group has the column, so a document form, a list, the Finances table, a ReusableTable "Fill all lines", a file import or a template can neither show nor carry it. There is nothing to hide, so nothing can leak by a forgotten column.
  • The register tables are written by SECURITY DEFINER functions only (as today): a client has SELECT, no insert / update / delete; a client value would be overwritten anyway.
  • A test (consolidationNotInDocumentsSql.test.ts) lists the document tables and fails if one gets a …Consolidation column; another (consolidationNotInUi.test.ts) greps the document and task-line column files.

Reports

  • Currency basis next to the VAT basis: CurrencyBasisSelect + useCurrencyBasis (kit8/pm/reports/common, kept in AsyncStorage like useVatBasis): Project currency | Consolidation currency. The amounts of the report switch; the columns stay the same (no doubled column set). The header says the currency ("Amounts in EUR (consolidation)").
  • With several projects of different budget currencies in the scope the report is forced to the consolidation basis. Consolidation is never off (the currency is obligatory), so there is always a correct total to show; a project currency basis over several currencies shows the projects side by side and no total.
  • In the consolidation basis the VAT basis selector is disabled and shows "set by the organization": the two switches of section 2 decide.
  • Used by Monitor01 (strip, totals, grid), Monitor02 / 03 (all-project totals, phase 2 with the ROI twins), Monitor07 (partner balance across contracts).
  • The Gantt tree column costTotalForBudget is a project view, not a report: it stays in the project currency.

New report Monitor08 Consolidation (Drawer → Reports)

  • Rows = projects of the organization (a row per project; the top row = the total), optional second level = month; columns = Budget (plan) · Ordered · Received · Used · Vendor Invoice · Customer Invoice · Cash in · Cash out, all in the consolidation currency, VAT basis switch as everywhere, filters = period, project selection (default all), genus.
  • Shows only the projects the user may read (the existing RLS / perm_projects): a member sees the consolidation of his own projects, the administrator that of the organization. No new permission profile.
  • A badge: Live / Recalculating (a progress count) / N gaps with a drill-down list of the movements without a rate; a double click on a number opens its movements (the drill-down of Monitor01).
  • Built on the shared layer kit8/pm/reports/common (data hook, filter bar, formats, age badge) and the report registry; Views (save / restore) work as in Monitor01.

Limits (NOT built, NOT promised)

  • Financial statement translation of IAS 21 / ASC 830 (closing rate for the balance, average rate for the result, translation reserve). Here: ONE rate per movement day.
  • Elimination of intercompany transactions (projects or legal entities of the same organization that trade with each other).
  • More than one consolidation currency, a consolidation per legal entity, a consolidation across several organizations.
  • A consolidated Gantt / project cost tree; the tree stays in the project currency.
  • Changing the currency of an old posted document line (Q1 alternative).
