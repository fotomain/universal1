Task templates

A task - or a stage with everything inside it - is saved under a title and can fill another task later, in any project of the organization. The structure is the one of the project versions (PM_VERSION_STRUCTURE.html), but for ONE task and shared by every user of the ORGANIZATION.

SQL PART 40 (start1_sql_tables.sql tables, start2_sql_code.sql code) · module kit8/pm/tasktemplate · Docker test tests/98_task_template.sql · Jest __tests__/pm/tasktemplate

The request

  1. The task three dots menu gets two items: Save to template and Fill from template.
  2. Separate SQL tables, just like for the project versions (version_ tables) - not the tables of the project templates.
  3. The templates are available for all users of the one organization.

The names say what they hold; a template has its OWN ids, so the template stays whole when the task it was made from is deleted or moved.

Relations

All three child tables are tied to task_template_header (and the task rows to each other) by foreign keys with ON DELETE CASCADE: deleting a template deletes its tasks, links and lines. Rows that were filled from a template are normal project rows and stay.

Save and fill

RPC task_template_save(p_task, p_title, p_description)

  1. The task must be in a project the user owns; the user must have an organization; the title must not be empty.
  2. One advisory lock per organization; the number = highest of the organization + 1.
  3. Copies the task and every row below it (tree path), with the parent as a GUID, the order, the cleaned rowJSON.
  4. Copies the links whose both ends are inside; copies the lines of those tasks (cleaned).
  5. Writes the counts into the header. Returns the template GUID.

RPC task_template_fill(p_template, p_task, p_replace)

  1. The target must be in a project the user owns; the template must be of the user's organization.
  2. New ids are made from one run id and the id in the template (so links and lines map to the new rows without a temp table).
  3. tree (the top row is a stage, or has rows inside): the rows inside the top row are created inside the target, after its rows; the links and the lines go with them.
  4. single (one task): its data (not the name, not the kind) go into the target and its lines are added after the lines of the target.
  5. Returns {mode, tasks, lines, dependencies}. Lines come unposted.

The four tables are written ONLY by the RPCs (SECURITY DEFINER); the client has SELECT, and DELETE on the header (the creator or the administrator; the rows follow). Row level security: the header by rowOrganizationGUID = organization_of_current_user(), the three child tables by task_template_visible(rowTemplateGUID). The tables are not in the realtime publication; the list is read again after every command.

Big templates

A request of the app may take 8 s (Supabase). Measured on the local Postgres 15 with ./bench_task_template.sh N (a stage with N rows inside, 2 task lines a row, a link for every 2nd row; every step is its own transaction, the time includes the start of psql).

What was slow and what was done

Hot spotCauseFix
pm_task_after_progress_change (every inserted / deleted task)recalculated the progress of the WHOLE project after every row, and the recalculation compared every row with every row (a CTE has no index)pm_recalc_project_progress uses the GiST index and the ancestor paths (n x depth, same result - tested); the fill switches the trigger off (app.task_bulk) and calculates ONCE at the end
user_calendar_project_task_syncper row; with the stale statistics of an empty calendar table the planner scanned the whole table: 7 ms a taskoff in bulk mode; the calendar rows of all new tasks are made by ONE statement, the rows of the deleted tasks are deleted by one statement
pm_task_dependency_after_delete (Replace)rebuilt the closure of the project for every deleted linkoff in bulk mode; pm_rebuild_dependency_closure once after the delete
pm_task_dependency_before_insertwalks the graph for a cycle: 1.2 ms a linkskipped in bulk mode: the links are copies of a saved acyclic set between brand-new rows (the check of a single link a user draws is unchanged)
Save: parent of a row, lines, linksa join / an EXISTS per row that scanned the project (all task lines of the database)parent from the path (the last label is the id), lines and links joined from the rows of the template through their keys; ANALYZE of the new rows when the template is big

The remaining time of Replace is the foreign key checks of the 30 tables that point at a task (the same cost as the Delete command on 10 000 rows). Hence the limit: a row with more than 5 000 rows inside is refused at Save ("save its parts as separate templates"). The picker shows the counts so a big template is no surprise; the Fill button shows a spinner while the database works.

The same fixes make Duplicate of a big stage, an import and every other bulk write of tasks faster, because they were in the shared triggers.

Decisions and limits

These were chosen without asking; each is one place to change if the owner wants it otherwise.

QuestionBuilt asTo change
What does "Fill" do with the name of the target?The target keeps its name and kind; a task template adds data + lines, a stage template creates the rows inside.task_template_fill, single branch
Who may rename / delete?The creator and the administrator of the organization.policy task_template_header_delete, task_template_set_title
Sums in the project currenciesNot copied; the user presses Recalculate. (Copying them would show the sums of another project's currency.)key list in task_template_clean_line
Can a template be changed after it was saved?Only its title and description (like a project version). A new state = a new template.-
Delete of a creator's userThe templates stay (the organization owns them); only the e-mail text in the header remains.-
Fill into a project of ANOTHER userNot possible: the target project must be owned by the user who fills.pm_owns_project in task_template_fill
Dependencies from / to rows outside the saved row, links of the stage itselfNot saved / not copied.-
Undo of a fillThere is no Undo step (the rows are written by the database). Delete the rows, or use "Replace".-

Install

  1. Run kit8/sql/start/start1_sql_tables.sql, then start2_sql_code.sql in the Supabase SQL editor (idempotent). start3 and start4 are not needed.
  2. Until then the picker shows a hint and saving answers "missing"; the rest of the app works as before.
  3. Check: SELECT table_name FROM information_schema.tables WHERE table_name LIKE 'task\_template\_%'; returns four rows.
  4. Remove everything: delete_sql_structure.sql (part 1a-00000000 drops the templates of ALL organizations).
