3. The principle: three bases, one switch

Standard accounting treats VAT by whether the entity can get it back:

  • Recoverable (input) VAT is not a cost. It is a receivable from the tax authority, so the cost of what was bought is the amount without it. IAS 2 (inventories) says the cost of purchase includes duties and taxes other than those the entity can recover from the tax authorities afterwards; IAS 16 (property, plant and equipment) likewise includes only non-refundable purchase taxes.
  • Non-recoverable VAT is part of the cost (not VAT-registered, exempt activity, non-deductible expenses, partly deductible VAT). The same standards put it into the cost of the item.
  • VAT charged to a customer is not revenue. It is an amount collected on behalf of the tax authority (IFRS 15.47). Revenue is without it, always; the VAT collected is never the project's cost.
  • US GAAP has no VAT standard (VAT is not a US tax); the same principle is applied to sales / use tax and to foreign VAT: tax that cannot be recovered goes into the cost of the asset or inventory, a recoverable one is a receivable. This is practice by analogy.
Sources and what was NOT checked. The IAS 2 / IAS 16 wording was looked up on 2026-10-20 only in secondary sources (Moore Global summary of IAS 2; the Australian GST interpretation AASB INT 1031; PwC on the presentation of taxes in revenue; IASB paper on sales tax, gross vs net). The paragraph numbers (IAS 2.11, IAS 16.16, IFRS 15.47) and the US GAAP position (ASC 330 / ASC 360) are NOT verified against the official texts: the owner's accountant should confirm them before the report is used for statutory purposes. The application is a project-management tool, not the ledger; this design only gives its reports the same basis the ledger would use.

So a report can show an amount on three VAT bases:

BasisName in the UIAmountUse
cost (DEFAULT)Cost (net + non-recoverable VAT)net + the part of VAT that is costthe IFRS / GAAP cost; budget vs actual
netNet of VATnetthe contract / invoice amount without tax
grossWith VATnet + all VATwhat is paid; cash planning; the owner's wish to see the VAT

While every VAT rate of the catalog is 100 % recoverable (the default, and the case of every existing row) the basis cost equals net: no number of any existing report changes until somebody marks a rate as not recoverable or picks With VAT.

5. Decisions (the owner can change them)

Components, not totals. Every stored money amount is split into net, VAT and VAT that is cost (vatInCost). The three bases of section 3 are computed from these three numbers by ONE function, so a report never decides the VAT treatment itself.
Recoverability lives on the VAT rate. A row of valueAddedTaxTable gets rowJSON.vatRecoverablePercent (0..100, missing = 100). A rate that is partly or not deductible is a row of its own ("VAT 21 % - not deductible", 0 %). The percent is copied into the line when the rate is chosen and frozen with it, so a later edit of the catalog does not rewrite posted documents. A project / organization switch "all VAT is non-recoverable" (an organization that is not VAT-registered) is NOT in this round; such an organization uses 0 % rows.
Customer invoice: the VAT is never cost. vatInCost of a sold movement is always 0, so the basis Cost equals Net for the Customer Invoice amount (IFRS 15.47); only With VAT adds the tax.
Currency. The VAT of the budget / accounting currency is converted exactly as the net sum is today (the rate of the plan of the line), so net + VAT in a currency equals the converted gross.
Nothing is dropped from a live database. No column is removed; the old meaning of every existing column stays.

8. The calculation (direction price → sums) and the VAT rate

Let r be the rate of the plan of the line: r = unitSumForAccounting / priceTaskLine (accounting currency per unit of the contract currency); rb = unitSumForBudget / priceTaskLine for the budget currency. Both come from the task line, copied into rowJSON when the line was made. Let k = vatRecoverablePercent / 100 (1 when missing).

sumForContract            = round(qty x price, 2)
vatForContract            = round(sumForContract x VAT% / 100, 2)

sumForAccountingBeforeVAT = round(sumForContract x r, 2)
sumForAccountingVAT       = round(vatForContract x r, 2)
sumForAccounting          = sumForAccountingBeforeVAT + sumForAccountingVAT        -- the total of the line

sumForBudget              = round(sumForContract x rb, 2)                          -- net, as today
vatForBudget              = round(vatForContract x rb, 2)

vatInCostForBudget        = round(vatForBudget x (1 - k), 2)       -- 0 on a customer invoice
vatInCostForAccounting    = round(sumForAccountingVAT x (1 - k), 2) -- 0 on a customer invoice

A line WITHOUT a plan price (an independent line, or a task line with no price) has no rate: the sums use the unit sums, as today (round(qty x unitSum, 2) for the net part, the VAT part from the VAT %). A line without a unit sum has NULL accounting / budget sums.

  • The VAT select. Source: valueAddedTaxTable (owner valueAddedTaxCatalog; rowJSON.vatTableTitle, vatTablePercent, vatRecoverablePercent), already loaded for the task lines (taskLineCatalogs.ts, key valueAddedTax). It replaces the number input of the VAT % column; it shows the title and the percent. A new line takes the VAT of the task line; an independent line takes the default of its product type / role if there is one, otherwise 0.
  • A legacy line whose percent is not in the catalog shows its number and stays valid (recoverable 100 %). A percent computed from a manual VAT edit has no catalog row: vatRateGUID is removed and the select shows the number.
  • The database check 0..100 of vatRatioInvoiced stays. The line trigger reads the catalog ONCE, when rowJSON.vatRateGUID is new or changed (vat_rate_lookup, SECURITY DEFINER): the percent and the recoverable share are copied into the line and frozen there, so a later edit of the catalog does not rewrite a document. A rate that does not exist is refused.

9. The manual edit and the calculation backwards

The trigger tells a manual edit from a recalculation by comparing the new row with the old one (UPDATE): the quantity, the price and the VAT % are the same, and one of the two editable accounting columns changed.

The user changesThe row does
Qty, price or VAT rateEverything is calculated again (section 8). A manual accounting value typed before is DROPPED: the accounting sums are the formulas again (no stale manual number beside a changed price).
sumForAccountingBeforeVATprice = round(value / r / qty, 4), then the contract sums from the new price, the VAT part of the accounting from the contract VAT, the budget sums, vatInCost…. The typed value stays AS TYPED (it is not replaced by the rounded product of the new price). Qty = 0 or no rate r: the edit is refused with a clear message.
sumForAccountingVATThe price does NOT change (VAT is not part of it). The VAT % is computed: VAT% = round(value / sumForAccountingBeforeVAT x 100, 3) (not above 100); vatForContract and the budget VAT follow; vatRateGUID is removed and the recoverable percent stays as it was.
sumForAccountingRead only (the total).

The two directions of the owner: contract price → contract sums → accounting sums (section 8) and accounting sums → contract sums → contract price (this section). A line with no rate (independent line) has the two accounting columns read only, because there is nothing to convert with.

14. Every future report: the VAT basis contract

A report that shows money MUST obey the following rules, so that no report invents its own VAT treatment:

  1. It stores or reads the three components (net, VAT, VAT in cost), never one pre-added total.
  2. It computes the shown amount only through the shared function: SQL vat_basis_amount(net, vat, vat_in_cost, basis) (IMMUTABLE, basis = 'cost' | 'net' | 'gross') and TypeScript amountOfVatBasis(...) in kit8/pm/vat/vatBasis.ts.
  3. It offers the same switch component VatBasisSelect (the three names of section 3, default Cost) and remembers the choice in the same place as Monitor01.
  4. Its header tips and README say which basis the amounts are on. Customer (revenue) amounts follow the rule of section 5: the Cost basis equals Net.
  5. A report that cannot show a basis (a quantity report) says nothing about it.

When this is built, KNOW_HOW.md gets one line with these rules, so every new report starts from them.
