Project Calculation: Automatic or Manual – Work Breakdown Structure

Scope: the MS Project command Project > Calculation Options > Automatic | Manual with Calculate Project (F9), for the Gantt chart of kit8/pm. Item A2 of MORE_GANTT_INPUT.html. Planning document – no implementation, nothing in the code was changed.

1. Goal

In MS Project, Automatic calculation reschedules the whole plan after every edit. In Manual mode the planner makes many edits (durations, links, new rows, moves) and the plan stays as it was until Calculate Project (F9) is pressed; a “Calculate” note in the status bar says that the numbers are old.

In the app every edit recalculates the plan at once and then writes the new dates to the database. For a big plan this has three costs that the user cannot avoid today: (1) bars of other tasks jump while a series of edits is half done; (2) every written start / finish day that changes unposts the posted task lines and payments of that task, and rewrites the user calendar, so a half-finished edit session can unpost work that the final plan would have left alone; (3) the CPU work of the client scheduler and of the write-back runs after each single edit.

This feature adds a per-project, per-user calculation mode. In Manual mode the plan is frozen on the screen and in the database until the user presses Calculate; the edits themselves are saved at once.

Hard constraint: Automatic is the default and behaves exactly as today. Nothing is frozen, no new banner or button is shown, and no stored data changes, until a user turns Manual on.

3. What recalculates today (checked in the code, 2026-10-26)

  1. Client – every change. store/store_pm.ts: hydrate() (task / dependency data) and setProjects() (project row: start, calendar) call store/storeDerive.ts derive(), which builds the tree index, runs scheduleProject() (CPM forward + backward pass, stage roll-up), computes the project progress and the visible rows. A task mutation updates the query cache first (optimistic), so the whole chain runs on every edit.
  2. Write-back – after 800 ms. crud/queries.ts useScheduleWriteBack: subscribes to store.schedule; one timer of 800 ms; skipped while mutations are in flight; compares every task’s stored rowJSON.startAt / rowDuration / stage progress with the computed value and sends only the different rows to the RPC pm_apply_schedule, which also calls pm_recalc_project_progress and subproject_propagate_dates (the origin tasks of other projects follow).
  3. Server reactions to the written dates. task_line_plan_unpost_on_dates and task_payment_plan_unpost_on_dates (a changed start or finish day unposts the lines and payments of the task); the user calendar entry of the task is updated; trg_project_task_zz_progress_* recalculates the stage and project % on a leaf change (independent of the scheduler).
  4. Already manual: the cost totals after a Post are debounced (cost/costRefreshScheduler.ts, 500 ms); Post, Repost all, Update project cost, Refresh the project are buttons in the project Actions menu (PMProjectActionsButton). Post reads the task dates from store.schedule (useTaskPost.ts, runTaskPost.ts).
  5. Realtime: an edit in another browser invalidates the query (paused while one of our own mutations is in flight) and ends in hydrate() again.
Not measured yet: how long derive() takes on a big plan. If it is a few milliseconds for several thousand tasks, the benefit of Manual mode is the protection against cascades (cost 2 above) and jumping bars, not speed. Work package 1.2 measures it before the design is fixed.

4. Proposed design (to confirm)

4.1 The mode and the frozen plan

  • Setting: uxuiSettings.projectCalculationMode = 'automatic' (default) | 'manual', saved per project and user in project_user_settings_table, read by uxuiSettingsOf(), mirrored in the store (viewSettingsOf).
  • Split of derive(): deriveTree() (tree index, visible rows, filters, sort – cheap, always live) and deriveSchedule() (scheduleProject, project progress, project start / finish). In Automatic both run as today. In Manual deriveSchedule() runs only on a load, a project switch, a mode switch and Calculate; the result is the frozen plan kept in store.schedule.
  • Rows the frozen plan does not know (a task created, or arriving from another browser, after the last calculation): a provisional row from the task’s own inputs (see 4.3); a deleted task simply leaves the plan; a moved task keeps its dates.

4.2 What is “pending”

Instead of marking pending inside every command (and missing the edits of other browsers), the store keeps the input signature of the last calculation: per task durationDays, rowKind, manualStartAt, (taskScheduleMode and taskManualStartAt when the Manually Scheduled Tasks feature exists), treePath, orderInList; the dependency list (rowGUID, rowDependsOnGUID, linkType, lagDays); the project projectStartAt, skipWeekends, planning units and calendar. After every hydrate() the new signature is compared with the saved one (O(n), much cheaper than CPM):

  • a changed task row → that row is pending (marker in the tree, tip in the bar);
  • an added / removed / changed dependency, a moved row, a changed project setting → structural pending (counted in the banner, no single row);
  • pending count = pending rows + structural changes; 0 = nothing to calculate, the banner disappears.

Not part of the signature (stay live): name, notes, color, custom columns, rowProgress, Kanban state, Finances lines.

4.4 Screen elements

  • Gantt bar: a button Calculate (icon calculate, the same icon as “Update project cost”) shown only in Manual mode, with the pending count as a badge; tip “Calculate the project (F9)”. Web: key F9 on the dashboard. Disabled while a write-back is running.
  • Project bar / chip: “Calculation: Manual” next to the project progress; in orange “Not calculated · N” while pending.
  • Actions menu (PMProjectActionsButton): “Calculate project” and “Calculation: Automatic / Manual” toggle.
  • Gantt settings window (PMGanttUXUISettinsModalWindow, tab Project): SegmentButtonsApp “Automatic | Manual”, searchable through uxuiSettingsIndex.ts.
  • Pending marker: the changed cell value is drawn in the pending color and italic; the bar of the task has a dashed outline until the calculation.

4.5 Where a calculation is forced

These actions read dates that would be old, so with pending edits they call Calculate first (ask or silent: Q4): Post / Repost all / Post unposted tasks and the Post of one task (useTaskPost, useProjectPostActions), Update project cost, Save project version and Restore version, Export to JSON / PDF / MS Project XML, Create subproject, and the Network view when opened (it draws from store.schedule; it may instead show the frozen plan with the banner – Q5).

4.6 Not a shared lock

The mode is per user. If another user (or another browser of the same user) has the project open in Automatic mode, that client calculates and writes the dates, and the realtime refresh brings the new data to the Manual client. A refresh that arrives while edits are pending makes the Manual client calculate (decision Q6). So Manual mode protects a single editing session, not the database against other editors.

6. Sequence and dependencies

  1. 1 Analysis – 1.2 (measurement) first; if the numbers show the CPU is not the problem, the text of the Goal and the labels (“Calculate” vs “Apply changes”) are reviewed, the design stays.
  2. 2 Setting and store – needs 1; 2.4 and 2.5 are pure and can be written and tested alone, before any UI.
  3. 3 Calculate and write-back – needs 2.
  4. 4 Display and 5 Menus – need 3; independent of each other.
  5. 6 Forced points – needs 3 (the helper) and can go in parallel with 4 and 5.
  6. 7 Quality – last; tests are drafted from step 2 onward.

The feature is independent of the Manually Scheduled Tasks feature (MORE_GANTT_ManuallyScheduledTasks_WBS.html), but the signature should include its two keys when both exist.

7. Acceptance criteria

  • With the mode never changed, nothing is different: same dates, same write-back calls, no new element on the screen.
  • In Manual mode, typing a duration on task A shows A’s new finish; its successors, the stage roll-up, the critical path and the project finish stay; the database dates (startAt, rowDuration) do not change and no posted line or payment is unposted.
  • The banner shows the number of pending edits; adding a link counts one; after Calculate (button or F9) all dates are the same as Automatic mode would have shown, the database has them, and the banner is gone.
  • Post, Update project cost, Save version and the exports never use old dates: with pending edits they calculate (or ask) first.
  • Switching to Automatic calculates first; a reload or project switch shows a calculated plan.
  • Stage and project % in Manual mode equal the database values and change when a leaf % is typed.
  • Names, notes, colors, custom columns, filters, sort, expand / collapse, Kanban and Finances work as before in both modes.

8. Questions for the owner (the answers change the design)

#QuestionProposal
Q1What is the main reason: speed on big plans, or protection from the cascade (bars jumping, posted lines unposted while editing)?The cascade. The benchmark 1.2 settles the speed question before the build starts.
Q2The mode per user and project (saved in uxuiSettings), or one switch for the whole project?Per user and project: no SQL, no effect on others. See 4.6 for the consequence.
Q3Does Manual mode survive a reload (the mode yes, the pending state no)?Yes: the mode is remembered, a load always calculates (R9).
Q4At a forced point (Post, exports …): ask “Calculate first?” or calculate silently?Silently for Post and cost (the user asked for the real plan); ask for versions and exports (“The plan has N edits that are not calculated”).
Q5Network view while edits are pending: calculate on open, or show the frozen plan with the banner?Show the frozen plan with the banner (the same rule as the Gantt).
Q6A realtime refresh arrives while edits are pending: calculate, or hold the refresh?Calculate (a frozen plan on top of someone else’s changes is wrong); the banner then clears.
Q7Should % complete roll-up stay live in Manual mode (it does in the database)?Yes, shown from the stored values; MS Project freezes it, but here the trigger is server-side and cheap.

9. Out of scope

  • “Calculate Now” of only the active project (MS Project Shift+F9) – there is one project on the screen.
  • A project-wide lock that stops the write-back of other users (4.6).
  • Moving the scheduler to the server or to a worker thread.
  • Partial calculation of one branch (“calculate this stage”).
  • Money reports (Monitor01–03, 07): they have their own refresh and are not affected.

10. Risks

#RiskHandling
Z1Many readers assume that every task has a row in store.schedule (bars, tree, Post, network).1.3 lists them; provisional rows (2.5) guarantee a row for every task; tests for a new task and a task from another browser.
Z2The user forgets to press Calculate and works with old dates.Orange banner with the count, marker on the rows, forced calculation at Post / exports (R7), and the calculation on every load (R9).
Z3The signature misses an input of the scheduler, so a real edit is not counted as pending (or a new feature adds an input later).A test builds the signature from the same field list the scheduler reads; a comment in scheduleProject points to calcSignature.ts; the Manually Scheduled Tasks keys are added when they exist.
Z4A manual-mode client and an automatic client edit the same project (4.6).Documented; Q6 rule; the automatic client’s write-back is the existing, correct behavior.
Z5The write-back fails or the app is closed between the edit and Calculate.No data is lost: the edits are saved at once; only the derived dates are old, and the next load calculates and writes them.
Z6Splitting derive() changes the result of Automatic mode by mistake.The comparison test in 2.2 and the regression 7.2.

11. Update steps when it is built (preview)

  1. No SQL file has to be run: the mode is a key of uxuiSettings in the existing JSONB; no table, no function, no seed, no pg_cron change.
  2. No .env change.
  3. Reload the app; Gantt settings → Project → “Calculation: Manual”, edit a duration, press Calculate (or F9).
