Why the Project module (Gantt) uses Zustand
and the rest of the app uses Redux Toolkit

The Gantt chart is a fast, interactive drawing: bars are dragged, rows hovered and zoomed dozens of times per second, and a lot of that code runs outside React (gestures, keyboard shortcuts, canvas hit-testing). Zustand gives that code a tiny, always-importable store. Redux Toolkit stays where it shines: app-wide data with sagas, persistence and realtime catalogs.

Short answer: it is not "Zustand is better than Redux". Each tool is used where it fits. The PM module needs a small, fast, self-contained view-state store - that is exactly what Zustand is. The server data of PM lives in React Query, not in any of the two.

For Dummies: a whiteboard vs a post office

Both keep "the current state of the app". They differ in how you read and change it.

🧑‍🏫 Zustand = a shared whiteboard

Anyone in the room can look at the board or write on it directly: usePMStore.getState().setHovered(id). People who only care about one corner of the board (e.g. "which row is hovered") are only told when that corner changes.

  • One file describes the whole board (store/store_pm.ts).
  • No envelopes, no forms, no mailman.
  • The board hangs on the wall - any code can walk up to it, even code that is not a React screen.

🏤 Redux Toolkit = a well-run post office

You never touch the data yourself: you send a letter (an action like createOne), clerks (reducers) file it, and couriers (sagas) talk to Supabase. Every step is logged and predictable.

  • Great when many departments share the same records (media posts, RACI members, currencies).
  • Great for long workflows (saga: read → realtime channel → reconnect → refetch).
  • More paperwork for tiny, very frequent changes like "the mouse moved to row 12".
Rule of thumb used in this repo: data that many screens share and that must be synced / persisted → Redux Toolkit (+ saga). Fast, local "what does the Gantt show right now" state → Zustand. Server truth of projects / tasks → React Query.

Same job, two ways: "highlight the row under the mouse"

Runs on every pointer move over the chart.

Zustand (what kit8/pm does)
// store/store_pm.ts
hoveredGUID: null,
setHovered: (g) => set({ hoveredGUID: g }),

// gesture callback (not a component)
usePMStore.getState().setHovered(guid);

// only components that read it re-render
const hovered = usePMStore((s) => s.hoveredGUID);
Redux Toolkit (how it would look)
// slice
setHovered: (state, a) => { state.hoveredGUID = a.payload },

// gesture callback: needs the store instance -
// in this app it is created inside WithState at runtime,
// so it must be threaded in through React context first
store.dispatch(pmSlice.actions.setHovered(guid));
// -> saga middleware, persist, serializable check, reducer

const hovered = useSelector((s) => s.pm.hoveredGUID);

Glossary for Dummies

State

What the app "remembers" right now: which project is open, which row is hovered, the zoom level.

Store

The box that holds the state. Zustand: usePMStore. Redux: the app store in WithState.

Selector

"Give me just this piece": (s) => s.hoveredGUID. Only components whose piece changed re-draw.

Action / dispatch

Redux's letter: { type: 'currencyReusable/createOne', payload }, sent with dispatch.

Saga

A background worker for Redux actions: talks to Supabase, listens to realtime, retries.

React Query

Keeps server data fresh (cache, refetch, optimistic updates). In PM it owns projects / tasks; Zustand only mirrors a render-ready view.
