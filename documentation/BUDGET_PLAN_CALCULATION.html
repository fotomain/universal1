Budget plan calculation

Design only - no code written. Source: Google Doc "W1 BUDGET WBS" (Part 1 the scenario catalog, Part 2 project_budget_cost_turnover). The doc asks for calculateBudgetPlan: the budget of each stage of the tree and of the project as a whole, designed after the best practice of 1C and Dynamics 365 (section 7).

Part 1

Budget scenarios

budgetScenarioTable (a plain list, seeded with Plan scenario-Project #1 and Fact scenario-Project #1) and two new keys of project_table.rowJSON: budgetScenarioForPlan, budgetScenarioForFact. Menu: Budgets group of the drawer.

Part 2

The turnover register

project_budget_cost_turnover: one row per day · scenario · budget item · business unit · resource · variant with two numbers (qty, sum). It is derived data: nobody writes it by hand, database triggers keep it equal to task_line_plan_movements.

Result

calculateBudgetPlan

One SQL function (+ a thin typed TypeScript wrapper) that returns the budget of the project, of every stage and of every task, for any period, grouped by item / unit / resource, as a plan, a cumulative S-curve and (when the fact scenario has data) plan vs fact.

Three things in the doc that need your decision before building (details in section 10): (1) the table has no task / stage column, so a stage cannot be summed from it alone - I propose that stages are summed from task_line_plan_movements through the task tree (ltree), and the turnover stays the project-level register exactly as you wrote it; (2) the table needs the technical column rowProjectGUID (project, RLS, cascade delete); (3) "hamburger menu: Budget" - I read it as the drawer, group Budgets. Tell me if you meant a menu inside the project.

1. Where it fits - the data flow

Nothing existing is replaced. Post still writes task_line_plan_movements; the budget register hangs below it.

task_line_table (lines: budget item, resource, variant, unit, sumForBudget)
        |  Post  (create_task_line_plan - exists, gets 4 small stamps, section 4)
        v
task_line_plan_movements   one row per LINE and DAY            (exists; the "recorder" rows)
        |  AFTER INSERT / UPDATE / DELETE triggers  (new, statement level, delta)
        v
project_budget_cost_turnover   one row per DAY, scenario, item, unit, resource, variant   (new, Part 2)
        |
        v
calculateBudgetPlan  --->  project  /  stage  /  task  /  period  /  item  /  unit  /  resource
                           (stages are summed from the movements through project_task_table.treePath, the project also from the turnover = a cross-check)

Fact side: the same trigger function is meant to feed the fact scenario later from actuals (time sheets, invoices). There is no fact movement table in the code yet, so in this step the fact scenario is chosen and stored, and the plan/fact report shows "no fact data".

3. Part 2 - project_budget_cost_turnover

Your structure, unchanged, plus technical columns. "Grouped by days": the grain is one calendar day; weeks, months, quarters are summed from it when asked, never stored.

created_at, updated_attimestamptzas every table
  • Key: UNIQUE (rowProjectGUID, budgetPeriod, budgetScenarioGUID, budgetItemGUID, budgetBusinessUnitGUID, resourceItemGUID, resourceItemVariantKey). The "none" values are '' not NULL, so the unique index treats them as equal and the upsert works (a NULL in a unique key is never equal to another NULL).
  • Read only for the app: GRANT SELECT + policy pm_owns_project(rowProjectGUID), realtime on (as task_line_plan_movements). Writes come from the triggers only (SECURITY DEFINER).
  • Indexes: the unique index (project, period, scenario ...) serves the period reports; a second one on (rowProjectGUID, budgetScenarioGUID, budgetItemGUID) serves the per-item reports.
  • Signs: costs and revenues are both stored positive; cost or revenue is told by the budget item (costsBudgetFolder / revenuesBudgetFolder / paymentsBudgetFolder, the budgetKind already kept on the movements). Profit = revenue - cost; payment items are never mixed into profit.
  • No row is kept with qty = 0 and sum = 0 (the trigger deletes them), so the table never grows with empty history.

4. How the turnover is filled - the 1C "recorder" pattern

In 1C an accumulation register of the Turnover type has movements written by a document (the recorder) and a totals table the platform keeps itself. Here the movements are task_line_plan_movements (recorder = the line / the task) and the totals are project_budget_cost_turnover. The totals are kept by statement-level triggers with transition tables, so every path that changes a movement is covered - Post, Correct033, a deleted line, a deleted task - and the Post procedure itself needs only the small stamps below.

Event on the movementsWhat the trigger does
AFTER INSERT (new rows of Post)group the new rows by the 7 key columns, INSERT ... ON CONFLICT (key) DO UPDATE SET qty = qty + EXCLUDED.qty, sum = sum + EXCLUDED.sum. Rows without a scenario are skipped.
AFTER DELETE (re-Post, a deleted line / task)group the old rows, UPDATE ... SET qty = qty - old.qty, sum = sum - old.sum (update only: when a whole project is deleted the turnover rows are already gone and nothing is inserted).
AFTER UPDATE (Correct033 moves the rounding difference to the last day)subtract the old rows, add the new ones, in one pass.
after each of themDELETE the touched keys whose qty and sum are both 0.

Why delta and not "recalculate the project"

  • A delta qty = qty + x is commutative: two tasks of one project posted at the same time cannot overwrite each other (the task lock of Post is per task). A recalculation would need a project-wide lock.
  • The amounts are already rounded to 2 digits and corrected to the line total (Correct033), so the sums of 2-digit numbers are exact - no rounding drift in the register.
  • To avoid deadlocks the grouped rows are written in key order (ORDER BY the key).
  • A repair function rebuild_project_budget_cost_turnover(project) (delete + re-aggregate from the movements) is the safety net and the migration for projects posted before the register existed; the consistency check (section 6, I1) tells when it is needed.

The four stamps Post adds to each movement's rowJSON (inside create_task_line_plan, PART 15)

The same idea as businessUnitAssigned: what was posted is kept on the posted day, so a later change of the line or of the project does not rewrite history, and the delete-trigger subtracts exactly what was added.

KeyValue
budgetDay'YYYY-MM-DD' = the calendar day of the post (days[].d); the timestamp rowPeriodDatetime depends on the time zone, so the day is kept as text
budgetScenariothe project's budgetScenarioForPlan at the time of Post (null = none: no turnover)
resourceItemthe line's taskResourceItem (null = none)
resourceVariantKeythe line's taskResourceAttributesKey (null = none)

Changing the plan scenario of a project that already has posted lines: the posted days keep their old scenario (correct history). New posts use the new one. The settings picker shows a warning and offers "Re-post all lines" (a button that posts every posted task again) when the user wants everything under the new scenario.

Lines that cannot be budgeted: sumForBudget is null when the project has no budget currency or a rate is missing (taskLineFx.ts). Such a movement adds 0 to the sum, but is counted: calculateBudgetPlan returns linesWithoutBudgetSum and the view shows "N lines have no budget sum", so a total is never silently too small. Nothing is guessed (no fallback to the contract currency).

6. calculateBudgetPlan - the budget of each stage and of the project

Same naming family as calculateTaskLinePlan. The heavy part (summing 105 rows) is in the database; the TypeScript part is pure and testable.

Request

calculateBudgetPlan({
  projectGUID,
  scenarioGUID,               // default: project.budgetScenarioForPlan
  compareScenarioGUID?,       // default: project.budgetScenarioForFact  -> plan vs fact
  nodes: 'tree' | 'stages' | 'tasks',   // which nodes of the WBS to return
  fromDay?, toDay?,           // the period; empty = the whole project
  granularity: 'total' | 'day' | 'week' | 'month' | 'quarter' | 'year',
  groupBy: [] | ['budgetItem'] | ['businessUnit'] | ['resource'] | ['genus'],
  cumulative?: boolean        // running total over the periods = the S-curve
})

Result (per node of the tree; the root is the project)

{ nodeGUID, parentGUID, kind: 'project'|'stage'|'task', title,
  total: { cost, revenue, profit, margin, payments },     // budget currency, 2 digits
  periods?: [ { from, to, cost, revenue, cumulativeCost, cumulativeRevenue } ],
  groups?:  [ { key, title, qty, cost, revenue } ],
  fact?:    { cost, revenue },  variance?: { cost, revenue },   // fact - plan, only when a fact scenario has data
  checks:   { linesPosted, linesNotPosted, linesWithoutBudgetSum } }

The calculation, step by step

  1. Source of the numbers. Project total, per period, per item / unit / resource: from project_budget_cost_turnover (already aggregated, fast). Stage and task totals: from task_line_plan_movements of the scenario (they know the task).
  2. Stage = the sum of the tasks under it. A stage has no lines of its own. Every movement is counted for every ancestor of its task in one pass, using the ltree path of project_task_table (treePath = project.stage.stage.task, GIST index exists): 
    SELECT subpath(t."treePath", 0, g)                       AS node_path,     -- g = 1 is the project, then every stage down to the task
       sum(p."sumForBudget") FILTER (WHERE p."rowJSON"->>'budgetKind' = 'cost')    AS cost,
       sum(p."sumForBudget") FILTER (WHERE p."rowJSON"->>'budgetKind' = 'revenue') AS revenue
  FROM task_line_plan_movements p
  JOIN project_task_table t ON t."rowGUID" = p."rowOwnerGUID"
 CROSS JOIN LATERAL generate_series(1, nlevel(t."treePath")) AS g
 WHERE p."rowProjectGUID" = :project AND p."rowJSON"->>'budgetScenario' = :scenario
   AND (p."rowJSON"->>'budgetDay')::date BETWEEN :from AND :to
 GROUP BY 1;
    One scan gives the whole tree. The label of a path element is pm_ltree_label(rowGUID), so the app maps a path back to its stage. (Sketch - to be tested in the Docker postgres at build time.)
  3. Periods. date_trunc('week'|'month'|'quarter'|'year', budgetPeriod) over the day rows; cumulative = sum(...) OVER (ORDER BY period). The last cumulative value of the project is the budget at completion.
  4. Groups. By budget item (the folder - costs / revenues / payments - gives the next level up), by business unit (rolled up through the unit tree in the same way as the stages are rolled up through the task tree, so a profit center shows its sub-units), by resource / variant.
  5. Quantities are returned only inside a group of one item or resource (hours of a person, pieces of a product). A stage total of "10 hours + 4 pieces" is meaningless and is not produced.
  6. Plan vs fact. The same query with compareScenarioGUID; variance = fact - plan, remaining = plan - fact. With no fact movements the fact block is empty.
  7. Completeness. linesNotPosted = lines with a budget item and taskIsPosted false; linesWithoutBudgetSum as in section 4. The view shows them beside the total.

Invariants (tests and a "Check budget" action)

Rule
I1for every project and scenario: sum(turnover.sumForBudget) = sum(movements.sumForBudget) of that scenario. A difference = run the rebuild function.
I2for every posted line: the sum of its days = the line's sumForBudget (Correct033, exists).
I3a stage = the sum of its children; the project = the sum of its stages and tasks.
I4no turnover row has qty 0 and sum 0; no sum is negative (line sums are >= 0 by CHECK).
I5project with no budgetScenarioForPlan: no turnover rows at all.

Where it is shown

No new screen is required by the doc. Proposed minimal use: a read-only Budget table (stage tree + totals per period) on the existing last main-view button (PM_LAST_VIEW_BUTTON), reading calculateBudgetPlan. Say if you want it in this step or after the register works.

9. Order of work and tests

  1. Scenarios (Part 1): SQL + catalog screen + menu + project keys. Test: seed rows, guards, pickers offer the right kind.
  2. Turnover table + triggers + stamps (Part 2): Docker test with the example of section 5 (insert, re-post delta, delete a line, delete a task, delete a project, Correct033 update, project with no scenario = no rows, two tasks posted in parallel).
  3. Rebuild function + invariants I1-I5 as SQL checks.
  4. calculate_budget_plan + calculateBudgetPlan.ts: jest for the pure part (periods, cumulative, variance, "no quantity across items"); Docker for the stage roll-up with a 3-level tree.
  5. The Budget table (optional, after the above).

Old behaviour guarded by tests: a project without a plan scenario posts byte-for-byte as before. The suites that already fail on this branch (list in the equipment notes) are not touched.
