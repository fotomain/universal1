Business units and Centers of Financial Responsibility built 2026-10-12

Source: Google Doc "W1 businessUnit" (PART 1: "do not code. improve and make ./documents/BUSINESS_UNIT_CFR_STRUCTURE.html" - this page; PART 2: the businessUnitTable catalog). I read the task-line, plan/post, budget-item, management-genus, project-settings, department and tree code and checked every statement below against it. (When this page was first written no application file had been changed; see the status below.)

Status: built. The answers Q1-Q9 were given and applied as follows. The text below this block is the proposal as it was written, before the work.
  • Q1 (priority): no ranking was given - the default is built: line › resource › role › budget item › contract › project. One line in taskLineBusinessUnit.ts changes it.
  • Q2: yes - a revenue line is refused on a cost center too; profit and investment centers take both. The investment center will take only investment (capex) lines later: the flags on cfrTypeTable are the place.
  • Q3: ok - a unit with no CFR inherits the nearest parent's; none up the tree = not checked.
  • Q4: "assign - for SQL data consistency": the CFR of the 29 example units is assigned in the SQL seed (9 units) and the tests parse exactly that seed.
  • Q5: the Departments catalog is removed (screens, routes, drawer item, the Organization tab, the SystemMetaData entry, the table in the structure / code files). An old database keeps an unused departamentTable; the delete file still drops it.
  • Q6: obligatory for new projects - a new project gets the first unit that fits each of the four fields and cannot be saved without them (projectBusinessUnitsRequired); a project made before is not forced.
  • Q7: the business unit has selectFromTree: true - any branch from any level. The generic default of the flag (absent / false) stays "leaves only".
  • Q8: businessUnitAssigned (+ budgetKind) is kept on the posted days (task_line_plan_movements.rowJSON) in this version, not phase 2; the line keeps its own column too, as the document says.
  • Q9: ok - English titles in the seed, fixed (an enumeration).
Where it lives: kit8/catalog/business_unit (README), kit8/ui/components/tree/CatalogTreeReusableCRUD.tsx + CatalogTreePicker.tsx, route /catalog/business/unit (drawer: Catalogs → Business units), SQL PART 18 of start_sql_structure.sql (also in start_sql_code.sql / start_sql_data.sql) and PART 15 of delete_sql_structure.sql - tested on Postgres 15 with kit8/docker/test_sql.sh and by hand (the enumeration is read-only, the guards, the three project-center rules, the Post check on a cost / revenue line and a CFR change that contradicts posted days). The spike of section 3 worked: ReusableTable + foldersTree shows the picked unit's sub-units when every row is also a node, with no change to the plugin. Not built (on purpose): a one-time migration of old projects, units on the Kanban / Gantt views, the capex rule of the investment center, a re-resolve of the unit of existing lines when a source changes later (a line is a snapshot, like the price; it follows the sources while a cell of it is edited).

What the document asks for (my reading)

  1. An enumeration cfrTypeTable - "Centers Of Financial Responsibility" - that works like a 1C enumeration: a fixed list the developer defines, the user only picks from it. A flat table, no folders, four values: costCenter, revenueCenter, profitCenter, investmentCenter (rowGUID = the code).
  2. A catalog businessUnitTable: route catalog/business/unit, drawer item Catalogs - Business units, code in kit8/catalog/business_unit. A tree of any depth in one table. Each unit may carry rowJSON.cfrAssigned = a cfrTypeTable.rowGUID.
  3. A new flag selectFromTree in the SystemMetaData entry of the catalog: true = the user may pick a unit of any level, the first level too.
  4. A new screen component CatalogTreeReusableCRUD.tsx that edits such a tree and assigns cfrAssigned to its nodes. The doc lists an example company (29 nodes, 9 of them with a CFR) - I use it as the seed / demo data and as the test case (section 2).
  5. A new task-line column businessUnitTaskLine, placed after budgetItemTaskLine.
  6. A CHECK on Post: a line whose budget item is a cost must not be posted when its unit is a revenue center.
  7. A default for the column: rowJSON.businessUnitAssigned is kept on projectTable (four obligatory fields projectCostCenter, projectRevenueCenter, projectProfitCenter, projectInvestmentCenter), contractTable, budgetItemTable, resourceRole, resourceTable, and there is a priority between them. The document ends there: the sentence "the priority to set ... :" has a colon and no list. I propose one (section 4) - it is question Q1.

What is already true in the code (the facts the proposal stands on)

Two-level catalogs exist, a deep tree does not.
managementGenusTable and budgetItemTable are folders (level 1) + items (level 2), rendered by FolderTreeReusable beside a ReusableTable that shows the items. A business unit is a node at any depth that is both a node and a row with attributes - the table cannot just list "items of the folder".
A genuine tree table is already in the schema.
departamentTable uses rowParentGUID = parent or 'empty' ("hierarchy as a tree"). The pattern (adjacency list in one table) is proven; only its screen is a card list, not the tree plugin.
There is no resourceTable.
The resource of a line is a personTable / equipmentTable row (Time, by taskResourceKind) or a productTable row; the role is resourceRoleTable. "resourceTable" in the doc therefore means those three; the unit lives on each of them (rowJSON.businessUnitAssigned).
The "cost or revenue" fact is already stored.
budgetItemTable items sit under costsBudgetFolder or revenuesBudgetFolder and carry managementGenusItem (time/material/expense = cost, revenue = revenue). The Post check needs no new field on the item.
Post already collects per-line problems.
runTaskPost → calculateTaskLinePlan returns errors per line; the line is left out, the others are posted, and one message names the first problem. The new check fits there, with the SQL procedure create_task_line_plan as the authority behind it.
Old projects must not change.
Every saved line has no unit. "No unit" must mean "as before": no check, no warning that blocks Post. Same rule as for equipment (a missing kind = person).

Small things in the document I corrected silently

  • "Plane table" = a plain (flat) table. "budgetIemTable" = budgetItemTable. "SystemMetadata structure" = the entity entries of kit8/redux/SystemMetaData.ts.
  • "Departament" in the example is spelled Department in the seed rows (the old catalog keeps its historical name departamentTable; the new one is not named after it).
  • Entries "rowGUID=costCenter:" mean: the rowGUID is the code string - the same convention as managementGenusTable (timeGenus) and budgetItemTable.

Decisions

Each is what I recommend; the open ones are in section 11 with a default so work can start without waiting.

#DecisionWhy
D1cfrTypeTable is a read-only enumeration: 4 seeded rows, no insert / update / delete for any app user (RLS has only a SELECT policy), no unlock button, a TS constant names the codes.That is what a 1C enumeration is. The genus catalog is "locked by default"; an enumeration is locked always, because code compares to the values.
D2The rule "which CFR accepts which budget kind" is data on the enumeration row (acceptsCosts, acceptsRevenues), read by SQL and TS alike.One source of truth; no TS rule that can drift from the SQL rule.
D3businessUnitTable = one table, adjacency list (rowParentGUID), any depth. This answers the "???" in the document: yes, one table.A unit is a node and a row at once; four levels already in the example; the genus "folders + items" split cannot express it.
D4The effective CFR of a unit = its own cfrAssigned, else the nearest ancestor's, else none.Most nodes in the example (Board, CEO, Sales ...) have no CFR; without inheritance they could never be checked.
D5selectFromTree is a boolean on the SystemMetaData entry, default false = only leaves are selectable; true = every node.False keeps the behaviour of the other catalogs (only the lowest level is chosen); the business unit sets it true.
D6CatalogTreeReusableCRUD is a generic component (any "tree in one table" catalog), not a business-unit screen. It has a catalog mode and a picker mode.The picker is needed in five places (line, project, contract, budget item, role/resource); Departments could move to it later.
D7The line's unit is resolved by a pure function from the sources in priority order, taking the first unit that is compatible with the line's kind, and is saved on the line (a snapshot with its source), like the price and the FX sums.Follows the proven priceAutoTaskLine / fxSnapshotTaskLine pattern; a line is explainable ("unit from the role").
D8The Post CHECK has three layers: the picker disables incompatible units, calculateTaskLinePlan leaves the line out with a message, the SQL procedure refuses. A line without a unit is never refused.Same three layers as managementGenusItem on a budget item; old projects stay unchanged.

1  cfrTypeTable - the enumeration

Centers of Financial Responsibility: who answers for what in the money.

The four values

rowGUID (the code)TitleAccountable foraccepts costsaccepts revenues
costCenterCost centercosts only (support units: accounting, IT, a team's cost budget)yesno
revenueCenterRevenue centerrevenue only (sales)noyes
profitCenterProfit centerrevenue and costs, i.e. the profityesyes
investmentCenterInvestment centerthe profit and the capital invested (ROI)yesyes
Only the first two rows come from the document ("cost budget item + revenue center = do not post"). The mirror (a revenue line on a cost center) and the two "both" rows are my reading of the standard definitions - confirm in Q2. An investment center would also take investments (capex); there is no capex budget item yet, so it is not modelled.

"Works just like 1C's enumeration" - what that means here

1C enumerationIn this app
Values are created in the configurator; users cannot add, rename or delete them.Rows are INSERTed by the SQL files only. RLS: SELECT for signed-in users, no INSERT / UPDATE / DELETE policy; plus a trigger that refuses writes from the API role (belt and braces, as the app can also call through service_role).
Code refers to Enum.CostCenter, never to a number.export const CFR_TYPE = { cost: 'costCenter', revenue: 'revenueCenter', profit: 'profitCenter', investment: 'investmentCenter' } as const and type CfrType = typeof CFR_TYPE[keyof typeof CFR_TYPE]. A test asserts the constant equals the seed rows.
Stored in other objects as a reference.rowJSON.cfrAssigned holds the rowGUID string. A trigger on businessUnitTable checks that it exists (the pattern of trg_budgetItemTable_genus); since a value cannot be deleted, it can never dangle.
Fixed order.orderInList 10, 20, 30, 40 (cost, revenue, profit, investment).
Shown as a drop-down; empty value allowed.A select column in the unit table; "empty" is allowed (a unit may carry no CFR).
No catalog form for it.No drawer item and no CRUD screen. It appears as the CFR column / picker and in the README. (If a viewer is wanted later it is the genus screen with noCrud and no unlock.)

Table shape (the standard def-table pattern)

cfrTypeTable          flat - rowParentGUID is always 'empty', no folders
  rowGUID       'costCenter' | 'revenueCenter' | 'profitCenter' | 'investmentCenter'
  rowOwnerGUID  'cfrTypeCatalog'
  rowParentGUID 'empty'
  orderInList   10 | 20 | 30 | 40
  rowJSON       { title, description, acceptsCosts: boolean, acceptsRevenues: boolean }

The seed uses INSERT ... ON CONFLICT (rowGUID) DO UPDATE so a re-run corrects titles and the flags without touching anything else.

2  businessUnitTable - the catalog

Route catalog/business/unit · drawer: Catalogs → Business units · code kit8/catalog/business_unit.

Table shape

businessUnitTable     one table, any depth
  rowGUID       uuid text (a unit has no natural code; the code is in rowJSON)
  rowOwnerGUID  'businessUnitCatalog'
  rowParentGUID parent unit rowGUID | 'empty' (a root = an enterprise)
  orderInList   order among siblings (the tree plugin writes it)
  rowJSON       { title, code?, description?, cfrAssigned: cfrTypeTable.rowGUID | null, isActive: boolean }
  • Guards (SQL triggers): a parent must exist; a unit cannot be its own ancestor (loop check by recursive CTE); cfrAssigned, when set, must exist in cfrTypeTable.
  • Delete: a unit with children is refused ("move or delete the children first") - safer than the genus rule "deleting a folder deletes its items", because a unit is referenced by lines, projects and contracts. A referenced unit is not deleted either, it is deactivated (isActive=false: still shown on old lines, not offered in pickers).
  • Index: (rowParentGUID), (rowOwnerGUID, orderInList), and an expression index on rowJSON->>'cfrAssigned'.
  • Relation to departamentTable: separate. A department is an org-chart box owned by an organization; a business unit is a unit of financial responsibility. Question Q5.

What the example teaches the design. (2) A leaf like "Team #1 costs" is the natural target of a cost line, but "PM Team #1" must be selectable too - this is what selectFromTree = true is for (D5). (3) The first level (Enterprise #1) is selectable and is an investment center, so a project may be booked to the whole enterprise.

3  CatalogTreeReusableCRUD.tsx and selectFromTree

The flag

// kit8/redux/SystemMetaData.ts - the entity entry of the catalog (spread from businessUnitMetaData.ts)
[BUSINESS_UNIT_TABLE.entity]: {
  tableName, itemLabel, updateValidator, defaultData, prepareCreateApi, prepareReadApi,
  selectFromTree: true,   // NEW, optional. true = a node of any level can be picked, the first level too. Absent / false = leaves only.
}

Read in one place: the picker mode of the component (isSelectable(node)). It is a UI rule only; SQL never cares which level a reference points to, only that the row exists.

The component

Catalog mode (the screen)
  • Left: FolderTreeReusable with every row as a node (FolderTreeNode {id, parentId, title, order} maps 1:1 to rowGUID, rowParentGUID, title, orderInList).
  • Right: ReusableTable of the picked node and its subtree (a switch "include sub-units"), columns: Unit, Code, CFR (select from the enumeration), Effective CFR (grey, computed), Parent path, Description, Active.
  • New unit goes under the picked node; "New root" creates an enterprise. Drag a node = move (loop-protected). Rename in the tree = rename in the table.
  • Editing on by default like the budget items (lock button for read-only).
Picker mode (a cell / a form field)
  • A modal / popover with the same tree and a search box; returns a rowGUID.
  • selectFromTree decides which nodes are clickable; the others are shown grey with the reason.
  • Optional isSelectable / disabledReason from the caller: the Cost line picker greys revenue centers ("Revenue center: not for a cost line") - layer 1 of the CHECK.
  • Shows the CFR badge next to each node (cost / revenue / profit / investment, or "inherits ...").
Open technical point (a spike before building). ReusableTable + foldersTree was written for rows that are items inside folders. Here a row is also a folder. I did not verify that it can show the picked node's subtree without a folder-filter conflict; the first build step is a half-day spike with the 29-node seed. If it cannot, the component uses the tree plugin + a table fed with a pre-filtered row list (no change to the plugin).
Where the tree-in-one-table pieces live: the model helpers (unitNodes, unitPath, unitDescendants, effectiveCfr) mirror managementGenusModel.ts.

4  The task line: businessUnitTaskLine

The column

  • task_line_table.rowJSON.businessUnitTaskLine = businessUnitTable.rowGUID | null. Column order in taskLineColumns.tsx: ... budgetItemTaskLine, businessUnitTaskLine, ... (as the document says).
  • Two companions, like the price: businessUnitSourceTaskLine = 'line' | 'resource' | 'role' | 'budget' | 'contract' | 'project' (where it came from) and businessUnitAutoTaskLine (the last unit the app suggested). While the line's unit equals the suggestion it follows the sources; typing a unit makes it 'line' and it stops following.
  • Any change of the unit sets taskIsPosted = false (the rule of taskLineCompute.ts), so the line must be posted again.
  • An empty unit on a line is valid and means "as before the feature".

Where the default comes from (the part the document left open)

All sources store rowJSON.businessUnitAssigned, except the project, which stores four named fields. Proposed priority, strongest first:

#SourceFieldIdea
1the line itselfbusinessUnitTaskLinethe user decided
2the resource: person / equipment / productrowJSON.businessUnitAssigned"this person works in that team", "this machine belongs to that workshop"
3the resource roleresourceRoleTable.rowJSON.businessUnitAssignedall Backend Developers → Development
4the budget itembudgetItemTable.rowJSON.businessUnitAssignedall "Expense: Transport" → Logistics cost center
5the contract of the linecontractTable.rowJSON.businessUnitAssigneda contract signed for one unit
6the project (always present - obligatory)cost line → projectCostCenter; revenue line → projectRevenueCenter; then projectProfitCenter, then projectInvestmentCenterthe last resort; the two last accept both kinds

The document lists them in a different order (project, contract, budget item, role, resource); I read that as the list of tables, not the ranking, and ranked from the most specific to the most general. Q1.

The rule: first compatible source wins

kind of the line
cost | revenue, from the budget item (else the genus)→ walk the sources 2 … 6→ take the first unit whose effective CFR accepts the kind
no CFR at all counts as "accepts"→ save unit + source on the line

Example: a revenue line for a Backend Developer. The person's unit is "Team #1 costs" (cost center) - it does not accept revenue, so it is skipped, the role's unit is empty, the budget item's is empty, the project's projectRevenueCenter = "Team #1" (revenue center) → chosen, source = project. The user sees where it came from and why the nearer sources were not used.

Implemented as one pure function resolveLineBusinessUnit(...) in kit8/pm/view/task/finances/taskLineBusinessUnit.ts, next to taskLineFx.ts, called from taskLineCompute.ts.

The four fields on the project

  • A new block Business units in the project settings Finances tab (PMProjectTaskEditScreenTab.tsx): four pickers; each offers only units whose effective CFR is the named type (or accepts what it stands for).
  • Obligatory for every project created after this feature (the project cannot be saved without them). A project that already exists keeps working with the four empty: the block shows a yellow "not set" and Post behaves as today. A plain "obligatory" would otherwise stop every old project from saving its settings.
  • projectProfitCenter and projectInvestmentCenter are also the roll-up for reports (the project's profit / investment owner), not only the last-resort fallback.

5  The Post CHECK

The rule of the document: do not post if budgetItemTaskLine is a cost but the unit is a revenue center. The full matrix (mirror = my addition):
Line (by budget item)costCenterrevenueCenterprofitCenterinvestmentCenterno CFR / no unit
Cost (Time, Material, Expense)postrefusepostpostpost
Revenuerefuse (mirror)postpostpostpost

Three layers (the pattern of managementGenusItem)

1 · screen
The unit picker of the line greys the incompatible units with the reason; a cell already holding one (budget item changed afterwards) turns red with "Cost line on a revenue center".
2 · calculation
calculateTaskLinePlan adds the line to errors: "<line>: a cost line cannot be posted to the revenue center '<unit>'". The line is left out, the other lines of the task are posted, the message reaches the user (Post button and the project actions).
3 · SQL
create_task_line_plan repeats the check with RAISE EXCEPTION, using the same acceptsCosts / acceptsRevenues flags from cfrTypeTable. A client that skips layers 1-2 still cannot write a wrong plan.

When the kind cannot be determined (no budget item): the line is not posted anyway (a line without a budget item is already refused) - no second message.

Changing a unit's CFR afterwards (profit → revenue while cost lines are posted on it): phase 1 shows a warning listing how many posted lines would conflict; phase 2 refuses it in SQL. See risks.

Which posted rows carry the unit (so a cost report by unit survives a later re-assignment) is the same question as the CHECK's last mile: task_line_plan rows would get the unit when a line is posted. It touches the procedure and calculateTaskLinePlan; I list it as phase 2 (Q8).

11  Questions - each has a default, so work can start

Q1 blocks step 5 The priority list.
The document stops at "the priority to set ... :". Default: line › resource › role › budget item › contract › project (section 4). Tell me if the project must win, or if the contract must come before the role.
Q2 The compatibility matrix.
The document gives one cell (cost line × revenue center). Default: the mirror is refused too; profit and investment centers accept both. Should an investment center accept only investment (capex) lines once such a budget item exists?
Q3 Units without a CFR.
Accounting, Warehouse, IT have none in the example. Default: inherit from the nearest parent (here: investment center, so anything is accepted); a unit with no CFR up the tree is not checked. Alternative: require a CFR on every unit that can be picked.
Q4 "you must assign cfrAssigned below".
I read the list under CatalogTreeReusableCRUD.tsx as the seed / demo tree with its CFR assignments, plus a CFR column the user can edit. Default: that. If "below" meant "assign the CFR on the child rows only", say so.
Q5 Business unit vs. Department.
Default: two separate catalogs, no link. A later optional rowJSON.departamentGUID on a unit could connect them. Or should the Departments screen be retired in favour of units?
Q6 Obligatory project centers.
Default: obligatory for new projects only; old ones stay empty with a hint. Alternative: a one-time migration giving every old project the first enterprise.
Q7 selectFromTree=false meaning.
Default: leaves only. Alternative: "level 2 and below" (the genus / budget-item behaviour literally).
Q8 Unit on the posted rows.
Default: phase 2. If cost reports by unit are due soon, it moves into phase 1 (it changes the Post procedure and task_line_plan).
Q9 CFR titles.
Default: English titles in the seed, translated through pmT; a user cannot rename them (enumeration).
